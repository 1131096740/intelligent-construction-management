## 五、已形成的工程能力

- 合同、结算、付款、实付、凭证、财务记录和审计之间有后端强顺序约束。
- 核心金额使用分值 `BigInt`，单价和数量使用高精度 Decimal。
- 付款等关键写入使用数据库事务、行锁和额度校验。
- 权限支持真实业务岗位、项目范围、委托和敏感动作二次确认。
- COS 使用私有桶，文件下载经过后端权限复核、短时效凭证和审计。
- 合同/结算文档、审批单、PDF、历史合同接管和历史余额扣减已有完整实现。
- Web 已完成 P0/P1 样板与六档桌面响应式治理候选，宽表格和专业工作区使用局部横向滚动。
- 自动化测试、构建和部署流水线已具备较好的工程基础。

## 六、正式扩大使用前的 P0 门禁

1. 用普通业务账号跑通 3–5 条真实合同长链路，覆盖合同、归档、结算、付款、实付、凭证、审计。
2. 完成真实历史合同批量接管和余额来源签认。
3. 完成普通员工、项目岗位、部门主管、财务和管理层的跨项目权限 UAT。
4. 完成真实合同母版和业务场景逐页验收。
5. 验证付款实付等财务写入在网络超时、重复点击和并发情况下的幂等性。
6. 对数据库 `NOT VALID` 约束涉及的历史数据做只读一致性检查，再决定是否安排受控验证迁移。
7. 对 5 个依赖安全公告做调用路径和升级兼容性评估。
8. 将生产发布改成“备份成功 → 人工批准 → 部署 → 深度健康检查 → 失败回滚”的可审计流程。
9. 为数据库、COS、磁盘、API 和关键业务依赖建立深度健康检查与可验证告警。

## 七、已识别但不应在当前阶段泛化重构的问题

- Web token 仍保存在 `localStorage`，公网尚无 CSP；需要独立认证安全专项。
- COS 直传会把文件整体读入 API 内存，大文件并发需要容量压测或 multipart 方案。
- 下载凭证和下载原因位于 URL 查询参数，后续宜改成不暴露业务信息的一次性票据。
- 部分页面仍有原生控件和浏览器 `confirm`，现有 `check:ui` 尚未真正覆盖全站。
- 部分核心 Service 和 Vue 页面超过 2,000 行，应在试运行稳定后按业务边界拆分，不能上线前大重写。
- 缺少统一请求 ID、结构化日志、指标/APM 和前端异常上报。
- 自动化 E2E 主要使用稳定 Mock，不能替代真实岗位和真实数据 UAT。

## 八、移动端方向

目标架构已确定为桌面与手机统一使用同一套 Web，微信只用于打开普通 HTTPS 页面，不再承担身份认证。

但当前代码仍保留小程序目录、微信登录入口和 `wxOpenid` 字段。小程序退出属于单独的两阶段任务：先删除运行时代码，再在生产数据为零、备份和恢复演练通过且获得单独授权后删除数据库字段。当前文档不得把“目标已确认”写成“代码已删除”。
