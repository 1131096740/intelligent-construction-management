## 二、前端技术（Web 管理端：apps/web-admin）

### Vue 3

**是什么？** 一个前端 UI 框架，帮你把网页拆成一个个"组件"来搭建。

**为什么选它？**
- 中文社区活跃，文档友好
- 学习曲线平缓，适合新手
- 比 React 更贴近传统 HTML 写法

**在这个项目里怎么用？**
- 每个页面是一个 `.vue` 文件（模板 + 逻辑 + 样式）
- 页面之间通过 `vue-router` 跳转
- 用户状态（登录信息、token）存在 `pinia` 里

### TypeScript

**是什么？** JavaScript 加上类型标注。比如这个变量只能是数字，那个参数必须是字符串。

**为什么用？**
- 写代码时 IDE 会提前提示错误，不用等到运行时才发现
- 多人协作时，类型定义就是"文档"，一看就知道接口长什么样

**项目中的体现：**
```typescript
// 这就是 TypeScript：给数据定义"长相"
interface Contract {
  id: string;
  code: string;      // 合同编号
  name: string;      // 合同名称
  counterparty: string;  // 对方单位
  status: string;    // 状态
}
```

### TDesign

**是什么？** 腾讯开源的企业级 UI 组件库。提供了按钮、表格、表单、弹窗等现成组件。

**为什么选它？**
- 自带企业后台风格，不用自己设计
- 和 Vue 3 完美配合
- 腾讯维护，质量有保障

**当前约束（2026-07-08）：**
- Web 管理端统一使用 `tdesign-vue-next`，不引入 Element Plus、Ant Design Vue、Naive UI、Vant、Arco 等第二套组件库。
- 小程序端继续使用 TDesign 小程序组件。
- 业务组件可以存在，例如动作面板、证据文件卡、审批时间线；它们承载业务语义，不作为新的通用组件库。
- 当前 Web 管理端还没有项目级设计 token。下一步采用薄 token 层收口背景、文本、边框、状态色、字号、间距和圆角，不重写 UI 底座。

**最小设计 token 方向：**

### Vite

**是什么？** 一个极速的前端构建工具。你写的 Vue/TS 代码需要"打包"成浏览器能运行的格式。

**为什么用？**
- 启动开发服务器不到 1 秒（传统工具可能要 30 秒+）
- 修改代码后页面秒级刷新

### Pinia

**是什么？** Vue 的状态管理库。项目里主要用于管理登录状态（token、用户信息）。

## 三、后端技术（services/api）

### NestJS

**是什么？** Node.js 的后端框架，借鉴了 Angular 的设计理念。

**核心概念：**

| 概念 | 通俗解释 |
|---|---|
| **Module（模块）** | 一个功能块，比如 `ContractModule` 管合同，`AuthModule` 管登录 |
| **Controller（控制器）** | 接收前端请求，比如 `GET /contracts/123` 查合同 |
| **Service（服务）** | 处理业务逻辑，比如"这个合同能创建结算吗" |
| **Guard（守卫）** | 守门员，比如"这个用户有权限做这个操作吗" |
| **Decorator（装饰器）** | `@` 开头的标记，用来给类/方法加特殊能力 |

**项目中的模块划分：**
- `AuthModule` — 登录、JWT 令牌
- `ContractModule` — 合同 CRUD、状态机
- `SettlementModule` — 结算 CRUD、状态机
- `PaymentModule` — 付款申请、金额校验、实际付款
- `ApprovalModule` — 审批引擎（冻结、流转、或签/会签）
- `FileModule` — 文件上传下载
- `AuditModule` — 审计日志

### PostgreSQL

**是什么？** 一个免费开源的关系型数据库。数据存在表里，表之间通过外键关联。

**为什么选它？**
- 免费、功能强大
- 支持事务（保证金额操作不出错）
- 比 MySQL 更适合复杂业务逻辑

### Prisma

**是什么？** 一个 ORM（对象关系映射）工具。让你用 TypeScript 代码操作数据库，不用写 SQL。

**为什么用？**
- 自动生成类型安全的代码
- schema 文件（`schema.prisma`）就是数据库的"设计图纸"
- 迁移（migration）自动管理数据库版本

**示例：**
```prisma
// schema.prisma 中定义表结构
model Contract {
  id        String   @id @default(uuid())
  code      String   @unique
  name      String
  status    String
  // ...
}
```
```typescript
// 代码中操作数据库
const contract = await prisma.contract.findUnique({
  where: { id: contractId },
  include: { versions: true }
});
```

### JWT (JSON Web Token)

**是什么？** 一种登录令牌。用户登录后，后端发一个加密的令牌，前端每次请求带着它证明身份。

**为什么用？**
- 无状态，不需要服务器存会话
- 可以携带用户信息（角色、岗位）
- 支持过期和刷新

**项目中的流程：**
1. 用户手机号+密码登录 → 后端返回 `accessToken`（短期）+ `refreshToken`（长期）
2. 前端每次请求带 `Authorization: Bearer <accessToken>`
3. accessToken 过期后，用 refreshToken 换一个新的

## 四、共享层（packages/shared-domain）

这个包里放的是前后端都需要遵守的定义。

| 文件 | 内容 |
|---|---|
| `roles.ts` | 17 个角色的 key 和中文名定义 |
| `statuses.ts` | 合同/结算/付款的状态定义 |
| `approval.ts` | 审批动作类型（提交、同意、驳回、转审等） |
| `money.ts` | 金额工具函数（分为单位，避免浮点数精度问题） |
| `permissions.ts` | 权限策略表：哪个动作需要什么角色 |
| `core-flow-read-model.ts` | 核心读数据的类型定义 |

**为什么单独放一个包？**
- 前后端共享同一份类型定义，不会各写各的导致不一致
- 修改一个地方，前后端同时生效

## 六、为什么这样选型？（架构决策理由）

| 决策 | 原因 |
|---|---|
| **Web 是主系统，非小程序** | 建筑企业的台账管理很复杂，手机操作不便。小程序只做移动审批。 |
| **NestJS 而非 Express** | NestJS 自带模块化、依赖注入、装饰器，适合企业级项目。Express 太"裸"。 |
| **PostgreSQL 而非 MySQL** | 对复杂查询、JSON 字段、事务支持更好。 |
| **Prisma 而非 TypeORM** | 类型安全更好，schema 即文档，迁移管理方便。 |
| **monorepo 而非多仓库** | 共享 domain 包，前端后端 API 类型一致，不用各自维护一份。 |
| **COS 私有桶而非公开 URL** | 合同、财务文件不能公开访问，必须走后端鉴权。 |
| **分为单位存金额** | 避免浮点数精度问题（0.1 + 0.2 ≠ 0.3 的问题）。 |
