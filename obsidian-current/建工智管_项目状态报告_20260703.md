# 建工智管 - 项目状态报告（2026-07-03）

> 本文档基于仓库 `PROGRESS.md`、当前方案讨论和 2026-07-03 已确认试运行边界同步。开发唯一进度真相仍以仓库 `PROGRESS.md` 为准。

## 一、当前结论

建工智管第一阶段已经从“证明核心链路能跑通”推进到“围绕一个真实项目上线试运行”的阶段。

当前最重要的产品判断是：公司短期内新合同不多，真实试运行项目大约有 20 个合同，且大部分已经签完并正在执行。因此接下来不能把重心继续放在“新合同从草稿到签署全流程演示”，而要转为：

```text
1 个真实项目
  -> 约 20 个已签历史合同接管
  -> 历史结算、已付、已批待付、总包代付、预付款扣回等余额初始化
  -> 3-5 个活跃合同继续跑后续结算/付款/实付/凭证/审计闭环
  -> 验证系统能否成为唯一业务事实
```

历史合同不重走合同编制、合同审批和用章审批。它们通过补录、归档、余额初始化、业务复核和接管确认，建立系统事实起点。

## 四、当前最大缺口

| P0 | 历史合同接管 | 需要支持约 20 个已签合同补录、A/B/C 分级、接管状态、历史余额初始化、业务确认和审计 |
| P0 | 历史余额进入付款控制 | 历史已付、已批待付、总包代付、预付款扣回、已生效结算必须扣减后续可付款金额 |
| P0 | 真实首页 | 登录后应看到真实待办、待补资料、待付款、待确认、异常提醒，而不是示例型首页 |
| P0 | 业务选择器 | 付款、结算、历史接管入口必须选择项目/合同/结算，不能让业务人员手填技术 ID |

| P0 | 合同母版人工验收 | 合同部/法务必须在生产等价字体环境打开 DOCX 逐页签认 |

## 五、试运行范围

本轮试运行不追求一次覆盖全公司所有项目。

进入试运行：

- 1 个真实项目；
- 约 20 个已签、正在执行的历史合同；
- 3-5 个最活跃合同跑后续结算、付款、实付、凭证、审计闭环；
- 项目经理、合同部、预算部、财务、董事长/总经理等真实岗位账号；
- 合同、结算、付款、项目经营、资料下载和审计相关核心操作。

不进入本轮：

- 全量小程序；
- 全项目铺开；
- 历史合同逐份 OCR 自动识别；
- 所有历史合同重走审批；
- 差旅、招待、开票、采购、考勤、人事等完整外围模块。

## 七、老板视角的价值判断

这个项目真正能带来的价值，不是多一个录入系统，而是把“合同、结算、付款、资料、审批、余额”从人脑、纸质文件和聊天记录里抽出来，变成公司可追责、可查验、可延续的唯一业务事实。

如果历史合同接管、余额控制、首页待办和业务选择器做不好，它会增加工作量，最终被业务人员绕开。如果这些 P0 能做好，它能减少反复问合同、查付款、翻纸质资料、人工核余额、老板拍脑袋确认的成本，并把超付、漏扣、资料缺失和审批口径不一致的问题提前拦住。

因此当前判断是：项目值得继续，但必须收窄到真实项目试运行，不再扩散功能。先证明它能在一个复杂真实项目里顺手、准确、可审计，再考虑全公司推广。
