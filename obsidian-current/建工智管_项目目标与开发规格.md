## 项目总目标

建工智管要建设成建筑企业项目经营管理系统，而不是单一微信小程序。

第一阶段目标是把企业最核心、风险最高的合同付款链路做成可审计、可追溯、可落地的闭环：

```text
合同编制
  -> 合同付款条款结构化录入
  -> 合同审批
  -> 用章审批
  -> 盖章合同归档确认
  -> 合同版本生效
  -> 结算审批
  -> 签章结算单归档确认
  -> 结算生效
  -> 付款申请
  -> 付款审批
  -> 审批通过待付款
  -> 出纳实际付款
  -> 付款凭证上传
  -> 财务流水
  -> PDF 留档
  -> 审计日志
```

系统成功的标准不是页面数量，而是后端能强制保证单据顺序、金额安全、版本追溯、文件私有、审批留痕。

## 当前试运行目标

当前上线试运行边界已经由用户确认：

- 先选择 1 个真实项目。
- 该项目约 20 个合同，大部分已经签完并正在执行。
- 历史合同不重走合同编制、合同审批和用章审批。
- 历史合同通过补录、归档、历史余额初始化和业务确认建立系统事实起点。
- 选 3-5 个活跃合同继续跑后续结算、付款、实付、凭证、财务记录和审计闭环。
- P0-7 常用单据进入试运行范围：项目付款审批表 PDF、结算附件模板下载、差旅/招待/报销最小综合费用付款闭环。
- 本轮目标是验证系统能否成为公司唯一业务事实，而不是继续扩展外围模块。

- 合同审批、用章审批、合同归档确认、合同版本生效。
- 结算创建、结算审批、结算归档确认、结算生效。
- 付款申请、付款审批、审批通过待付款。
- 出纳实际付款登记、付款凭证上传、财务流水生成。
- PDF 留档。
- 审计日志。
- 私有文件上传、权限校验、短时效下载地址。
- 历史合同接管、历史余额付款容量控制、真实首页、业务选择器和 P0-7 常用单据最小闭环。
- Web 管理端作为主系统和本轮试运行入口。
- 微信小程序作为移动审批和移动查看端预留，但不进入本轮 Web/API 试运行 P0。

第一阶段暂不建设完整版本：

- 物资领料审批。
- 请假考勤。
- 人事入离调。
- 完整成本驾驶舱。
- 安全闭环。
- 节超奖励池。

这些模块只保留未来扩展点，不允许稀释第一阶段合同付款主线。

## 架构方向

### 总体架构

```text
apps/web-admin
  Vue 3 + TypeScript + TDesign Web + Vite
  企业后台主系统

apps/miniprogram
  原生微信小程序 + TDesign 小程序
  移动工作端

services/api
  Node.js + NestJS + PostgreSQL + Prisma
  业务规则、审批、权限、文件、PDF、审计中枢

packages/shared-domain
  角色、状态、金额、审批、读模型等共享领域定义

storage
  腾讯云 COS 私有桶

deploy
  腾讯云轻量应用服务器 + HTTPS + PostgreSQL + 自动备份
```

前端改造约束（2026-07-08）：

- Web 管理端组件库统一为 TDesign Web，业务组件只能封装 TDesign 能力，不引入第二套 UI 组件库。
- 当前尚未形成项目级设计 token；下一步用薄 token 层统一背景、文本、边框、状态色、字号、间距和圆角。
- Gitee 参考仓库只吸收成熟后台经验：RuoYi 系列的权限/日志治理，RuoYi-Flowable-Plus 的任务办理与流程记录 UX，JeecgBoot 的表单配置思路，Soybean Admin 的 Vue 3 工程纪律。
- 不迁移到若依、JeecgBoot、Flowable 或任何低代码后台底座；业务状态机、金额校验、文件权限和审计仍由后端 API 和事务负责。

### 关键架构约束

- Web 和小程序都必须调用统一后端 API。
- 前端不得直连 PostgreSQL。
- 前端不得直连 COS。
- 所有状态流转、金额限制、权限判断必须由后端和数据库事务保证。
- Web 可以做提示和按钮禁用，但不能作为业务安全边界。
- 敏感文件必须经后端鉴权后生成短时效 URL。
- 所有关键动作必须写审计日志。
- 密钥不得提交到仓库，不得暴露到 Web 或小程序客户端。

## 核心业务规则

### 合同与条款版本

- 合同草稿创建时必须同时创建合同版本 v1 和付款条款版本 v1。
- 合同生效后不得直接编辑合同条款。
- 合同变更或补充协议必须走审批、用章、归档确认，然后生成新合同版本。
- 付款比例、账期、质保金、触发条件变化时，必须生成新的付款条款版本。
- 历史结算和付款必须保留创建时绑定的：
  - `contract_id`
  - `contract_version_id`
  - `payment_terms_version_id`

### 单据顺序

- 非 `effective` 合同版本不得创建结算。
- 非 `effective` 或 `partially_paid` 结算不得创建付款申请。
- 合同和结算必须归档确认后才可生效。
- 付款审批通过不等于实际付款。
- 付款审批通过后进入 `approved_pending_payment`。
- 实际付款必须由财务/出纳登记，并上传付款凭证。

### 付款金额控制

付款申请默认按合同累计结算发起，不再要求业务人员围绕单张结算单手工判断。本次可申请金额必须满足：

```text
本次申请金额
  <= 合同当前累计可付款金额
     - 已实际付款金额
     - 已审批待付款金额
     - 审批中占用金额
     - 总包代付金额
     - 本次应扣回预付款金额
     - 历史接管余额占用金额
```

要求：

- 金额统一使用分为单位的整数。
- 金额校验必须在后端事务中执行。
- 同一结算允许多次付款申请。
- 同一付款申请允许多次实际付款执行，直到付清。
- 合同级付款实付后，系统必须生成分摊/抵扣台账，避免后续重复释放额度。
- 历史合同接管后的已付、已批待付、总包代付和预付款扣回必须扣减后续可付款容量。
- 禁止仅在前端计算剩余额度。

### 审批规则

- 合同签订和合同变更需要董事长/总经理最终或签。
- 董事长和总经理节点为 OR-sign：任一人通过即通过。
- 结算审批不经过董事长/总经理。
- 所有付款审批都需要董事长/总经理最终或签。
- 合同归档件由合同部成员上传，合同部主管确认。
- 结算归档件由合同部成员上传，合同部主管确认。
- 财务可读取合同/结算归档件，但不负责上传业务归档件。

审批引擎必须支持：

- 审批流定义。
- 审批实例冻结。
- 条件节点。
- 会签。
- 或签。
- 转审。
- 委托/代理。
- 撤回。
- 驳回到上一节点。
- 打回申请人。
- 超时催办。
- 全审批历史。

## 后续开发总路线

以下 Milestone 是阶段路线。按照 2026-07-04 进度，Milestone 1-6 和“历史合同接管与单项目试运行”最小切片已基本收口；当前重点不是启动小程序，而是把现有 Web/API 放到生产等价环境，用真实岗位账号、真实历史合同和真实常用单据完成 Go-Live Gate。

### Milestone 1：本地可运行业务闭环

目标：在本地 Docker PostgreSQL 上跑通合同、结算、付款读写闭环。

优先事项：

1. 固化 Prisma schema。
2. 建立 migration。
3. seed 一套完整核心链路数据。
4. 确保 API 可以读取合同、结算、付款详情。
5. Web 详情页接真实 API。

验收：

- `docker compose up -d` 可启动 PostgreSQL。
- Prisma migrate 可执行。
- seed 可重复执行。
- 核心链路验证脚本通过。
- Web 端合同/结算/付款详情能从 API 读取数据。

### Milestone 2：合同状态机

目标：合同从草稿到生效由后端强制控制。

优先事项：

1. 合同提交审批。
2. 审批通过后进入待用章。
3. 用章审批通过。
4. 合同部成员上传盖章合同归档件。
5. 合同部主管确认归档。
6. 合同版本进入 `effective`。

验收：

- 非有效合同不能创建结算。
- 未上传归档件不能确认归档。
- 非合同部主管不能确认合同归档。
- 生效合同不能直接修改付款条款。
- 所有关键动作写审计日志。

### Milestone 3：结算状态机

目标：结算从有效合同版本创建，并在归档确认后生效。

优先事项：

1. 仅允许从 `effective` 合同版本创建结算。
2. 结算审批按合同类型选择节点。
3. 结算审批通过后进入待归档。
4. 合同部成员上传签章结算单。
5. 合同部主管确认结算归档。
6. 结算进入 `effective`。

验收：

- 非有效合同版本不能创建结算。
- 非有效结算不能创建付款申请。
- 结算绑定原合同版本和付款条款版本。
- 财务可读取结算归档件，但不能上传业务归档件。

### Milestone 4：付款审批与实际付款

目标：付款审批和实际付款彻底分离。

优先事项：

1. 从有效结算创建付款申请。
2. 后端事务校验付款申请剩余额度。
3. 付款审批通过后进入 `approved_pending_payment`。
4. 财务/出纳登记实际付款。
5. 上传付款凭证。
6. 生成财务流水。
7. 更新付款申请和结算已付金额。
8. 生成 PDF 留档。

验收：

- 付款审批通过不更新为已付款。
- 超额付款申请被后端拒绝。
- 实际付款必须有凭证。
- 支持同一结算多付款申请。
- 支持同一付款申请多次实际付款。
- 所有金额更新在数据库事务内完成。

### Milestone 5：审批引擎完善

目标：审批流可配置、实例可冻结、历史可追溯。

优先事项：

1. 审批流定义表和节点表落地。
2. 提交业务单据时冻结节点。
3. 支持会签和或签。
4. 支持条件节点。
5. 支持驳回上一节点。
6. 支持打回申请人。
7. 支持撤回。
8. 支持转审和委托。
9. 支持催办记录。

验收：

- 已发起审批不受审批模板后续修改影响。
- 董事长/总经理或签节点任一通过即可流转。
- 会签节点所有人通过才可流转。
- 每个动作有操作人、动作、意见、时间。

### Milestone 6：文件、PDF、审计、安全

目标：达到企业资料安全和审计要求。

优先事项：

1. 接入 COS 私有桶。
2. 文件上传只经过后端。
3. 文件下载走权限校验和短时效 URL。
4. 合同、结算、付款凭证形成资料库记录。
5. 关键单据生成 PDF。
6. 登录、审批、归档、付款、下载、权限变更写审计。
7. 敏感操作二次确认。

验收：

- 前端拿不到 COS 永久公开地址。
- 非授权岗位不能下载敏感文件。
- 每次敏感下载有审计记录。
- PDF 可从单据详情追溯。

### Milestone 7：小程序移动端

目标：移动端只做移动工作入口，不承载复杂配置。

优先事项：

1. 微信登录与员工绑定。
2. 待我审批。
3. 审批详情。
4. 附件预览。
5. 审批同意/驳回/退回。
6. 移动端上传必要附件。
7. 消息提醒。

验收：

- 小程序不直连数据库或 COS。
- 小程序不承担复杂权限配置。
- 小程序审批动作与 Web 共用同一后端审批引擎。

### Milestone 8：部署上线

目标：可在腾讯云轻量应用服务器上稳定运行。

优先事项：

1. 生产环境变量和密钥管理。
2. HTTPS。
3. PostgreSQL 不开放公网。
4. COS 私有桶。
5. 数据库备份。
6. 附件备份策略。
7. 日志和错误监控。
8. 上线初始化脚本。

验收：

- 生产密钥不在代码仓库。
- 数据库公网不可访问。
- 每日备份可恢复。
- 关键服务重启后可恢复。
