# 建工智管 - 第一阶段 MVP 产品与架构设计

日期：2026-06-19

当前实现状态同步：2026-07-15。后端核心闭环、企业级合同工作台、合同 DOCX/PDF、结算模板/导入、历史合同接管、历史余额付款容量、真实首页、常用单据、私有文件、审计和 Web 核心入口已有真实实现；Web/API、HTTPS、COS、备份恢复和基础告警已有生产证据，P0/P1 UI 与六档桌面响应式治理形成尚未部署的发布候选。当前重点是历史合同批量接管、3-5 条真实长链路、合同母版/场景、普通账号权限、财务幂等和发布回滚验证。详见 [[建工智管_项目状态报告_20260715]]。

## 版本定位

建工智管不是单纯微信小程序，而是建筑企业项目经营管理系统。

目标架构采用：

- 响应式 Web：桌面与手机共用的企业主系统。
- 统一后端：业务规则、权限、审批、文件、PDF、审计的中枢。

当前仓库仍保留历史小程序骨架、微信登录入口和 `wxOpenid`，只表示退出尚未实施，不属于继续建设范围。

本版本以 `建工智管_完整方案_20260608` 为主依据。旧版 6 类审批、8 个角色、41 个云函数的小程序实现仅作为历史参考，不作为当前建设依据。

## 第一阶段主线

第一阶段聚焦审批与合同付款闭环：

```text
合同编制
  → 合同付款条款结构化录入
    → 合同审批
      → 用章审批
        → 盖章合同归档确认
          → 合同版本生效
            → 月度/节点结算
              → 结算审批
                → 签章结算单归档确认
                  → 结算单生效
                    → 付款申请
                      → 付款审批
                        → 审批通过待付款
                          → 出纳实际付款
                            → 上传付款凭证
                              → 财务流水、PDF 留档、审计日志
```

第一阶段暂缓：物资领料审批、请假考勤、人事入离调、完整成本看板、安全闭环、节超奖励池。这些模块在数据结构上预留接口，但不稀释第一阶段主线。

## 当前试运行切割（2026-07-03）

当前上线试运行不再以“少量新合同完整跑通”为主，而是以 **历史合同接管** 为主：

- 选择 1 个真实项目试运行。
- 约 20 个已签并正在执行的历史合同进入系统台账。
- 其中 3-5 个近期有结算或付款动作的活跃合同完整跑后续结算/付款链路。
- 历史合同不重走合同编制、合同审批和用章审批，只做补录、归档、历史余额初始化和业务确认。
- 试运行开始后的新合同、新结算、新付款、实际付款、凭证和归档必须进入系统。
- 历史余额必须参与后续付款容量控制，不能只展示不控制。
- 项目付款审批表 PDF、结算附件模板下载和差旅/招待/报销最小综合费用付款闭环纳入本轮 P0；完整 OA 报销、发票识别、行程明细、多人报销和预算科目树不纳入本轮。

历史合同按 A/B/C 分级接管：

- A 级：近期有结算或付款，必须补齐付款条款、历史累计结算、历史已付、已批待付、总包代付、预付款扣回、质保金和关键附件。
- B 级：执行中但近期不付款，先录基础信息、合同金额、合同类型、附件和历史已付概况；发生结算或付款前升级为 A 级。
- C 级：已完结或低频合同，只做台账和文件归档，不强制拆解付款条款和历史付款明细。

## 技术架构

```text
apps/web-admin
  Vue 3 + TypeScript + TDesign Web + Vite

mobile
  与桌面共用 Vue 3 响应式 Web

services/api
  Node.js + NestJS + PostgreSQL

storage
  腾讯云 COS 私有桶

deploy
  腾讯云轻量应用服务器 + HTTPS + 自动备份
```

所有客户端请求都必须经过后端 API。前端不得直连数据库或对象存储。

Web 管理端继续统一使用 TDesign Web，不引入 Element Plus、Ant Design Vue、Naive UI、Vant、Arco 等第二套 UI 组件库。2026-07-15 复核结论：依赖层面统一为 `tdesign-vue-next`，P0/P1 样板、Design Token 和 33 个有效路由页面的六档桌面响应式治理已经形成发布候选。Gitee 上的 RuoYi-Vue、RuoYi-Vue-Plus、RuoYi-Flowable-Plus、JeecgBoot、Soybean Admin 仅作为权限治理、流程待办、密集表单和前端工程纪律参考，不迁移后台底座、流程引擎或低代码运行时。

## 部署与安全

采用腾讯云轻量应用服务器，不做固定 IP 白名单。项目部和办公地点经常变化，安全策略以身份、权限、文件私有和审计为主。

安全基线：

- 全站 HTTPS。
- PostgreSQL 不开放公网。
- COS 私有桶，文件下载由后端鉴权后生成短时效链接。
- 合同、结算、付款凭证、工资、财务资料不得公开直链。
- 关键操作写审计日志。
- 合同归档确认、结算归档确认、付款最终审批、实际付款登记、权限变更、单据作废需要二次确认。
- 每日数据库备份，重要附件开启版本或备份策略。
- COS 密钥、数据库密码、JWT 密钥和其他生产凭据不得写入任何客户端或代码仓库。

## 合同版本与付款条款

合同生效后不允许直接修改原合同条款。

合同变更或补充协议必须走审批，审批通过、用章、归档确认后生成新的合同版本。

合同版本变化不一定意味着付款条款变化：

- 供货数量、单价、分包内容变化：生成新合同版本，付款条款可沿用。
- 付款比例、账期、质保金、付款触发条件变化：生成新合同版本，同时生成新付款条款版本。

结算单和付款单必须绑定创建时有效的：

- `contract_id`
- `contract_version_id`
- `payment_terms_version_id`

历史结算和付款永远按当时绑定的版本追溯。

## 付款条款模型

合同付款条款由合同部成员录入，合同部主管负责审核。预算岗位保留业务复核资格，但不作为合同审批的强制节点。

付款条款支持多阶段规则：

- 预付款。
- 进度款。
- 月度结算款。
- 节点款。
- 竣工款。
- 质保金。
- 特殊条款，如收到发票后、收到甲方款后、验收后 N 天。

每条付款条款至少包括：

- 条款名称。
- 合同原文。
- 计算基准：合同金额、本期结算金额、累计结算金额、固定金额、手动金额。
- 比例或固定金额。
- 触发条件。
- 账期起算点。
- 账期天数。
- 是否需要发票。
- 是否允许提前付款。
- 是否允许分批付款。
- 是否涉及质保金。

## 单据强顺序规则

第一阶段采用硬顺序：

- 未归档生效的合同版本，不允许创建结算单。
- 未归档生效的结算单，不允许创建付款申请。
- 付款审批通过不等于已付款。
- 出纳实际付款并上传付款凭证后，付款才进入已付款或部分付款状态。

付款金额控制：

```text
本次申请金额
  ≤ 当前结算单可付金额
    - 已审批待付款金额
    - 已实际付款金额
```

同一结算单支持多次付款和分批付款。

## 合同审批与用章归档

新签合同和普通合同变更使用以下主流程：

```text
合同部成员编制合同和付款条款
  → 董事长/总经理或签
  → 自动触发用章审批
  → 综合部主管
  → 项目经理
  → 用章通过
  → 合同部成员上传盖章归档件
  → 合同部主管确认归档
  → 合同版本生效
```

严格超过原始金额 10%，或无限额合同发生任意非零金额变化的重大合同变更，审批路线增强为：

```text
合同部成员编制合同变更/补充协议
  → 财务主管
  → 合同部主管
  → 董事长/总经理或签
  → 后续用章、归档确认与版本生效链路保持不变
```

预算部主管不再是重大合同变更的强制审批节点；预算角色继续保留，可承担业务复核和后续可配置审批资格。

董事长和总经理节点为或签：任一人通过即通过，任一人驳回即驳回。

## 结算审批与归档

结算不经过董事长/总经理。

物资类/机械类结算：

```text
合同部成员编制结算单
  → 物资员
  → 物资主管
  → 合同部主管
  → 项目经理
  → 财务总监
  → 合同部成员上传签章归档件
  → 合同部主管确认归档
  → 结算单生效
```

劳务/专业分包类结算：

```text
合同部成员编制结算单
  → 工长
  → 项目总工
  → 工程技术部
  → 合同部主管
  → 项目经理
  → 财务总监
  → 合同部成员上传签章归档件
  → 合同部主管确认归档
  → 结算单生效
```

结算归档件由合同部成员上传，合同部主管确认。财务部只读取归档件，不负责上传业务归档件。

## 付款申请与实际付款

试运行后的普通合同付款默认按合同发起，系统自动纳入该合同全部已生效结算、付款条款、历史余额、审批中占用、已批待付、总包代付和预付款扣回。单张结算付款和合同预付款作为受控来源保留。

付款审批：

```text
发起付款申请
  → 项目经理
  → 财务总监
  → 董事长/总经理或签
  → 审批通过待付款
```

实际付款：

```text
出纳/财务人员登记实际付款
  → 上传银行回单/付款凭证
  → 生成财务流水
  → 更新结算单已付款金额
  → 生成 PDF 留档
  → 写入审计日志
```

付款状态：

- 草稿。
- 审批中。
- 审批驳回。
- 审批通过待付款。
- 部分付款。
- 已付款。
- 已作废。

## 审批引擎能力

第一阶段审批引擎必须支持：

- 审批流定义。
- 审批实例固化。
- 条件节点，如合同金额 ≥ 100 万。
- 会签。
- 或签。
- 转审。
- 审批代理。
- 撤回。
- 驳回到上一级。
- 打回发起人重来。
- 必填审批意见。
- 审批超时催办，但不自动通过、不自动升级。
- 节点处理人按岗位、项目、部门解析。
- 全审批历史留痕。

## 移动端设计范围

手机浏览器使用与桌面相同的响应式 Web、手机号密码身份和统一后端权限，不另建第二套业务事实或审批逻辑。

必须包含：

- 工作台待办。
- 审批列表。
- 审批详情。
- 移动审批。
- 签名。
- 附件查看。
- 附件/照片上传。
- 消息提醒。
- 我的签名和个人信息。

复杂合同条款、专业清单、结算选行和批量资料管理在窄屏下可以通过专业工作区内部滚动保持完整，不强制压缩到不可用布局。

当前小程序退出按两阶段执行：第一阶段清理运行时代码和微信登录；第二阶段只有生产 `wxOpenid` 非空数量为零、备份和恢复演练通过并获得单独授权后才删除数据库字段。

## 资料库与文件

资料库按部门和业务单据归档：

- 合同归档件。
- 补充协议归档件。
- 结算归档件。
- 付款审批 PDF。
- 银行回单/付款凭证。
- 审批附件。

财务资料默认仅财务部、董事长、总经理可见。项目经理可看付款状态，不默认查看银行回单。

所有文件下载必须鉴权并记录审计。

## 验收标准

第一阶段验收至少覆盖：

1. 合同部成员可创建合同并录入多阶段付款条款。
2. 新签合同由董事长/总经理或签；重大合同变更先经财务主管、合同部主管审批，再进入董事长/总经理或签。
3. 董事长/总经理任一人可完成合同最终审批。
4. 合同审批通过后自动生成用章流程。
5. 用章通过后，合同部成员上传归档件，合同部主管确认后合同版本生效。
6. 未生效合同不能创建结算。
7. 结算审批不经过董事长/总经理。
8. 结算审批通过后必须上传归档件并确认，才可发起付款。
9. 未生效结算不能创建付款申请。
10. 付款申请金额不能超过合同条款计算出的可申请余额。
11. 同一结算单可分批付款。
12. 付款审批必须经过董事长/总经理或签。
13. 付款审批通过后状态为待付款，不自动变成已付款。
14. 出纳登记实际付款并上传凭证后，付款进入已付款或部分付款。
15. 历史结算和付款可追溯到当时的合同版本和付款条款版本。
16. 敏感文件不可公开访问。
17. 所有审批、归档、付款、下载动作都有审计日志。
