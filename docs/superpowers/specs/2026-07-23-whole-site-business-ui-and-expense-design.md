# 建工智管整站业务工作台、费用报销与 UI 标准设计

日期：2026-07-23

状态：业务规则与页面标准已由用户逐项确认；等待用户对本文书面复核

范围：整站信息架构、工作台与详情页标准、多维表格、响应式 Web、审批与待办、正式编号、PDF 与手写签名，以及项目、合同、历史合同接管、结算、统一资金办理、零星采购、费用报销、借款、资料和审计模块的目标体验

## 2. 目标与非目标

### 2.1 目标

- 让用户打开任何单据后立即知道“现在轮到我做什么”。
- 让合同、结算、付款、零星采购、报销和借款使用同一套页面语言，但保留各自业务规则。
- 把零星材料付款已经验证过的任务型体验提升为整站标准。
- 把费用与报销做成第一个完整采用新标准的业务模块。
- 让所有填写表格的业务采用适合工程管理的多维表格体验。
- 在电脑全屏、窗口、半屏、四分之一屏和常见手机尺寸下完成同一业务链路。
- 保留熟悉的公司纸质表单版式，并把审批、签名、实际付款和归档事实准确投影到正式 PDF。
- 统一最小授权、草稿、附件、并发、错误、审计和性能规则。

### 2.2 非目标

- 不建设完整采购 ERP、库存、材料领用、供应商门户或询比价系统。
- 不建设结构化发票 OCR、验真、抵扣和发票台账系统。
- 不建设低代码平台、万能表单引擎或第二套工作流引擎。
- 不引入第二套基础 UI 组件库。
- 不以一次性全站重写替代增量迁移。
- 不建设具有法律认证效力的电子签名平台。
- 不接入短信、企业微信、公众号或邮件外部提醒。
- 当前阶段不开放通用全量 Excel 导出。

## 3. 方案选择

### 3.1 不采用：保持各模块独立设计

优点是改动小；缺点是按钮、状态、筛选、表格、移动端和详情页继续不一致，用户每进入一个模块都要重新学习。

### 3.2 不采用：购买或建设全套低代码业务平台

优点是短期可以快速生成表单；缺点是会形成第二套权限、状态、文件和组件体系，难以承载现有审批、金额、版本、归档和审计不变量。

### 3.3 采用：共享交互骨架，领域规则独立

整站统一设计令牌、页面骨架、多维表格、状态、附件、审批时间线、签名和错误处理。合同、结算、付款、报销等领域仍由各自服务和状态机负责。

实施采用一个候选分支、分模块提交、统一 UAT 候选的方式：

1. 设计令牌和共享组件。
2. 费用与报销标准模块。
3. 项目、合同、历史接管和结算。
4. 统一资金办理和零星采购。
5. 审批中心、首页、资料和系统配置。
6. 全尺寸视觉验收、自动化回归和真实岗位 UAT。

不把半成品逐段发布到生产。

本文是整站总规格，不对应一次巨型代码任务。后续实施计划必须按阶段拆成可独立验证的子计划，每个子计划都以本总规格和对应领域旧规格为输入，不允许用“大重构”代替逐模块验收。

## 5. 整站视觉标准

### 5.1 视觉方向

采用已确认的 B 方案：克制、专业、中等密度、轻边框、弱阴影、企业蓝主色。视觉重点来自信息层级和任务优先级，不来自大色块或装饰。

### 5.2 设计令牌

- 页面标题 24px，区块标题 18px，卡片标题 16px。
- 桌面正文 14px，辅助文字 12px。
- 手机输入框文字至少 16px，避免浏览器自动放大。
- 行高约 1.5。
- 间距使用 `4 / 8 / 12 / 16 / 24 / 32px` 体系。
- 普通按钮高 36px，主要表单按钮高 40px；手机点击区域不小于 44px。
- 普通控件圆角 6px，卡片 8px，弹窗和抽屉 10px。
- 阴影只用于弹窗、抽屉和悬浮层。
- 颜色、字号、间距、圆角、阴影和布局尺寸统一进入 TDesign 变量及 `--jg-*` token。

### 5.3 按钮与状态

- 同一操作区域最多一个实心主按钮。
- 按钮文字、内边距和高度必须协调，禁止短文字挤在过大的方块中。
- 非交互状态使用自适应宽度的状态标签或“圆点 + 文字”，不得伪装成按钮。
- 状态颜色只作辅助：完成为绿，当前待办为蓝或紫，风险/退回为橙，失败/作废为红，冻结/普通状态为灰。
- 颜色永远不能替代状态文字。

## 6. 公共组件边界

跨模块只建立以下共享组件，不建立万能低代码页面：

- `JgWorkbenchShell`：工作台标题、统计、筛选、列表和分页。
- `JgPageHeader`：正式编号、标题、状态和关键摘要。
- `JgTaskCard`：当前账号现在要做的任务。
- `JgFilterBar`：基础筛选、高级条件和已选标签。
- `JgBusinessGrid`：RevoGrid 多维表格适配层。
- `JgStatusTag`：状态语义和统一尺寸。
- `JgDetailTabs`：详情页签和吸顶行为。
- `JgApprovalTimeline`：完整审批路线与历史。
- `JgAttachmentPanel`：选择、上传、预览、冻结、替换和追加。
- `JgActionBar`：保存、上一步、下一步和提交。
- `JgDocumentPreview`：正式 PDF 预览与版本切换。
- `JgSignaturePanel`：扫码签名、手机签名和签名状态。
- `JgResultState`：骨架、空数据、失败、无权限、已失效和重试。

所有组件组合 TDesign，不重写按钮、输入框、选择器、上传器、抽屉、弹窗或消息系统。领域页面通过 props、slots 和稳定读取模型提供内容，公共组件不理解合同金额、借款余额或结算周期等领域规则。

## 7. 多维表格标准

### 7.1 选型

采用 RevoGrid Community 的 Vue 3 包装层作为高性能明细编辑底座，并封装为 `JgBusinessGrid`。官方文档确认其 Vue 3 集成、高性能滚动和 MIT 社区许可证。Pro 能力不作为本期依赖；树形、透视、甘特、AI、服务端分析等商业能力不进入当前范围。

官方依据：

- https://rv-grid.com/guide/vue3/
- https://rv-grid.com/guide/
- https://rv-grid.com/guide/licensing

TDesign 仍是整站唯一基础 UI 组件库。RevoGrid 只负责复杂业务明细网格，不替换 TDesign 的普通台账、表单、弹窗或导航。

### 7.2 使用范围

以下填写型明细采用 `JgBusinessGrid`：

- 合同清单和付款条款。
- 历史合同接管明细。
- 结算工程量和调整项。
- 合同付款构成与账户明细。
- 零星采购材料。
- 零星付款材料和渠道。
- 报销费用明细。
- 其他出现多行、多列、计算和校验关系的业务明细。

普通只读台账继续使用 TDesign 表格或工作台列表，不为“统一”而强制套用编辑网格。

### 7.3 表格行为

- 关键字段固定左侧，操作列固定右侧，中间列局部横向滚动。
- 用户可调整非关键列宽、隐藏非关键列；偏好保存在当前设备，可恢复默认。
- 默认行高约 48px。
- 编号、状态、金额、日期保持单行。
- 项目名称、合同名称和摘要最多两行，超出省略并可查看全文。
- 禁止把中文标题逐字挤成竖排。
- 计算、权限和最终校验由后端完成；前端合计只用于即时预览。
- 键盘可完成单元格导航、录入、复制和粘贴；粘贴仍逐格校验。
- 大量明细使用虚拟渲染，只渲染可见区域。
- 手机端转换为逐条业务卡片编辑，不把桌面网格整体缩小。

## 8. 页面骨架

### 8.1 工作台

所有工作台固定顺序：

1. 页面标题、一句业务说明、唯一主操作。
2. 可点击的待办数量卡。
3. 项目、状态、类型和关键词基础筛选；高级筛选按需展开。
4. 已选条件标签和一键重置。
5. 表格或移动端卡片。
6. 总记录数和分页。

分页由服务端完成，默认每页 20 条，可切换 20、50、100 条。筛选、排序和关键词查询均由服务端执行。返回工作台时恢复原筛选、页码和滚动位置，不使用无限下拉。

由上游自动生成的业务不提供误导性的“新建”按钮。例如零星付款必须从已批准采购自动草稿进入。

### 8.2 详情页

所有详情页首屏固定顺序：

1. 正式编号、业务名称、状态。
2. 项目或使用单位、发起人/责任人、当前节点、下一步。
3. “当前办理”任务卡。
4. 一个主操作；次要操作收入“更多”。
5. 业务信息、审批进度、实际办理、附件和归档页签。

详情页不提供系统内返回按钮，依赖浏览器返回并恢复原工作台现场。页签滚动时吸顶，手机允许横向滑动。

### 8.3 页面、抽屉和弹窗边界

- 多步骤新建或编辑、包含多维表格、多个附件或超过一个屏幕的表单使用独立路由页面。
- 查看少量明细、补全少量字段、登记一笔实际付款或退款使用右侧抽屉。
- 删除、退回、作废和单一确认使用小型弹窗。
- 不嵌套第二层抽屉。
- 手机端抽屉变为全屏。
- 独立业务页面有稳定 URL，可刷新、收藏和直接访问。

## 9. 响应式与浏览器标准

响应依据是页面和组件可用宽度，不依赖设备型号：

- `≥1280px`：完整桌面布局，侧栏展开，普通表单最多两列。
- `960–1279px`：紧凑桌面布局，减少留白，不缩小文字和操作。
- `768–959px`：图标侧栏，表单逐步切为单列。
- `<768px`：移动抽屉侧栏、单列表单、卡片列表和底部操作栏。
- `<360px`：核心业务仍可完成；整页不得横向溢出，只有网格内部可以滑动。

长表单规则：

- 电脑普通字段最多两列；长文本、附件和网格独占整行。
- 半屏、窄窗口和手机切为单列。
- 手机按步骤分段，底部固定“上一步 / 保存草稿 / 下一步或提交”，同时只突出一个主按钮。
- 切换步骤校验当前步骤，并定位第一个错误。
- 改变窗口大小和横竖屏不能丢失已填写内容。

正式支持：

- Chrome、Edge 最近两个主要版本。
- macOS Safari 最近两个主要版本。
- iOS Safari、Android Chrome。
- 微信内置浏览器中的登录、查看、审批、附件上传和直接手写签名。

不支持 Internet Explorer。检测到不兼容浏览器时显示升级提示，不允许白屏。

## 10. 表单、草稿与附件

### 10.1 字段标准

- 字段名称独立显示，不能只使用 placeholder。
- 必填项统一星号；条件必填在条件触发后显示。
- 单位使用输入框后缀。
- 金额输入同步显示千分位预览和中文大写。
- 帮助文字只解释真实业务边界。
- 错误紧贴字段，并说明修正方法。
- 冻结字段显示事实和冻结原因，不使用难以阅读的灰色输入框。

### 10.2 数字规则

- 新写入数量、金额、单价和税率最多两位小数。
- 金额显示两位小数和千分位，如 `¥4,100.00`。
- 数量去掉无意义的尾零，如 `1`、`1.5`、`1.25`。
- 税率显示 `13%`、`3%` 或 `0%（免税）`。
- 历史超过两位小数的事实只读保留，不批量四舍五入或改写。
- 金额继续使用整数分或项目现有精确金额契约；前端不得用浮点数作为最终业务事实。

### 10.3 手动服务端草稿

- 不自动保存。
- 用户显式点击保存草稿。
- 第一次成功保存时由服务端生成正式编号，编号不回收。
- 未保存离开时提醒；失败保留当前输入。
- 附件选择后立即上传到受控临时区，不要求先保存整张草稿。
- 附件上传与保存草稿互不阻断；提交时再检查附件业务绑定。
- 提交审批前必须先成功保存当前完整版本。

草稿生命周期继续遵循 `2026-07-19-draft-lifecycle-governance-design.md`：纯净草稿可以安全放弃，曾提交或已形成业务证据的记录只能撤回、放弃申请、作废或异常终止，不能物理删除。

### 10.4 并发编辑

采用服务端版本号和乐观锁：

- 当前授权办理人可编辑，其他人只读。
- 每次保存携带版本号。
- 旧标签页、办理人变化或并发保存不得覆盖新版本。
- 冲突时显示最新修改人和时间；保留用户当前输入供复制，不静默合并。
- 不使用长期占用式编辑锁。
- 保存成功、冲突和办理人变化进入审计。

### 10.5 附件组件

- 选择后立即上传并显示进度、成功、失败和重试。
- 图片和 PDF 在线预览；Office 文件受控下载。
- 草稿阶段按权限删除或替换。
- 提交冻结后只能按领域规则追加或生成新版本。
- 上传失败不清空表单；保存草稿失败不删除已成功上传的临时文件。
- 文件绑定、替换、下载和敏感预览均由后端鉴权并审计。

## 11. 状态、待办与审批

### 11.1 状态语言

页面始终分开显示：

- 业务状态。
- 当前节点。
- 当前办理人（岗位 + 真实姓名）。
- 下一步。

不使用无上下文的“办理中”“处理中”。多人节点显示全部实际候选人；已处理节点显示实际处理人的职位和姓名。

### 11.2 审批中心

固定视图：

- 待我审批。
- 我已审批。
- 我发起的。
- 全部审批（仅公司级授权岗位）。

表格列：业务编号、类型、项目/事项、申请人、金额、当前节点、当前办理人、等待时长、提交时间和操作。没有金额的业务显示“无金额”，不得显示 `¥0.00`。

审批详情先展示决策事实和正式文件预览，再展示完整审批路线，最后展示动作区。标准动作：

- 通过。
- 退回上一可修改节点或申请人，原因必填。
- 终止仅在领域规则允许时放入“更多”，需要二次确认和原因。

不提供批量审批。转交、委托等能力只在领域明确允许时出现，费用报销和本轮标准流程不默认开放。

所有流程参与者以及公司全局业务权限角色，在各自业务范围内可以查看完整流程进度，包括每个节点的职位、姓名、意见、签名和时间。

### 11.3 首页和统一待办

首页、侧栏角标、审批中心和各工作台使用同一服务端工作项数据。待办至少包括：

- 审批。
- 退回修改。
- 补全付款主体或账户。
- 登记实际付款和凭证。
- 收货确认和复核。
- 用章、归档。
- 借款冲销和还款确认。
- 票据或证据确认。

完成动作、浏览器恢复焦点和重新进入页面时立即刷新；平时每 60 秒刷新。当前项目没有 WebSocket，本期不为此单独引入实时连接。

### 11.4 自审

费用与报销流程允许同一真实人员在其实际岗位节点自审，包括综合部主管本人发起后办理综合部主管节点。自审必须明确标记、显示真实岗位和姓名，并遵循该节点既有密码、签名和审计规则，不通过伪造跳过记录实现。

其他领域是否允许自审继续由各自现有不变量决定，本文不以费用规则静默放宽合同、结算或付款。

## 14. 项目模块

项目模块只有“项目工作台”和“项目花名册”。项目经营信息进入项目详情，不保留独立项目经营菜单。

### 14.1 项目可见范围

- 启用的项目花名册成员看到本人项目。
- 公司级业务岗位按公司授权范围查看。
- 参与某张业务审批只获得该业务单据权限，不自动获得整个项目权限。
- `super_admin` 是技术角色，不自动获得业务数据权限。
- 列表、选择器、详情和 API 使用同一可见范围。

### 14.2 项目工作台

列：项目编号、名称、责任公司、项目经理、本人角色、合同/结算/付款摘要、状态、更新时间和操作。无经营金额权限的用户不显示金额。

项目详情页签：项目概览、经营概览、合同、结算、付款、零星采购、费用、花名册、资料和审计。

项目生命周期固定为：筹备中、进行中、已暂停、已完工待收口、已归档。每次状态变化由后端检查未完成合同、结算、付款、零星采购、报销和归档事项；前端不能用一个下拉框绕过收口条件。

### 14.3 花名册

字段：姓名、电话、项目角色、实际职务、部门、生效日期、失效日期、状态、权限来源和操作。

- 一人可有多个项目角色。
- 施工员、工长和技术人员使用统一工程岗位权限映射，同时保留实际职务文本。
- 材料部和物资部视为同一部门；成员和主管分别映射物资员和物资主管。
- 无账号人员可以作为花名册记录，但不能登录、审批或办理；绑定真实账号后才获得系统能力。
- 不创建占位账号。

## 15. 合同模块

### 15.1 合同工作台

合并旧合同工作台和合同管理。视图：待我办理、我的草稿、审批中、待我方用章、待归档、已生效、全部合同。

一行代表一个合同根单；变更、补充协议和版本进入详情。列：合同编号、项目/合同名称、乙方、类型/计价方式、合同金额或控制金额、状态、当前办理人和更新时间。

新建/编辑使用四步独立页面：

1. 基本信息。
2. 合同清单和付款条款。
3. 文件与附件。
4. 核对并提交。

合同清单和付款条款使用 `JgBusinessGrid`。我方当前只办理作为甲方的合同；我方作为乙方暂不实施。

### 15.2 合同业务规则

- 计价方式支持固定总价、暂定金额和单价合同。
- 暂定金额和单价合同必须有控制金额。
- 发起审批前必须上传已经先由外部乙方签字盖章的 PDF。
- 项目在首次保存时冻结。
- 我方公司主体从主数据选择并冻结快照。
- 合同乙方必须来自合作单位档案并冻结快照。
- 合同中不强制填写乙方收款账户、开户行或账号。
- 合同付款时由财务人员补全实际收款账户；账户户名不要求机械等于合同乙方名称，但必须保留实际收款对象和差异事实。

合同审批路线按合同类型使用已确认的条件首审，再进入合同主管、项目经理、财务主管和董事长/总经理 OR 签。审批后：综合部主管登记用章，合同员上传最终双方签署 PDF，合同主管确认归档生效。

条件首审固定映射：

- 材料采购、机械设备类：物资主管。
- 劳务、专业分包、工程施工类：项目工程负责人。
- 通用及其他类：综合部主管。

同一人员同时满足多个岗位时仍按冻结路线展示真实岗位与处理事实，不伪造重复签名。

详情页签：当前办理、合同信息、清单与条款、合同文件、审批进度、用章与归档、结算与付款、版本与变更、归档资料。

同一合同同时只允许一个活跃变更或补充流程。合同归档生效后历史版本不可覆盖。

### 15.3 合同模板库与合作单位

合同模板库桌面使用表格，手机使用卡片。字段：模板名称、合同类型、当前发布版本、状态、维护人、更新时间和操作。预览模板与使用模板创建合同是两个明确动作；停用模板不能用于新合同，但历史合同继续读取原版本。

模板名称和操作按钮必须保留合理最小宽度，禁止出现逐字竖排。模板、版式、标准条款和编号规则继续使用现有版本化发布能力，不建设另一套模板引擎。

合作单位档案用于正式合同乙方。合同选择后冻结单位快照；档案后续改名不改变历史合同。零星采购商户不自动进入合作单位档案，只保留项目内轻量历史名称快捷选择。

### 15.4 最终结算后的合同封闭

最终结算归档生效后，原合同永久关闭新增金额。任何新增工作或新增金额必须新签合同，不能再通过原合同变更、补充协议或结算更正增加。

最终结算后的受控更正只能减少金额或修正不增加金额的事实。

## 16. 历史合同接管

历史接管只由合同员、财务人员和合同主管负责：

```text
合同员录入
  -> 财务人员核对历史金额与付款事实
  -> 合同主管确认接管
```

不要求项目经理、董事长或其他岗位重新审批已签历史合同。工作台视图：待我录入、待财务核对、待合同主管确认、C 类受限待补、已接管、全部。

- 一份合同逐份办理，不提供批量业务操作。
- 保留 A/B/C 接管等级；C 类可确认但受限，并清楚展示限制。
- 历史付款凭证由财务人员补充。
- 接管确认建立系统事实起点，不伪造过去审批。
- 接管后的文件、金额和风险修订保留不可变历史。

## 17. 结算模块

合并结算工作台和结算管理。视图：待我办理、我的草稿、审批中、待归档、已生效、全部结算。

列：结算编号、项目/合同、期次、乙方、本期申报/审定金额、累计已生效结算、状态、当前办理人和更新时间。

### 17.1 期间规则

- 只能从已生效合同创建结算。
- 严格要求上一期结算生效后才能创建下一期。
- 第一期从合同开始日期到本次选择的结算截止日。
- 后续期间从上期截止日次日到本次截止日。
- 期次受合同结算周期指导，但允许因工程量较少延迟结算。
- 期间不得重叠。

### 17.2 表单与文件

四步：合同/期间、明细/调整、现场复核与乙方签章、核对/提交。

结算明细使用 `JgBusinessGrid`，至少包含合同数量、以前累计、本期数量、结算后累计、剩余、单价、本期金额和备注。调整项独立展示，原因必填。

发起审批前上传乙方已经签字盖章的结算文件。页面顺序、版本和必要签章位置必须匹配；只有模板明确要求时才强制逐页章或骑缝章。

- 现场复核人从项目花名册选择：唯一候选时自动带出，多名候选时由发起人选择，没有合法候选时阻止提交并说明应先补花名册。
- Excel 导入只作为当前结算网格的可选录入辅助，必须经过预检和人工应用；不提供批量创建结算或绕过服务端校验。

审批完成后系统把内部真实手写签名和日期合成正式结算文件，合同主管确认归档后生效。结算审批不经过董事长/总经理；成本控制节点由合同主管负责，其他可选复核不成为默认强制节点。

结算详情页签：当前办理、结算信息、明细与调整项、乙方签章文件、审批进度、归档资料、关联付款、更正与历史。

## 18. 统一资金办理

合同付款、零星材料付款、费用报销补付和借款放款保留各自来源页；财务人员、财务主管和综合部主管使用一个统一“资金办理工作台”。

视图：待我办理、审批中、已批待付、部分支付、待退款处理、待补票据、已完成、全部。

筛选来源：合同付款、零星材料付款、费用报销、借款。

列：业务编号、来源、项目/来源单据、付款事由、收款对象、我方付款主体、金额进度、状态/当前办理人、更新时间和操作。

详情页签：当前办理、申请信息、审批进度、实际付款与凭证、退款记录、发票与票据、关联来源、归档资料。

### 18.1 实际付款

- 审批通过只进入待付，不等于已经付款。
- 一张付款申请允许一笔或多笔实际付款。
- 每笔实际付款独立冻结金额、时间、方式、批准渠道、操作人和凭证。
- 非现金付款必须有成功付款凭证；现金按业务类型使用收据等已确认凭证。
- 选择文件后先上传临时区，确认登记时以幂等键绑定凭证和实付事实。
- 网络重试不得重复记账。
- 退款必须关联某笔原始实际付款，累计退款不得超过该笔有效实付。
- 银行手续费只作为银行实际扣费记录，不占用合同应付金额。
- 业务相关人员可在详情中查看完整收款信息；列表保持紧凑，不堆叠账户字段。

### 18.2 合同付款

合同付款来源必须是已生效结算、合法预付款或已到期付款条件。未付款余额口径：

```text
累计已生效结算金额 - 累计已付款
```

付款申请允许多个批准账户，实际付款总额必须等于审批金额后才显示全额付清。合同付款审批表沿用公司 A4 竖向《项目付款审批表》。审批路线：经办人提交、项目经理、合同主管、财务人员补全账户事实、财务主管、董事长/总经理 OR 签，随后进入财务实际付款。

合同付款的业务收款方必须是合同乙方。实际银行账户户名可以与合同乙方名称不同，由财务人员补全并保存差异说明；这不把账户持有人自动变成新的合同乙方。

发票可以先取得，也允许先付款后补发票；一张付款可关联多张发票。发票不与开户许可证或个人身份证复印件绑定，本期不要求这些资料。

## 19. 零星采购模块

继续保留三个工作台：

- 零星采购工作台：申请、审批和总体状态。
- 零星材料付款工作台：物资员补齐商户、材料、价格、渠道并提交付款审批。
- 收货确认工作台：经办人/受托人确认收货，物资主管复核。

实际付款、退款和财务凭证进入统一资金办理工作台。

三个工作台的主列固定为：

| 工作台 | 主列 |
| --- | --- |
| 零星采购 | 采购编号、项目、申请人/采购人、到位日期、材料与原因摘要、关联付款、收货、状态/当前办理人、更新时间、操作 |
| 零星材料付款 | 付款编号、采购编号、项目、商户/收款对象、审批金额、实付/退款/剩余摘要、收货/发票、状态/当前办理人、更新时间、操作 |
| 收货确认 | 采购/付款编号、项目、材料摘要、已付金额、批准数量、收货责任人/受托人、状态、更新时间、操作 |

列表不直接展开长项目名称、完整账户或每笔凭证。点击主编号或唯一主操作进入任务页。

### 19.1 采购申请

- 沿用 A4 竖向《零星/小额材料采购申请表》。
- 标题下增加项目名称和正式采购编号。
- 申请部门和申请人由采购人手工填写；当前不要求申请人有账号。
- 采购部门由系统按采购人当前所属物资部/材料部名称带出并冻结快照，不要求采购人重复输入。
- 全部材料共用一个要求到位日期。
- 必填采购原因。
- 材料只有名称、型号、单位、数量和备注。
- 不填写申请日期、供应商、单价、金额、发票类型或税率。
- 报价单、材料清单和现场参考照片均可选。
- 路线：物资员/物资主管发起、物资主管、项目经理。
- 物资主管本人发起时跳过本人的重复节点，保留跳过事实。

### 19.2 零星付款

- 采购审批通过后自动生成唯一付款草稿。
- 经办人从采购原单或付款工作台直接进入四步表单。
- 实际商户和收款对象默认相同；确有差异时打开例外并填写简短说明。
- 历史商户名称只作快捷选择，不建立正式供应商。
- 一张付款申请一个收款对象，可以有多个渠道且只能有一个主渠道。
- 付款材料来自批准采购材料，数量不得超过批准数量。
- 填写含税/无票单价、预计票据和税率；税率由经办人自由填写，0 表示免税，不依赖税率主数据。
- 我方付款主体由财务人员、综合部主管或财务主管在合法阶段共享补全。
- 路线：综合部主管、项目经理、财务主管、董事长/总经理 OR 签。
- 一张申请可多次实付，每笔独立凭证。
- 发票通常一张并关联整张付款申请，但附件模型允许后续追加，不强制结构化拆分。
- 报价单、收据和发票均不作为申请提交的强制附件。

### 19.3 收货

- 首笔实际付款后开放收货。
- 一张采购只有一张最终收货确认，不建立批次或车辆对象。
- 经办人可以委托同项目人员上传并确认；物资主管只复核。
- 至少一张材料现场照片，允许现场拍照或相册上传。
- 图片上传后由服务端生成类似水印相机的水印，不要求定位。
- 水印包含项目、材料摘要/经办备注、拍摄或上传时间、上传人和“相册上传”来源标识。
- 送货单照片可选。
- 少货且已付款只允许商户补货，或商户退差额后由财务登记退款和凭证。
- 不再使用“转商户余额”。
- 正式办结前允许按规则撤销；办结后不允许普通更正。

## 20. 费用与报销模块

费用与报销是独立模块，不并入零星采购。工作台统一承载费用报销、借款申请和借款冲销结果；实际公司付款进入统一资金办理工作台。

### 20.1 工作台

视图：待我办理、我的草稿、审批中、待付款/待冲销、已完成、全部。

主操作：新建费用报销、新建借款。借款冲销从报销或具体借款余额进入，不建立第三个重复“新建冲销”入口。

列：正式编号、业务类型、报销人/借款人、项目或使用单位、事由摘要、申请金额、冲销/实付结果、状态、当前办理人和更新时间。

### 20.2 报销发起身份

支持三种：

1. 本人报销。
2. 为已有系统账号人员代办。
3. 综合部为无系统账号人员代办。

无账号人员只要求真实姓名和电话号码：

- 不要求系统账号。
- 不要求部门。
- 不要求所属项目。
- 不创建占位账号。
- 报销单“经报人”显示真实姓名，并注明“由综合部某某代办”。
- 代办人的账号、岗位、签名和操作时间作为独立事实保存，不能伪装成报销人本人签名。

使用单位必须从我方公司主体中选择；项目按实际费用归属可选。报销日期由发起人填写。

实际付款主体默认等于使用单位。财务人员、综合部主管或财务主管在合法阶段可以调整实际付款主体，但必须从我方公司主体选择、填写原因并冻结调整人和时间；调整不得静默改写报销使用单位。

### 20.3 四步表单

1. 报销人和基本信息。
2. 费用明细和证据。
3. 借款冲销和收款信息。
4. 核对并提交。

费用明细使用 `JgBusinessGrid`，列：费用类别、发生日期、用途说明、单据张数、金额、证据类型和备注。

同一项目、同一报销人可以在一张单中合并多类费用。非项目报销在同一使用单位下办理。

证据类型：

- 发票。
- 收据或其他凭证。
- 无凭证。

附件属于整张报销申请，不强制逐行绑定；可选标注费用类别。没有凭证时原因必填。所有附件可以后续在合法阶段追加，但不得覆盖审批时冻结的附件快照。

报销经办人、综合部主管、财务人员和财务主管可以在各自合法阶段追加资料。追加人、岗位、时间、资料类别和文件版本必须留痕；追加不能修改已冻结费用明细、审批意见或原附件版本。

本期不采集发票号码、查验码、抵扣状态或 OCR 字段，不建立发票系统。

### 20.4 借款冲销

- 只冲销同一报销人、同一项目的借款。
- 可以冲销多笔借款。
- 默认按实际放款时间 FIFO。
- 提交时冻结可用借款余额和分配快照。
- 退回、撤回或作废释放冲销预留。
- 财务主管可以调整被冲销批次，但不能改变总冲销金额、费用金额或公司补付金额，原因必填。
- 报销金额超过可用借款时，差额成为公司补付任务。
- 没有公司补付时，审批通过并成功写入冲销分录后办结。

### 20.5 报销审批

默认路线：

```text
发起人提交
  -> 综合部主管
  -> 项目经理或事实证明人
  -> 财务主管
  -> 董事长/总经理 OR 签
```

- 有项目：第二业务节点为项目经理。
- 无项目：由发起人选择系统中的部门负责人或事实证明人。
- 综合部代办无账号人员且无项目：综合部代办人选择系统中的事实证明人。
- 任何节点仍只由冻结的真实岗位人员审批。
- 费用报销允许真实人员在其岗位节点自审，必须明确标注并留签名、日期和审计。

### 20.6 A5 费用报销单

沿用公司现行 A5 横向《费用报销单》结构：

- 使用单位、项目名称、报销日期。
- 用途。
- 单据张数、金额。
- 财务审核意见。
- 综合部、财务部、董事长/总经理签字格。
- 部门或证明人、经报人。
- 金额合计大写和小写。
- 付讫记录：现金、银行、转账等真实付款结果。

“部门或证明人”根据路线显示项目经理、部门负责人或事实证明人的实际职位和姓名。每个审批签字格显示真实手写签名和日期。

主表不得超过 A5 横向尺寸。费用行超过容量时生成 A5 横向附页，附页重复正式编号、表头和连续页码。

审批完成版与最终付讫版分开冻结；只有真实付款或正式借款冲销事实形成后才能显示付讫或冲销结果。

### 20.7 借款申请

借款表单至少包含：

- 使用单位。
- 项目。
- 申请日期。
- 借款人和电话。
- 借款原因。
- 借款金额。
- 预计清账日期。
- 收款方式和账户。
- 备注及可选附件。

审批路线：综合部主管、项目经理、财务主管、董事长/总经理 OR 签。审批完成进入待放款；真实放款登记成功后才增加“员工 + 项目”借款余额。

预计清账日期只用于提醒，不自动扣款或关闭借款。

借款详情显示当前余额、累计放款、累计冲销、累计还款、已预留冲销和可用余额。余额来自不可变分录，不直接编辑。

### 20.8 员工还款

员工还款不伪装成报销单：

```text
登记还款
  -> 财务人员核对金额、时间、方式和凭证
  -> 财务主管确认
  -> 写入借款台账减项
```

确认前不减少余额。更正使用反向分录，不删除原记录。

## 21. 资料、审计与配置

### 21.1 资料库

资料库是业务归档索引，不是任意网盘。列：名称、类别、业务类型/编号、项目、版本、归档状态、创建人、归档时间、大小和操作。

允许下载：发起人、当前或历史办理人、业务主体、冻结审批人、下游办理人、归档责任人以及按公司范围授权的业务岗位。仅是项目花名册成员不自动获得全部附件下载权。

### 21.2 审计日志

业务详情提供业务可读的版本与历史；独立审计日志提供治理证据。

关键动作必须记录：提交、审批、退回、撤回、作废、归档、实际付款、退款、收货、签名绑定、敏感预览/下载和权限变化。

重要字段修改记录前值、后值、操作人、岗位、时间和原因。草稿不记录每次键盘输入，只记录成功保存版本。

### 21.3 基础数据选择

- 项目、我方主体、合同、系统人员和岗位必须选择受控主数据。
- 选择后冻结必要快照。
- 零星商户、无账号报销人和备注性收款对象允许自由填写。
- 历史快捷选择只复制文本，不自动创建正式档案。
- 下拉框只返回当前用户有权选择的数据；空选项必须说明原因。

我方公司主体进入系统配置。业务人员按权限选择和查看，只有受控岗位可以维护。

### 21.4 全局搜索

全局搜索只检索当前账号有权访问的结构化业务数据，包括正式编号、名称、项目、合作单位、人员和摘要字段。当前阶段不做附件 OCR 或附件全文检索。搜索结果按业务类型分组，点击进入稳定详情 URL；无权限记录不得以标题、数量或命中片段泄露存在性。

## 22. 权限、安全与隐私

- 无权记录不出现在列表、搜索和统计中。
- 直接访问无权限 URL 显示独立无权页面，不泄露项目、金额、人员或附件名称。
- 永远无权的动作不显示；有权但阶段未到的动作可禁用并说明等待节点。
- 前端只使用后端下发的 `availableActions`、任务和权限事实，不根据岗位字符串自行猜测。
- 权限在页面打开后被收回时，下一次读取、下载或写入立即失败。
- 私有文件经后端鉴权和短时地址访问。
- 敏感动作使用二次确认；实际付款、退款、作废和受控更正需要当前密码。
- 业务相关人员可以在详情中看到完整收款信息；列表不展开完整账户。
- `super_admin` 不因技术身份自动获得业务附件和审批权限。

## 23. 错误、性能和操作反馈

### 23.1 操作等级

- 普通操作：保存草稿、筛选、切换页签，直接执行。
- 流程操作：提交、审批、退回、归档，先展示摘要再确认。
- 高风险操作：实际付款、退款、作废、受控更正，二次确认并验当前密码。

按钮点击后进入 loading 并阻止重复点击。关键写入带幂等保护。成功后重新读取服务端事实；失败保留输入和已上传文件。用户错误使用可执行中文说明，不展示数据库、堆栈或第三方原始异常。

### 23.2 加载与性能

- 工作台只加载当前页。
- 关键词停止输入约 300ms 后查询。
- 详情首屏先加载头部、当前办理和关键事实，其他页签按首次进入加载。
- 图片先缩略图，原图和 PDF 按需加载。
- 快速切换筛选时取消旧请求。
- 首次加载显示骨架；局部失败只重试局部。
- 刷新失败时保留最后一次成功数据并提示重试。

### 23.3 页面状态

必须区分：加载中、真实空数据、无权限、读取失败、记录不存在、已失效/已作废。任何情况不得退化为白屏或用“暂无数据”掩盖权限和错误。

## 24. 时间与展示格式

- 数据库存储使用项目统一标准时间，页面按 `Asia/Shanghai` 展示。
- 正式编号和系统动作时间使用服务端北京时间。
- 业务日期按权限填写，并同时保留系统登记时间。
- 页面日期 `YYYY-MM-DD`，时间 `YYYY-MM-DD HH:mm`；审计可显示到秒。
- 正式 PDF 沿用对应公司表单日期版式。
- PDF 使用业务事实日期，不使用打开页面的当前时间。

## 25. 导出与通知边界

### 25.1 导出

- 按权限下载正式 PDF、审批单和业务附件。
- 当前阶段不提供工作台全量 Excel 导出。
- 业务确需的单据自身明细可以提供受控下载，不等于导出整个项目台账。
- 浏览器打印不能绕过正式 PDF 权限。

### 25.2 通知

当前阶段只做系统内提醒：首页、侧栏、审批中心和工作台共享待办事件。外部短信、微信、公众号和邮件后置，未来只能复用同一待办事件源扩展。

## 26. 测试与验收

### 26.1 自动化

- 公共组件：Vitest 覆盖状态、动作、响应式映射、错误和可访问性。
- Web 页面：定向 Vitest、typecheck、lint、`check:ui`、build。
- API：金额、权限、状态、版本、PDF、归档、签名和审计使用定向 Jest、typecheck、lint、`check:business-errors`。
- 关键链路：Playwright 覆盖真实角色和页面跳转。
- 所有改动执行 `git diff --check`。

### 26.2 视口矩阵

公共页面至少验证宽度：

```text
1920 / 1440 / 1280 / 1024 / 768 / 430 / 390 / 360 / 320
```

验收：

- 无整页横向滚动。
- 文字不被截断成不可理解内容。
- 按钮文字和尺寸协调。
- 弹窗、抽屉、上传和网格可操作。
- 浏览器放大 200% 后核心流程仍可完成。
- 键盘和手机触控均可完成关键动作。

### 26.3 真实业务 UAT

至少按真实岗位完成：

- 项目成员和选择器权限。
- 合同录入、乙方文件、审批、用章、归档。
- 历史合同逐份接管。
- 结算期间、明细、乙方签章、审批和归档。
- 合同付款、财务补账户、审批、多次实付和凭证。
- 零星采购、付款、收货、退款和发票追加。
- 本人报销、代系统用户报销、综合部代无账号人员报销。
- 多类费用、无凭证原因、借款 FIFO 冲销和公司补付。
- 借款审批、实际放款、员工还款和财务主管确认。
- 电脑扫码签名、手机直接签名和签名版本冻结。
- A4/A5 PDF 逐页打印尺寸和签字格检查。

静态测试和模拟账号不等于真实 UAT。

## 28. 生产数据边界

- 不批量删除、重建或改写现有草稿和业务数据。
- Schema 前向兼容，历史记录继续可读。
- 新规则无法从旧数据可靠推断时显示“历史单据，未按新流程采集”，不伪造事实。
- 历史超过两位小数、旧签名、旧 PDF 和旧状态只读保留。
- 代码和迁移发布不自动授权业务数据初始化、白名单变化或真实链路创建。
- 每个生产写入动作仍需单独、明确授权。

## 29. 完成定义
