# 建工智管历史合同接管与单项目试运行设计

日期：2026-07-03
状态：P0-1 至 P0-7 已完成最小实现；真实试运行尚需生产验收、数据初始化和人工签认
范围：Web/API 上线试运行，不包含小程序全量建设

## 1. 背景与结论

当前系统已经具备合同、结算、付款、实际付款、PDF、私有文件、权限和审计的核心闭环。继续推进时，重点不是再扩更多模块，而是让一个真实项目能以系统作为唯一业务真相试运行。

用户确认的真实业务情况是：试运行项目大约有 20 个合同，且大部分是已经签完并正在执行的历史合同，新合同短期内较少。因此试运行设计必须从“新合同全流程验证”调整为“历史合同接管 + 少量活跃合同继续跑结算付款闭环”。

本设计的核心结论：

- 试运行范围为 1 个真实项目、约 20 个历史合同建账、3-5 个活跃合同完整跑后续结算和付款链路。
- 已签历史合同不重走合同编制、合同审批和用章审批。
- 历史合同通过补录、归档、余额初始化和确认，建立系统事实起点。
- 试运行开始后，新发生的合同、结算、付款、实付和归档必须进入系统。
- 后续 Codex 执行应优先把系统变成“经营事实链”，不得扩成大而全 OA。

## 2. 目标

### 2.1 业务目标

让老板、合同部、预算部和财务在一个真实项目上达成以下共识：

- 项目下有哪些合同；
- 每份合同签给谁、金额多少、属于什么类型；
- 每份合同已经结算多少、已经付款多少、还可能付多少；
- 哪些合同资料齐全，哪些缺合同、结算、付款凭证或补充协议；
- 哪些合同近期会发生结算或付款；
- 哪些付款可以申请，哪些因为未到账期、超额度、缺归档或历史余额不清不能申请；
- 所有关键动作可追到人、时间、文件和审批意见。

### 2.2 系统目标

试运行版必须把系统从“核心功能已完成”推进到“真实项目可用”：

- 历史合同能轻量接管；
- 活跃合同能继续走系统结算和付款；
- 首页能展示真实待办和风险；
- 用户操作不依赖技术 ID；
- 生产环境安全、备份、文件私有和审计可验收；
- UAT 后能明确是否扩大到第二个项目。

## 3. 试运行边界

### 3.1 纳入范围

本轮纳入：

- 1 个真实项目；
- 约 20 个已签历史合同；
- 3-5 个近期有结算或付款动作的活跃合同；
- 与该项目有关的业主主合同、业主审定、业主收款、总包代付和垫资额度；
- 合同部、预算部、项目经理、财务、老板/总经理等关键岗位；
- Web 管理端和后端 API；
- 私有文件、短时效下载、二次确认、审计日志；
- 合同、结算、付款、项目经营、资料库、审计、系统配置中与试运行直接相关的功能。
- 真实常用单据最小补齐：付款申请 PDF 对齐公司真实审批表、结算附件模板下载后上传归档、差旅/招待/报销的最小综合费用付款闭环。

### 3.2 暂不纳入

本轮不做：

- 全公司一次性切换；
- 小程序全量功能；
- 物资领料、考勤、人事、安全隐患、节超奖励；
- 完整差旅、招待、报销体系（P0-7 只做最小综合费用付款申请）；
- 完整审批流配置后台；
- OCR 自动识别合同；
- 历史单价库正式产品化；
- 花哨经营大屏；
- 批量导入平台；
- 所有历史合同重走审批。

这些内容只有在试运行证明主链顺畅后，才进入后续阶段。

## 4. 产品原则

### 4.1 唯一业务真相

试运行后，项目经营链条中的以下事项以系统为准：

- 合同是否已接管或生效；
- 结算是否已归档生效；
- 付款是否已审批；
- 实际付款是否已执行；
- 凭证和归档文件是否存在；
- 可申请付款金额；
- 历史累计结算和已付余额。

纸质件、扫描件、微信群和 Excel 仍可作为资料来源，但不能替代系统中的最终业务状态。

### 4.2 历史不返工，未来进系统

历史合同接管的目标是建立事实起点，不是追溯补办审批。已签合同不重走合同审批和用章审批。

试运行开始后的新发生事项必须走系统：

- 新合同走合同工作台；
- 新结算走结算审批和归档确认；
- 新付款走付款申请、审批、实付和凭证；
- 新归档文件经系统上传并确认；
- 新下载和敏感动作写审计。

### 4.3 复杂规则藏在后端

付款条款、到账期、预付款扣回、质保金释放、总包代付占用、历史已付占用等规则可以复杂，但用户界面只展示：

- 当前可申请金额；
- 本次最多可申请金额；
- 不能申请的原因；
- 影响计算的关键来源行。

不得让一线用户手工计算或复制技术 ID。

### 4.4 角色视图收敛

不同角色看到不同入口：

- 老板/总经理：项目经营、金额风险、待审批、审计查询；
- 合同部：历史合同接管、合同工作台、模板、合作单位、归档；
- 预算部：合同金额、结算金额、付款条款和历史余额复核；
- 财务：付款审批、出纳实付、凭证、资金占用、财务记录；
- 项目经理：项目内合同、结算、付款和待办；
- 普通审批人：待办、单据摘要、附件、审批意见。

普通审批人不应看到模板中心、编号规则、系统配置、复杂后台。

## 5. 历史合同分级接管

20 个历史合同按业务活跃度分 A/B/C 三类，不同级别要求不同。

### 5.1 A 级：近期有结算或付款

适用：

- 本月或下月需要发起结算；
- 近期要付款；
- 已有预付款、进度款、质保金或扣回；
- 金额较大或风险较高。

必须录入：

- 合同基础信息；
- 合同类型；
- 合同金额；
- 签订日期；
- 相对方信息；
- 付款条款结构化；
- 历史累计结算；
- 历史累计已付；
- 已批待付；
- 总包代付；
- 预付款已付和已扣回情况；
- 质保金规则；
- 合同扫描件、补充协议、已有结算单、付款凭证；
- 余额确认记录。

接管后：

- 后续结算必须走系统；
- 后续付款必须走系统；
- 系统付款容量计算必须扣除历史余额；
- 合同详情和项目经营必须能解释可付款金额。

### 5.2 B 级：执行中但近期不付款

适用：

- 合同仍在执行；
- 短期无明确付款计划；
- 未来可能发生结算或付款。

必须录入：

- 合同基础信息；
- 合同类型；
- 合同金额；
- 相对方；
- 当前状态；
- 合同扫描件；
- 历史累计已付概况；
- 是否缺资料。

可后补：

- 完整付款条款；
- 历史结算明细；
- 付款凭证细项；
- 预付款扣回明细。

触发补细规则：

- 一旦该合同要发起结算或付款，必须升级为 A 级，补齐付款条款和历史余额。

### 5.3 C 级：已完结或低频合同

适用：

- 已完结；
- 金额小；
- 短期不会发生付款；
- 只需项目合同全貌和资料归档。

必须录入：

- 合同编号；
- 合同名称；
- 相对方；
- 合同金额；
- 当前状态；
- 合同扫描件或缺失说明。

不要求：

- 付款条款完整拆解；
- 历史付款逐笔凭证；
- 结算明细结构化。

## 6. 历史合同接管流程

### 6.1 流程图

```text
选择试运行项目
  -> 创建/选择历史合同
  -> 录入基础信息和合同类型
  -> 上传已签合同及附件
  -> 录入付款条款摘要或结构化条款
  -> 录入历史累计结算/已付/待付/总代付
  -> 系统计算初始剩余额度
  -> 合同部复核资料
  -> 预算/财务复核金额
  -> 接管确认
  -> 合同版本成为历史接管生效版本
  -> 后续结算/付款从系统继续
```

### 6.2 接管状态

历史合同需要独立接管状态：

- 未接管：仅有草稿或待录入；
- 录入中：基础信息或文件尚未完整；
- 待复核：提交给合同部、预算或财务复核；
- 已接管：可作为系统事实起点；
- 需补资料：缺关键文件或金额无法确认；
- 已作废：误录或不纳入试运行。

接管状态与合同履约状态不同。履约状态描述合同本身，接管状态描述系统是否接受该合同为业务事实。

### 6.3 履约状态

历史合同履约状态至少包括：

- 已签订未开工；
- 执行中；
- 暂停；
- 已完结；
- 已终止；
- 争议中。

试运行版可以先用固定枚举，不做复杂状态配置。

## 7. 历史余额初始化

### 7.1 余额类型

历史接管必须建立以下初始余额：

- 合同金额；
- 历史累计生效结算；
- 历史累计已审批待付；
- 历史累计实际付款；
- 历史总包代付；
- 历史预付款已付；
- 历史预付款已扣回；
- 历史质保金已扣留；
- 历史质保金已释放；
- 其他需说明的例外额度。

### 7.2 余额来源

每个余额应记录来源：

- 财务台账；
- 银行回单；
- 历史结算单；
- 付款审批单；
- 总包代付记录；
- 合同部确认；
- 预算部确认；
- 老板/总经理确认；
- 其他说明。

金额来源可以先以附件和备注证明，不要求所有历史凭证第一天逐笔结构化。

### 7.3 余额确认

接管确认前必须完成：

- 合同部确认合同和附件；
- 预算部确认结算口径；
- 财务确认已付和待付；
- 项目负责人确认项目归属和业务状态。

若岗位人员暂时不足，可由实际承担职责的人以对应项目岗位完成确认。不得以 super_admin 代替业务确认。

### 7.4 对付款容量的影响

接管后的后续付款容量计算必须扣减历史余额。系统不得因为历史记录不是由系统内流程产生，就把额度重新释放。

后续付款可申请金额至少满足：

```text
可申请金额
  = 根据合同付款条款和已生效结算计算的到期可付
    - 历史累计已付
    - 历史已批待付
    - 系统内审批中占用
    - 系统内已批待付
    - 历史及系统内总包代付
    - 应扣未扣预付款
    - 其他确认占用
```

如果历史余额缺失或未确认，系统应禁止该合同发起付款，并提示需要完成接管确认。

## 8. 新合同处理

新合同短期内较少，但必须保留现有合同工作台能力。

新合同仍走：

```text
合同工作台
  -> 合同审批
  -> 用章审批
  -> 已签合同归档确认
  -> 合同版本生效
  -> 结算
  -> 付款
```

不为新合同另建简化流程。简化只针对已经签完的历史合同。

## 9. 用户体验设计

### 9.1 首页

首页不得继续作为占位页。试运行版首页是工作入口。

必须展示：

- 待我审批；
- 待我归档确认；
- 已批待付款；
- 近期可付款；
- 金额风险；
- 缺资料合同；
- 最近被驳回事项。

首页指标只展示当前登录人可见项目范围内的数据。

### 9.2 合同列表

合同列表应支持试运行项目总览：

- 合同编号；
- 合同名称；
- 相对方；
- 合同类型；
- 合同金额；
- 接管状态；
- 履约状态；
- 累计结算；
- 累计已付；
- 剩余额度；
- 资料完整度；
- 下一步动作。

默认视图建议：

- 待接管；
- 需补资料；
- 近期要付款；
- 已接管；
- 全部合同。

### 9.3 历史合同接管页

新增或改造入口：

- 从合同列表点击“接管历史合同”；
- 不进入完整合同工作台；
- 采用分步表单或分区表单。

页面分区：

1. 基础信息；
2. 合同类型和项目归属；
3. 相对方；
4. 已签文件和补充协议；
5. 付款条款；
6. 历史结算和付款余额；
7. 缺资料说明；
8. 复核与接管确认。

要求：

- 对 A/B/C 级合同采用不同必填规则；
- 不强迫 C 级合同录完整付款条款；
- A 级合同缺付款条款或历史余额时禁止接管为可付款状态；
- 接管确认后关键金额不可静默修改，需走更正动作。

### 9.4 付款发起

付款发起界面不得要求用户手填 `contractVersionId`、`settlementId` 等技术 ID。

必须使用业务选择器：

- 先选项目；
- 再选合同；
- 系统展示合同接管/生效状态；
- 系统展示可申请金额；
- 系统展示可申请来源行；
- 用户填写本次申请金额；
- 超额或缺资料时给出原因。

付款发起默认按合同发起普通付款。单结算付款和合同预付款作为可选高级来源，但不作为普通员工默认路径。

### 9.5 项目经营

项目经营页是老板和财务的核心入口。

试运行版必须展示：

- 业主主合同金额；
- 业主累计审定；
- 业主累计收款；
- 总包代付；
- 下游合同总额；
- 下游累计结算；
- 下游累计已付；
- 已批待付；
- 项目垫资占用；
- 合同缺资料数量；
- 可付款风险。

页面重点是经营事实，不做装饰大屏。

## 10. 权限与安全

### 10.1 权限原则

历史合同接管不是技术管理员行为。接管必须由业务岗位完成。

建议权限：

- 合同部成员：录入历史合同、上传资料；
- 合同部主管：确认合同资料；
- 预算部主管/预算人员：确认历史结算和付款条款口径；
- 财务总监/财务人员：确认历史已付、待付、凭证；
- 项目经理：确认项目归属和履约状态；
- 董事长/总经理：查看项目经营和重大异常；
- super_admin：只做账号、配置和故障处理，不代表业务确认。

### 10.2 敏感动作

以下动作必须写审计：

- 创建历史合同；
- 修改历史合同关键金额；
- 上传或删除历史合同文件；
- 提交接管复核；
- 接管确认；
- 接管退回；
- 历史余额更正；
- 发起付款；
- 下载敏感文件；
- 权限变更。

以下动作建议二次确认：

- 接管确认；
- 历史余额更正；
- 发起超常规付款例外；
- 文件下载票据签发；
- 实际付款登记。

## 11. 数据与实现方向

本设计不要求立刻重构全部模型。后续实现应优先复用现有模型，最小新增必要字段和表。

### 11.1 可复用现有能力

已有能力可继续使用：

- `Contract` 和 `ContractVersion`；
- `PaymentTermsVersion` 和 `PaymentTermsStage`；
- `Settlement`；
- `PaymentRequest`；
- `PaymentExecution`；
- `PaymentExecutionAllocation`；
- 私有 `FileObject`；
- `ArchiveRecord`；
- `AuditLog`；
- 审批实例、转审、委托、退回、催办；
- 项目经营的业主收款、主合同、总包代付、垫资额度能力。

### 11.2 建议新增最小数据能力

为历史接管补充：

- 合同来源：系统新建、历史接管；
- 接管状态；
- 履约状态；
- 签订日期；
- 接管等级 A/B/C；
- 接管确认时间和确认人；
- 历史余额快照；
- 历史余额来源说明；
- 余额更正记录。

如果需要新表，优先新增一个聚合表记录历史接管余额，而不是把历史余额散落进多个业务表。

建议概念模型：

```text
ContractTakeover
  contractId
  contractVersionId
  projectId
  level
  takeoverStatus
  lifecycleStatus
  signedAt
```

### 11.3 历史结算是否需要逐笔建 Settlement

试运行版不要求把所有历史结算逐笔补成正式 `Settlement`。

规则：

- A 级合同：若近期付款计算需要追溯每期结算，补关键历史结算行；
- B/C 级合同：可先使用历史累计结算余额；
- 试运行后的新结算必须创建正式 `Settlement` 并走审批归档；
- 历史累计余额不得与系统内新结算重复计算。

### 11.4 历史付款是否需要逐笔建 PaymentExecution

试运行版不要求把所有历史付款逐笔补成正式 `PaymentExecution`。

规则：

- 有凭证且影响近期付款的历史实付，可补关键付款记录；
- 只用于余额扣减的历史已付，可进入历史余额快照；
- 试运行后的实际付款必须创建正式 `PaymentExecution` 并上传凭证；
- 历史余额和系统实付必须在读模型中清晰分列。

## 13. 实施分期

### Phase 0：试运行准备

目标：不用写大量新功能，先确认资料、人员和环境。

任务：

- 确定试运行项目；
- 整理 20 个合同清单；
- 标记 A/B/C 级；
- 确定 3-5 个完整跑链路的活跃合同；
- 初始化真实人员和项目岗位；
- 修改 seed 密码；
- 接入 COS、备份、日志告警；
- 合同母版验收。

验收：

- 真实用户可登录；
- 真实岗位授权正确；
- 生产文件私有；
- 试运行合同清单齐备。

### Phase 1：历史合同接管基础

目标：让 20 个合同进入系统并形成项目合同总账。

任务：

- 增加历史合同接管入口；
- 支持合同来源、接管状态、履约状态；
- 支持 A/B/C 级录入规则；
- 支持已签合同和附件上传；
- 支持历史余额快照；
- 支持接管确认和审计；
- 合同列表展示接管状态和缺资料状态。

验收：

- 20 个历史合同可建账；
- A 级合同可标记为已接管；
- B/C 级合同可作为台账存在；
- 缺资料合同可被清晰识别。

### Phase 2：历史余额进入付款容量

目标：系统付款不突破历史事实。

任务：

- 付款容量计算扣减历史累计已付、已批待付、总包代付、预付款扣回；
- 未接管或余额未确认合同禁止付款；
- 付款申请页展示历史余额影响；
- 合同详情展示历史余额和系统内新增金额分列；
- 项目经营页汇总历史和系统内金额。

验收：

- A 级合同能基于历史余额继续申请付款；
- 超额付款被拦截；
- 缺历史余额时无法发起付款；
- 老板能看项目合同总额、已结算、已付、待付和风险。

### Phase 3：真实首页和去技术化入口

目标：让员工从工作入口使用系统，而不是从技术页面找功能。

任务：

- 首页接真实待办；
- 合同、结算、付款入口使用业务选择器；
- 消除用户手填技术 ID；
- 按角色收敛导航；
- 普通审批详情突出摘要、附件、金额和风险。

验收：

- 普通审批人进入首页能处理待办；
- 付款发起无需复制 `contractVersionId`；
- 结算发起无需复制技术 ID；
- 不同角色看到的导航明显不同。

### Phase 3.5：真实常用单据补齐

目标：补齐试运行人员真实会用、缺了就容易回到纸质流程的单据，但不扩成完整 OA。

任务：

- 付款申请 PDF 严格还原公司项目付款审批表；
- 提供收方单、签工单、零星机械签认单、台班记录表模板下载；
- 结算附件先线下填写，再上传归档；
- 支持差旅、招待、报销的最小综合费用付款申请；
- 综合费用进入项目、类型、事由、金额、附件、审批、已批待付、实付、凭证和审计闭环。

验收：

- 财务和老板认可付款申请 PDF 可作为真实审批单据；
- 结算人员能下载常用附件模板并把签字盖章件上传到对应结算；
- 差旅、招待、报销可以作为项目综合费用发起、审批、实付和留痕；
- 系统不要求发票识别、行程明细、多人报销、预算科目树或在线填写复杂附件。

### Phase 4：试运行 UAT

目标：用真实业务验证系统是否值得扩大使用。

任务：

- 选 3-5 个活跃合同跑后续结算和付款；
- 记录每个流程卡点；
- 对比财务台账和系统金额；
- 检查文件下载、审计和权限；
- 固化试运行操作手册；
- 根据反馈修少量 P0 体验问题。

验收：

- 至少 1 条真实付款从系统发起、审批、实付、凭证归档；
- 至少 1 条真实结算从系统审批并归档生效；
- 财务认可付款金额口径；
- 合同部认可补录工作量；
- 老板认可项目经营视图能辅助决策。

## 14. 验收标准

### 14.1 功能验收

- 20 个历史合同可进入项目合同台账；
- 合同可按 A/B/C 级分类；
- A 级合同可完成接管确认；
- 历史合同不重走合同审批；
- 新合同仍走合同工作台完整流程；
- 历史余额可影响付款容量；
- 未接管合同不能发起付款；
- 缺资料合同能被识别；
- 首页展示真实待办；
- 付款发起不需要手填技术 ID；
- 项目经营展示历史与系统内金额合计。

### 14.2 安全验收

- 未登录写接口返回 401；
- 无岗位权限写接口返回 403；
- 文件不公开直链；
- 下载敏感文件写审计；
- 实付和接管确认有二次确认；
- 真实账号替代 seed 通用密码；
- 生产密钥不进入仓库。

### 14.3 运维验收

- 生产 PostgreSQL 不公网暴露；
- COS 私有桶可用；
- 每日备份可恢复；
- API 和 Nginx 日志有轮转；
- 错误告警可触达负责人；
- 证书续期状态可检查；
- 生产环境配置有留痕。

### 14.4 使用验收

- 合同部能在不明显增加负担的情况下完成历史合同补录；
- 财务能用系统金额解释付款余额；
- 项目经理能看懂本项目合同和付款状态；
- 老板能看到项目经营事实；
- 使用者不会因为找不到入口而回到纸质或微信。

## 15. 执行护栏

后续 Codex 执行本设计时必须遵守：

1. 优先让真实项目跑起来，不扩通用平台能力。
2. 先支持 20 个合同人工补录，不先做复杂批量导入。
3. 历史合同不重走审批，只做接管确认。
4. 历史余额必须进入付款容量，不能只展示不控制。
5. 技术 ID 不出现在普通用户操作路径中。
6. 合同类型必须显式化，不能继续依赖名称推断新数据路线。
7. 普通审批人界面只保留摘要、附件、金额、风险和审批意见。
8. 模板中心、编号规则、审计日志、系统配置只给少数角色。
9. 小程序、OCR、历史单价库、完整成本大屏全部后置。
10. 每个实现切片都要更新 `PROGRESS.md`，并验证相关测试。

## 16. 风险与应对

### 16.1 补录工作量过大

风险：20 个合同资料不齐，补录拖垮试运行。

应对：

- 使用 A/B/C 分级；
- C 级只建台账；
- A 级优先处理近期付款；
- 缺资料允许明确标记，不要求第一天补全。

### 16.2 历史余额不准确

风险：系统可付款金额与财务台账不一致。

应对：

- 接管确认前禁止付款；
- 历史余额记录来源和确认人；
- 金额更正必须审计；
- UAT 期间对 A 级合同逐个与财务核对。

### 16.3 用户觉得复杂

风险：员工回到纸质和微信。

应对：

- 首页做待办入口；
- 按角色收敛导航；
- 去掉技术 ID；
- 新增历史接管入口，不让历史合同进入完整新合同工作台；
- 只要求近期业务完整补细。

### 16.4 试运行变成继续开发无限延期

风险：不断加模块，无法上线。

应对：

- 坚持单项目试运行；
- 非主链能力全部后置；
- 每个新增需求必须回答是否影响合同、结算、付款、归档、审计事实链；
- 不影响主链的需求不得进入 P0。
