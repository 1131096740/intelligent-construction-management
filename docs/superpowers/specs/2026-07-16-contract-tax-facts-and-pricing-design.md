# 建工智管合同税务事实与含税计价设计

- 日期：2026-07-16
- 状态：业务方案已确认，待书面规格复核
- 适用范围：新建合同、合同变更、历史合同接管、合同清单、结算编制与审批
- 不适用范围：发票开具、发票号码、查验认证、抵扣、红冲和完整税务台账

## 1. 文档目的

本设计把发票类型、税率和含税价格从页面字段提升为可冻结、可追溯、可审计的合同业务事实，解决以下问题：

- 新建合同虽然已有发票类型、税率和含税单价字段，但主要依赖模板配置，尚未形成跨模板一致的后端硬规则。
- 历史合同接管目前没有规范的发票类型、税率和含税单价事实，不能区分“原合同未明确”和“已确认”。
- 历史合同资料不完整时，既不能强迫合同员猜测，也不能让未知税务事实直接进入正式结算审批。
- 合同清单的数量、含税单价、含税金额、税额和不含税金额需要使用统一精度与舍入口径。
- 已生效合同的税务与价格事实不能被后续编辑追溯改写。

本设计不建设完整发票管理平台，只治理合同约定、合同价格和结算引用所必需的税务事实。

## 2. 已确认的核心原则

1. 每个合同版本只能选择一种发票类型：
   - 增值税普通发票；
   - 增值税专用发票。
2. 新建合同在提交内部审批前必须明确发票类型和数字税率。
3. 历史合同税务资料缺失不阻断接管，但不能被系统默认为已确认。
4. 历史合同发票类型或税率未确认时，可以创建、编辑和保存结算草稿，但不得发起新的结算审批。
5. 有计价清单的合同必须按真实项目填写含税单价；纯固定总价且原合同没有单价清单时，不虚构单价。
6. 数量和含税单价均最多保留 2 位小数，超出精度直接报错，不自动截断或舍入。
7. 行金额由后端计算，合同员不能直接修改计算结果。
8. 有总价清单的合同总价严格等于真实清单行合计，不设置调差、抹零、负数抵扣或虚构项目。
9. 无总价框架合同可以不填写预计数量；预计金额只用于参考，不形成合同金额或结算上限。
10. 已确认或已生效的税务与价格事实按合同版本冻结。

## 3. 当前仓库事实与差距

### 3.1 已有能力

当前合同工作台已经具备以下基础：

- 核心合同模板配置了 `invoiceType` 和 `taxRatePercent` 必填字段。
- 发票类型选项已经包含“增值税普通发票”和“增值税专用发票”。
- 合同清单行已经保存 `unitPrice` 和 `taxRate`。
- 合同清单、Excel 导入和合同文件生成已经能够展示税率、含税单价和含税金额。
- 合同提交前已有完整性检查服务，可拦截模板必填字段和清单必填列。
- 结算行已经具备合同单价和税率快照，可继续承担历史版本追溯。

### 3.2 现有差距

当前实现仍存在以下差距：

- 新合同的票种和税率约束主要来自模板字段，不是所有合同类型共享的后端领域不变量。
- 当前税率选项包含 `0%`，与本次确认的“只接受大于 0 的数字税率”不一致。
- 当前清单数量支持 3 位小数，含税单价的底层存储也允许超过 2 位，与本次确认的统一精度不一致。
- 清单编辑器的通用列名仍显示“单价”，没有在所有入口明确为“含税单价”。
- 历史合同接管模型、接口、表单、导入预检和读模型均未保存规范的发票类型、税率或含税单价事实。
- 历史接管不能表达“原合同未明确、待财务复核、待合同部确认、已确认”等状态。
- 目前缺少历史合同税务事实补录、双岗位复核和更正账本。
- 结算提交尚未统一检查合同版本的票种、税率和所选项目含税单价是否已经确认。

## 4. 合同税务事实模型

### 4.1 版本级事实

每个合同版本保存一组规范税务事实：

| 字段 | 规则 |
| --- | --- |
| 发票类型 | 只能为增值税普通发票或增值税专用发票 |
| 计税模式 | 单一税率或特殊多税率 |
| 默认税率 | 大于 0 且不超过 100 的数字百分比 |
| 事实状态 | 未明确、待财务复核、待合同部确认、已确认 |
| 事实来源 | 合同文件明确、依据补充资料确认、经业务与财务复核确认 |
| 确认说明 | 无依据附件时必填；有附件时可用于补充说明 |
| 依据附件 | 可选，不因缺少附件阻断补录与确认 |
| 补录信息 | 补录人和补录时间 |
| 财务复核信息 | 财务主管、复核时间和复核意见 |
| 合同确认信息 | 合同部主管、确认时间和确认意见 |

这些字段必须是后端可查询、可约束的规范事实，不能只存在于合同正文、模板 JSON 或前端表单中。

### 4.2 单一税率

普通合同使用单一税率：

- 合同版本保存默认税率。
- 所有清单行继承该税率。
- 页面不要求合同员重复填写每一行税率。
- 合同变更前，清单行不得自行覆盖合同税率。

### 4.3 特殊多税率

确有多税率的合同可以启用特殊多税率模式：

- 合同版本仍保存一个默认税率。
- 只有例外清单行可以明确覆盖默认税率。
- 每个计价行最终都必须能确定唯一数字税率。
- 同一合同版本的所有清单行仍使用同一种发票类型。
- 不能通过多税率模式混用增值税普通发票和增值税专用发票。

### 4.4 税率录入

- 常用快捷选项为 1%、3%、6%、9%、13%。
- 提供“其他税率”录入能力，避免政策或特殊业务变化时必须修改代码。
- 其他税率使用规范数字百分比，最多保留 3 位小数。
- 当前业务不支持“免税”“不征税”或“零税率”等非数字税务状态。
- 已生效合同版本保留其原始税率，不因以后调整快捷选项而变化。

## 5. 新建合同规则

### 5.1 提交审批硬门槛

所有新建合同在提交内部审批前必须满足：

- 已选择发票类型。
- 已填写有效数字税率。
- 单一税率合同的清单行能够继承合同税率。
- 特殊多税率合同的每个例外行已经明确税率。
- 需要计价清单的合同已经填写真实清单项目。
- 所有计价行已经填写含税单价。
- 清单数量、含税单价和系统计算金额符合精度与一致性规则。
- 合同正文、结构化税务事实和清单内容不存在未解决差异。

前端必填只能改善录入体验，最终提交必须由后端重新检查并拒绝不完整合同。

### 5.2 纯固定总价合同

纯固定总价且原合同没有单价清单时：

- 必须填写发票类型。
- 必须填写税率。
- 必须填写含税合同总价。
- 不强制填写数量和含税单价。
- 不允许为了通过校验而虚构“数量 1、含税单价等于合同总价”的清单。
- 系统根据含税合同总价和税率计算合同级不含税金额与税额。

### 5.3 有清单合同

有计价清单的合同：

- 每行必须有真实业务名称。
- 普通有总价清单的数量必须填写且大于 0。
- 每行含税单价必须填写且大于或等于 0；是否允许零价真实项目由具体模板另行限制，零价项目不得承担隐藏调差。
- 行含税金额、行不含税金额和税额均由后端计算。
- 合同含税总价严格等于所有计入合同价的真实清单行含税金额之和。
- 不能手工覆盖合同总价绕开清单合计。

### 5.4 禁止的清单做法

有清单合同禁止：

- 手工修改系统计算的行金额。
- 添加“调差”“抹零”“优惠”“抵扣”等无真实计价事实的金额行。
- 使用负数量、负单价或负金额冲抵合同总价。
- 用虚构数量或虚构项目使清单合计对齐目标金额。
- 先填写手工总价，再让系统忽略清单合计差异。

如果双方协商价格发生变化，应调整真实项目的合同含税单价；已经冻结或生效后发生变化的，必须走合同变更或补充协议。

## 6. 数量、价格和金额计算

### 6.1 输入精度

- 数量最多保留 2 位小数。
- 含税单价最多保留 2 位小数。
- 超过 2 位时直接提示修改。
- 系统不能静默截断，也不能在保存时自动四舍五入用户输入。
- 输入和导入必须执行相同规则，不能允许 Excel 绕过网页校验。

### 6.2 逐行计算

后端按以下顺序计算：

```text
不含税单价展示值 = 含税单价 ÷（1 + 税率）
不含税单价展示值按四舍五入保留 2 位小数

行含税金额 = 数量 × 含税单价
行含税金额按四舍五入保留到分

行不含税金额 = 行含税金额 ÷（1 + 税率）
行不含税金额按四舍五入保留到分

行税额 = 行含税金额 - 行不含税金额
```

金额舍入采用十进制定点计算和四舍五入，不得使用 JavaScript 浮点数直接计算合同金额。

含税单价是合同录入和冻结的价格事实；不含税单价是供合同、结算和财务查看的只读派生值。为避免单价舍入造成二次误差，行不含税金额必须从已舍入的行含税金额反算，不能使用“数量 × 已舍入的不含税单价展示值”重新计算。

### 6.3 汇总

- 合同含税总价汇总每行已经舍入到分的含税金额。
- 合同不含税总价汇总每行已经舍入到分的不含税金额。
- 合同税额汇总每行税额。
- 必须保证：含税总价＝不含税总价＋税额。
- 不能先汇总未舍入的高精度金额再做一次统一舍入。

### 6.4 后端唯一事实

- 前端可以即时预览计算结果，但不能成为最终事实来源。
- Excel 公式只用于用户预览，导入后必须由后端根据原始数量、含税单价和税率重算。
- DOCX、PDF、Excel、合同详情、结算和付款必须引用同一后端计算结果。
- 需要展示价格明细的合同与结算文件，应同时展示含税单价、不含税单价、税率、含税金额、不含税金额和税额。

## 7. 无总价框架合同

无总价框架合同只约定含税单价，并按实际发生量结算：

- 发票类型必填。
- 税率必填。
- 清单项目和含税单价必填。
- 预计数量可以为空。
- 预计数量填写后最多保留 2 位小数。
- 预计金额仅标记为参考，不形成合同总价、结算上限或付款上限。
- 预计数量为空时，页面显示“按实际发生量结算”，不能用 `0` 冒充数量。
- 结算使用本期实际核定数量乘以合同版本冻结的含税单价。
- 同一范围内实际数量可以超过预计数量。
- 新项目、新范围或含税单价变化必须走合同变更或补充协议。

框架合同不能因为清单存在预计金额，就被错误纳入普通总价合同的 10% 增项上限判断。

## 8. 历史合同接管

### 8.1 接管不因税务缺口硬阻断

历史合同原件没有明确发票类型、税率或部分含税单价时：

- 允许创建接管草稿。
- 允许提交接管复核并完成接管确认。
- 缺失字段必须显示“原合同未明确”或“含税单价待确认”。
- 不允许系统默认选择票种、默认使用 `0%` 或根据经验猜测税率。
- 不允许使用合同总价反推不存在的含税单价。
- 接管确认时必须明确展示税务事实缺口和后续影响。

### 8.2 后续业务限制

历史合同接管后：

- 可以查看合同和历史账本。
- 可以补录税务资料。
- 可以创建、编辑和保存结算草稿。
- 发票类型或税率未确认时，不得发起新的结算审批。
- 某个历史清单项目缺少含税单价时，只阻断包含该项目的结算审批。
- 价格完整的其他项目仍可正常进入结算，不因单个缺价项目冻结整份合同。
- 纯固定总价且原合同无单价清单时，不适用项目含税单价阻断。

阻断反馈必须说明：

1. 缺少什么；
2. 是否影响当前草稿；
3. 为什么不能提交审批；
4. 去哪里补录和确认。

### 8.3 历史税务事实补录流程

```text
合同员补录
  -> 财务主管复核
  -> 合同部主管确认
  -> 税务事实变为已确认
  -> 解除对应结算审批阻断
```

职责边界：

- 合同员负责录入发票类型、税率和适用的含税单价。
- 财务主管复核发票类型、税率及税额口径。
- 合同部主管确认这些事实确实适用于当前合同及合同版本。
- 合同员不能通过自行保存解除审批阻断。
- 本流程不是重新发起整套合同审批。

### 8.4 依据附件与确认说明

依据附件可选：

- 有原合同或合同清单时，事实来源标记为“合同文件明确”。
- 有补充文件、发票或双方确认资料时，事实来源标记为“依据补充资料确认”。
- 没有附件时，必须填写简短确认说明，事实来源标记为“经业务与财务复核确认”。

无附件不会阻断补录、复核或确认，但系统必须保留说明、操作人和时间，不能将人工确认伪装成原合同明文约定。

### 8.5 批量导入

历史合同批量导入应支持：

- 发票类型；
- 税率；
- 税务事实来源；
- 确认说明；
- 清单项目含税单价；
- 缺失状态。

导入预检必须区分：

- 格式错误：阻断该行生成接管草稿；
- 税务事实缺失：允许生成接管草稿，但给出明确风险提醒；
- 超精度数量或含税单价：阻断该清单行导入；
- 不受支持的发票类型或 `0%` 税率：阻断并要求修正。

## 9. 结算引用规则

### 9.1 创建与保存

- 结算只能引用指定合同版本。
- 创建结算草稿时读取该版本的发票类型、税率、含税单价和事实状态。
- 税务事实缺失不阻断创建或保存草稿。
- 页面不得把缺失值显示成 `0` 或一个看似有效的禁用数字。

### 9.2 提交审批

提交结算审批前，后端必须重新检查：

- 合同版本已经有效或符合既有历史接管使用条件。
- 发票类型已确认。
- 所有实际结算行的税率已确认。
- 所有实际结算行的合同含税单价已确认。
- 数量和金额计算符合本设计的精度与舍入口径。
- 结算行保留合同版本、清单行、含税单价和税率快照。

任何一项缺失均只阻断提交，不删除或清空用户已填写的结算草稿。

### 9.3 历史稳定性

- 已提交或已生效结算继续引用提交时冻结的合同版本和价格税率快照。
- 后续税务事实更正或合同变更不能追溯改写历史结算。
- 付款和实付继续沿用结算所引用的合同版本及税务快照。

## 10. 锁定、更正与合同变更

### 10.1 锁定时点

- 新合同在进入内部审批后冻结本次审批使用的税务与价格事实。
- 历史合同税务补录在合同部主管确认后锁定。
- 合同版本生效后，普通编辑入口不得直接修改税务事实或清单价格。

### 10.2 录入错误

确认后的录入错误使用“税务事实更正”：

- 必须填写更正原因。
- 保存更正前后的完整值。
- 重新经过财务主管复核和合同部主管确认。
- 保留更正人、复核人、确认人和时间。
- 不覆盖已经引用旧事实的历史结算、付款和归档文件。

### 10.3 双方约定变化

发票类型、税率或含税单价的合同约定发生变化时：

- 必须走合同变更或补充协议。
- 形成新的合同版本。
- 新版本按其生效时间影响后续结算。
- 旧版本继续服务历史追溯。
- 不能用“税务事实更正”绕过合同变更审批。

## 11. 权限与审计

### 11.1 权限

- 合同员：录入新合同税务事实、补录历史税务事实。
- 财务主管：复核历史补录的发票类型、税率和税额口径。
- 合同部主管：确认补录事实属于对应合同版本，确认更正结果。
- 其他人员：按既有权限只读查看，不得解除税务事实阻断。
- 技术管理员不得以管理权限代替业务复核或合同确认。

不扩大现有项目、合同、结算和文件权限，只在既有角色权限中增加对应业务动作。

### 11.2 审计

以下动作必须写入审计日志：

- 新合同税务事实首次保存和提交冻结；
- 历史税务事实补录；
- 财务主管复核；
- 合同部主管确认；
- 复核退回；
- 税务事实更正；
- 因税务事实缺失阻断结算提交；
- 合同变更新版本生效。

审计至少保存合同、合同版本、修改前后值、事实来源、说明、附件引用、操作者、岗位、时间和结果。

## 12. 用户体验与反馈

- 字段统一使用“含税单价”，不再显示含义不明的“单价”。
- 发票类型使用固定中文选项，不允许自由输入近义词。
- 税率显示百分号，存储和计算使用规范数值。
- “原合同未明确”必须以文字表达，颜色不能作为唯一提示。
- 历史接管使用提醒而不是大面积危险色块。
- 结算提交阻断必须保留已录入内容，并提供直达补录入口。
- 缺价项目在清单和结算行中精准标记，不把整份历史合同显示为不可用。
- 框架合同预计金额明确标注“仅供参考，不作为合同上限”。
- 所有计算字段只读，并说明计算关系。

## 13. 兼容与迁移原则

- 不追溯猜测现有合同的票种、税率或单价。
- 已有新合同数据优先从当前结构化字段和清单行迁移；无法证明的值进入“未明确”状态。
- 已接管历史合同默认不因新增字段失效，但在发起新结算审批时执行新门槛。
- 已提交、已生效或已归档的合同、结算和付款保持原版本引用，不做批量覆盖。
- 数据迁移必须可回滚，并在临时恢复库或隔离数据库中验证。
- 实施前必须统计生产中合同版本、历史接管、清单行和未完成结算的实际分布。

## 14. 验收标准

### 14.1 新合同

- 任一合同模板缺少发票类型或税率时，后端仍能阻断提交。
- 发票类型只能二选一。
- `0%` 和负税率不能提交。
- 有清单合同缺含税单价时不能提交。
- 纯固定总价无清单合同可以只凭含税总价提交。
- 数量或含税单价超过 2 位小数时，网页和 Excel 导入均拒绝。
- 行金额由后端重算，篡改前端合计无效。

### 14.2 历史接管

- 缺票种、税率或单价时仍可完成接管。
- 缺失值显示为未知事实，不显示为 `0`。
- 缺票种或税率时可以保存结算草稿，但不能提交审批。
- 某项目缺单价时只阻断包含该项目的结算。
- 无附件补录可以完成，但必须填写确认说明。
- 只有财务主管复核和合同部主管确认后才能解除阻断。

### 14.3 计算

- `1.23 × 4.56` 的行含税金额为 `5.61` 元。
- 合同总价汇总逐行舍入后的金额。
- 含税金额、不含税金额和税额始终对平。
- Web、API、DOCX、PDF、Excel 和结算快照显示一致。
- 不存在调差行、负数抵扣或手工覆盖计算金额的入口。

### 14.4 版本和审计

- 生效合同不能通过普通编辑修改票种、税率或含税单价。
- 录入错误更正保留前后值并重新复核确认。
- 双方约定变化必须产生新合同版本。
- 历史结算和付款不会因新版本或更正而漂移。
- 所有敏感动作均有完整审计记录。

## 15. 明确不做

本设计不包含：

- 发票申请和开票审批；
- 发票号码、代码、查验和验真；
- 进项认证和抵扣；
- 红字发票和红冲管理；
- 电子发票归集；
- 税务申报；
- 自动判断税收政策；
- OCR 自动识别合同或发票税务信息；
- 通用财税平台。

如果真实使用以后需要上述能力，应作为独立项目评估，不在本次合同税务事实治理中顺带建设。

## 16. 后续实施边界

本规格获书面复核后，下一步只编写实施计划，不立即修改代码。实施计划必须：

- 先统计生产数据与现有迁移影响。
- 将数据库规范事实、API 校验、历史接管、合同工作台和结算门槛拆成可回滚阶段。
- 先补后端领域不变量和测试，再调整页面。
- 不改变现有合同、结算、付款金额的历史事实来源。
- 不修改审批路线、角色范围、路由地址或文件上传 API。
- 未经单独授权，不推送 `main`、不部署生产、不执行生产迁移。
