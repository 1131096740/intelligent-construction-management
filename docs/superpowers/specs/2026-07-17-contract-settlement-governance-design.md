# 建工智管合同、结算与我方主体统一治理设计

- 日期：2026-07-17
- 状态：业务设计已逐章确认，用户已于 2026-07-17 批准书面规格
- 适用范围：新合同审批、签署用印归档、授权委托书、合同变更与金额上限、结算审批与签名、税务计价事实、我方公司主体
- 当前实现状态：目标设计，不代表当前生产或当前分支已经完整实现
- 后续顺序：按已批准实施计划分批实施 → 隔离库迁移演练与 UAT → 形成发布候选 → 用户单独批准目标 SHA 后方可发布

## 1. 文档目的

本设计把此前分散确认的合同、结算、税务、文件、审批和我方主体规则收口为一个统一业务事实模型，作为后续实施计划、代码修改、测试和 UAT 的共同依据。

本次设计解决的核心问题包括：

- 当前新合同审批路线过于简单，未按合同类型分流；
- 合同审批前、用印后和归档后的正式文件事实尚未严格分层；
- 授权委托书仍停留在通用附件层，未形成合同版本级门禁；
- 当前仍保留“重大/增强变更”，且超过 10% 只是升级审批而非强制新签；
- 当前结算先审批、后上传签章件，与真实业务顺序相反；
- 结算签名尚未形成每页底部的乙方及我方签名链；
- 税务、价格和金额需要在合同、结算、付款及文件中使用同一后端事实；
- 我方公司主体仍是简单字典和自由文本，缺少精确权限、版本历史及提交冻结。

## 2. 规格权威性与兼容关系

本规格是上述七个业务范围的新目标规则。现有代码、`AGENTS.md`、旧规格或进度记录中与本规格冲突的目标设计，应在对应实施切片中同步修正。

需要特别说明：

- 已生效、已归档或已作废的历史业务事实不因本规格被重写；
- 当前生产仍按已部署代码运行，本规格获批不等于功能已经上线；
- `docs/superpowers/specs/2026-07-16-contract-tax-facts-and-pricing-design.md` 中不冲突的税务计价规则继续有效，并由本规格吸收；
- 历史合同接管继续遵循“建立事实起点，不追溯补办历史审批”的原则；
- 实施不得改变既有付款实付、入账、元分转换和后端金额事实来源。

## 3. 已确认的总体原则

1. 主数据可以修改，但已提交业务必须冻结提交时事实。
2. 合同变更形成新版本，不直接覆盖原合同版本。
3. 正式文件只能新增版本，不覆盖原始文件。
4. 审批实例提交时冻结路线、岗位和具体人员。
5. 审批发生时冻结实际审批人、岗位、时间及当时签名摘要。
6. PDF、DOCX、Excel 和页面是后端事实的展示，不是金额事实来源。
7. 公司主体、项目岗位或个人签名后续变化，不得改变历史合同、结算和审批文件。
8. 结构化金额门禁必须在后端事务中执行，前端预检不能替代后端判断。
9. 颜色、提示或人工声明不能替代后端权限、状态和文件版本约束。
10. 所有敏感文件下载、审批、同意用章、归档及退回必须写审计日志。

## 4. 统一事实模型

### 4.1 主数据层

保存当前可维护资料及不可覆盖的历史版本：

- 我方公司主体；
- 项目岗位及当前有效任职；
- 用户签名文件；
- 合同模板、结算模板及业务场景。

### 4.2 合同版本层

每个新合同或合同变更形成独立合同版本，并冻结：

- 我方主体快照；
- 相对方事实；
- 合同类型；
- 含税金额、含税单价、税率、发票类型；
- 付款阶段和付款条款；
- 清单、期限、范围等合同事实；
- 双方授权委托书选择及关联；
- 本次审批使用的正式合同文件。

### 4.3 文件证据层

分别保存且永不覆盖：

- 乙方签章的内部审批版本；
- 我方授权委托书；
- 乙方授权委托书；
- 《合同审批单》；
- 双方最终签署版本；
- 结算乙方签章原始扫描件；
- 结算最终审批签名合成件；
- 其他辅助依据附件。

正式文件至少记录：

- 文件 ID；
- SHA-256；
- 页数；
- 文件用途；
- 对应业务版本；
- 上传人和上传时间；
- 当前是否有效；
- 被哪一份新文件替代或因何失效。

### 4.4 审批事实层

审批实例提交时冻结：

- 节点顺序；
- 节点岗位；
- 具体候选人员或选定人员；
- 项目或公司级岗位作用域；
- 或签、会签及转交/委托规则。

每次审批冻结：

- 实际审批人；
- 所代表岗位；
- 审批意见；
- 审批时间；
- 当时签名文件 ID 及摘要；
- 委托或转交关系。

### 4.5 业务账本层

合同、结算、付款及项目经营金额判断全部使用后端结构化事实。任何客户端计算、Excel 公式或 PDF 文本均不得反向覆盖账本金额。

## 5. 新合同审批

### 5.1 发起人

- 合同部成员可以创建并发起新合同；
- 合同部主管可以创建并发起新合同；
- 合同部主管本人发起时跳过合同部主管节点，避免自己审批自己；
- 申请人不得利用兼任岗位审批自己发起的合同；
- 如申请人兼任后续岗位，应由该岗位的其他有效人员审批，或使用现有受审计的转交、委托机制。

### 5.2 分类审批路线

| 合同类型 | 审批路线 |
| --- | --- |
| 材料采购 | 合同部主管 → 物资主管 → 项目经理 → 财务主管 → 董事长/总经理或签 |
| 机械租赁 | 合同部主管 → 物资主管 → 项目经理 → 财务主管 → 董事长/总经理或签 |
| 劳务分包 | 合同部主管 → 所属项目总工 → 项目经理 → 财务主管 → 董事长/总经理或签 |
| 专业分包 | 合同部主管 → 所属项目总工 → 项目经理 → 财务主管 → 董事长/总经理或签 |
| 通用合同 | 合同部主管 → 综合部主管 → 项目经理 → 财务主管 → 董事长/总经理或签 |

合同部主管本人发起时，上表中的首个合同部主管节点自动跳过，其他节点保持不变。

### 5.3 人员冻结

- 项目经理和项目总工根据合同所属项目确定；
- 公司部门主管节点使用公司级全局岗位；
- 项目总工缺失或同一项目存在冲突配置时阻止提交；
- 公司级审批岗位缺失时阻止提交；
- 提交后冻结审批路线及具体人员，不因后续调岗自动变化；
- 董事长、总经理为或签节点，任一人通过即完成最终节点。

## 6. 审批前合同文件

### 6.1 正式审批版本

发起内部审批前必须上传一份完整合并 PDF，顺序为：

```text
合同正文
→ 全部附件和清单
→ 所需授权委托书
→ 最终签署页
```

正式审批版本必须满足：

- 乙方已在合同签署页完成签字和盖章；
- 整份合同已按要求加盖骑缝章，不要求在正文每一页重复签字盖章；
- 不是零散图片、单独签署页或多份未合并文件；
- 系统结构化事实与 PDF 内容一致；
- 保存文件页数、SHA-256 和对应合同版本。

其他零散资料可以作为辅助附件上传，但不能替代正式审批版本。

### 6.2 不采用 OCR 作硬判断

系统不通过 OCR 自动判断签名或印章真伪。合同员作完整性声明，审批人审阅冻结 PDF，后端负责文件、版本、状态和审计约束。

## 7. 授权委托书

### 7.1 双方独立选择

每份合同分别选择：

- 我方是否需要授权委托书；
- 乙方是否需要授权委托书。

选择“需要”后，必须在发起内部审批前上传。

### 7.2 合同版本级管理

授权委托书：

- 按合同版本保存；
- 不能只挂在往来单位通用档案；
- 作为合同组成页放在最终签署页之前；
- 保存授权方、被授权人、授权范围摘要、文件及对应合同版本；
- 不强制维护独立过期日期。

### 7.3 合同变更中的复用

原授权书明确覆盖“签署、履行、变更及补充协议”等范围，且代理人未变化时，可以在同一合同后续变更中关联复用。

以下情况必须重新上传：

- 代理人变化；
- 授权范围不足；
- 原文件不可用；
- 本次业务明确要求新的授权书。

复用只建立关联，不复制或覆盖原文件。

## 8. 合同签署、用印与归档

### 8.1 状态链

```text
合同草稿
→ 提交前完整性校验
→ 内部审批中
→ 待同意用章
→ 待完成我方签署与盖章
→ 待合同部主管确认归档
→ 合同版本生效
```

### 8.2 同意用章

- 内部审批完成后自动创建用章任务；
- 综合部主管执行的系统动作名称为“同意用章”；
- “同意用章”只代表允许经办人线下使用对应公司公章；
- 系统不能把该动作描述成已经完成盖章；
- 公章仍由综合部主管线下保管，经办人按现实流程办理。

### 8.3 双版本留存

永久保留：

1. 乙方已经签章、用于内部审批的完整 PDF；
2. 经我方签字盖章后的双方最终签署 PDF。

最终签署版相对审批版只允许增加：

- 我方签字或签章；
- 我方公司公章；
- 骑缝章；
- 签署日期。

如公司主体、金额、税率、清单、付款条款、授权书、业务范围或正文发生实质变化，禁止确认归档，必须重新生成文件并重新走内部审批。

### 8.4 正式内容变化与文件失效

合同被退回或撤回后：

- 正式 PDF 内容发生任何变化，原乙方签章 PDF 自动失效；
- 必须重新生成并让乙方重新签章后再提交；
- 只有正式 PDF 完全未变，仅补充说明或重新提交时，才允许复用原签章版本。

### 8.5 归档确认与职责分离

- 经办人上传双方最终签署版本；
- 合同部主管确认归档后合同版本生效；
- 上传人与归档确认人不能是同一个人；
- 合同部主管本人作为经办人时，可以上传，但必须由另一名公司级合同部主管确认；
- 如果只有一名合同部主管，应由合同部成员上传、合同部主管确认。

资料缺页、错页或上传错误可以退回补正；涉及正式内容变化时必须重新审批，不能使用资料补正绕过审批。

## 9. 《合同审批单》

内部审批完成后，系统自动生成独立《合同审批单》，冻结：

- 合同版本和主要业务事实；
- 审批路线；
- 每个审批岗位；
- 实际审批人；
- 委托或转交关系；
- 审批意见和时间；
- 审批发生时的签名文件及摘要。

《合同审批单》：

- 是内部审批记录；
- 不插入对外合同正文；
- 不使用所有内部审批人的签名替代合同对外签署；
- 与具体合同版本永久关联；
- 后续人员更换签名不会改变历史文件；
- 支持受控下载。

允许查看和下载的人员：

- 合同经办人；
- 合同部成员、合同部主管；
- 该合同实际审批人；
- 所属项目经理；
- 财务人员、财务主管；
- 综合部主管；
- 董事长、总经理。

下载必须经后端鉴权、填写下载用途并写入审计日志。

## 10. 合同变更与金额上限

### 10.1 取消重大变更

新产生的合同变更不再区分普通、重大或增强变更，统一称为“合同变更”。

统一审批路线：

```text
合同部成员或合同部主管发起
→ 合同部主管
→ 项目经理
→ 财务主管
→ 董事长/总经理或签
```

合同部主管本人发起时跳过合同部主管节点。

历史已经完成的重大或增强变更不重写名称、路线和审批历史，只按原事实只读展示。

### 10.2 新版本原则

合同变更基于当前生效合同版本创建下一版本，可以调整：

- 合同金额；
- 清单范围、数量和单价；
- 税率及发票类型；
- 付款条款；
- 履约范围、期限和其他合同条款；
- 授权委托书关联。

不能通过合同变更替换我方签约公司主体。需要从甲公司改为乙公司签约时，必须新签合同。

新版本生效后旧版本标记为被替代，历史结算和付款继续引用原合同版本。

### 10.3 累计增项 10% 硬限制

```text
累计增项比例 = 历次增项金额合计 ÷ 原始合同含税金额
```

规则：

- 累计增项小于或等于 10% 时允许合同变更；
- 严格超过 10% 时禁止提交变更，要求新签合同；
- 减项不抵消历史增项，也不释放增项额度；
- 减项本身不受 10% 限制，但仍走完整合同变更审批；
- 累计增项只统计已经完成归档并曾经生效的正向变更金额；
- 当前仍为生效状态或已经被后续版本替代的历史生效变更均计入累计增项；
- 草稿、审批中、已退回、已驳回、已撤回、待用章、待归档和已作废版本不计入历史累计增项；
- 草稿可以保存，超过限制时显示“必须新签合同”并阻止提交；
- 提交当前变更时，后端在同一事务和合同锁内以“历史已生效累计增项 + 本次拟增项”重新判断。

### 10.4 有总价合同的结算上限

- 累计结算超过当前有效合同含税金额时禁止提交结算；
- 尚未发生金额变更且仍在 10% 可变更范围内，提示先完成合同变更；
- 已经完成金额增加后，累计结算仍超过变更后金额，提示必须新签合同；
- 尚在审批、用印或归档中的合同变更不能作为结算额度；
- 项目结算例外额度不能突破合同金额上限；
- 执行顺序必须为“先合同金额上限，再项目经营或上游额度”。

合同金额上限的占用口径：

- 结算草稿不占用合同额度；
- 结算成功提交审批后立即占用额度；
- 审批中、审批通过待生成文件、待确认归档、生效、部分付款和已付款结算持续占用额度；
- 已退回申请人、已驳回、已撤回和已作废结算释放额度；
- 提交时必须锁定合同及相关结算占用记录，在同一事务中计算“当前有效占用 + 本次结算”；
- 不能仅依赖提交前页面预览或非锁定查询判断剩余额度；
- 退回、驳回、撤回和作废释放占用时必须写入审计。

预算部岗位继续保留，仍可用于其他明确授权或未来可选复核，但不作为本规格中合同、合同变更或结算的强制审批节点。

### 10.5 无总价框架合同

只约定单价、按实际发生量结算的框架合同：

- 不设置合同总金额上限；
- 实际数量可以超过预计数量；
- 仍必须使用冻结的含税单价、税率和清单范围；
- 新增项目、改变单价、改变税率或扩大范围必须先完成合同变更；
- 不得为通过校验补填虚假合同总金额。

## 11. 结算适用范围与审批路线

### 11.1 需要结算的合同

- 材料采购；
- 机械租赁；
- 劳务分包；
- 专业分包。

通用合同不创建过程结算或最终结算，直接根据生效合同版本及付款条款申请付款。

### 11.2 过程结算和最终结算

两者审批路线完全相同。最终结算只增加完结性校验，不增加审批岗位。

最终结算提交前额外检查：

- 合同范围内应结事项已经完成；
- 历史过程结算已经完整纳入累计数据；
- 不存在尚未处理的结算草稿或审批中结算；
- 本次累计结算符合当前有效合同金额上限；
- 合同员已经明确选择“最终结算”并确认后续不再发起普通过程结算。

### 11.3 材料、机械结算

```text
合同员编制发起
→ 所属项目中选定的物资员
→ 物资主管
→ 合同部主管
→ 项目经理
→ 财务主管
```

合同员根据物资员在线下提供的核量、核价依据编制结算并录入本期核定价。依据附件不是提交结算审批的强制条件，但物资员仍作为正式审批节点，对本期材料或机械事实进行确认。

### 11.4 劳务、专业分包结算

```text
合同员编制发起
→ 所属项目中选定的工长/施工员
→ 所属项目的项目总工
→ 合同部主管
→ 项目经理
→ 财务主管
```

合同员根据施工员或工长在线下提供的工程量及结算依据编制结算。依据附件不是强制条件，选定的工长或施工员仍作为正式审批节点，对本期现场事实进行确认。

### 11.5 人员选择与冻结

- 合同员是编制人，不是审批节点，不审批自己；
- 编制人仍在最终结算单中生成签名和日期；
- 多名物资员、工长或施工员存在时，由合同员选择一人；
- 只能选择所属项目当前有效任职人员；
- 每份结算只选择一人，不要求多人会签；
- 项目总工由系统按所属项目自动确定；
- 缺少人员或项目总工冲突时阻止提交；
- 提交后冻结具体人员，后续调岗不改变实例；
- 换人需要撤回重选，或使用受审计的转交、委托机制；
- 公司工程技术部部长永久退出结算审批；
- 董事长、总经理不参与结算审批。

## 12. 结算单、乙方签章与逐页签名

### 12.1 冻结版结算单

合同员完成结算事实录入后，系统生成冻结版本：

- A4 横向；
- 多页时每页重复清单表头；
- 每页显示结算编号、版本号、页码和总页数；
- 每页底部预留横向签名区；
- 业务事实变化后旧文件自动失效。

清单按适用情况展示：

- 序号；
- 名称；
- 规格、型号；
- 单位；
- 数量；
- 含税单价；
- 不含税单价；
- 税率；
- 含税金额；
- 不含税金额；
- 税额；
- 备注。

### 12.2 乙方签章

乙方：

1. 打印系统生成的完整结算单；
2. 在每页指定位置签名并填写日期；
3. 每页按要求盖章；
4. 多页文件加盖骑缝章；
5. 将完整文件扫描为一个 PDF。

合同员上传原始扫描件，并确认签名、日期、逐页盖章和骑缝章要求已经完成。

系统不使用 OCR 识别印章真伪，但检查 PDF 格式、页数、页面顺序、横向尺寸、版本匹配、SHA-256 以及是否存在影响签名合成的裁边、旋转或尺寸异常。

### 12.3 审批签名冻结

审批通过时冻结：

- 审批岗位；
- 实际审批人；
- 审批意见和时间；
- 当时签名文件 ID 和摘要；
- 委托或转交关系。

个人后续更换签名不能改变历史结算文件。

### 12.4 最终签名合成件

全部审批通过后，以乙方原始扫描 PDF 为底稿，在每页底部固定位置叠加我方签名。

材料、机械结算签名栏：

```text
乙方
编制人
物资员
物资主管
合同部主管
项目经理
财务主管
```

劳务、专业分包结算签名栏：

```text
乙方
编制人
工长/施工员
项目总工
合同部主管
项目经理
财务主管
```

每格使用“岗位名称—签名—日期”的紧凑布局，保持单行横向排列。不得为了容纳更多岗位自动缩成不可读小字；未来确需更多岗位时使用专门模板。

永久保留：

- 乙方签章原始扫描件；
- 最终审批签名合成件；
- 对应结算事实快照；
- 审批和文件生成审计。

### 12.5 归档与退回

```text
全部内部审批通过
→ 自动生成最终签名合成件
→ 待合同部主管确认归档
→ 结算生效
```

正常情况下合同员无需再次上传归档文件。

仅签名位置、字体或系统渲染异常，且原始文件、业务事实和审批记录均未变化时，可以修复后重新生成，不重新审批。

以下情况必须作废原审批结果并完整重走：

- 替换乙方原始扫描件；
- 缺页、错页或页面顺序改变；
- 金额、数量、单价、税率变化；
- 清单、备注或正文变化；
- 乙方签名、日期或盖章不完整；
- 重新生成后页数发生变化。

## 13. 税务与计价事实

### 13.1 发票类型和税率

每个合同版本必须选择：

- 增值税普通发票；或
- 增值税专用发票。

普通合同使用单一税率。特殊合同可以启用多税率，但：

- 合同仍保存默认税率；
- 只有例外行覆盖税率；
- 每行最终必须有唯一税率；
- 同一合同版本不能混用普通发票和专用发票。

税率必须大于 0 且不超过 100%，常用税率提供快捷选项，特殊税率最多三位小数。当前范围不支持免税、不征税或零税率等非普通数字状态。

### 13.2 数量、单价和金额

- 数量最多两位小数；
- 含税单价最多两位小数；
- 超精度直接拒绝，不静默截断；
- 后端使用十进制定点数和“分”计算；
- 前端、Excel、PDF、合同、结算和付款必须使用同一后端结果。

```text
行含税金额 = 数量 × 含税单价
行不含税金额 = 行含税金额 ÷（1 + 税率）
行税额 = 行含税金额 - 行不含税金额
```

### 13.3 计价类型

有清单总价合同：

- 使用真实项目、数量和含税单价；
- 合同总价等于真实清单行合计；
- 禁止手工覆盖、调差、抹零、负数抵扣和虚构项目。

纯固定总价合同：

- 必须填写票种、税率和含税总价；
- 不虚构“数量 1、单价等于总价”的清单；
- 后端计算合同级不含税金额和税额。

无总价框架合同：

- 清单范围、含税单价、票种和税率必填；
- 预计数量可以为空；
- 预计金额仅供参考；
- 按实际核定数量结算。

### 13.4 历史合同税务补录

历史资料缺少票种、税率或含税单价时，不猜测、不默认 0，也不阻断历史接管。

可以保存结算草稿，但事实未确认前不能提交相关结算审批。

补录流程：

```text
合同员补录
→ 财务主管复核
→ 合同部主管确认
→ 税务事实生效
```

依据附件不是强制要求；没有附件时保留人工确认说明。更正必须保存前后值，不能覆盖历史结算和付款。

## 14. 通用合同直接付款

通用合同不进入结算流程。

付款必须：

- 引用已生效合同版本；
- 选择合同中已冻结的付款阶段或付款条款；
- 使用后端核算的可申请额度；
- 继续经过既有付款审批、实付登记、凭证上传和财务入账。

合同没有可执行付款条款时，禁止临时手工编造付款依据，必须先完成合同变更。

材料、机械、劳务和专业分包付款继续以生效结算作为来源。

## 15. 我方公司主体

### 15.1 字段范围

建立独立“我方公司主体”页面，每个主体仅维护：

- 公司全称，必填；
- 统一社会信用代码，必填；
- 注册地址，选填；
- 启用或停用状态；
- 创建及修改信息；
- 不可覆盖的历史版本。

不维护：

- 法定代表人；
- 联系电话；
- 银行账户；
- 公章图片或印章档案；
- 营业执照附件；
- 备注；
- 导出能力。

### 15.2 公司级全局权限

| 公司级全局岗位 | 权限 |
| --- | --- |
| 综合部主管 | 新增、修改、停用、重新启用、查看历史 |
| 合同部成员 | 新增、修改、停用、重新启用、查看历史 |
| 合同部主管 | 新增、修改、停用、重新启用、查看历史 |
| 财务人员 | 只读查看当前资料和历史 |
| 财务主管 | 只读查看当前资料和历史 |
| 董事长、总经理 | 只读查看当前资料和历史 |

其他岗位无入口和接口权限，`super_admin` 不自动获得业务权限。

项目级岗位不能维护全公司主体。后端必须校验公司级全局岗位，不能使用会合并任意项目岗位的宽松判断。

### 15.3 信用代码校验

- 必填；
- 去除首尾空格并转为大写；
- 必须为 18 位规范字符；
- 执行统一社会信用代码校验位算法；
- 全局唯一。

公司名称必填。名称重复时提示，但不作为硬唯一约束。

录入错误可以更正信用代码并保留历史；实际为另一法人主体时必须新增主体。

### 15.4 直接生效和历史

新增、修改、停用和重新启用：

- 直接生效；
- 不走审批；
- 不要求填写变更原因；
- 不要求再次输入密码；
- 不允许物理删除；
- 不允许覆盖历史版本；
- 不提供一键回滚。

历史记录保存修改前后内容、操作人、岗位、时间及操作类型。

主体列表同时展示启用和停用数据，并支持：

- 按启用状态筛选；
- 搜索当前公司名称；
- 搜索历史公司名称；
- 搜索统一社会信用代码。

### 15.5 合同选择与冻结

新合同：

- 必须从启用主体中选择；
- 不允许自由输入；
- 不默认选中某一主体；
- 同一项目可以选择不同的已启用我方公司主体，不将项目与某一家签约公司写死；
- 草稿保存稳定主体 ID；
- 页面显示名称和信用代码。

草稿期间主体变化时提示合同员同步，旧预览和正式文件失效；未同步或主体已停用时不能提交审批。

提交审批时冻结：

- 主体 ID；
- 主体版本 ID；
- 公司全称；
- 统一社会信用代码；
- 注册地址。

提交后主体主数据变化不得影响该合同版本及下游结算、付款和文件。

### 15.6 停用和历史接管

- 停用主体不能用于新合同；
- 已选择但未提交的草稿必须改选有效主体；
- 已提交、生效或归档业务继续使用冻结事实；
- 历史合同接管允许关联停用主体，以还原历史事实；
- 历史接管保留原合同中的主体名称和稳定主体 ID；
- 缺失或非法信用代码的存量主体标记“资料待补全”，只用于历史查询和匹配。

历史接管确认后的主体匹配错误：

```text
合同员发起更正
→ 合同部主管确认
→ 保存修改前后值和审计
```

不修改原始扫描件，不伪造历史合同文本。

### 15.7 下游继承与经营口径

- 合同变更继承原合同的我方主体，不能通过变更换成另一家公司；
- 结算继承对应合同版本冻结的主体事实；
- 付款继承合同或结算所对应的责任主体；
- 发生代付时另行记录实际付款主体，但同一业务金额在项目经营中只统计一次；
- 项目仍是主要经营分析维度，公司主体作为辅助筛选和责任归属维度；
- 相同统一社会信用代码视为同一法人主体，经营查询可以按当前名称汇总；
- 历史合同和文件继续显示各自冻结时的主体名称；
- 不同统一社会信用代码的主体不得合并统计为同一法人主体。

## 16. 跨域只读与台账导出边界

以下岗位按现有项目可见范围获得跨域只读能力：

- 财务人员；
- 财务主管；
- 综合部主管。

允许：

- 查看历史合同接管列表和详情；
- 查看历史合同税务修订记录；
- 导出历史合同接管台账及单合同结构化详情；
- 查看合同台账和合同详情；
- 导出合同台账；
- 查看结算台账和结算详情；
- 导出结算台账。

这里的“导出”是经过后端权限校验、生成并写审计的结构化台账或详情文件，不代表获得对所有归档附件的无条件下载权。敏感合同、结算和审批文件仍执行既有后端文件权限、下载用途、短时效票据和审计要求。

上述只读与导出权限不得授予：

- 新建合同或历史接管草稿；
- 修改合同、接管或结算事实；
- 上传、替换或删除合同及结算文件；
- 提交合同或结算审批；
- 同意用章；
- 合同部归档确认；
- 合同部税务事实确认；
- 其他仅属于合同部的业务动作。

财务主管仍按第 13.4 节执行历史税务事实的财务复核，但该专门复核资格不能扩展为合同编辑、合同部确认或其他写权限。

我方公司主体页面本身不提供导出能力；本节的台账导出不能解释为公司主体档案导出。

## 17. 新旧流程过渡

采用“历史不改、未生效重走”：

- 已生效、已归档、已作废的合同和结算保持原状；
- 尚未提交的草稿适配新字段和门禁；
- 正在审批、待用章或待归档的未生效合同，终止旧实例，补齐资料后按新路线重新提交；
- 正在审批或待归档的未生效结算，终止旧实例，补齐乙方签章原件后按新路线重新提交；
- 旧审批记录永久保留并标记“因业务规则升级终止”；
- 已发起付款、实付和入账继续使用原冻结事实；
- 新规则启用后新提交的业务全部执行本规格。

迁移不得猜测票种、税率、公司主体、授权书需要情况或旧文件签章完整性。无法可靠推导的数据进入待补全状态。

## 18. 错误、审计与安全

所有阻断反馈必须说明：

1. 发生了什么；
2. 为什么不能继续；
3. 已填写内容是否保留；
4. 下一步应到哪里处理。

提交失败不得清空草稿、辅助附件或已选审批人。

必须审计：

- 公司主体新增、修改、停用和启用；
- 正式审批文件上传、失效和替换；
- 授权委托书上传和复用；
- 审批路线及人员冻结；
- 同意用章；
- 最终签署文件上传；
- 合同和结算归档确认、退回；
- 审批单及敏感文件下载；
- 结算签名合成及重新生成；
- 金额、税务或文件门禁阻断；
- 旧流程实例因规则升级终止。

## 19. 实施方式

采用按业务闭环分批交付：

1. 公司主体、税务计价及版本冻结基础；
2. 新合同分类审批、项目人员选择和实例冻结；
3. 审批前签章 PDF 与双方授权委托书；
4. 同意用章、最终签署件、归档及《合同审批单》；
5. 统一合同变更及累计增项 10% 硬门禁；
6. 结算路线、乙方扫描件、逐页签名合成和归档；
7. 通用合同直接付款与付款来源分流；
8. 存量迁移、全链路回归、真实业务 UAT 和发布候选审计。

每个切片：

- 由一个代理负责明确文件边界；
- 不允许多个代理同时修改同一核心服务、Schema 或迁移；
- 先运行定向测试，再运行全量检查；
- 更新 `PROGRESS.md`；
- 形成独立 Conventional Commit；
- 由主代理审查全部 diff、Schema、金额和状态机。

## 20. 验收标准

### 20.1 合同

- 五种合同类型均冻结正确审批路线和具体人员；
- 合同部主管发起时跳过自身节点；
- 缺失或冲突项目岗位时阻止提交；
- 双方授权书四种组合均正确处理；
- 审批前必须有乙方签章完整 PDF；
- 审批版和双方最终签署版均永久保留；
- 上传人与归档确认人职责分离；
- 《合同审批单》签名不会因用户换签而漂移。

### 20.2 合同变更

- 所有新变更使用统一路线；
- 正好累计增项 10% 可以提交；
- 严格超过 10% 必须新签合同；
- 减项不释放增项额度；
- 更换我方主体必须新签合同；
- 历史增强/重大变更不被重写。

### 20.3 结算

- 两类结算路线及具体人员正确冻结；
- 过程结算和最终结算路线相同；
- 通用合同不能创建结算；
- 乙方扫描件必须在审批前上传；
- 多页结算单每页重复表头和签名区；
- 每页正确叠加编制人和审批人签名；
- 原始扫描件和最终合成件同时保留；
- 原始文件或业务事实变化后必须重新审批；
- 合同金额上限不能被项目例外额度绕过。

### 20.4 税务和付款

- 票种、税率和含税价格在合同版本中冻结；
- 数量和含税单价超过两位小数时拒绝；
- 含税、不含税和税额在各展示渠道一致；
- 无总价框架合同可以按实际数量结算；
- 通用合同付款必须选择冻结付款条款；
- 没有付款条款时不能手工编造付款依据。

### 20.5 公司主体

- 维护和只读权限仅由公司级全局岗位获得；
- 项目岗位不能越权维护全公司主体；
- 信用代码执行格式、校验位和唯一性检查；
- 停用主体不能用于新合同；
- 已提交业务保持冻结快照；
- 历史接管可以关联停用主体并保留原文名称；
- 所有修改均存在不可覆盖历史。

### 20.6 跨域只读与导出

- 财务人员、财务主管和综合部主管可按项目可见范围读取历史接管、合同及结算台账；
- 三类岗位可以生成经过审计的结构化台账和详情导出；
- 只读权限不会开放合同或结算的新建、修改、上传、提交和归档确认；
- 财务主管只保留明确的税务事实财务复核动作，不获得合同部确认权限；
- 敏感附件下载仍执行独立后端文件权限和下载审计；
- 我方公司主体页面不提供导出。

### 20.7 工程质量

- 定向单元测试；
- API 权限、状态和事务测试；
- Web Vitest；
- API/Web typecheck、lint；
- Web `check:ui`；
- P0 E2E；
- PDF/Excel 固定数据和页面版式验证；
- 隔离恢复库迁移演练；
- `git diff --check`；
- 受保护业务目录和非目标模块无意外差异。

## 21. 发布与回滚门禁

全部实施完成后只形成发布候选，必须报告：

- 最终目标 SHA；
- 相对生产和 `main` 的提交列表；
- 实际修改文件；
- 数据库迁移数量及内容；
- 隔离库迁移演练结果；
- 全部测试和 UAT 结果；
- 存量未生效业务处理清单；
- 未解决问题；
- 应用及数据库回滚方式。

未经用户针对最终目标 SHA 明确批准，不得：

- 推送 `main`；
- 部署生产；
- 执行生产迁移；
- 终止或改写生产中的业务实例；
- 写入真实业务数据。

## 22. 明确不做

本次不建设：

- 在线可配置的通用审批流设计器；
- OCR 自动判断合同或结算签章真伪；
- 电子签章平台；
- 完整印章档案系统；
- 工商信息平台；
- 银行账户管理平台；
- 发票开具、查验、认证、抵扣、红冲或税务申报；
- 为容纳任意审批节点而自动压缩到不可读的动态签名模板；
- 对已生效历史合同、结算、付款和文件进行追溯重写。
