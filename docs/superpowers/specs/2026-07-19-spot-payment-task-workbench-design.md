# 建工智管零星材料付款任务化工作台与详情体验设计

日期：2026-07-19

状态：用户已于 2026-07-19 逐项确认整体设计；等待用户审阅本文档后进入实施计划

范围：零星材料付款工作台、付款详情信息架构、A5 付款申请填写、岗位动态待办、付款审批面板、逐笔实际付款入口及相关读取模型

决策：在已经生产发布的独立零星采购 A4/A5 闭环上做增量体验重构，不重建采购、审批、付款、收货、退款、发票、PDF、私有文件或审计底座

## 1. 文档优先级与实施边界

本文是 `docs/superpowers/specs/2026-07-18-spot-procurement-real-form-redesign.md` 的付款工作台与详情体验增量规格。发生冲突时：

1. 本文优先于旧规格中付款工作台列布局、付款详情页签、付款表单呈现方式和付款审批操作入口。
2. 旧规格中的 A4/A5 业务事实、付款主体权限、审批节点、分次实付、收货、退款、发票、PDF、归档和最小授权继续有效。
3. 本文把零星付款审批结果收口为“通过”与“退回申请人修改”。通用审批引擎仍可为其他业务保留更多决策类型，但新版 A5 零星付款不得暴露或接受终止性“拒绝”。
4. 本文不修改已经冻结的 A4/A5 PDF 版式，也不建立第二套签名系统；公共审批单固定签字格能力仍由统一分支接入。
5. 本设计确认不等于授权修改业务代码、迁移数据库、推送、部署、生产写入或代替真实人员完成 UAT。

## 2. 当前事实与问题

当前独立零星采购模块已经具备真实业务闭环：

- 采购审批通过后自动生成唯一付款草稿。
- 付款草稿支持实际商户、一个收款对象、多个渠道、付款材料、含税或无票单价、预计票据和付款依据。
- 付款主体由财务人员、综合部主管或财务主管在合法阶段受控维护。
- 付款审批固定为综合部主管、项目经理、财务主管、董事长或总经理 OR 签。
- 审批通过只进入待付款；一张申请可登记多次实际付款，每笔有独立凭证。
- 首笔实际付款后开放一次最终收货；少货只允许补货或退款。
- 发票为付款级可追加附件，不阻断办结。

当前问题不是业务能力缺失，而是用户很难从页面判断“现在轮到我做什么”：

- 付款工作台即使缩减到七列，仍以台账为中心，待办不够突出。
- 付款详情把付款事实、审批操作、付款主体维护、逐笔实付和归档同时放在长页面中。
- 物资员需要从列表进入详情，再寻找付款草稿编辑入口。
- 物资主管、财务人员和财务主管看到近似页面，却承担完全不同的责任。
- 状态采用类似按钮的色块，容易被误认为可点击操作。
- A5 付款表单使用长对话框，字段密集且缺少明确步骤。

## 3. 目标与非目标

### 3.1 目标

1. 用户进入付款工作台后，第一眼看到自己当前可办理的任务。
2. 每张已批准采购申请都能从采购工作台和采购详情直接进入对应付款任务。
3. 所有岗位使用同一付款详情地址和资料结构，但“当前办理”按岗位、权限和状态动态变化。
4. 物资员以四步流程填写付款申请，不需要理解后台付款状态机。
5. 审批人先看到岗位相关的核对摘要，再通过单一入口办理审批。
6. 财务人员在审批通过后直接看到逐笔实际付款任务。
7. 工作台保持财务台账能力，但不再用超宽表格承载全部事实。
8. 状态与操作在视觉上清晰分离。

### 3.2 非目标

- 不新增完整采购订单、询比价、库存、供应商门户或正式供应商主数据。
- 不新增 OCR、发票验真、发票分摊或结构化发票系统。
- 不改变采购、付款、收货、退款和发票的已确认办结规则。
- 不把物资主管加入零星付款审批流程。
- 不让前端自行推测权限或绕过后端状态门禁。
- 不在本轮重做全系统其他模块的工作台。

## 4. 总体体验架构

```text
已批准采购申请
  -> 自动生成付款草稿
  -> 采购工作台/采购详情直接进入付款详情“当前办理”
  -> 物资员四步填写并提交
  -> 综合部主管审批
  -> 项目经理审批
  -> 财务主管审批
  -> 董事长/总经理 OR 签
  -> 财务人员逐笔登记实际付款与凭证
  -> 首笔实付后进入收货、差异、退款和发票既有闭环
```

付款工作台是集中待办和台账入口，不再是办理付款草稿的唯一入口。付款详情是单据唯一任务页面，不为不同岗位复制不同详情路由。

## 5. 付款工作台

### 5.1 页面结构

采用“任务优先 + 精简台账”布局，固定三档视图：

1. `待我办理`：默认视图，只返回当前账号可执行的个人任务和共享协作任务。
2. `全部申请`：返回账号业务可见范围内的全部付款申请。
3. `已办结`：返回已结清、已办结、已作废或异常终止的历史申请。

默认首屏顺序：

1. 页面标题与刷新。
2. 视图切换及待办数量。
3. 最多五张高优先任务卡。
4. 项目、状态和关键词筛选。
5. 当前视图的精简台账。

原四个全局金额汇总卡不再占据所有岗位的默认首屏。财务岗位在“全部申请”视图可以继续查看其有权汇总的审批金额、累计实付、累计退款和净付金额；物资岗位默认不展示全局财务汇总。

### 5.2 任务队列

`待我办理`包括：

- 物资员：付款草稿待填写、退回后待修改、保存未提交的付款申请。
- 综合部主管：待审批付款、付款主体或拟付款方式待补全的共享事项。
- 项目经理：到达本人节点的付款审批。
- 财务人员：付款主体共享补全、已批待付款、部分付款、退款待登记或凭证异常待处理。
- 财务主管：到达本人节点的付款审批、受控付款主体调整、异常终止确认。
- 董事长/总经理：到达 OR 签节点且本人有权完成的最终审批。

物资主管在付款阶段只有监督查看权，不因“可查看”生成待办；其收货复核继续进入收货确认工作台。

任务排序由服务端提供稳定优先级：

1. 退回、凭证异常、退款待处理等阻断事项。
2. 当前账号独占办理的审批、实付或草稿任务。
3. 付款主体等多个受控岗位均可完成的共享事项。
4. 同优先级按进入当前状态的时间升序，较早进入的先显示。

多人共享任务由第一位合法保存者完成。其他人再次操作时，服务端返回状态已变化，页面刷新后移除该任务，不制造重复事实。

### 5.3 精简台账

工作台主表固定为六个信息组：

| 信息组 | 内容 |
| --- | --- |
| 付款申请 | 付款编号、关联采购编号 |
| 项目 / 商户 | 项目简称、实际商户；草稿未填时显示“待填写” |
| 金额 | 审批金额；草稿未形成金额时显示“待确定” |
| 当前状态 | 彩色圆点和状态文字 |
| 当前任务 | 当前需要完成的业务动作或“无需办理” |
| 操作 | 填写、处理或查看 |

表格不得再同时展开全部付款主体、收款渠道、累计实付、退款、净付、剩余、收货、发票、审批人和更新时间。上述事实进入付款详情相应页签。

在 1366 像素宽度应直接读完六个信息组；在 1024 像素及以下，优先折行和响应式收窄，只有确实无法容纳时才由表格区域自身滚动，页面主体不得横向溢出。

## 6. 采购到付款的直接入口

采购审批通过并生成付款草稿后：

- 采购工作台当前行显示“填写付款申请”或当前付款任务。
- 采购详情的关联付款区域显示主操作“进入付款申请”。
- 两个入口均进入现有付款详情路由，并默认打开“当前办理”。
- 付款工作台仍提供同一详情入口，但不要求用户必须先经过付款工作台。
- 一个采购根单只有一个当前有效付款申请，不提供“新建第二张付款申请”按钮。

## 7. 付款详情统一资料顺序

所有岗位共享六个固定页签：

1. `当前办理`
2. `付款申请`
3. `审批进度`
4. `实际付款与凭证`
5. `收货与发票`
6. `归档资料`

不再使用“付款事实”“审批与办理”“审批原件与归档”三个抽象名称。进入详情默认打开“当前办理”；用户切换其他页签只影响当前浏览，不改变业务状态。

### 7.1 当前办理

`当前办理`只展示当前账号现在能做的主任务、必要摘要和明确下一步。没有权限时只显示只读说明，不渲染禁用的高风险按钮。

| 岗位 / 场景 | 首屏主任务 | 首屏重点 |
| --- | --- | --- |
| 物资员，付款草稿或退回修改 | 补全付款信息并提交 | 采购审批已通过、待填金额、提交后节点、采购原单摘要 |
| 物资主管，付款办理中 | 当前无需办理付款 | 采购与付款材料对照、差异、后续收货复核责任 |
| 综合部主管，待审批 | 办理付款审批；必要时协作补全付款主体 | 资料完整性、付款事由、我方付款主体和拟付款方式 |
| 项目经理，待审批 | 办理付款审批 | 项目需要、采购与付款材料一致性、数量和金额 |
| 财务人员，审批前 | 协作补全付款主体与方式 | 共享任务完成状态、实际操作人、后续实付责任 |
| 财务人员，审批完成 | 登记实际付款 | 剩余待付、冻结主体、批准渠道、凭证要求 |
| 财务人员，少货退款 | 登记退款 | 应退差额、退款金额、到账时间、方式和凭证 |
| 财务主管，待审批 | 办理付款审批 | 金额、主体、收款对象、渠道、票据条件和风险摘要 |
| 董事长/总经理，待 OR 签 | 办理最终审批 | 最终金额、付款主体、收款对象、前序审批和异常提示 |
| 其他有查看权用户 | 当前无需办理 | 当前节点、下一责任岗位、只读业务摘要 |

综合部主管、项目经理、财务主管和董事长/总经理共用同一审批骨架，只替换岗位核对重点，不复制四套页面。

### 7.2 其他页签

- `付款申请`：展示当前 A5 申请冻结事实、付款材料、商户、收款对象、付款主体、批准方式、渠道和付款依据。
- `审批进度`：展示审批节点、人员、时间、结果、意见、退回与重新提交历史。
- `实际付款与凭证`：展示审批金额、累计实付、退款、净付、剩余和逐笔执行记录。
- `收货与发票`：只读展示收货进度、差异、退款衔接和付款级发票；有权人员可进入既有办理入口。
- `归档资料`：展示不可变 A5 审批原件、A4 明细、归档版本、生成状态和受控下载。

## 8. A5 付款申请四步办理

点击“填写付款申请”后，不弹出超长对话框。付款详情切换为同页四步办理模式：

```text
1. 商户与付款方式
2. 材料与价格
3. 收款渠道与附件
4. 核对并提交
```

页面支持保存退出和继续填写。每一步只校验本步已填写内容；最终提交由后端执行全量校验和金额重算。

步骤进度是前端办理状态，不新增步骤表或另一套草稿模型。每次保存仍通过既有付款草稿更新入口保存完整当前草稿，重新进入时根据已保存字段恢复到第一个未完成步骤。

### 8.1 商户与付款方式

- 付款类型：公司直付或经办人垫付报回。
- 实际商户名称支持同项目历史名称建议，只复制名称。
- 正常情况下收款对象默认等于实际商户，不要求重复输入。
- 只有开启“收款对象与实际商户不一致”后，才显示独立收款对象和必填不一致说明。
- 经办人垫付报回继续按既有规则冻结经办人为收款对象。
- 物资员不能选择我方付款主体。

数据层继续分别保存实际商户和收款对象，不因表单简化合并两个业务事实。

### 8.2 材料与价格

- 材料名称、型号、单位和批准数量从采购版本带入。
- 经办人选择实际付款材料并填写付款数量和含税或无票单价。
- 预计票据为无发票、增值税普通发票或增值税专用发票；有票时选择税率。
- 行金额和整单金额始终由后端重算，前端合计只作即时反馈。
- 新增材料或超批准数量必须返回采购版本变更，不在付款表单内放宽。

本页面触及的数量、单价、实付金额和退款金额按已确认的全系统兼容规则处理：

- 新建和修改最多两位小数。
- 金额继续以整数分和规范十进制字符串传输及存储。
- 历史三至六位小数资料原样只读，不自动四舍五入或改写。
- 全系统其他模块的两位小数收紧仍按 `PROGRESS.md` 中的独立任务推进，不在本体验重构中顺带大范围修改。

### 8.3 收款渠道与附件

- 一张申请只有一个收款对象，可以登记多个该对象的收款渠道。
- 必须且只能选择一个主渠道。
- 银行转账填写账户名、账号和开户行；微信、支付宝、现金或其他方式按既有渠道规则填写。
- 商家收据、报价单、当时已有的发票和其他付款依据均可选。
- 列表和非必要岗位继续只显示脱敏渠道。

### 8.4 核对并提交

最终核对页集中展示：

- 项目和采购申请。
- 付款类型、实际商户和收款对象。
- 付款材料、数量、单价、预计票据和金额合计。
- 收款渠道和主渠道。
- 当前付款主体状态。
- 提交后的首个审批节点。

提交成功后退出办理模式，`当前办理`自动切换为等待审批或下一合法任务。

## 9. 付款主体共享协作

我方付款主体不指定唯一维护人。财务人员、综合部主管和财务主管在既有合法阶段共享一个受控任务：

- 第一个合法保存者冻结公司 ID、公司名称和统一社会信用代码快照，并记录实际操作人和时间。
- 其他有权岗位刷新后立即看到已完成事实，不再显示未完成任务。
- 综合部主管审批通过前必须存在有效付款主体和至少一种拟付款方式。
- 财务主管在自身审批节点调整付款主体时，必须填写原因并二次确认；综合部主管和项目经理既有本轮通过动作失效，流程从综合部主管重新开始。
- 最终审批完成或任一有效实际付款后永久锁定。

## 10. 付款审批体验

### 10.1 单一审批入口

审批岗位首屏只显示一个实心主按钮“办理审批”。不在首屏并排放置“通过、退回、拒绝”等结果按钮。

点击后：

- 桌面端打开右侧抽屉，原付款详情仍保留在左侧上下文中。
- 移动端打开全屏审批面板。
- 抽屉展示岗位核对摘要、审批结果、审批意见和二次确认入口。

### 10.2 审批结果与意见

新版 A5 零星付款只允许：

1. `通过`：进入下一审批节点；终审通过进入已批待付。
2. `退回申请人修改`：退回物资员；重新提交后从综合部主管开始完整重审。

意见规则：

- 通过时意见可选；未填写时服务端冻结为“同意”。
- 退回时原因必填，空白原因由后端拒绝。
- 不提供“拒绝并永久终止”。需要结束尚未实付的申请时，继续使用既有撤销或作废受控流程；发生实付后使用既有异常终止流程。

转办和委托不是审批结果。若当前通用审批引擎和冻结实例允许，继续通过其独立受控入口办理，不出现在“通过/退回申请人修改”结果选择器中。本轮不修改通用转办、委托和 OR 签规则；历史已驳回记录继续只读展示。

二次确认必须展示：审批结果、付款金额、我方付款主体、收款对象和下一去向。服务端仍以当前审批节点、人员、委托、OR 签和状态事实决定是否允许提交。

## 11. 实际付款办理

付款终审完成后，财务人员的`当前办理`自动切换为“登记实际付款”：

- 本次实付金额默认带出剩余待付，可修改但不得超过剩余金额。
- 金额最多两位小数。
- 每次选择一个已批准且已冻结的收款渠道。
- 银行转账、微信、支付宝等必须上传本笔成功付款凭证。
- 现金付款必须上传本笔商家收据。
- 每次登记形成独立实付记录、幂等键、凭证绑定和审计事实。
- 一笔付款的文件上传或绑定失败时，不增加累计实付。
- 仍有余额时显示“部分付款，继续登记”；余额为零时显示“已付款”。
- 首笔有效实付后开放收货确认。

实际付款使用与审批抽屉一致的受控侧边面板壳层，但表单内容独立；桌面端保留付款摘要，移动端全屏。重复提交、网络重试或页面刷新不得生成重复实付。

少货且物资主管已确认选择退款路径时，财务人员的当前任务切换为登记退款；退款继续使用既有应退差额、到账时间、方式、凭证和审计规则，不恢复“转商户余额”。

## 12. 状态表达规范

非交互状态统一使用“彩色圆点 + 纯文字”，不使用类似按钮的矩形色块：

| 颜色 | 语义 | 示例 |
| --- | --- | --- |
| 灰蓝 | 草稿、未开始 | 付款草稿 |
| 橙色 | 办理中、待补全 | 审批中、待补全主体、部分付款 |
| 紫色 | 当前账号必须处理 | 待我审批、待我付款 |
| 绿色 | 成功或完成 | 已通过、已付款、已办结 |
| 红色 | 退回或异常阻断 | 已退回、凭证异常、退款待处理 |

颜色不能作为唯一信息来源，始终同时显示明确状态文字。真正可点击的操作继续使用 TDesign 按钮。

## 13. 读取模型与权限契约

### 13.1 服务端任务事实

前端不得根据角色名称和状态字符串自行拼出权限。付款列表与详情读取模型应在既有 `availableActions`、`primaryAction` 和 `payerManagement` 基础上增加稳定任务摘要：

```ts
type SpotPaymentCurrentTask = {
  key: string;
  label: string;
  hint: string;
  priority: number;
  scope: "personal" | "shared" | "none";
  enabled: boolean;
  disabledReason: string | null;
};
```

`SpotPaymentCurrentTask` 是从既有付款、审批、收货、差异和权限事实实时推导的读取投影，不建立新的任务业务表，也不把任务卡状态作为第二份业务真相。

前端按 `key` 映射已注册页面动作，不接受服务端下发任意 URL。所有写接口继续重新校验项目、岗位、当前节点、单据状态、金额、文件和并发版本。

付款工作台查询增加受控视图参数 `mine | all | closed`，服务端完成可见范围、可办理范围、共享任务和稳定排序；不能先返回全部可见单据再由浏览器过滤“我的待办”。

### 13.2 最小授权

- 物资员只办理本人作为付款经办人的付款申请；收货委托不自动扩大付款申请权限。
- 物资主管付款阶段只读监督，不获得付款主体、审批或实付权限。
- 财务人员只能在有权项目和合法阶段维护付款主体、登记实付或退款。
- 综合部主管、项目经理、财务主管和董事长/总经理只在冻结审批节点可办理审批。
- 完整账户、付款凭证、退款凭证、发票和归档下载继续使用既有最小授权、下载原因、短时地址、水印和审计。

## 14. 前端组件边界

当前 `SpotProcurementPaymentDetailPage.vue` 同时承担详情、编辑、付款主体、审批、实付和归档。实施时应做与本需求直接相关的局部拆分，不进行全站重写：

- `PaymentCurrentTaskPanel.vue`：岗位和状态动态首屏。
- `PaymentApplicationStepper.vue`：四步付款申请。
- `PaymentApprovalDrawer.vue`：统一审批抽屉和二次确认。
- `PaymentExecutionDrawer.vue`：逐笔实付表单和凭证。
- `PaymentTaskQueue.vue`：工作台待办卡和视图切换。
- `BusinessStatusText.vue`：跨页面复用的圆点状态文字；只组合 TDesign 和 `--jg-*` token。

页面保留数据加载、路由和动作编排；领域组件不直接调用 `fetch`，API 调用继续集中在 `apps/web-admin/src/api/spot-procurement.api.ts`。

## 15. 错误、并发与恢复

- 列表或详情读取失败时保留页面结构，显示可重试错误，不显示空白页。
- 当前任务已被其他共享岗位完成时，保存返回稳定冲突错误，刷新后展示新事实。
- 审批节点已变化时不得继续提交旧审批结果。
- 付款主体调整触发重审时，必须先成功保存业务和审计事实，再刷新任务摘要。
- 分步表单保存失败时保留本地输入并明确指出失败步骤。
- 最终提交以后端校验结果为准；金额、材料、渠道或付款主体异常时不创建审批实例。
- 实付凭证上传、文件绑定或付款事务任一步失败时不增加已付金额。
- 归档生成失败继续按既有 best-effort 重试机制处理，不回滚已成功的审批或付款事实。

## 16. 响应式与可访问性

- 桌面端优先为 1366 像素及以上；1024 像素保持主页面不横向溢出。
- 付款工作台在窄屏将任务卡改为单列，表格字段适度折行。
- 四步付款申请在手机上使用纵向步骤导航。
- 审批、实付抽屉在移动端自动全屏。
- 状态圆点有文字标签；按钮、页签、步骤和表单均支持键盘焦点。
- 打开抽屉后焦点进入标题，关闭后回到触发按钮；二次确认不得绕过。
- 不显示预计办理时长。

## 17. 验收与测试

### 17.1 服务端

- `mine | all | closed` 可见性、任务范围和排序测试。
- 个人任务与共享付款主体任务并发完成测试。
- 物资主管无付款写权限测试。
- 零星付款只接受通过和退回申请人，拒绝终止性驳回测试。
- 通过空意见自动冻结“同意”，退回空原因失败测试。
- 付款主体缺失阻止综合部主管通过测试。
- 财务主管调整付款主体触发完整重审测试。
- 数量、单价、实付和退款新写入最多两位小数测试。
- 多次实付累计上限、逐笔渠道、逐笔凭证和幂等测试。

### 17.2 Web

- 三档工作台视图、最多五张任务卡和六列台账测试。
- 采购工作台与采购详情直达付款任务测试。
- 物资员、物资主管、综合部主管、项目经理、财务人员、财务主管、董事长/总经理七类当前办理视图测试。
- 商户与收款对象默认一致、例外开关和不一致原因测试。
- 四步保存、继续填写、最终校验和提交测试。
- 单一审批入口、右侧抽屉、两种结果和二次确认测试。
- 灰蓝、橙、紫、绿、红五类状态文本测试。
- 实付默认剩余金额、两位小数、渠道和凭证必填测试。

### 17.3 浏览器验收

至少覆盖：

1. 物资员从已批准采购直接进入并提交付款申请。
2. 物资员从付款工作台待办卡继续未完成草稿。
3. 退回申请人在工作台置顶并重新提交。
4. 物资主管只读监督且无越权按钮。
5. 财务人员、综合部主管或财务主管完成共享付款主体任务后，其他人立即看到完成。
6. 四级审批均看到岗位相关摘要，终审 OR 签正常。
7. 财务人员登记两笔实际付款，每笔独立上传凭证，最终变为已付款。
8. 现金实付只接受商家收据作为本笔凭证。
9. 1366、1024、768 和 390 像素视口无页面级横向溢出。
10. 返回工作台、刷新、网络失败重试和并发冲突不会出现白屏或重复业务事实。

验证至少运行 Web 定向 Vitest、API 定向 Jest、API/Web typecheck、lint、`check:business-errors`、`check:ui`、构建、相关 Playwright 和 `git diff --check`。
