# 建工智管项目接管与第一版可上线设计

- 日期：2026-07-10
- 状态：已于 2026-07-10 书面复核通过，进入实施
- 适用范围：第一版上线范围、现有代码治理和后续实施计划

## 1. 文档目的

本设计用于重新建立项目唯一主线。后续开发、验收和发布都应以本设计、`AGENTS.md` 和 `PROGRESS.md` 为依据，不再从历史方案中任意挑选规则实施。

本设计解决以下问题：

- 项目文档多，但缺少统一业务边界。
- 合同、结算、付款已有较多实现，但一线操作体验不连贯。
- 历史接管、付款来源、审批角色、资金上限和权限规则存在口径漂移。
- 代码中存在金额类型、超大服务、重复审批逻辑和文件存储接入等风险。
- 软件发布不应被额外的 Go-Live 材料审批流程拖慢。

## 2. 第一版目标

第一版不推倒重来，保留现有技术栈和已验证业务能力，完成一条能够使用真实数据、可追溯、可审计的企业核心链路：

```text
合同草稿
  -> 付款条款录入
  -> 合同审批
  -> 用印审批
  -> 签署合同归档确认
  -> 合同版本生效
  -> 结算编制与审批
  -> 签章结算归档确认
  -> 结算生效
  -> 付款申请与审批
  -> 已批准待付款
  -> 出纳登记实付并上传回单
  -> 扣减项目现金池
  -> 财务记录、PDF 归档和审计
```

第一版同时包含：

- 历史合同 A/B/C 风险接管与受限确认。
- 合同变更、补充协议和合同新版本。
- 普通付款、报销和零星采购。
- 业主主合同额度、项目超额授权和项目现金池。
- 完整的组织、人员、固定角色和项目权限管理 UI。
- 合同工作台、合同模板、结算工作台和结算模板的办公化改造。
- 腾讯 COS 私有桶的应用接入。

## 3. 第一版不做的事项

第一版不扩展以下大模块：

- 完整材料出入库。
- 考勤、人事、安全、OCR 和发票平台。
- 大型经营驾驶舱和全量成本分析。
- 通用低代码审批、BPMN 或可任意拼装权限的平台。
- 在线 Office 生产集成。
- 为软件发布建设 Go-Live 材料包或签字审批模块。

这些事项只有在真实试用明确阻塞核心链路时才能重新进入范围。

## 4. 技术架构边界

保留现有架构：

- Web 管理端：Vue 3、TypeScript、TDesign Vue Next、Vite。
- 移动端：原生微信小程序，继续调用统一后端 API。
- 后端：Node.js、NestJS。
- 数据库：PostgreSQL。
- 文件存储：腾讯 COS 私有桶。
- 部署：现有域名、腾讯云轻量应用服务器和 Git 仓库。

前端不得直接访问 PostgreSQL，也不得持有 COS 密钥。所有业务规则、金额校验、状态迁移、文件权限和审计必须由后端执行。

## 5. 金额与版本基础规则

### 5.1 金额类型

单笔合同、结算或付款可能超过 2100 万元。现有 32 位 `Int` 分值存在溢出风险，第一阶段必须完成金额字段治理：

- 金额统一按分保存为 PostgreSQL `BIGINT`。
- Node.js 内部使用 `bigint` 或不丢精度的金额值对象。
- API 不以 JavaScript `number` 传递大额分值，使用字符串承载。
- 前端按元显示和录入，后端负责转换、舍入和校验。
- 累计金额、额度和现金扣减必须在数据库事务内计算。

### 5.2 版本追溯

- 合同生效后不能直接修改。
- 付款条款随合同版本冻结。
- 结算必须引用有效合同版本。
- 付款必须保留原合同版本、付款条款版本和结算来源。
- 历史结算和付款不得随合同新版本发布而漂移。

## 6. 合同、结算和模板的办公化体验

### 6.1 统一操作原则

合同和结算共享以下操作逻辑：

- 顶部显示业务名称、当前阶段、保存状态和一个主操作。
- 阶段统一表达为准备、起草或编制、审批、签署、归档。
- 草稿自动保存，提交前统一检查完整性。
- 阻断提示说明缺什么、为什么不能继续、去哪里补充。
- 页面不得向普通用户展示内部字段、状态码、接口名和版本 ID。

合同与结算使用不同画布：

- 合同以文档为中心，右侧显示结构化业务数据和缺项。
- 结算以全宽表格为中心，异常、附件和依据通过抽屉展开。

### 6.2 合同工作台

新建合同流程：

```text
选择项目
  -> 选择业务场景
  -> 系统推荐合同模板
  -> 查看预览或更换兼容模板
  -> 创建合同草稿
```

工作台中央显示合同正文预览，右侧集中维护：

- 合同名称和主体。
- 合作单位。
- 合同金额、税率和计价方式。
- 付款条款。
- 合同清单。
- 必传资料和提交缺项。

第一版采用本机 Word 往返模式：

```text
系统生成 Word
  -> 合同员在本机 Word 修改
  -> 拖拽上传修订稿
  -> 系统生成预览
  -> 检查正文与结构化数据差异
  -> 保存修订历史
```

Word 正文中的金额、付款条款或清单变化不得自动覆盖系统账本。提交审批前必须解决正文与结构化数据的差异。

### 6.3 合同模板

普通用户采用“流程推荐 + 独立模板库”：

- 新建合同时优先推荐当前业务场景的模板。
- 用户可以浏览全部已发布模板并查看预览。
- 只有合同主管和授权管理员看到模板管理入口。

模板采用 Office 优先、系统兜底的方式：

- Word 文件负责正文、条款表述、表格和版式。
- 系统提供中文变量，不要求主管手写内部字段标识。
- 合同主管在本机 Word 编辑，上传后形成新模板版本。
- 系统检查未知变量、缺失变量和重复变量。
- 发布前必须生成带测试数据的 DOCX 和 PDF 预览。
- 已发布模板不可覆盖，只能克隆形成新草稿版本。

合同金额、付款条款、清单、适用合同类型和附件要求仍由系统管理。Office 文件不能成为业务事实来源。

### 6.4 结算工作台

新建结算不再要求用户先填写结算总金额。流程调整为：

```text
选择有效合同
  -> 推荐兼容结算模板
  -> 从合同清单引出明细
  -> 网页表格录入、粘贴或导入 Excel
  -> 预览导入错误
  -> 应用明细并由后端重算
  -> 补充异常原因和依据
  -> 检查并提交
```

结算工作台采用全宽网页表格，并保留：

- Excel 模板下载。
- Excel 导入预览和应用。
- 多行复制粘贴。
- 批量修改数量和备注。
- 结果导出。
- 固定在表格底部的行数、异常数和本期合计。

结算金额、累计金额和异常项必须由后端按明细重算，不能信任前端合计或 Excel 公式。

### 6.5 结算模板

- 选择合同后，根据合同计价方式推荐结算模板。
- 只有存在多个兼容模板时才要求用户选择。
- 结算模板用 Excel 管理表头、列顺序、打印区域和签字区。
- 系统管理计价方式、明细来源、必传依据和异常规则。
- 上传模板后生成测试结算单和 PDF 预览，验收后发布。

## 7. 历史合同接管

### 7.1 A/B/C 风险等级

A/B/C 只表示接管风险，不表示合同是否完结：

- A 级：资料、金额和履约事实完整可信。
- B 级：存在少量缺口，但金额可核、风险可控。
- C 级：资料严重缺失、金额无法完全核实或存在争议。

合同是否履约中、已完结或已终止使用独立生命周期字段。

### 7.2 受限确认

历史合同允许受限确认：

- 可以建立期初合同、历史结算、历史已付和未付余额。
- 只有主体、金额和余额能够确认的部分可以继续流转。
- 无法核实或存在争议的金额硬拦截。
- 资料补齐后重新确认并解除限制。
- 原确认、补充和更正过程必须保留审计记录。

### 7.3 历史付款来源

接管形成的历史期初结算可以作为普通付款来源，但必须引用已确认或受限确认的接管事实，并保留原合同版本、付款条款和来源快照。

## 8. 合同变更和补充协议

合同变更和补充协议属于第一版 P0：

```text
创建变更草稿
  -> 形成新合同版本
  -> 合同审批
  -> 用印审批
  -> 上传签署件
  -> 归档确认
  -> 新版本生效
```

合同签订和合同变更的最终审批节点为董事长或总经理 OR 签。

## 9. 付款、报销和零星采购

### 9.1 普通付款来源

普通付款允许以下来源：

- 有效结算。
- 有效合同中的预付款条款。
- 已确认或受限确认的历史期初结算。

### 9.2 审批流程

普通付款：

```text
经办人发起
  -> 综合部主管
  -> 项目经理
  -> 财务总监
  -> 董事长或总经理
```

报销：

```text
申请人发起
  -> 综合部主管
  -> 项目经理
  -> 财务总监
  -> 董事长或总经理
```

零星采购：

```text
经办人发起
  -> 材料主管
  -> 项目经理
  -> 财务总监
  -> 董事长或总经理
```

付款审批不包含合同部和预算部节点。报销和零星采购第一版不按金额分级。

上述流程只适用于付款和支出。结算审批保持现有业务边界，不经过董事长或总经理；结算只有在审批通过、签章件上传并由合同主管确认归档后才生效。

### 9.3 审批与实付分离

- 审批通过只进入“已批准待付款”。
- 审批通过不预占、不扣减项目现金。
- 出纳先上传回单，文件进入待确认状态，此时不扣减现金。
- 出纳确认提交实付时，后端在数据库事务中重新检查现金余额、绑定回单文件、登记实付、写入现金流水并更新付款状态。
- 确认事务失败时不得扣款，已上传文件保持未绑定状态并进入后续清理或重新提交流程。
- 同一付款只能成功扣减一次。
- 补传或替换回单不能重复扣款。
- 冲销通过反向流水处理，不修改原现金流水。

## 10. 业主额度与项目现金池

### 10.1 项目承诺成本

业主有效合同金额形成项目承诺成本上限。承诺成本包括：

- 对外合同及合同变更。
- 未关联合同的零星采购。
- 未关联合同的报销支出。

合同结算和付款是履行已有承诺，不重复占用额度。

正常业务超过业主合同额度时硬拦截。确需超额时，必须取得董事长或总经理批准的专项超额授权。授权必须记录原因、额度、审批人和有效状态。

为防止并发审批突破上限，提交和最终批准时都必须在后端事务内重新计算。审批中和已批准但未作废的承诺都计入占用展示。

### 10.2 项目现金池

项目现金池由财务维护当前可用余额：

- 财务人员录入人工调整。
- 财务总监确认后生效。
- 录入人不能确认自己的调整。
- 每次调整记录调整前余额、调整金额、调整后余额、原因、人员和时间。
- 调整记录只能冲销，不能静默删除。

现金不足不阻断付款申请和审批，只在出纳确认实付时硬拦截。实付扣减必须与付款状态、回单文件和现金流水在同一业务事务中保持一致。

## 11. 组织和权限管理

第一版提供完整管理 UI，但不建设通用权限平台。

- 使用固定业务角色和固定权限项。
- 权限同时包含全局范围和项目数据范围。
- 超级管理员管理部门、人员和全局审批职务。
- 项目经理只能管理本项目成员和普通项目岗位。
- 项目经理不能授予董事长、总经理和财务总监等敏感角色。
- 权限变更必须二次确认并记录审计。

董事长和总经理可以同时拥有 `super_admin`，但技术管理身份与业务审批身份分离。超级管理员不能修改审批结果或绕过业务规则。

董事长或总经理可以终审自己发起的业务，但必须：

- 填写自审原因。
- 完成二次确认。
- 在审批记录和审计日志中明确标记“自审”。

其他角色不得审批自己发起或经办的业务。

## 12. COS 私有文件体系

### 12.1 当前状态

腾讯 COS 私有桶已经创建，桶安全配置已经人工核验，但应用尚未正式接入。应用接入属于第一阶段 P0。

### 12.2 上传流程

```text
前端上传文件
  -> 后端验证用户和业务权限
  -> 后端校验类型、大小和业务对象
  -> 后端上传 COS 私有桶
  -> PostgreSQL 保存文件元数据和版本
  -> 返回业务文件记录
```

### 12.3 下载流程

```text
用户申请下载
  -> 后端校验登录、角色和项目范围
  -> 记录敏感下载审计
  -> 生成短时有效访问链接
  -> 用户下载
```

### 12.4 存储职责

腾讯 COS 私有桶保存：

- 合同正文、签字件和合同附件。
- 结算依据、签章件和验收材料。
- 付款回单和财务凭证。
- 其他正式业务文件。

PostgreSQL 保存：

- 所属业务对象。
- COS Key。
- 文件名、类型、大小和哈希。
- 版本、上传人、上传时间和状态。
- 归档确认、作废和替换关系。

审计日志记录上传、替换、确认、作废和下载。

约束：

- COS 密钥只存在于服务端环境变量。
- Bucket 禁止公开读取和公开列举。
- 文件替换生成新 COS Key 和新版本，不覆盖原对象。
- 已确认文件不能直接删除，只能作废或上传新版本。
- COS 上传成功但数据库登记失败时必须清理孤立对象。
- Git 仓库只保存脱敏空白模板、字段说明和操作规范。
- Google Drive 和其他第三方网盘不参与正式业务存储。

## 13. 软件发布方式

软件发布采用轻量问题闭环，不建设 Go-Live 正式材料流程：

```text
用户收集问题或提出需求
  -> 审计现状并确认方案
  -> 小步实现和测试
  -> 用户实际体验验收
  -> 部署更新
  -> 检查生产健康状态
  -> 更新 PROGRESS.md
```

不要求：

- Go-Live 审批表或上线档案包。
- 董事长或总经理批准软件发布。
- 正式 UAT 签字台账。
- 将权限矩阵制作成签字文件。

发布仍必须满足最低技术安全条件：

- 相关测试、类型检查、Lint 和构建通过。
- 数据库迁移前完成备份。
- 更新后检查 Web、API、数据库和文件链路。
- 高风险更新具备明确回滚方式。
- Git 提交、部署日志和 `PROGRESS.md` 能追溯生产版本。

真实数据初始化清单只作为执行辅助，最终结果以 PostgreSQL 中的业务数据为准。权限关系通过组织权限管理 UI 和权限变更审计记录维护，需要时可以导出查看，不要求形成正式签字材料。

### 阶段 0：恢复可发布基线

- 收敛当前分支与 `main` 的发布主线。
- 修复现有 API 测试失败。
- 修复域名、HTTPS 和生产部署链路。
- 完成大额金额字段迁移。
- 接入 COS 私有桶。
- 补齐统一输入验证和中文业务错误。

验收：全量基础检查通过，生产域名可用，COS 上传下载闭环通过，大额金额不会溢出。

### 阶段 1：组织权限与真实业务基础

- 完成组织权限管理 UI。
- 完成业主主合同、承诺额度、超额授权和现金池。

验收：普通业务账号可以按项目范围工作，越权访问被拒绝，历史确认范围能够控制下游金额。

### 阶段 2：合同工作台与合同模板

### 阶段 3：结算工作台与结算模板

- 建立结算明细行和导入记录。

- 后端重算结算金额、累计金额和异常项。
- 完成审批、签章上传和归档确认。

验收：结算人员可从有效合同清单编制真实结算，错误能定位到行，审批稿和有效结算可追溯。

### 阶段 4：付款、报销和零星采购闭环

- 落实三类付款来源和已确认审批流。
- 完成回单上传后现金扣减。
- 完成现金不足、重复提交、超额授权和历史来源校验。
- 由用户收集真实使用问题，按小批次修正和发布。

验收：普通付款、报销和零星采购均可走到实付、回单、现金流水、财务记录和审计。

## 15. 针对性代码治理

不做全量重写，只治理进入当前业务链的高风险共享点：

- 将金额计算、额度占用和现金扣减集中到后端事务服务。
- 逐步收敛重复的审批动作和角色解析，不重写整个审批引擎。
- 建立单一 COS 文件存储服务，业务模块不得各自拼接 COS 逻辑。
- 按业务画布、动作面板和只读详情拆分超大页面。
- 页面只能通过 `apps/web-admin/src/api/` 调用后端，不直接 `fetch`。
- 继续使用 TDesign 和 `--jg-*` 设计 Token，不引入第二套 UI。
- 相似结构出现两次后评估复用，新增第三处前必须抽取共享组件。
- 每个切片以业务规则、验收标准和针对性测试为入口。

## 16. 测试与验收

以下内容必须有后端测试：

- 超 2100 万元金额和累计计算。
- 合同、结算和付款版本追溯。
- 历史接管确认范围和争议金额拦截。
- 项目数据隔离和权限变更。
- COS 上传、替换、过期链接和越权下载。
- 审批状态迁移和董事长、总经理 OR 签。
- 自审标记和自审原因。
- 回单重复提交和现金池原子扣减。
- Excel 导入错误定位和后端重算。
- 合同正文与结构化金额不一致。

Web 修改至少运行针对性 Vitest、`typecheck`、`lint` 和 `check:ui`。API 修改至少运行针对性 Jest、`typecheck` 和 `lint`。影响金额、权限、状态、归档、PDF 和审计的修改必须执行后端测试。

## 18. 明确结论

- 不推倒重来，采用局部治理。
- 不新增大技术栈，不引入通用低代码平台。
- 合同前台像文档工具，结算前台像表格工具，后台仍是业务账本。
- Office 文件负责正文和版式，系统负责结构化业务事实。
- COS 私有桶负责正式业务文件，Git 只保存脱敏模板和说明。
- 软件更新由用户反馈驱动，不建设 Go-Live 材料审批流程。
- 所有阶段都必须小步提交、独立验收并更新 `PROGRESS.md`。
