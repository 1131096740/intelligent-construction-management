# 建工智管合同工作台、资金与挂靠业务受控重构设计

日期：2026-07-28
状态：全项目体检的业务决策已逐项确认并锁定，待按五个实施包执行
范围：合同草稿工作台、清单价税、模板与签名、零星支付与全局资金、挂靠业务持续接管、历史合同接管、前后端能力矩阵、旧接口与小程序退役

## 1. 背景

当前合同工作台和历史合同接管已经具备大量前后端能力，但主流程出现了几类结构性问题：

- 合同台账携带精确合同版本进入工作台，后端却可能按合同自行选择另一份“最新可编辑版本”，导致已填资料消失并进入只读状态；
- 顶部“保存”只保存普通字段，清单使用另一套“保存全部”，用户无法确认一份草稿是否已经完整保存；
- 草稿删除入口与后端“放弃草稿”语义不一致，未提交纯净草稿无法按期望清理；
- Excel 模板税率的存储格式、合同默认税率和导入校验口径不一致；
- 页面显示的不含税单价精度与合同总价的计算顺序不统一，可能在大额合同中形成数元差异；
- 历史接管仍以单次确认直接生效为中心，不能表达合同部和财务部并行录入、分别确认；
- 一批后端能力没有前端入口，另有一批旧前后端接口已无页面调用，接口数量与实际业务能力不再一一对应。

本设计采用前后端业务编排重构、分阶段替换方案。它不推倒审批、权限、文件、审计、结算和付款底座，而是重新建立一条清晰的合同草稿聚合主线和历史接管聚合主线。

2026-07-28 全项目体检进一步确认：原生小程序不再建设；挂靠企业是项目施工
主体；我方签约业务与挂靠企业签约业务必须分轨；零星材料支付、零星费用
支付、项目资金来源、垫资额度、上游收款与扣款、合同资料规则、Word 版式和
标准条款必须纳入同一能力矩阵。本规格后半部分记录这些锁定规则，并继续
沿用原五个实施包，不另起一套彼此冲突的改造计划。

## 2. 目标

### 2.1 合同工作台

- 合同台账中的“继续办理”始终打开该行对应的精确合同版本；
- 顶部唯一“保存草稿”覆盖合同草稿中全部可编辑业务资料；
- 后台自动保存与顶部保存共用同一个后端保存模型；
- 左侧持续显示合同文档，右侧完成结构化资料编辑和资料检查；
- 清单、Excel、税率、页面汇总和合同文档使用同一套后端金额算法；
- 纯净草稿在日常界面按权限逻辑删除；物理清理由受控保留任务执行，正式流程事实和审计历史不可删除；
- 前端入口、前端 API 和后端业务接口形成可检查的一一对应关系。

### 2.2 历史合同接管

- 合同部和财务部在同一接管详情页并行办理；
- 两个部门拥有独立数据区、修订号、保存和确认动作；
- 双方确认后才激活合同并创建历史期初事实；
- 历史结算、实际付款、预付款和异常超付分别建模；
- 接管合同激活后可以正常发起新结算和付款申请。

### 2.3 资源控制

- 草稿只保留最新一份 DOCX 和 PDF 预览；
- 临时附件、Excel 导入文件和文档中间文件按明确期限自动清理；
- 自动保存幂等记录有明确 TTL，后台自动保存不会无限制造永久审计记录；
- 新旧流程不长期双写，不因兼容层持续制造重复数据和重复对象。

### 2.4 全项目业务闭环

- 区分我方签约付款、挂靠企业签约付款和上游资金事实，禁止签约主体与付款
  主体错配；
- 建立零星材料支付、零星费用支付、合同付款和垫资额度共同遵守的项目资金
  硬门禁；
- 普通经办人只选择业务场景，系统自动确定合同类型、资料规则和默认文件
  版式；
- 所有审批单使用审批人预先登记并按审批动作冻结的手写电子签名；
- 每个后端业务动作都必须归类为页面动作、内部动作、外部接管动作或待退出
  旧动作，不允许无归属路由长期存在；
- 原生微信小程序按共享依赖和生产数据门禁分阶段彻底退役，移动端统一使用
  响应式 Web。

## 3. 非目标

本轮不做：

- OCR 识别历史合同、结算单或付款凭证；
- Word 反解析并自动覆盖系统结构化数据；
- 多人按章节同时编辑同一份合同草稿；
- 替换现有审批引擎、项目岗位权限、审计、私有文件下载、结算和付款主链路；
- 在本轮同时重构全站合同履约状态存储和全部下游状态流转；本轮只统一工作台、台账和详情的状态读模型，写模型另行实施；
- 把电子签章、银企直联或发票系统扩入当前范围；
- 改写已生效合同、已归档文件或历史审批事实。
- 代替挂靠企业自身的合同、结算和付款审批；
- 把外部口头通知伪造成正式凭证；
- 用“预计发生金额”冒充无固定总价合同的法律金额上限；
- 新增合同例外额度或结算例外额度流程；
- 物理删除正式业务、审计、付款凭证或外部接管账本；
- 在未完成生产只读调用证明前直接删除共享认证、移动 Web 或正式读取路径。

## 4. 方案比较与决策

### 4.1 未采用：补丁式修复

只修复草稿丢失、税率和删除入口，改动小，但会继续保留双重保存、错误版本选择、单部门接管和接口遗留，后续仍需重复返工。

### 4.2 未采用：只重做前端

界面可以改善，但后端仍按旧语义读写，前端需要长期承担兼容、拼装和状态判断，不能根治数据丢失和半保存问题。

### 4.3 采用：前后端业务编排重构，分阶段替换

保留稳定底座，重建合同草稿聚合和历史接管聚合；新流程先上线验证，旧流程只作短期回退，确认无调用后删除。

## 5. 总体架构

```text
合同工作台
  -> 精确合同版本草稿聚合
      -> 全局草稿保存事务
          -> 字段、主体、清单、税率、条款、付款、附件关联
      -> 草稿文档预览任务
          -> 最新草稿 DOCX/PDF

历史接管详情
  -> 合同部数据区与确认
  -> 财务部数据区与确认
      -> 双部门确认门禁
          -> 合同版本激活
          -> 结算类历史期初结算 / 直接付款类合同容量
          -> 历史实付、预付款及风险余额
```

架构原则：

- `contractVersionId` 是合同草稿办理的唯一定位键；
- 资料保存是数据库原子事务，文档生成是独立异步任务；
- 金额、权限、状态转换和确认门禁都由后端决定；
- 前端使用后端返回的可用动作、禁用原因和字段定位信息；
- 同一业务记录不得同时由新旧接口写入；
- 审批、用印、签署、归档、结算和付款继续复用现有正式服务。

## 6. 合同工作台前端

### 6.1 桌面布局

保留用户认可的“左边看文档、右边填资料”双栏结构。

顶部固定区域展示：

- 返回合同台账；
- 合同名称、临时编号或正式编号；
- 当前状态；
- 正在保存、已保存或保存失败；
- 最后保存时间；
- 唯一的“保存草稿”按钮；
- “提交审批”按钮及禁用原因。

左侧文档区：

- 展示最近一次成功生成的草稿文档；
- 支持 PDF 在线查看和 DOCX 下载；
- 明确区分“资料保存状态”和“文档预览状态”；
- 资料修订更新后显示“预览待更新”；
- 生成失败时保留上一份可用预览并提供重试入口。

右侧资料区内部使用窄竖向章节目录和当前章节表单。

章节目录为：

1. 资料检查
2. 基本信息
3. 合同主体
4. 专业字段
5. 清单与价税
6. 结算付款
7. 合同条款
8. 附件与资质
9. 磋商与文档
10. 流程记录

每个章节显示完成标记或问题数量。“资料检查”汇总必填项、金额和价税差异、清单错误、附件缺项、条款问题及送审准备状态。点击问题必须切换到对应章节，并聚焦具体字段或清单行。

“流程记录”只读展示审批、用印、签署、归档、版本和审计摘要，不在草稿表单中混入正式流程操作。

### 6.2 移动端和窄屏

- 不将左右两栏强行压缩；
- 顶部提供“合同资料”和“文档预览”切换；
- 资料页的章节目录可收起；
- 保存状态和“保存草稿”始终可见；
- 所有业务规则与桌面端共用同一 API。

### 6.3 页面行为

- 切换右侧章节不会丢失本地内容；
- 离开工作台前立即执行全局保存；
- 保存失败时阻止离开并显示准确原因；
- 不提供“放弃修改并离开”；
- 浏览器被强制关闭时，使用最后一次服务端自动保存和账号、设备、草稿、修订隔离的本地副本提示恢复；
- 本地副本不是权威草稿，成功保存、删除草稿或正式提交后必须清理。

本地副本只保存结构化草稿，不保存附件字节、租约 token、密码、下载地址或
COS 对象键；按账号、设备、项目、合同版本和服务端修订号隔离，24 小时过期，
退出登录时清理。恢复前必须先读取服务端最新修订，不能把旧副本静默覆盖到
新草稿。

## 7. 全局保存

### 7.1 一个保存模型

顶部“保存草稿”和后台自动保存调用同一个后端保存服务。一次保存覆盖当前草稿所有已变更资料：

- 基本信息和专业字段；
- 合同主体及附件关联；
- 清单行、行顺序和计税信息；
- 结算付款约定；
- 合同条款；
- 附件与资质关联；
- 磋商及文档引用信息。

后端在一个事务中校验并写入。任一分区失败时，整次资料保存不提交，禁止形成“基本信息已保存、清单未保存”的半成品。

请求必须携带：

- 精确 `contractVersionId`；
- 当前草稿修订号；
- 本次保存幂等标识；
- 当前编辑租约标识；
- 发生变化的资料分区。

请求始终携带完整权威快照。`changedSections` 只用于诊断和性能提示，服务端
必须根据锁定后的数据库事实自行计算实际变化，不能因客户端漏报分区而丢失
修改或跳过校验。服务端按稳定业务 key 只写实际变化的行；完整快照不等于
每次自动保存都重建整张 1000 行清单。无实际变化时不增加修订和业务审计。

响应返回：

- 新草稿修订号；
- 服务端保存时间；
- 各章节问题数量；
- 资料检查结果；
- 文档是否过期；
- 当前可用动作和禁用原因。

### 7.2 后台自动保存

- 用户停止输入约 2 秒后自动保存；
- 首次编辑即可保存到服务器，不等待第一次手动保存；
- 自动保存只保存结构化资料，不生成 DOCX/PDF；
- 自动保存失败后保留本地内容并允许重试；
- 修订冲突或编辑租约失效时不得静默覆盖。
- 保存请求发出时冻结本次快照，并区分本地编辑代次、已发送代次和已确认代次；
  旧响应只能更新对应代次的服务端修订，不能覆盖请求发出后的新输入。
- 输入处于暂时不可序列化状态时保持本地 dirty，不发送必然失败的请求；离开
  页面时仍必须修正或明确被阻止。

### 7.3 顶部“保存草稿”

点击后：

1. 取消等待中的自动保存；
2. 全局提交当前全部修改；
3. 等待资料事务成功；
4. 创建当前修订的文档预览任务；
5. 显示“资料已保存，正在更新预览”；
6. 文档生成成功后刷新左侧预览。

顶部保存只覆盖当前权威草稿，不创建可恢复检查点。后台自动保存也不创建版本。现有检查点创建、恢复和最近五份检查点能力退出新主流程。

### 7.4 合同编号

- 草稿阶段只使用临时编号；
- 后台自动保存和顶部“保存草稿”都不得提前分配正式合同编号；
- 提交审批时，后端先完成全局保存和送审就绪检查；
- 只有审批实例成功创建并冻结送审快照时，才在同一受控流程中分配正式合同编号；
- 分配结果写入合同版本和审批冻结快照，页面随后显示正式编号；
- 送审失败不得留下“已有正式编号但没有审批实例”的半成品。
- 送审请求必须携带当前 `expectedRevision`、编辑租约 token 和提交幂等键；
  网络重试返回第一次成功的审批实例和正式编号，不重复创建审批或消耗编号。

### 7.5 并发和编辑租约

- 同一草稿同时只允许一个编辑会话；
- 其他人员进入时只读；
- 合同部主管可以二次确认后接管编辑权；
- 接管后原会话立即变成只读；
- 所有写入接受草稿修订号和编辑租约双重校验；
- 冲突时保留本地未保存内容，返回服务器最新修订和冲突原因，不自动合并金额、清单或附件。
- 前端按 30 秒心跳维持 120 秒租约；页面从后台恢复时立即核验，租约自然
  失效后只允许显式重新取得，不能自动接管其他会话。
- 原始租约 token 只保存在当前页面内存中，不进入本地恢复副本、日志、审计或错误。

## 8. 文档生成和存储

### 8.1 任务语义

- 资料保存事务和 DOCX/PDF 生成任务分离；
- 资料保存成功后不因文档生成失败而回滚；
- 相同合同版本、相同草稿修订只允许一个生成任务；
- 新修订到来时取消尚未开始的旧任务；
- 已经执行的旧任务可以结束，但不得覆盖更新修订的预览；
- 失败时保留上一份可用预览并允许重试。

### 8.2 草稿预览保留

- 草稿阶段只保留最新一份 DOCX 和一份 PDF；
- 新预览生成成功并完成数据库指针切换后，才删除上一份草稿预览；
- 审批冻结稿、双方签署稿和正式归档文件永久保留；
- 草稿保存不产生额外文档历史。

### 8.3 临时文件清理

- 未关联业务记录的待关联附件：24 小时后删除；
- Excel 导入原文件和预检结果：保留 7 天后删除；
- DOCX/PDF 转换中间文件：任务结束后立即清理；
- 清理任务保留轻量审计收据，不保留文件副本；
- 已关联正式附件、付款凭证、审批冻结稿和归档文件不得进入临时清理。
- 草稿保存幂等请求记录保留 7 天后清理；手动保存保留业务审计，后台自动
  保存只保留短期技术收据和最新保存人/时间，不逐次写永久 AuditLog。

跨数据库和 COS 的删除使用可重试的清理任务。只有数据库记录、对象删除和审计收据均完成时，才报告清理成功。

## 9. 合同主体

- 草稿提交审批前，经办人可以新增、修改角色、替换资料或删除合作单位；
- 工作台支持从合作单位档案选择具体版本，也支持只用于本合同的临时快照；
- 档案引用和临时快照必须在页面上明确区分；
- 提交审批后合同主体快照锁定；
- 后续修改必须通过合同变更或补充协议产生新版本；
- 新工作台通过全局保存写入合同主体，不再保留“只能新增、不能修改或删除”的页面逻辑。

## 10. 清单、税率和金额

### 10.1 唯一权威算法

手工录入、Excel 导入、页面汇总、DOCX/PDF 生成全部调用同一套后端金额计算器。

每一行固定按以下顺序计算：

```text
含税总价 = 数量 × 含税单价，四舍五入到分
不含税总价 = 含税总价 ÷（1 + 税率），四舍五入到分
税额 = 含税总价 - 不含税总价
不含税单价 = 不含税总价 ÷ 数量，四舍五入保留 6 位小数
```

合同汇总只累加权威行总价：

- 合同含税总价等于各行含税总价之和；
- 合同不含税总价等于各行不含税总价之和；
- 合同税额等于合同含税总价减合同不含税总价；
- 不得用页面显示的两位不含税单价重新乘数量。

数量、单价和税率使用十进制定点数，不使用 JavaScript 浮点数。行总价、合同总价和税额精确到分。不含税单价内部保留 6 位，页面默认显示 2 位，悬停或展开时显示完整 6 位。

### 10.2 单一税率

- 合同草稿税率是唯一权威来源；
- 下载模板时自动写入并锁定税率；
- 模板不要求用户重复填写税率；
- 导入时使用合同默认税率；
- 合同税率变化后，旧模板标记为过期并要求重新下载。

### 10.3 特殊多税率

- 合同税率作为默认值；
- 只有例外清单行允许指定其他税率；
- 未填写例外税率的行继承合同默认税率；
- 导入预检必须列出全部例外行和税率。

### 10.4 Excel 模板和导入

- 税率 9% 在 Excel 中存储为数值 `0.09`，显示为 `9%`；
- 禁止把整数 `9` 和百分比 `9%` 混用；
- 隐藏元数据记录模板版本、合同版本、清单标识和税率快照；
- 公式使用与后端相同的“总价优先”顺序；
- 导入只执行预检，不直接写数据库；
- 预检展示新增、修改、删除、税率异常和金额差异；
- 用户确认后把候选清单载入当前前端草稿；
- 最终由顶部“保存草稿”与其他资料一并写入。

合同部提供的实际 Excel 必须成为发布前固定回归样本。验收需输出逐行差异，解释现有约 5 元差异来自哪些行和哪种舍入顺序，并证明系统、模板、导入结果和合同文档一致到分。

## 11. 合同状态

### 11.1 前端单一当前状态读模型

合同生效前显示办理进度：

```text
草稿编制
-> 待审批
-> 审批中
-> 待用印
-> 待双方签署
-> 待归档确认
```

合同归档生效后显示履约状态：

```text
未开始
履约中
已暂停
已完成
已终止
```

存在争议、异常超付和资料缺失作为独立风险标记，不作为主状态。

### 11.2 履约状态权限

- 合同经办人可以更新未开始、履约中和已暂停；
- 已完成和已终止需要合同部主管确认；
- 已完成合同不再发起正常履约结算；
- 已终止合同只能进入终止清算或更正流程；
- 状态变化保留操作人、时间和原因。

后端仍可保留流程状态、归档状态和履约状态等必要维度，但台账只展示一个当前
状态和一个下一步动作。本轮通过读模型投影统一展示，不在草稿聚合包内同时
新增全站履约状态写接口。

## 12. 草稿删除

### 12.1 草稿分类

后端区分：

- 纯净草稿：从未提交审批、没有正式流程事实；
- 审批草稿：曾提交、退回、驳回或撤回；
- 正式合同记录：已进入用印、签署、归档或生效。

这些分类用于权限和删除门禁，不额外作为一套面向用户的状态。

### 12.2 纯净草稿日常删除

- 当前经办人可以逻辑删除自己的纯净草稿；
- 合同部主管可以逻辑清理本部门纯净草稿；
- 主管代删必须填写原因并验证当前密码；
- 删除请求携带精确草稿修订号；
- 只有服务端重新确认仍为纯净草稿后才进入不可编辑、列表隐藏的 tombstone。

日常删除不立即跨数据库和 COS 物理清除。受控保留任务在宽限期后重新检查
审批、正式文件、归档、结算、付款、共享文件和其他版本依赖；只有全部为零且
取得首次启用或专项清理授权后，才物理清理合同草稿及版本、字段、主体快照、
清单、付款条款、条款、临时附件关联、草稿预览和未转为正式证据的 COS 对象。

只保留最小删除收据：删除人、时间、草稿标识摘要、原因和删除结果，不保留合同正文或附件副本。

### 12.3 已进入流程的记录

- 曾提交审批的合同不能物理删除；
- 驳回、撤回或终止后进入“已结束”；
- 审批记录、意见、冻结快照和正式文件保留；
- 可以按保留策略清理可再生成的临时文件和过期预览；
- 正式合同及历史事实不得通过草稿删除入口清除。

## 13. 历史合同接管

### 13.1 页面和并行办理

同一接管详情页分为：

- 合同资料区：合同员录入，合同部主管确认；
- 历史付款区：财务人员录入，财务主管确认。

双方可以并行办理，都能查看整体进度和对方已保存的只读摘要，只能修改本部门数据。

两个区域分别拥有：

- 独立修订号；
- 独立后台自动保存；
- “保存本部门资料”；
- “确认本部门资料”；
- 独立保存状态和确认记录。

一方保存不得覆盖另一方数据。离开页面前只检查当前用户负责区域的保存状态。
两侧自动保存都携带短期幂等键，使用各自 revision 做 CAS；技术收据 7 天后
清理，网络重试不能重复增加修订或永久审计。

### 13.2 合同部数据

合同部录入：

- 合同编号、名称、项目和合同类型；
- 合同相对方和签订日期；
- 原始签约金额；
- 当前履约状态；
- 历史累计结算总额；
- 一份或多份历史结算和确认资料；
- 后续结算付款所需的合同基本约定。

只录入历史累计结算总额，不逐份登记历史结算。

### 13.3 财务部数据

财务逐笔录入已经实际支付的历史款项：

- 实付日期和金额；
- 收款单位；
- 付款方式及流水说明；
- 一份或多份付款凭证；
- 必要备注和异常说明。

一份凭证只归属于一笔实付记录，一笔实付可以关联多份凭证。

没有历史付款时，财务必须提交明确的“历史实付为零”声明，不能以空白代替确认。

旧系统中的待审批、已批准未支付或其他尚未实际付款申请不迁移。财务确认时必须声明旧申请已经停止，未付款事项在新系统重新申请。

### 13.4 双部门确认

- 两个部门主管分别确认；
- 确认后锁定本部门数据区；
- 正式激活前，主管可以填写原因撤回本部门确认；
- 任一方撤回后双确认门禁关闭；
- 激活后不得直接撤回，只能发起带原因、附件和审计的更正流程；
- 双确认同时成立时只允许执行一次幂等激活。
- 财务侧保存和确认必须记录其所依据的合同侧修订号；
- 合同侧修改累计结算、付款条款或其他影响财务分类的字段时，财务侧确认必须
  失效并重新确认；不影响财务判断的合同字段变化才允许保留财务确认；
- 财务保存仍记录当时看到的合同侧完整修订号用于追溯，但激活门禁比较的是
  `financeBasisRevision`；合同侧非财务字段变化并重新确认后，只要财务 basis
  未变化，已有财务确认可以继续有效。

### 13.5 激活结果

双确认成功后，后端在事务中：

1. 创建或激活历史合同版本；
2. 对结算类合同创建一笔历史期初结算，金额等于历史累计结算总额；通用直接
   付款合同不得为了兼容而伪造结算；
3. 对结算类合同挂接合同部历史结算资料；直接付款合同冻结其固定金额或无
   固定总价性质；
4. 激活逐笔历史实付事实并挂接唯一权威凭证绑定；
5. 结算类历史实付占用历史期初结算；直接付款历史实付占用合同固定金额，
   无固定总价时只累计展示；
6. 结算类计算历史结算未付款差额；固定金额直接付款类计算合同剩余金额；
7. 形成历史预付款余额或异常超付风险；
8. 根据录入事实设置合同履约状态；
9. 写入完整接管审计记录。

历史结算未付款差额或固定金额合同剩余金额只表示上限，不自动等于当前可付款
金额。后续每次付款仍需填写申请金额和依据，并重新走完整付款审批。无固定
总价直接付款合同不使用虚构剩余差额，但继续展示累计风险并执行项目资金
硬门禁。

历史实付是已发生事实，不伪造成普通待审批付款申请，也不补造审批实例。统一
付款台账通过 `sourceType=historical_takeover` 的只读投影展示这些事实；新发生
的付款继续使用普通 `PaymentRequest -> PaymentExecution` 链路。

### 13.6 历史实付超过结算

对于结算类合同，如果历史累计实付大于历史累计结算：

- 默认阻止财务最终确认；
- 财务必须将超出部分选择为历史预付款或异常超付；
- 必须填写说明并上传依据；
- 财务主管确认后才允许完成财务侧确认；
- 系统不得自动修改合同部确认的历史累计结算金额。

对于固定金额直接付款合同，历史累计实付超过合同有效金额同样进入异常超付
分类；无固定总价直接付款合同不因缺少合同总额形成异常超付，但每笔历史实付
仍须逐笔登记和确认。

激活后：

- 历史预付款形成独立余额，后续有效结算自动抵扣；
- 异常超付形成合同风险标记；
- 异常解除前禁止新的付款申请；
- 更正或主管解除必须保留原因、依据和审计。

历史预付款采用不可变余额流水：期初、抵扣、反向更正和主管确认后的调整均
追加新记录，不覆盖原实付或原凭证；同一结算、同一来源和同一幂等键只能抵扣
一次。异常超付更正同样以 delta/reversal 记录生效，不能只修改父表累计字段。

### 13.7 激活后的业务

- 结算类合同可以发起新的正常结算；
- 结算类合同可以针对历史期初结算未付款差额分多次发起付款申请；
- 结算类合同可以针对后续新结算发起付款申请；
- 通用直接付款合同按固定金额或无固定总价规则直接发起付款申请，不伪造结算；
- 所有新付款使用正常审批、实付、凭证和财务入账流程；
- 历史付款作为已发生事实，不重新审批；
- 已结束历史合同保留查询和更正，不继续发起正常履约业务。

## 15. 数据模型调整

合同草稿需要明确：

- 当前经办人；
- 编辑租约和租约修订；
- 全局草稿修订号；
- 章节化草稿数据；
- 当前预览对应草稿修订；
- 最新成功预览文件指针；
- 保存幂等记录；
- 草稿生命周期分类。

历史接管需要明确：

- 合同部数据修订和确认记录；
- 财务部数据修订和确认记录；
- 财务侧所依据的合同侧修订号；
- 逐笔历史实付；
- 一对多付款凭证；
- 合同侧结算依据和异常超付依据的独占文件关联；
- 零付款声明；
- 历史预付款不可变余额流水；
- 异常超付事实、delta/reversal 更正和风险解除；
- 双确认激活幂等标识；
- 结算类历史期初结算关联或直接付款类合同容量关联。

保存幂等记录必须有过期时间和清理索引；历史付款凭证只有一个权威业务绑定，
任何只读投影只能引用事实或凭证记录 ID，不能把同一 `fileId` 再绑定到另一
业务表。

金额继续使用数据库定点数和分值边界，不使用浮点数。

## 16. 错误处理

后端返回稳定业务错误类型，包括：

- 草稿修订冲突；
- 编辑租约失效；
- 字段或附件校验失败；
- 清单具体行列错误；
- Excel 模板过期；
- 税率或金额计算异常；
- 文档生成失败；
- 历史接管另一方数据变化；
- 历史实付超额但未分类；
- 异常超付付款门禁；
- 草稿不满足物理删除条件。

校验错误携带章节、字段或清单行定位信息。前端不暴露数据库字段、内部枚举、堆栈或 COS 地址。

## 17. 前后端能力矩阵

每个业务动作必须登记：

| 字段 | 要求 |
|---|---|
| 业务动作 | 使用业务语言命名 |
| 前端入口 | 明确显示条件或明确声明无需入口 |
| 前端 API | 有唯一封装 |
| 后端路由 | 有唯一业务语义 |
| 权限 | 后端强制 |
| 后端测试 | 覆盖状态、权限和失败路径 |
| 页面测试 | 覆盖入口和禁用原因 |

构建检查需要发现：

- 前端调用不存在的后端路由；
- 后端新增业务动作却没有声明前端入口策略；
- 页面绕过后端 `availableActions` 自行放行；
- 已迁移业务仍在调用旧接口。

## 18. 迁移和遗留接口退出

### 18.1 分阶段替换

第一阶段：

- 先生成当前能力矩阵、生产只读数据形态报告、文件绑定目录和真实 Excel 回归；
- 新增前向数据库结构和新接口；
- 旧页面只作短期回退；
- 对现有草稿执行只读迁移预检；
- 不修改正式合同和历史财务事实。

第二阶段：

- 迁移能够确定映射的草稿；
- 新工作台只调用新接口；
- 已迁移草稿禁止旧接口写入；
- 冲突草稿保留原记录只读并进入人工清单。

第三阶段：

- 使用至少 3–5 份真实合同验证新建、保存、预览、送审、接管、结算和付款；
- 核对数据库、COS 对象和审计记录；
- 结合静态能力矩阵和生产旧路由调用证据确认没有旧客户端后，先关闭旧写和
  保留旧表只读；物理删表延后到独立前向清理阶段。

### 18.2 旧草稿

- 上线前自动预检；
- 能安全映射的字段、清单、条款和附件自动迁移；
- 无法确定的数据列入人工处理清单；
- 迁移失败保持原记录只读，不产生半迁移记录；
- 正在审批、已生效及已归档合同不通过草稿迁移改写。

### 18.3 计划退出的能力

验证完成后删除：

- 按合同 ID 自行寻找最新草稿的读取方式；
- 旧草稿列表、软作废和恢复接口；
- 草稿检查点创建和恢复；
- 清单逐行独立保存、删除和排序接口；
- Excel 独立应用写入接口；
- 只新增但不能修改或删除的合同主体页面逻辑；
- 历史接管单次确认直接生效逻辑；
- 无页面调用的旧前端 API 封装。

审批、用印、签署、归档、文件权限、审计、结算和付款正式接口继续保留。

### 18.4 迁移门禁

生产迁移前必须完成：

1. 最新数据库备份及可恢复性检查；
2. 现有草稿、附件和接管记录只读盘点；
3. 自动映射报告和人工冲突清单；
4. 隔离恢复库迁移演练；
5. 迁移前后记录数、金额、附件和修订指纹对比；
6. 明确回退版本、回退条件和负责人。

任何迁移不得静默舍弃字段、清单行、附件或金额。生产迁移、真实数据修改、文件清理和部署仍需分别获得明确授权。

## 22. 当前结论

原合同工作台和历史接管部分已完成第一轮审计修订。以下第 23–29 节是全项目
体检后逐项确认的扩展决策，与前述规则共同构成实施基线；出现冲突时，以后
补充且更具体的规则为准。

## 23. 项目主体、挂靠企业与业务分轨

### 23.1 项目与挂靠企业

- 每个项目原则上且在系统中强制只对应一家挂靠企业；
- 项目的实际经营归属我方，但施工主体、与业主签约主体为挂靠企业；
- 业主与挂靠企业签订业主主合同；
- 挂靠企业可以直接与供应商、分包商或班组签约并付款，也可以先与我方签约，
  再由我方与实际相对方签约付款；
- 实际付款主体必须与对下合同签约主体一致：挂靠企业签约的合同只能由挂靠
  企业付款，我方签约的合同只能由我方付款；后端必须在合同、结算、付款和
  实付事务中硬性检查，不依赖前端提示。

### 23.2 业主主合同

- 系统只登记已经在线下签完的业主主合同；
- 合同人员上传，合同主管确认，不进入我方合同审批和用章流程；
- 主合同用于项目总控和风险比较，不把挂靠企业签约主体伪造成我方；
- 尚未登记主合同，或者我方对下合同累计金额超过主合同有效金额时，不绝对
  阻断我方对下合同；
- 系统必须醒目标示缺失、超额金额和风险，董事长或总经理在最终审批时明确
  确认；
- 不再设置“合同例外额度”流程。

### 23.3 挂靠企业签约并付款的对下业务

- 彻底取消我方合同、结算和付款审批；
- 改为“挂靠业务持续接管”：外部已经完成的合同、结算和付款文件是业务依据；
- 我方只做按岗位录入、核对确认、不可变账本和审计，不补造我方审批实例；
- 外部文件可以晚于事实补齐；没有正式凭证时可以记录口头通知，但必须明确
  标记依据类型，不能生成虚假文件或虚假签字；
- 已确认记录不得覆盖；更正使用 delta/reversal 或等价追加事实；
- 挂靠企业签约对象、结算对象和付款对象必须一致，且不得从我方资金账户
  执行实际付款。

### 23.4 我方签约并付款的对下业务

- 继续保留合同审批、我方用章、正式归档、结算审批、付款审批、实际付款、
  凭证和审计完整流程；
- 这类业务没有外部系统替我方完成审批，不能降级为接管台账；
- 正常付款是否必须结算，按第 25 节锁定的合同类型判断；正式合同预付款是
  明确例外。

## 24. 上游结算、资金流入和挂靠扣款

### 24.1 业主对挂靠企业的上游结算

- 上游结算由挂靠企业或业主决定，我方没有审批权；
- 项目预算人员录入并确认外部结算事实；公司没有预算主管岗位，不设置无人
  可办的预算主管强制节点；
- 同一项目预算人员可以完成录入和确认，保留密码、签名和审计；
- `budget_director` 不再作为当前业务必需岗位，实施前审计全部引用后合并到
  项目预算人员或退出旧岗位；
- 上游结算文件是依据，不把确认动作包装成我方审批。

### 24.2 业主向挂靠企业实际付款

- 逐笔记录金额和日期，作为项目上游资金事实；
- 该资金未进入我方账户，不增加我方项目可用资金；
- 公司财务人员负责录入和确认；
- 有正式凭证时，财务人员或财务主管均可确认；
- 只有口头通知时，财务人员可以录入，财务主管最终确认；财务主管本人录入
  时允许同人确认，但必须执行独立确认动作；
- 页面和报表必须把“书面依据”和“口头通知”分开显示。

### 24.3 挂靠企业向我方拨款

- 这是我方真实项目资金流入，计入我方项目可用资金；
- 不硬性要求先完成挂靠企业与我方结算，可以先记录到账，后续再核对归属；
- 项目正常收款来源只保留“挂靠企业向我方拨款”；
- 删除“业主直接向我方付款”和泛化的“其他收款”新建路径；历史记录只读
  保留；
- 业主向挂靠企业付款与挂靠企业向我方拨款是两笔不同事实，报表禁止重复
  计入我方收入或可用资金。

### 24.4 挂靠企业扣款

- 独立记录管理费、税费、保证金、保险费和其他费用；
- 有书面依据时，财务人员或财务主管均可确认；
- 只有口头通知时，财务人员录入、财务主管确认；财务主管可以录入后执行
  独立确认；
- 单纯“应收与到账差额”不得自动转成成本或扣款，先进入待核对差额；
- 后续确认扣款类型时追加分类或更正记录，不覆盖原到账事实。

## 25. 合同类型、结算前置和金额性质

### 25.1 用户只选择业务场景

- “合同类型”是后端稳定分类，用于编号、审批、结算、付款、权限和统计；
- “业务场景”是经办人看到的入口；
- 每个业务场景固定归属于一个合同类型；
- 经办人只选择业务场景，系统自动确定合同类型、合同资料与规则和默认文件
  版式；
- 页面不再要求经办人重复选择合同类型或输入模板版本 ID；
- 挂靠企业外部完成、系统仅持续接管的合同不走模板生成选择。

### 25.2 六类合同

系统保留或新增以下稳定类型：

1. 材料采购合同；
2. 工程机械设备租赁合同；
3. 劳务分包合同；
4. 专业分包合同；
5. 通用结算类合同；
6. 通用直接付款合同。

前五类正常付款必须来自已生效结算；正式合同中冻结的预付款约定是结算前
唯一常规例外。通用直接付款合同不办理结算，按合同约定直接发起付款审批。
不得再以模糊 `generic_contract` 自动绕过结算；旧 `generic_contract` 先盘点，
能确定的迁入两类通用合同，不能确定的作为历史待分类合同只读保留。

合同类型在提交审批时冻结，改变类型必须走合同变更或补充协议。

### 25.3 固定金额与无固定总价

通用直接付款合同支持两种金额性质：

- **固定金额／最高限额：** 必须登记有效金额；审批中、已批待付和已实际支付
  的累计占用不得超过有效金额；超过时硬阻断，必须先完成合同变更；
- **无固定总价：** 适用于只约定单价、期限、计费方式或按实际发生支付的
  合同；不虚构法律金额上限。

无固定总价合同每次付款必须填写付款事项和金额计算说明；页面同时展示累计
申请、累计批准、累计实付和本次付款后的累计金额，并向董事长或总经理醒目
提示“无固定总价”。项目可用资金和垫资额度仍然硬阻断。

可以选填“预计发生金额”用于项目测算，但它不是合同金额、付款上限或可用
资金。金额性质提交审批后冻结，改变性质必须走合同变更。

## 26. 零星材料支付、零星费用支付和全局资金

### 26.1 分类和金额门禁

- 同一张材料申请单按全部材料合计金额判断；
- 合计金额大于等于 3000 元，必须走材料采购审批，不得拆行或拆单后转成零星
  材料支付；
- 合计金额小于 3000 元，属于零星材料支付，只走付款审批；
- 零星费用支付覆盖服务、临时机械台班、零星用工和其他非材料临时费用；
- 零星费用支付必须关联具体项目，不设金额上限；
- 系统发现材料类申请达到 3000 元时硬性阻止并要求重新提交正确流程，不自动
  篡改或迁移原审批单；
- 支撑附件在零星材料支付和零星费用支付中均为选填，不把没有附件等同于
  不得提交。

### 26.2 零星材料支付办结

- 实际付款和收货可以任意先后；
- 材料员即发起经办人负责收货，可以按既有受控规则委托同项目人员；
- 收货必须上传收货照片，差异、委托、复核和退款保留可追溯事实；
- 只有实际付款和收货两项都完成后才允许办结；
- 发票是否到位不影响办结，发票继续作为后续独立记录；
- 零星费用支付在实际付款完成后即可办结，不创建虚假收货任务。

### 26.3 全项目统一资金规则

- 合同付款、零星材料支付、零星费用支付、报销补付和其他我方实际资金支出
  共同使用项目资金可用性服务；
- 支付审批通过不锁定垫资额度；只有实际支付完成并上传支付凭证后，才锁定
  对应资金来源和垫资额度；
- 实际支付事务必须重新计算可用资金，额度不足时硬性阻止；
- 退款、更正和终止使用不可变资金流水，不删除原支付；
- 支撑文件、付款凭证、签约主体、付款主体和资金来源必须在同一事务中校验。

### 26.4 项目垫资额度

- 保留现有后端能力并补齐完整页面入口；
- 财务人员或财务主管可以发起；
- 财务主管审批；财务主管本人发起时允许执行独立的本人审批动作；
- 董事长或总经理 OR 签最终审批；
- 项目经理不进入该审批链；
- 有自有资金时先自动分配自有资金，再使用垫资额度；
- 有效期选填，不要求必须设置；
- 增加人工终止路径；终止后禁止新的额度占用，历史占用和流水不删除；
- 删除结算例外额度模型、页面和接口；下游结算超过上游只警示并审计，不用
  额度放行，合同有效金额上限仍按其自身规则控制。

## 27. 模板、版式、标准条款和审批签名

### 27.1 两类模板

- “业务模板”在产品界面改称“合同资料与规则”，定义字段、清单、条款、
  附件要求和校验；
- “合同版式版本”改称“合同文件版式”，定义 DOCX/PDF 的段落、表格、字体、
  页眉页脚、占位符和签章位置；
- 两者底层独立版本化；样式变化不得改写业务含义，业务规则变化不得静默
  改写历史文件；
- 一套资料规则可以关联多个兼容版式，但只能有一个默认版式；
- 发布时校验字段、条款、清单和 Word 占位符兼容性。

### 27.2 业务场景映射

- 每个“业务场景＋合同类型”同一时刻只能有一套生效的合同资料与规则；
- 同时绑定一个默认文件版式，可以绑定若干兼容备选版式；
- 取消经办人多模板推荐列表、优先级选择和人工版本 ID；
- 合同主管维护映射；`super_admin` 只读排查，不拥有业务配置权；
- 替换映射保留历史，不改写已创建草稿和历史合同；
- 缺少已发布资料规则时，硬性禁止创建新合同草稿；
- 资料规则存在但没有可用默认版式时，允许保存资料草稿，但禁止生成正式
  文件和提交审批。

### 27.3 停用语义

- 保留资料规则、文件版式、标准条款和结算模板的“停用”；
- 删除资料规则和文件版式重复的“撤销发布”路由和前端封装；
- 因新版本发布而自动停用时，现有草稿保留冻结旧版本并提示升级；提交前必须
  升级，或由合同主管明确确认继续使用旧版本；
- 因错误或合规风险手动停用时，所有未提交草稿硬性禁止提交，必须更换；
- 已进入审批、已签署和已生效合同不自动改写，分别走退回、终止或合同变更；
- 标准条款同一条只允许一个当前有效版本；发布新版自动停用旧版；合同主管
  可以停用整条条款；
- 不提供恢复旧发布版本路径；需要重新使用时复制为新草稿并重新提交发布；
- 未提交、未引用的纯净模板或条款草稿仍可以废弃。

### 27.4 全项目手写电子签名

- 所有审批单使用审批人预先创建的手写电子签名；
- 电脑端创建签名时生成一次性二维码，审批人用手机扫描后横屏签名；
- 手机端打开时可以直接横屏签名；
- 签名保存为不可变版本，审批动作冻结精确签名版本和文件摘要；
- 不得在审批 PDF 生成时读取用户“当前签名”覆盖历史；
- 缺少有效签名时阻断审批动作，并引导先完成签名；
- 密码确认、签名冻结、审批动作和审计必须属于同一受控事务。

## 28. 前后端能力清理和小程序退役

### 28.1 能力矩阵分类

每个后端业务路由必须属于以下一种：

1. 有页面入口的用户动作；
2. 明确无需页面的内部命令、回调或任务；
3. 外部完成后由我方录入确认的接管动作；
4. 有生产调用证据、处于迁移宽限期的旧动作；
5. 已满足零调用门禁、应删除的旧动作。

前端 API 封装必须有真实页面、composable 或测试消费者；同一路由不得保留多个
同义封装。构建检查必须同时发现“按钮调用不存在路由”“无消费者封装”和
“未声明入口策略的后端业务路由”。

### 28.2 已确认退出集合

满足静态调用矩阵和生产只读零调用门禁后退出：

- 旧合同草稿列表、旧软作废和旧恢复接口，不保留恢复旧草稿路径；
- 草稿检查点创建、恢复和对应旧写代码；先只读隔离，物理清理属于 Release C2；
- 合同清单逐行新增、修改、删除、排序四套写接口，改由聚合保存；
- 旧 `/me/workbench-summary`；
- 旧合同生命周期台账和旧结算生命周期台账；
- 前端重复别名 `createContractDraft`、`submitContractApproval`，保留新工作台
  唯一封装及其仍在使用的后端路由；
- 旧直接 `POST /settlements` 及其前端封装，统一使用结算草稿工作台；
- 合同资料规则和合同文件版式的 `revoke` 路由、服务分支和前端封装；
- `owner_direct_payment`、泛化 `other` 项目收款新建路径；
- 结算例外额度页面、接口、服务和新写模型。

任何删除都必须先证明正式历史读取、PDF、审计和外部接管不依赖该写路径。

### 28.3 原生小程序

- 原生微信小程序确定不再建设；
- 响应式 Web 是电脑端和手机端唯一业务客户端；
- 先盘点 `apps/miniprogram`、`/auth/wx-login`、`wxOpenid`、共享上传下载、
  签名二维码和备份恢复依赖；
- 先关闭新入口并保留可观测期，再删除运行时、登录路由和专属字段；
- 不得把移动 Web、共享手机号登录、私有文件或签名二维码能力与小程序一并
  删除；
- 生产字段和历史登录事实的物理清理必须另行授权并经过隔离恢复演练。

## 29. 扩展后的完成标准

除第 21 节外，五个实施包 Release B/C1 还必须同时满足：

- 六类合同及两种金额性质由后端硬性执行，旧 `generic_contract` 不再自动
  绕过结算；
- 我方签约付款与挂靠企业签约付款无法交叉；
- 业主付款、挂靠拨款、挂靠扣款和待核对差额不重复计入我方资金；
- 零星材料 3000 元分类、付款/收货任意顺序及零星费用直接办结通过真实岗位
  验收；
- 项目资金不足时所有实际支付硬性失败，垫资额度只在实付凭证落库后占用；
- 项目垫资申请、审批、自动资金来源和人工终止有完整页面；
- 合同资料与规则、合同文件版式、业务场景和标准条款不再要求经办人理解内部
  版本 ID；
- 所有审批 PDF 使用冻结手写签名版本；
- 挂靠企业外部业务只形成接管账本，不生成我方审批；
- 能力矩阵不存在可见按钮调用不存在接口、无消费者前端封装或未归类后端
  业务路由；
- 小程序新入口和运行时已按阶段退出，响应式 Web 手机链路通过验收；
- 所有旧接口删除均有生产零调用证据，生产物理数据清理仍保持独立授权。

本规格和五个实施包的修订不代表业务代码、Schema、迁移或生产功能已经实现。
下一步按实施总索引先执行只读基线和 TDD；推送、合并、生产备份、迁移、部署、
真实数据修订和物理删除仍分别需要明确授权。
