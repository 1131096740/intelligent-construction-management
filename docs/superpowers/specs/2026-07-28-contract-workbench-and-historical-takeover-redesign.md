# 合同工作台与历史合同接管重构设计

日期：2026-07-28
状态：用户已逐节确认，待用户复核书面规格
范围：合同草稿工作台、清单价税、草稿文档预览、历史合同接管及其与结算付款的衔接

## 1. 背景

当前合同工作台和历史合同接管已经具备大量前后端能力，但主流程出现了几类结构性问题：

- 合同台账携带精确合同版本进入工作台，后端却可能按合同自行选择另一份“最新可编辑版本”，导致已填资料消失并进入只读状态；
- 顶部“保存”只保存普通字段，清单使用另一套“保存全部”，用户无法确认一份草稿是否已经完整保存；
- 草稿删除入口与后端“放弃草稿”语义不一致，未提交纯净草稿无法按期望清理；
- Excel 模板税率的存储格式、合同默认税率和导入校验口径不一致；
- 页面显示的不含税单价精度与合同总价的计算顺序不统一，可能在大额合同中形成数元差异；
- 历史接管仍以单次确认直接生效为中心，不能表达合同部和财务部并行录入、分别确认；
- 一批后端能力没有前端入口，另有一批旧前后端接口已无页面调用，接口数量与实际业务能力不再一一对应。

本设计采用前后端业务编排重构、分阶段替换方案。它不推倒审批、权限、文件、审计、结算和付款底座，而是重新建立一条清晰的合同草稿聚合主线和历史接管聚合主线。

## 2. 目标

### 2.1 合同工作台

- 合同台账中的“继续办理”始终打开该行对应的精确合同版本；
- 顶部唯一“保存草稿”覆盖合同草稿中全部可编辑业务资料；
- 后台自动保存与顶部保存共用同一个后端保存模型；
- 左侧持续显示合同文档，右侧完成结构化资料编辑和资料检查；
- 清单、Excel、税率、页面汇总和合同文档使用同一套后端金额算法；
- 纯净草稿可以按权限物理清理，正式流程事实和审计历史不可删除；
- 前端入口、前端 API 和后端业务接口形成可检查的一一对应关系。

### 2.2 历史合同接管

- 合同部和财务部在同一接管详情页并行办理；
- 两个部门拥有独立数据区、修订号、保存和确认动作；
- 双方确认后才激活合同并创建历史期初事实；
- 历史结算、实际付款、预付款和异常超付分别建模；
- 接管合同激活后可以正常发起新结算和付款申请。

### 2.3 资源控制

- 草稿只保留最新一份 DOCX 和 PDF 预览；
- 临时附件、Excel 导入文件和文档中间文件按明确期限自动清理；
- 新旧流程不长期双写，不因兼容层持续制造重复数据和重复对象。

## 3. 非目标

本轮不做：

- OCR 识别历史合同、结算单或付款凭证；
- Word 反解析并自动覆盖系统结构化数据；
- 多人按章节同时编辑同一份合同草稿；
- 替换现有审批引擎、项目岗位权限、审计、私有文件下载、结算和付款主链路；
- 把电子签章、银企直联或发票系统扩入当前范围；
- 改写已生效合同、已归档文件或历史审批事实。

## 4. 方案比较与决策

### 4.1 未采用：补丁式修复

只修复草稿丢失、税率和删除入口，改动小，但会继续保留双重保存、错误版本选择、单部门接管和接口遗留，后续仍需重复返工。

### 4.2 未采用：只重做前端

界面可以改善，但后端仍按旧语义读写，前端需要长期承担兼容、拼装和状态判断，不能根治数据丢失和半保存问题。

### 4.3 采用：前后端业务编排重构，分阶段替换

保留稳定底座，重建合同草稿聚合和历史接管聚合；新流程先上线验证，旧流程只作短期回退，确认无调用后删除。

## 5. 总体架构

```text
合同工作台
  -> 精确合同版本草稿聚合
      -> 全局草稿保存事务
          -> 字段、主体、清单、税率、条款、付款、附件关联
      -> 草稿文档预览任务
          -> 最新草稿 DOCX/PDF

历史接管详情
  -> 合同部数据区与确认
  -> 财务部数据区与确认
      -> 双部门确认门禁
          -> 合同版本激活
          -> 历史期初结算
          -> 历史实付、预付款及风险余额
```

架构原则：

- `contractVersionId` 是合同草稿办理的唯一定位键；
- 资料保存是数据库原子事务，文档生成是独立异步任务；
- 金额、权限、状态转换和确认门禁都由后端决定；
- 前端使用后端返回的可用动作、禁用原因和字段定位信息；
- 同一业务记录不得同时由新旧接口写入；
- 审批、用印、签署、归档、结算和付款继续复用现有正式服务。

## 6. 合同工作台前端

### 6.1 桌面布局

保留用户认可的“左边看文档、右边填资料”双栏结构。

顶部固定区域展示：

- 返回合同台账；
- 合同名称、临时编号或正式编号；
- 当前状态；
- 正在保存、已保存或保存失败；
- 最后保存时间；
- 唯一的“保存草稿”按钮；
- “提交审批”按钮及禁用原因。

左侧文档区：

- 展示最近一次成功生成的草稿文档；
- 支持 PDF 在线查看和 DOCX 下载；
- 明确区分“资料保存状态”和“文档预览状态”；
- 资料修订更新后显示“预览待更新”；
- 生成失败时保留上一份可用预览并提供重试入口。

右侧资料区内部使用窄竖向章节目录和当前章节表单。

章节目录为：

1. 资料检查
2. 基本信息
3. 合同主体
4. 专业字段
5. 清单与价税
6. 结算付款
7. 合同条款
8. 附件与资质
9. 磋商与文档
10. 流程记录

每个章节显示完成标记或问题数量。“资料检查”汇总必填项、金额和价税差异、清单错误、附件缺项、条款问题及送审准备状态。点击问题必须切换到对应章节，并聚焦具体字段或清单行。

“流程记录”只读展示审批、用印、签署、归档、版本和审计摘要，不在草稿表单中混入正式流程操作。

### 6.2 移动端和窄屏

- 不将左右两栏强行压缩；
- 顶部提供“合同资料”和“文档预览”切换；
- 资料页的章节目录可收起；
- 保存状态和“保存草稿”始终可见；
- 所有业务规则与桌面端共用同一 API。

### 6.3 页面行为

- 切换右侧章节不会丢失本地内容；
- 离开工作台前立即执行全局保存；
- 保存失败时阻止离开并显示准确原因；
- 不提供“放弃修改并离开”；
- 浏览器被强制关闭时，使用最后一次服务端自动保存和账号、设备、草稿、修订隔离的本地副本提示恢复；
- 本地副本不是权威草稿，成功保存、删除草稿或正式提交后必须清理。

## 7. 全局保存

### 7.1 一个保存模型

顶部“保存草稿”和后台自动保存调用同一个后端保存服务。一次保存覆盖当前草稿所有已变更资料：

- 基本信息和专业字段；
- 合同主体及附件关联；
- 清单行、行顺序和计税信息；
- 结算付款约定；
- 合同条款；
- 附件与资质关联；
- 磋商及文档引用信息。

后端在一个事务中校验并写入。任一分区失败时，整次资料保存不提交，禁止形成“基本信息已保存、清单未保存”的半成品。

请求必须携带：

- 精确 `contractVersionId`；
- 当前草稿修订号；
- 本次保存幂等标识；
- 当前编辑租约标识；
- 发生变化的资料分区。

响应返回：

- 新草稿修订号；
- 服务端保存时间；
- 各章节问题数量；
- 资料检查结果；
- 文档是否过期；
- 当前可用动作和禁用原因。

### 7.2 后台自动保存

- 用户停止输入约 2 秒后自动保存；
- 首次编辑即可保存到服务器，不等待第一次手动保存；
- 自动保存只保存结构化资料，不生成 DOCX/PDF；
- 自动保存失败后保留本地内容并允许重试；
- 修订冲突或编辑租约失效时不得静默覆盖。

### 7.3 顶部“保存草稿”

点击后：

1. 取消等待中的自动保存；
2. 全局提交当前全部修改；
3. 等待资料事务成功；
4. 创建当前修订的文档预览任务；
5. 显示“资料已保存，正在更新预览”；
6. 文档生成成功后刷新左侧预览。

顶部保存只覆盖当前权威草稿，不创建可恢复检查点。后台自动保存也不创建版本。现有检查点创建、恢复和最近五份检查点能力退出新主流程。

### 7.4 合同编号

- 草稿阶段只使用临时编号；
- 后台自动保存和顶部“保存草稿”都不得提前分配正式合同编号；
- 提交审批时，后端先完成全局保存和送审就绪检查；
- 只有审批实例成功创建并冻结送审快照时，才在同一受控流程中分配正式合同编号；
- 分配结果写入合同版本和审批冻结快照，页面随后显示正式编号；
- 送审失败不得留下“已有正式编号但没有审批实例”的半成品。

### 7.5 并发和编辑租约

- 同一草稿同时只允许一个编辑会话；
- 其他人员进入时只读；
- 合同部主管可以二次确认后接管编辑权；
- 接管后原会话立即变成只读；
- 所有写入接受草稿修订号和编辑租约双重校验；
- 冲突时保留本地未保存内容，返回服务器最新修订和冲突原因，不自动合并金额、清单或附件。

## 8. 文档生成和存储

### 8.1 任务语义

- 资料保存事务和 DOCX/PDF 生成任务分离；
- 资料保存成功后不因文档生成失败而回滚；
- 相同合同版本、相同草稿修订只允许一个生成任务；
- 新修订到来时取消尚未开始的旧任务；
- 已经执行的旧任务可以结束，但不得覆盖更新修订的预览；
- 失败时保留上一份可用预览并允许重试。

### 8.2 草稿预览保留

- 草稿阶段只保留最新一份 DOCX 和一份 PDF；
- 新预览生成成功并完成数据库指针切换后，才删除上一份草稿预览；
- 审批冻结稿、双方签署稿和正式归档文件永久保留；
- 草稿保存不产生额外文档历史。

### 8.3 临时文件清理

- 未关联业务记录的待关联附件：24 小时后删除；
- Excel 导入原文件和预检结果：保留 7 天后删除；
- DOCX/PDF 转换中间文件：任务结束后立即清理；
- 清理任务保留轻量审计收据，不保留文件副本；
- 已关联正式附件、付款凭证、审批冻结稿和归档文件不得进入临时清理。

跨数据库和 COS 的删除使用可重试的清理任务。只有数据库记录、对象删除和审计收据均完成时，才报告清理成功。

## 9. 合同主体

- 草稿提交审批前，经办人可以新增、修改角色、替换资料或删除合作单位；
- 工作台支持从合作单位档案选择具体版本，也支持只用于本合同的临时快照；
- 档案引用和临时快照必须在页面上明确区分；
- 提交审批后合同主体快照锁定；
- 后续修改必须通过合同变更或补充协议产生新版本；
- 新工作台通过全局保存写入合同主体，不再保留“只能新增、不能修改或删除”的页面逻辑。

## 10. 清单、税率和金额

### 10.1 唯一权威算法

手工录入、Excel 导入、页面汇总、DOCX/PDF 生成全部调用同一套后端金额计算器。

每一行固定按以下顺序计算：

```text
含税总价 = 数量 × 含税单价，四舍五入到分
不含税总价 = 含税总价 ÷（1 + 税率），四舍五入到分
税额 = 含税总价 - 不含税总价
不含税单价 = 不含税总价 ÷ 数量，四舍五入保留 6 位小数
```

合同汇总只累加权威行总价：

- 合同含税总价等于各行含税总价之和；
- 合同不含税总价等于各行不含税总价之和；
- 合同税额等于合同含税总价减合同不含税总价；
- 不得用页面显示的两位不含税单价重新乘数量。

数量、单价和税率使用十进制定点数，不使用 JavaScript 浮点数。行总价、合同总价和税额精确到分。不含税单价内部保留 6 位，页面默认显示 2 位，悬停或展开时显示完整 6 位。

### 10.2 单一税率

- 合同草稿税率是唯一权威来源；
- 下载模板时自动写入并锁定税率；
- 模板不要求用户重复填写税率；
- 导入时使用合同默认税率；
- 合同税率变化后，旧模板标记为过期并要求重新下载。

### 10.3 特殊多税率

- 合同税率作为默认值；
- 只有例外清单行允许指定其他税率；
- 未填写例外税率的行继承合同默认税率；
- 导入预检必须列出全部例外行和税率。

### 10.4 Excel 模板和导入

- 税率 9% 在 Excel 中存储为数值 `0.09`，显示为 `9%`；
- 禁止把整数 `9` 和百分比 `9%` 混用；
- 隐藏元数据记录模板版本、合同版本、清单标识和税率快照；
- 公式使用与后端相同的“总价优先”顺序；
- 导入只执行预检，不直接写数据库；
- 预检展示新增、修改、删除、税率异常和金额差异；
- 用户确认后把候选清单载入当前前端草稿；
- 最终由顶部“保存草稿”与其他资料一并写入。

合同部提供的实际 Excel 必须成为发布前固定回归样本。验收需输出逐行差异，解释现有约 5 元差异来自哪些行和哪种舍入顺序，并证明系统、模板、导入结果和合同文档一致到分。

## 11. 合同状态

### 11.1 前端单一当前状态

合同生效前显示办理进度：

```text
草稿编制
-> 待审批
-> 审批中
-> 待用印
-> 待双方签署
-> 待归档确认
```

合同归档生效后显示履约状态：

```text
未开始
履约中
已暂停
已完成
已终止
```

存在争议、异常超付和资料缺失作为独立风险标记，不作为主状态。

### 11.2 履约状态权限

- 合同经办人可以更新未开始、履约中和已暂停；
- 已完成和已终止需要合同部主管确认；
- 已完成合同不再发起正常履约结算；
- 已终止合同只能进入终止清算或更正流程；
- 状态变化保留操作人、时间和原因。

后端仍可保留流程状态、归档状态和履约状态等必要维度，但台账只展示一个当前状态和一个下一步动作。

## 12. 草稿删除

### 12.1 草稿分类

后端区分：

- 纯净草稿：从未提交审批、没有正式流程事实；
- 审批草稿：曾提交、退回、驳回或撤回；
- 正式合同记录：已进入用印、签署、归档或生效。

这些分类用于权限和删除门禁，不额外作为一套面向用户的状态。

### 12.2 纯净草稿物理删除

- 当前经办人可以删除自己的纯净草稿；
- 合同部主管可以清理本部门纯净草稿；
- 主管代删必须填写原因并验证当前密码；
- 删除请求携带精确草稿修订号；
- 只有服务端重新确认仍为纯净草稿后才执行。

删除范围包括合同草稿及版本、字段、主体快照、清单、付款条款、条款、临时附件关联、草稿预览和未转为正式证据的 COS 对象。

只保留最小删除收据：删除人、时间、草稿标识摘要、原因和删除结果，不保留合同正文或附件副本。

### 12.3 已进入流程的记录

- 曾提交审批的合同不能物理删除；
- 驳回、撤回或终止后进入“已结束”；
- 审批记录、意见、冻结快照和正式文件保留；
- 可以按保留策略清理可再生成的临时文件和过期预览；
- 正式合同及历史事实不得通过草稿删除入口清除。

## 13. 历史合同接管

### 13.1 页面和并行办理

同一接管详情页分为：

- 合同资料区：合同员录入，合同部主管确认；
- 历史付款区：财务人员录入，财务主管确认。

双方可以并行办理，都能查看整体进度和对方已保存的只读摘要，只能修改本部门数据。

两个区域分别拥有：

- 独立修订号；
- 独立后台自动保存；
- “保存本部门资料”；
- “确认本部门资料”；
- 独立保存状态和确认记录。

一方保存不得覆盖另一方数据。离开页面前只检查当前用户负责区域的保存状态。

### 13.2 合同部数据

合同部录入：

- 合同编号、名称、项目和合同类型；
- 合同相对方和签订日期；
- 原始签约金额；
- 当前履约状态；
- 历史累计结算总额；
- 一份或多份历史结算和确认资料；
- 后续结算付款所需的合同基本约定。

只录入历史累计结算总额，不逐份登记历史结算。

### 13.3 财务部数据

财务逐笔录入已经实际支付的历史款项：

- 实付日期和金额；
- 收款单位；
- 付款方式及流水说明；
- 一份或多份付款凭证；
- 必要备注和异常说明。

一份凭证只归属于一笔实付记录，一笔实付可以关联多份凭证。

没有历史付款时，财务必须提交明确的“历史实付为零”声明，不能以空白代替确认。

旧系统中的待审批、已批准未支付或其他尚未实际付款申请不迁移。财务确认时必须声明旧申请已经停止，未付款事项在新系统重新申请。

### 13.4 双部门确认

- 两个部门主管分别确认；
- 确认后锁定本部门数据区；
- 正式激活前，主管可以填写原因撤回本部门确认；
- 任一方撤回后双确认门禁关闭；
- 激活后不得直接撤回，只能发起带原因、附件和审计的更正流程；
- 双确认同时成立时只允许执行一次幂等激活。

### 13.5 激活结果

双确认成功后，后端在事务中：

1. 创建或激活历史合同版本；
2. 创建一笔历史期初结算，金额等于历史累计结算总额；
3. 挂接合同部历史结算资料；
4. 创建逐笔历史实付事实并挂接凭证；
5. 将正常历史实付占用到历史期初结算；
6. 计算历史结算未付款差额；
7. 形成历史预付款余额或异常超付风险；
8. 根据录入事实设置合同履约状态；
9. 写入完整接管审计记录。

历史结算未付款差额只表示付款上限，不自动等于当前可付款金额。后续每次付款仍需填写申请金额和依据，并重新走完整付款审批。累计申请和实付不能超过剩余差额。

### 13.6 历史实付超过结算

如果历史累计实付大于历史累计结算：

- 默认阻止财务最终确认；
- 财务必须将超出部分选择为历史预付款或异常超付；
- 必须填写说明并上传依据；
- 财务主管确认后才允许完成财务侧确认；
- 系统不得自动修改合同部确认的历史累计结算金额。

激活后：

- 历史预付款形成独立余额，后续有效结算自动抵扣；
- 异常超付形成合同风险标记；
- 异常解除前禁止新的付款申请；
- 更正或主管解除必须保留原因、依据和审计。

### 13.7 激活后的业务

- 可以发起新的正常结算；
- 可以针对历史期初结算未付款差额分多次发起付款申请；
- 可以针对后续新结算发起付款申请；
- 所有新付款使用正常审批、实付、凭证和财务入账流程；
- 历史付款作为已发生事实，不重新审批；
- 已结束历史合同保留查询和更正，不继续发起正常履约业务。

## 15. 数据模型调整

合同草稿需要明确：

- 全局草稿修订号；
- 章节化草稿数据；
- 当前预览对应草稿修订；
- 最新成功预览文件指针；
- 保存幂等记录；
- 草稿生命周期分类。

历史接管需要明确：

- 合同部数据修订和确认记录；
- 财务部数据修订和确认记录；
- 逐笔历史实付；
- 一对多付款凭证；
- 零付款声明；
- 历史预付款余额；
- 异常超付事实和风险解除；
- 双确认激活幂等标识；
- 历史期初结算关联。

金额继续使用数据库定点数和分值边界，不使用浮点数。

## 16. 错误处理

后端返回稳定业务错误类型，包括：

- 草稿修订冲突；
- 编辑租约失效；
- 字段或附件校验失败；
- 清单具体行列错误；
- Excel 模板过期；
- 税率或金额计算异常；
- 文档生成失败；
- 历史接管另一方数据变化；
- 历史实付超额但未分类；
- 异常超付付款门禁；
- 草稿不满足物理删除条件。

校验错误携带章节、字段或清单行定位信息。前端不暴露数据库字段、内部枚举、堆栈或 COS 地址。

## 17. 前后端能力矩阵

每个业务动作必须登记：

| 字段 | 要求 |
|---|---|
| 业务动作 | 使用业务语言命名 |
| 前端入口 | 明确显示条件或明确声明无需入口 |
| 前端 API | 有唯一封装 |
| 后端路由 | 有唯一业务语义 |
| 权限 | 后端强制 |
| 后端测试 | 覆盖状态、权限和失败路径 |
| 页面测试 | 覆盖入口和禁用原因 |

构建检查需要发现：

- 前端调用不存在的后端路由；
- 后端新增业务动作却没有声明前端入口策略；
- 页面绕过后端 `availableActions` 自行放行；
- 已迁移业务仍在调用旧接口。

## 18. 迁移和遗留接口退出

### 18.1 分阶段替换

第一阶段：

- 新增前向数据库结构和新接口；
- 旧页面只作短期回退；
- 对现有草稿执行只读迁移预检；
- 不修改正式合同和历史财务事实。

第二阶段：

- 迁移能够确定映射的草稿；
- 新工作台只调用新接口；
- 已迁移草稿禁止旧接口写入；
- 冲突草稿保留原记录只读并进入人工清单。

第三阶段：

- 使用真实合同验证新建、保存、预览、送审、接管、结算和付款；
- 核对数据库、COS 对象和审计记录；
- 确认没有旧客户端调用后删除遗留代码。

### 18.2 旧草稿

- 上线前自动预检；
- 能安全映射的字段、清单、条款和附件自动迁移；
- 无法确定的数据列入人工处理清单；
- 迁移失败保持原记录只读，不产生半迁移记录；
- 正在审批、已生效及已归档合同不通过草稿迁移改写。

### 18.3 计划退出的能力

验证完成后删除：

- 按合同 ID 自行寻找最新草稿的读取方式；
- 旧草稿列表、软作废和恢复接口；
- 草稿检查点创建和恢复；
- 清单逐行独立保存、删除和排序接口；
- Excel 独立应用写入接口；
- 只新增但不能修改或删除的合同主体页面逻辑；
- 历史接管单次确认直接生效逻辑；
- 无页面调用的旧前端 API 封装。

审批、用印、签署、归档、文件权限、审计、结算和付款正式接口继续保留。

### 18.4 迁移门禁

生产迁移前必须完成：

1. 最新数据库备份及可恢复性检查；
2. 现有草稿、附件和接管记录只读盘点；
3. 自动映射报告和人工冲突清单；
4. 隔离恢复库迁移演练；
5. 迁移前后记录数、金额、附件和修订指纹对比；
6. 明确回退版本、回退条件和负责人。

任何迁移不得静默舍弃字段、清单行、附件或金额。生产迁移、真实数据修改、文件清理和部署仍需分别获得明确授权。

- 草稿重新进入后资料完整且可编辑；
- 顶部保存覆盖所有草稿资料；
- 清单金额与实际 Excel 一致到分；
- 税率导入不再误报；
- 纯净草稿可以按权限彻底删除；
- 双部门历史接管可以并行办理并独立确认；
- 接管后能够正常结算、申请付款和记录实付；
- 没有可见按钮调用不存在的接口；
- 没有未归类的后端业务动作；
- 旧接口和临时文件按计划完成清理；
- 正式合同、审批、签署、归档和财务审计记录不受损。
