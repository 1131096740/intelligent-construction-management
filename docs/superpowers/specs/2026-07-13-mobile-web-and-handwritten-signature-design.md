# 建工智管手机 Web 与手写签名设计

日期：2026-07-13

状态：书面设计已完成并通过自审，待用户复核

范围：Web Admin 手机端外壳、首页、台账、审批、个人设置、手写签名和电脑端微信扫码创建签名

定位：同一套 Web 业务系统的响应式移动能力，不是第二套应用，不是微信小程序重写

## 1. 背景与当前事实

建工智管当前以 Vue 3、TypeScript、TDesign Vue Next 和 Vite 构建 Web Admin，后端为 NestJS 与 PostgreSQL，私有文件进入腾讯 COS。手机用户的主要任务是：

- 查看合同、结算和付款台账。
- 查看单据、附件和审批进度。
- 处理各类审批。
- 创建和维护本人手写签名。
- 修改本人姓名、手机号和密码，以及退出登录。

手机用户不使用合同、结算、付款的复杂新建和编辑表单。这些业务操作继续由电脑端完成。

当前代码已有签名雏形，但不符合本设计：

- `User.signatureFileId` 只指向一个可替换文件。
- `/me/signature` 接受 PNG/JPEG 图片上传。
- 审批单和结算审批文档渲染时，会按审批人读取其当前 `signatureFileId`，而不是读取审批发生时的签名版本。

因此现有方式同时存在“可上传他人签名图片”和“更换签名可能影响历史文档再生成”两个问题。本设计将其改为手机实时手写、版本不可变和审批时精确绑定。

## 2. 目标

- 让常见 iPhone 和安卓手机通过浏览器舒服、快速地使用系统。
- 所有权限可见页面都能从手机菜单进入，不留白屏、断路由或无法返回的页面。
- 把手机首页、审批和台账收口为任务优先的办公体验。
- 在不引入第二套业务系统的前提下，保持手机与电脑共用路由、登录、权限、API、状态机和审计。
- 取消产品支持的签名图片上传来源，为内部审批提供可更换但历史不漂移的手写签名。
- 保持现有电脑端复杂业务流程和业务规则不变。

## 3. 不做事项

- 不建立第二个移动 SPA。
- 不在本轮重写为微信小程序或 PWA。
- 不把合同、结算、付款复杂表单全部搬到手机。
- 不开放拍照、相册、文件选择或电脑本地图片作为个人签名来源。
- 不自行仿造数字证书、司法存证、区块链存证或第三方可靠电子签名服务。
- 不引入第二套 UI 组件库、通用工作流引擎或全站重写。
- 不因移动端隐藏按钮而削弱后端权限校验。

## 4. 方案选择

采用“同一 Web 应用 + 专用移动外壳 + 共用业务事实”方案。

放弃的备选方案：

- 独立移动 Web：可以完全独立设计，但会复制路由、会话、组件和测试。
- PWA 或微信小程序：移动体验上限更高，但需要额外处理安装、平台登录、更新和双端回归，超出本轮范围。

手机外壳建议在 CSS 视口宽度不大于 767px 时启用。实现必须使用共享的媒体查询或响应式状态，页面不得自行猜测设备型号或用户代理字符串。

## 5. 移动外壳与安全区

### 5.1 顶部栏

- 顶部使用 `env(safe-area-inset-top)` 为刘海、灵动岛和前置摄像头留出动态空间。
- 安全区下方是 56px 单层固定顶栏。
- 左侧是菜单入口，中间是当前页面中文名称，右侧是待审批数量。
- 滚动时顶栏保留，但正式界面不显示“滚动时菜单保留”或“安全区”等说明文字。

### 5.2 左侧分组抽屉

抽屉宽度约为视口的 86%，顶部展示当前账号、部门、岗位和当前项目，并提供页面搜索。业务分组固定为：

1. 工作入口。
2. 项目资金链。
3. 合同。
4. 结算。
5. 付款。
6. 资料与治理。

抽屉直接复用现有路由的权限过滤结果，不维护第二份权限菜单。点击路由、关闭按钮或遮罩层后关闭抽屉。手机端禁止的复杂新建和编辑页不出现在抽屉中。

### 5.3 底部导航

底部固定四项：

- 首页。
- 待审批。
- 台账。
- 我的。

操作区高 56px 至 58px，下方使用 `env(safe-area-inset-bottom)` 避开系统手势区。正文容器必须同时为顶部栏和底部栏预留空间。

### 5.4 项目选择

- 全局账号首次进入默认“全部项目”。
- 用户切换后，跨页面和后续登录记住上次选择。
- 只有一个项目的账号自动选中；拥有多个项目的普通账号记住上次选择。
- 合同、结算和付款台账跟随当前项目。
- 审批中心始终汇总账号可审批的所有项目，不受当前项目限制。

## 6. 首页与台账

### 6.1 综合首页

手机首页优先展示：

1. 当前项目与切换入口。
2. 待我审批、即将超时、我发起的、风险事项。
3. 合同、结算和付款的关键数量与金额摘要。
4. 进入台账和审批的快捷入口。

手机首页不显示新建合同、新建结算、新建付款等复杂业务入口。

### 6.2 台账中心

底部“台账”进入统一台账中心，展示：

- 合同台账。
- 结算台账。
- 付款台账。

每个入口展示当前项目、记录数、待处理数和关键金额。不直接跳入上次台账，避免用户不知道当前处于哪个业务域。

### 6.3 手机台账表达

- 电脑端表格在手机上转为纵向业务卡片。
- 卡片优先展示单据名称、合作单位、金额、状态和最近更新时间。
- 搜索框保留在列表顶部；项目、状态、日期、合作单位等条件收入筛选面板。
- 点击卡片进入只读详情，复杂清单使用分组折叠和逐项展开。
- 保留审批记录、附件预览和经后端授权的敏感文件下载。
- 只有列关系无法拆解的少量表格允许局部横向滚动，禁止让整个页面横向溢出。

### 6.4 移动能力矩阵

手机端可用：

- 首页、审批中心、审批详情、台账、只读详情、附件预览与授权下载。
- 姓名、手机号、密码、手写签名和退出登录。
- 审批同意、驳回、退回上一节点、退回申请人、转交和委托，具体以流程和权限为准。

手机端禁止：

- 合同、结算和付款的新建、编辑和删除。
- 模板、版式、编号规则、组织权限和其他复杂治理配置的写操作。
- 实际付款执行、凭证登记等必须在电脑上完成的财务操作。

历史链接或手工输入直接进入手机禁止页时，显示中文只读说明“请在电脑端操作”和可返回的安全入口，不渲染复杂表单。

## 7. 审批体验

### 7.1 审批中心

审批中心始终跨项目汇总，分为：

- 待我处理。
- 即将超时。
- 我已处理。
- 我发起的。

列表卡片优先展示项目、单据类型、金额、申请人、到达时间和风险状态。手机端不提供批量审批。

### 7.2 摘要先行审批详情

第一屏必须显示：

- 项目。
- 单据名称和类型。
- 关键金额。
- 申请人。
- 合作或收款单位。
- 当前审批节点。

业务详情、审批历程、附件与凭证按分组展开。底部固定“驳回”和“同意并签名”，其他审批动作收入“更多”。

“更多”只显示当前流程与当前账号允许的动作，可包含转交、委托、退回上一节点和退回申请人。退回或驳回必须选择目标并填写原因。

### 7.3 同意并签名

1. 客户端提交前重新读取审批任务和单据版本。
2. 没有当前签名时，进入签名创建，成功后返回原审批单。
3. 确认面板再次展示项目、单据、金额、审批意见和当前签名预览，并保留该预览对应的签名版本标识。
4. 用户每次输入当前登录密码，不使用十分钟免验或仅点击确认。
5. 后端在现有业务域事务内重新验证账号、密码、权限、当前节点、单据版本、业务状态和签名版本。客户端提交的签名版本必须与确认面板预览版本一致，并且在事务内仍是本人当前有效版本；不一致时返回冲突，不得静默改绑新版本。
6. 同一事务写入业务状态、`ApprovalActionLog`、签名版本绑定和权限审计。
7. 成功后显示明确结果，可进入下一条待审批事项。

审批意见可为空时应继续遵守各业务域现有规则，本设计不一律强制“同意”填写意见；驳回、退回和领导自审仍遵守已有必填原因、密码或独立确认规则。

## 8. 手写签名

### 8.1 业务定位

本期手写签名是公司内部审批的可视签名与审计事实，不宣称它单独等同于《电子签名法》下的可靠电子签名。对外电子合同如需实名认证、数字证书、签署意愿认证、防篡改和司法存证，后续通过腾讯电子签、e 签宝、法大大或上上签等合规服务实现，不在本轮自建。

### 8.2 创建入口

- 手机端：“我的 → 我的签名 → 创建签名”。
- 首次登录不强制创建。
- “我的签名”持续显示未创建状态。
- 用户第一次点击“同意并签名”时，若尚无签名，必须先创建；创建成功后返回原审批单。
- 电脑端：不提供鼠标签字和图片上传，而是显示微信可扫的一次性二维码。

### 8.3 手机签字板

1. 进入时提示横置手机。
2. 在浏览器支持且条件允许时，请求全屏与横屏；方向锁定失败时显示旋转引导，不将其视为致命错误。
3. 签字区尽可能占满扣除安全区和工具栏后的屏幕。
4. 支持手指和触控笔，同一个指针事件流处理书写，签字期间禁止画布滚动和缩放。
5. 提供“撤销上一笔、全部清除、取消、完成”，不增加颜色、粗细、艺术字或自动仿写。
6. 笔迹过少、只有一点或一条极短线时禁止保存。
7. 完成后裁去透明空白，展示黑色笔迹和透明背景的预览。
8. 用户明确点击“确认保存”后才上传生成结果，退出或取消不保存草稿。

实现优先使用浏览器 Canvas、Pointer Events 和现有 TDesign 控件，不因签字板引入第二套 UI 系统。生成文件使用足够分辨率的透明 PNG。后端必须校验服务端签发、当前账号绑定且未过期的签字板会话，并检查 PNG 真实文件头、可解码性、尺寸和大小上限，不仅信任 MIME 声明。登录用户从“我的签名”直接创建时，也先由后端签发短时签字板会话；电脑扫码场景则由扫码会话换取。

### 8.4 签名版本

新增不可变签名版本事实，至少保存：

- 所属用户。
- 私有文件标识。
- 文件 SHA-256、宽度、高度和 MIME 类型。
- 创建时间、创建方式和有限的设备摘要。
- 当前有效或已被新版本替代的状态。

每个用户同一时间只有一个当前有效版本。重新创建签名会在事务内把原版本标记为已替代并创建新版本。已绑定历史审批的签名版本不得修改或硬删除。

私有签名文件没有公开 URL。业务用户只能预览本人当前签名；不提供他人签名原图的通用下载入口。审批文档只能通过服务端读取审批动作绑定的签名版本进行渲染，不再读取用户的当前签名指针。

## 9. 电脑端微信扫码创建签名

### 9.1 会话规则

电脑端点击“创建签名”时，后端创建扫码会话：

- 绑定电脑端当前登录用户。
- 生成高熵一次性令牌，数据库只保存令牌摘要。
- 有效期 5 分钟，只能成功使用一次。
- 保存创建时间、到期时间、使用时间和状态。
- 二维码不包含姓名、手机号或用户标识等明文业务信息。

电脑端只轮询本会话的有限状态：待扫码、手机已打开、已完成、已过期、已取消。完成后电脑端重新读取本人当前签名，不从轮询接口接收签名原图。

### 9.2 微信内置浏览器

- 二维码使用 `https://jgzg.site` 同源链接，必须能被微信“扫一扫”在内置浏览器打开。
- 不要求安装 App，不强制跳转外部浏览器。
- 微信内置浏览器与 Safari/Chrome 的会话相互独立。用户第一次在微信内扫码时，使用本人手机号和密码登录；后续在微信内复用正常 Web 登录会话。
- 登录账号与扫码会话绑定账号不一致时拒绝进入签字板。
- 本期不接入微信网页授权、公众号 OpenID 或“扫码即登录”。微信只是打开 HTTPS 页面的扫码工具，不是身份凭证。

链接页面必须使用 `Referrer-Policy: no-referrer`，页面不加载第三方资源，避免一次性令牌通过引用地泄漏。

## 10. 后端边界与数据流

### 10.1 边界组件

- `SignatureVersionService`：创建、替换和读取本人当前签名版本。
- `SignaturePairingService`：创建、校验、消费和查询一次性扫码会话。
- `ApprovalSignatureService`：在现有业务域审批事务内完成密码复核、当前签名版本校验和绑定输入解析。

这些服务不接管合同、结算、付款、项目支出和其他业务域的状态机。各业务服务仍是自身审批状态的唯一写入者，只在现有事务内调用共享签名校验与绑定能力。不借本轮重写审批引擎。

### 10.2 审批动作绑定

`ApprovalActionLog` 对实际“同意”动作增加显式、可查询的签名版本绑定，而不只把文件标识塞进无约束 JSON。驳回、退回、转交、委托、提醒和撤回不绑定个人签名。

在单个业务事务内：

1. 锁定当前单据与审批实例。
2. 验证账号和当前密码。
3. 验证审批节点、角色、自审边界、委托和并发版本。
4. 按客户端提交的签名版本标识锁定记录，验证其属于当前用户，与确认面板预览一致，并且仍是当前有效版本。
5. 写业务状态和审批实例。
6. 写带签名版本的审批动作。
7. 写业务审计。

任一步失败时整体回滚。审批文档、时间线和审计详情都以该动作的签名版本为事实源。

## 11. 前端边界

跨域复用组件：

- `MobileShell`：手机外壳、安全区和正文间距。
- `MobileHeader`：菜单、页面标题和待审批提示。
- `NavigationDrawer`：权限过滤的分组路由和页面搜索。
- `MobileBottomNav`：首页、待审批、台账和我的。
- `ProjectSwitcher`：当前项目选择与按账号记忆。
- `MobileLedgerCard` 和 `MobileFilterSheet`：台账卡片和筛选面板。
- `MobileApprovalSummary` 和 `ApprovalActionSheet`：审批摘要和操作确认。
- `HandwrittenSignaturePad` 和 `SignaturePreview`：签字板和预览。
- `DesktopSignatureQrBridge`：电脑端二维码与状态同步。

业务域仍保留自己的详情内容和 API 封装；移动组件只统一容器、交互和共享信息结构，不建立一个无限配置的“万能手机页面”。

页面和组件继续使用 TDesign 和 `--jg-*` 设计 token，API 调用仍进入 `apps/web-admin/src/api/`，不在 Vue 页面直接使用 `fetch`。

## 12. 全站手机适配规则

- 表格优先变为业务卡片。
- 电脑弹窗在手机上变为底部面板或全屏页面。
- 可点击区域的边长不小于约 44px。
- 金额使用等宽数字或稳定数字宽度并右对齐。
- 状态、错误、空状态和技术说明对业务用户只显示中文业务语义。
- 不显示数据库模型、岗位代码、UUID、英文状态或内部路由名。
- 加载失败时保留页面外壳、明确原因和重试入口。
- 返回列表时恢复原筛选、搜索和滚动位置。
- 中文路由可直接打开、登录后回跳和硬刷新，不因 URL 编码产生白屏。

## 13. 错误与并发处理

- 密码错误时不写任何审批事实，连续错误经现有或统一限流处理。
- 审批任务已被处理、节点变化或单据版本变化时返回冲突，不重复写审批。
- 网络中断后如果结果不明确，客户端先重读审批状态，不盲目重复提交。
- 签名文件写入失败时不创建有效签名版本；如对象存储成功但数据库失败，复用现有孤儿对象补偿机制。
- 扫码会话过期、已使用、已取消或账号不匹配时拒绝创建签名，电脑端可生成新二维码。
- 所有权限和业务状态都由后端复核，前端按钮可见性不是安全边界。

## 14. 审计

至少记录以下动作：

- 签名创建。
- 签名替换。
- 扫码会话创建、成功使用、过期和账号不匹配。
- 同意并签名。
- 驳回、退回、转交和委托。
- 敏感文件预览和下载。

审计元数据可包含签名版本标识、文件摘要、审批实例、单据标识、节点和结果，但不记录密码、一次性令牌原文、签名图片 base64、私有 COS URL 或完整用户代理字符串。

## 15. 验证标准

### 15.1 自动化验证

前端：

- 移动外壳的安全区、抽屉、底部导航和项目记忆测试。

## 16. 分阶段实施与发布闸门

### 阶段 1：移动外壳

### 阶段 4：移动审批

- 审批中心、摘要先行详情、密码复核、签名版本绑定和高级审批动作。
- 所有已支持的审批域逐个接入，不允许只有前端签名动画而后端未绑定事实。

## 18. 研究依据

国内产品共性：手机手写只是签名图形来源，可靠性还需身份、意愿、文件绑定、防篡改和存证链。本设计参考：

- [上上签：新增、编辑签名](https://www.bestsign.cn/help/FAQ/481)：电脑端发起、手机扫码手写、返回电脑保存和默认签名。
- [法大大：手机浏览器现场手绘](https://support.fadada.com/d/1743208091632095233.html)：手机签名板手写、预览和确认。
- [e 签宝：个人手机端快速签署](https://help.esign.cn/h5/detail?id=ke3yp8&nameSpace=cs3-dept%2Fexboae)：H5 手绘签名、签章位置和签署意愿认证。
- [腾讯电子签：签名方式数据结构](https://cloud.tencent.com/document/api/1323/70369)：区分实时手写与保存到个人中心的长效手写签名。
- [腾讯电子签：产品动态](https://cloud.tencent.com/document/product/1323/53793)：可强制每份文件重新手写并禁止一键复用。
- [MDN：`ScreenOrientation.lock()`](https://developer.mozilla.org/en-US/docs/Web/API/ScreenOrientation/lock)：屏幕方向锁定不是所有主流浏览器的稳定基线，通常还受全屏和移动环境限制。

## 19. 已确认决策摘要

- 采用同一 Web 应用的专用移动外壳。
- 采用单层固定顶栏、左侧分组抽屉和底部四项导航。
- 审批跨项目，台账跟随当前项目。
- 全局账号首次默认全部项目，后续记住选择。
- 底部“台账”进入统一台账中心。
- 手机隐藏合同、结算和付款的复杂新建/编辑/删除。
- 审批详情采用摘要先行卡片式。
- 底部只固定驳回与同意并签名，高级审批动作收入更多。
- 每次同意审批都重新输入当前密码。
- 签名创建一次后复用，更换产生新版本，历史审批保留原版本。
- 首次登录不强制创建签名，首次同意审批时硬拦并引导创建。
- 手机用手指在横屏签字板书写，手机和电脑均不支持图片上传。
- 电脑用微信可扫的五分钟一次性二维码在手机创建签名。
- 微信内首次使用手机号和密码登录，扫码账号必须与电脑发起账号一致。
