# 建工智管零星采购真实表单重构设计

日期：2026-07-18

状态：设计讨论已逐项确认，待用户审阅本书面规格；尚未形成新版实施计划，尚未授权恢复生产入口

范围：零星采购申请、零星材料付款、分次实际付款、收货确认、付款后发票附件、审批 PDF 和持续归档包

决策：继续沿用公司现行《零星/小额材料采购申请表》和《项目零星付款申请单》，采购申请只审批采购需求与材料范围，实际商户、价格、金额、收款和预计票据条件移到付款申请确定

## 1. 文档优先级与当前生产边界

本设计是 2026-07-16《建工智管零星采购与费用报销升级设计》的零星采购变更规格。发生冲突时，按以下顺序执行：

1. 本设计优先于旧设计中零星采购、零星付款、收货、票据、办结、PDF、工作台和验收规则。
2. 旧设计中“费用与报销”模块的借款、报销冲销、员工还款和员工项目往来台账不受本设计修改。
3. `docs/superpowers/plans/2026-07-16-spot-procurement.md` 基于旧零星采购规则编写，不能继续作为重构执行依据；用户确认本设计后必须另写变更实施计划。
4. 生产零星采购白名单当前为空，新模型生产业务记录为 0。完成前向迁移、代码重构、自动回归、受控 UAT 和用户重新授权前，入口必须保持关闭。
5. 本设计确认不等于代码、迁移、推送、部署、生产写入或恢复白名单授权。

## 2. 结论

本次重构采用“熟悉纸质主表 + 系统结构化明细 + 不可变审批原件 + 可持续追加归档包”：

- 零星采购继续作为独立模块，不退回旧 `ProjectExpenseRequest`。
- A4 竖向《零星/小额材料采购申请表》只审批为什么买、买什么、规格、单位、数量和要求到位日期。
- 采购阶段不填写供应商、单价、金额、发票类型或税率。
- 采购审批通过后自动创建唯一的当前有效付款草稿，经办人补齐后自行提交。
- A5 横向《项目零星付款申请单》审批实际采购商户、付款数量、单价、金额、预计票据条件、收款对象、付款主体和拟付款方式。
- 一张付款申请允许登记多次实际付款，但始终使用同一批准付款主体和同一收款对象。
- 第一次实际付款后开放收货；正常办结要求资金结算完成和收货复核完成，发票不阻断办结。
- 商家报价单、收据和发票均为可选附件，不上传不阻断申请、审批或付款。
- 办结后仍允许经办人或财务人员补传发票，但不得修改审批事实。
- 取消“转商户余额”；少货多付只允许继续补货或由商户退款。
- 费用与报销仍是另一个独立模块；采购经办人垫付报回仍属于零星采购付款，不生成普通报销单。

本设计不是完整采购 ERP、供应商门户或发票系统。未来可以增加商户主数据、询比价、采购订单、库存、OCR、验真和结构化发票账本，但不得提前塞入本轮。

## 3. 现有能力的复用与替换

### 3.1 继续复用

当前独立零星采购模块已经具备大量成熟基础能力。本轮应在原模块上做前向重构，不从零重建：

| 能力 | 处理方式 |
| --- | --- |
| 项目白名单 | 继续复用；重构期间保持关闭 |
| 审批引擎 | 继续复用实例冻结、退回、撤回、OR 签、审批日志和待办 |
| 项目岗位 | 继续复用物资员、物资主管、综合部主管、项目经理、财务人员、财务主管、董事长/总经理 |
| 私有文件 | 继续复用后端授权上传、私有存储、哈希、替换链、短时效下载和下载审计 |
| 实际付款 | 继续复用一张付款申请多笔执行、幂等、累计上限、凭证绑定和项目现金账本 |
| 收货 | 继续复用单张最终收货、委托、服务端水印、原图/水印图、物资主管复核和审计 |
| PDF | 继续复用私有生成、失败隔离、重试、下载授权和最新指针基础设施 |
| 审计 | 继续复用统一审计服务，不另建业务日志系统 |
| 金额 | 继续使用整数分、`BIGINT`、规范十进制字符串和后端重算 |

### 3.2 必须替换的旧事实

现有生产运行代码仍按旧设计保存以下事实，本轮必须修改：

| 旧事实 | 新事实 |
| --- | --- |
| 采购申请冻结供应商 | 采购申请不含商户；实际采购商户在付款申请填写 |
| 采购申请填写单价、金额和票据条件 | 采购申请只保存材料范围与批准数量 |
| 采购审批金额由申请明细计算 | 采购申请无金额；付款申请形成审批金额 |
| 同一采购可有多张有效付款申请 | 同一采购只允许一张当前有效付款申请 |
| 多张付款申请实现分次付款 | 一张付款申请下登记多次实际付款 |
| 财务直付必须付给冻结供应商 | 商户与收款对象允许不同，但必须说明 |
| 供应商余额可转入和跨单抵扣 | 本轮取消商户余额，只允许补货或退款 |
| 发票覆盖/无票确认是办结条件 | 发票状态独立，不阻断业务办结 |
| 票据保存结构化号码、金额并参与覆盖计算 | 本轮只保存发票文件和基础上传审计 |
| 采购审批后即可先收货 | 第一次实际付款后才开放收货 |

既有数据库表和代码中的供应商余额、票据覆盖等能力不得在本轮直接破坏性删除。由于生产新模型为 0 单，可以通过前向迁移和路由/能力收口让新流程不再写入；是否物理删除旧列和表，留给后续退役设计。

## 4. 模块与工作台

Web 左侧导航设置与“合同、结算、付款”并列的“零星采购”业务标题，包含：

1. 零星采购工作台。
2. 采购详情页。
3. 零星材料付款工作台。
4. 收货确认工作台。

“费用与报销”继续作为另一个独立业务标题，不放入零星采购菜单。

### 4.1 零星采购工作台

一行代表一张采购申请，至少显示：

- 采购申请编号。
- 项目。
- 申请部门、申请人。
- 采购人。
- 要求到位日期。
- 材料项数。
- 关联付款金额：付款未提交前显示“待确定”。
- 累计已付和剩余待付。
- 收货状态。
- 发票状态。
- 当前审批或办理节点。
- 采购业务状态。

采购申请阶段没有单价和金额，工作台不得伪造“采购申请金额”。付款申请形成后，才显示“关联付款金额”。

### 4.2 采购详情页

详情页集中展示：

- 采购申请及版本。
- 采购审批时间线。
- 唯一当前有效付款申请。
- 分次实际付款及凭证。
- 收货确认、委托、照片、水印和复核。
- 少货补货或退款处理。
- 发票状态和后补文件。
- 审批 PDF、归档包版本和审计记录。

### 4.3 零星材料付款工作台

一行代表一张付款申请，至少显示：

- 付款申请编号和关联采购编号。
- 项目。
- 实际采购商户。
- 收款对象。
- 我方付款主体。
- 审批金额。
- 累计已付、已退款和净支付。
- 剩余待付。
- 发票状态。
- 当前节点和付款状态。

列表中的银行账号、微信号、支付宝账号等敏感字段必须脱敏。

### 4.4 收货确认工作台

优先展示：

- 待收货。
- 待物资主管复核。
- 复核退回。
- 存在数量差异。
- 差异处理中。
- 已完成收货。

工作台提供收货填写、照片上传、委托确认和物资主管复核入口，不建立批次或车辆层级。

## 5. 零星采购申请

### 5.1 表头和责任人

采购申请必须区分三类事实：

- 系统发起人/采购人：当前登录的物资员或物资主管，保存用户 ID 和姓名快照。
- 纸质表中的申请人：由采购人手工填写的必填文本，当前不要求其拥有系统账号。
- 纸质表中的申请部门：由采购人手工填写的必填文本，当前不绑定组织主数据。

同项目内为申请人和申请部门提供历史文本建议。选择建议只复制文本，不创建账号、人员主数据或组织关系，也不反向修改历史单据。

采购部门由采购人的当前组织部门自动带出并保存名称快照，不允许手工修改。以后工程部开放系统账号时，可以增加可空的申请人用户引用，但历史文本快照保持不变。

### 5.2 采购申请字段

采购申请版本至少保存：

- 项目 ID、项目名称快照。
- 系统采购申请编号。
- 申请部门文本快照。
- 申请人文本快照。
- 采购部门名称快照。
- 采购人用户 ID 和姓名快照。
- 全单统一的要求采购到位日期。
- 物资用途及采购原因，必填。
- 可选备注。
- 材料明细。
- 可选申请附件。

采购申请不保存：

- 申请日期字段。
- 供应商或实际采购商户。
- 单价和金额。
- 发票类型、税率或预计票据方式。
- 收款对象、账户、付款主体或付款方式。

提交时间仍由服务器保存，用于版本、审批和审计，但不打印成纸质表中的“申请日期”。

### 5.3 材料明细

明细列固定为：

- 序号。
- 名称。
- 型号。
- 单位。
- 数量。
- 备注。

同一张采购申请的所有材料共用一条要求到位日期。采购审批只冻结材料范围和批准数量，不冻结商户、价格或票据事实。

### 5.4 附件

申请附件全部可选，允许上传：

- 商家报价单。
- 商品或材料清单。
- 现场参考照片。
- Excel。
- Word。
- PDF。
- 其他受控文件类型。

申请阶段的现场照片不是收货照片，不能代替收货环节至少一张正式水印照片。

### 5.5 审批与版本

审批流程固定为：

```text
物资员/物资主管发起
  -> 物资主管
  -> 项目经理
  -> 采购申请批准
  -> 自动创建付款草稿
```

物资主管本人发起时跳过物资主管节点，跳过保存为流程事实，不生成虚假审批签名。

提交后冻结申请人文本、申请部门文本、采购人、采购部门、要求到位日期、采购原因、材料和附件快照。尚未发生实际付款时，材料新增、删除、规格、单位或批准数量变化必须创建新采购版本并重新审批。发生实际付款后不允许普通版本变更。

## 6. 零星材料付款申请

### 6.1 唯一当前有效付款申请

采购申请批准后，系统自动创建一张付款草稿，不自动替经办人提交。付款经办人默认沿用采购人。

同一采购根单只能存在一张当前有效付款申请：

- 分次支付通过该付款申请下的多笔实际付款实现。
- 不允许为同一采购并行提交多张付款申请。
- 原付款尚未发生实际付款且已作废时，才允许创建替代付款申请。
- 已发生任何实际付款后，不允许替换付款申请。

### 6.2 付款申请字段

付款经办人负责填写：

- 实际采购商户。
- 付款类型：公司直付或经办人垫付报回。
- 付款事由。
- 收款对象及不一致说明。
- 收款渠道。
- 拟付款方式。
- 各材料付款数量、单价、金额和预计票据条件。
- 可选付款依据附件。

系统自动保存：

- 项目和关联采购。
- 付款申请编号。
- 付款申请日期：当前版本提交日期。
- 付款经办人。
- 申请金额小写和自动转换的大写金额。
- 当前版本和审批快照。

我方付款主体由财务人员、综合部主管或财务主管按第 6.6 节选择，经办人无权选择。

### 6.3 实际采购商户

实际采购商户是零星采购业务中的自由文本事实，不等同于合同供应商门户或正式合作单位主数据。

- 经办人手工填写商户名称。
- 同项目提供历史商户名称快捷建议。
- 选择建议只复制商户名称，不复制收款账户。
- 不跨项目推荐。
- 不自动合并相似名称。
- 不创建正式供应商档案。

本轮不建立商户余额。名称相同也不能据此跨单抵扣款项。

### 6.4 材料、金额和预计票据条件

付款明细继承采购申请中的材料名称、型号、单位和批准数量。经办人填写：

- 付款数量。
- 含税单价或无票单价。
- 行金额。
- 预计票据方式：无发票、增值税普通发票、增值税专用发票。
- 预计税率：选择普通或专用增值税发票时必填。

规则：

- 付款数量不得大于采购批准数量。
- 新材料或超批准数量必须先走采购版本变更。
- 行金额和申请金额由后端按定点数量与单价重算。
- 有票价格使用含税单价。
- 采购申请 PDF 永远不显示这些价格和金额。
- 付款申请工作台和 PDF 才显示审批金额。

### 6.5 付款类型、商户和收款对象

付款类型为：

1. 公司直付。
2. 经办人垫付报回。

一张付款申请只能有一个收款对象，但可以为该对象登记多个收款渠道，例如银行账户、微信、支付宝或现金。

商户与收款对象可以不一致：

- 不要求上传二者关系证明。
- 经办人必须填写简短不一致说明。
- 经办人垫付报回时，收款对象和账户持有人必须为付款经办人本人。
- 经办人垫付报回的不一致说明自动显示“经办人垫付后报回”。
- 经办人垫付报回不得再次进入普通费用报销。

### 6.6 我方付款主体和拟付款方式

我方付款主体是本次实际出款的公司名称，同一项目的不同零星付款可以选择不同我方公司。

付款主体必须从我方公司字典选择并冻结：

- 公司 ID。
- 公司全称快照。
- 统一社会信用代码快照。

操作边界：

- 经办人不能选择或修改付款主体。
- 经办人可以在付款主体尚未确定时提交付款申请，但综合部主管审批前必须已经选择有效付款主体，否则不能审批通过。
- 综合部审批完成前，财务人员、综合部主管或财务主管可以选择或调整付款主体和拟付款方式。
- 综合部审批完成后正常冻结。
- 财务主管在自身审批节点仍可调整，但必须填写原因，并使综合部主管、项目经理既有审批失效，从综合部主管节点重新审批。
- 最终审批完成或发生任何实际付款后永久锁定。

拟付款方式允许多选。每次实际付款必须从已批准方式中选择；一张付款申请的多次实际付款可以使用不同已批准方式。

### 6.7 付款依据附件

付款申请阶段可以上传：

- 商家收据。
- 商家报价单。
- 当时已经取得的商家发票。
- 其他受控付款依据。

以上全部可选。缺少任何一种都不阻断付款申请提交、审批或实际付款。

- 图片和 PDF 可以进入持续归档包的原始资料页。
- Word 和 Excel 保留为私有原文件，并在归档包附件目录列示，不强制转换。
- 原文件必须继续单独私有保存。

### 6.8 付款审批

审批流程固定为：

```text
付款经办人提交
  -> 综合部主管
  -> 项目经理
  -> 财务主管
  -> 董事长或总经理 OR 签
  -> 已批待付
```

固定签字格映射：

| 纸质格子 | 系统事实 |
| --- | --- |
| 经办人 | 付款申请人姓名快照和提交时间 |
| 部门经理 | 项目经理审批人姓名、时间和意见 |
| 综合部 | 综合部主管审批人姓名、时间和意见 |
| 财务部 | 财务主管审批人姓名、时间和意见 |
| 董事长/总经理 | 实际完成 OR 签的董事长或总经理姓名、时间和意见 |

财务人员选择付款主体不是审批动作，不生成“财务部”签名。

审批人不能直接修改商户、收款对象、账户、材料、数量、价格、金额或预计票据条件，只能同意、退回或驳回。上述事实变化必须退回经办人修改并从综合部主管节点重新审批。

## 7. 实际付款

### 7.1 多次实际付款

审批完成只进入“已批待付”，不代表已经付款。一张付款申请可以登记一笔或多笔实际付款。

每笔实际付款至少保存：

- 实付金额。
- 实付时间。
- 实际付款方式。
- 实际使用的已批准收款渠道。
- 财务操作人。
- 一到多个付款凭证文件。
- 幂等键、作废状态和审计记录。

约束：

- 累计有效实付不得超过付款审批金额。
- 所有实际付款使用同一批准付款主体和收款对象。
- 实际方式必须属于已批准拟付款方式。
- 实际付款和有效凭证必须在同一受控事务中登记成功，才能增加已付金额。
- 每一笔实际付款必须拥有自己的凭证，不得用一份凭证覆盖多笔付款记录。

### 7.2 各付款方式凭证

- 银行转账：银行回单或网银电子凭证。
- 微信或支付宝：支付成功截图或平台电子凭证。
- 现金：收款方收据即可。

现金付款与是否取得发票相互独立。现金可以有发票，转账也可以最终没有发票。

## 8. 收货确认

### 8.1 开放条件和单据结构

第一次有效实际付款登记成功后开放收货确认。未发生实际付款时不得提交收货确认。

一张采购申请只对应一张最终收货确认单，不建立批次、车辆或分批到货对象。多车到场只需在同一收货确认中上传多张照片。

每条材料保存：

- 采购批准数量。
- 付款数量。
- 实际到货数量。
- 差异说明。

付款数量不是实际到货数量，不得互相覆盖。

### 8.2 责任与委托

- 默认由采购经办人填写实际到货数量、上传照片并确认收货。
- 经办人可以委托同项目人员代为上传和确认。
- 系统保存委托人、受托人、实际操作人、时间和范围。
- 委托不改变采购经办人的业务责任。
- 收货提交后由物资主管复核。

### 8.3 照片和水印

- 至少上传一张材料现场照片。
- 支持系统拍照和相册上传。
- 不请求、不保存、不校验定位。
- 图片上传后由服务端自动生成统一水印。
- 水印至少显示项目名称、采购申请编号、上传时间、上传人和可选备注。
- 水印视觉采用类似水印相机的照片下方信息卡样式，尽量不遮挡材料主体。
- 经办人可以填写照片备注，例如“免烧砖”。
- 乙方送货单照片可选，不能替代材料现场照片。
- 原图、水印图、哈希和来源标签均私有保存。

### 8.4 提交、复核和更正

- 草稿提交前可以删除、替换照片和修改备注。
- 首次提交后，既有正式照片不能删除、覆盖或替换，只能追加并填写原因。
- 物资主管可以复核通过或退回。
- 正式办结前发现录入错误，可以撤回收货确认、创建新修订并重新提交；旧修订、照片和复核记录全部保留。
- 正式办结后不能更正收货事实。

## 9. 少货、补货与退款

收货实际数量少于付款数量时进入“差异处理中”，不能直接正常办结。

系统按付款审批时冻结的单价计算差异：

```text
实际应付金额 = Σ（物资主管复核认可的实际到货数量 × 付款审批单价）
已多付金额 = 累计有效实付金额 - 实际应付金额
```

客户端不得手工填写差异金额。

### 9.1 尚未支付的差额

如果尚有未支付金额，系统按已批准单价计算不再需要支付的差额，关闭对应未执行额度。关闭只影响剩余待付，不改写原审批金额。

### 9.2 已经多付的差额

只允许两种处理：

1. 商户继续补货；补货后重新提交收货修订并由物资主管复核。
2. 商户退回差额；财务人员登记退款金额、时间、方式和退款凭证。

本轮明确取消“转商户余额”：

- 不建立零星采购商户余额账本。
- 不按商户名称跨单抵扣。
- 不复用正式供应商门户余额。
- 现有供应商余额表和路由在新流程中停写，物理退役另行设计。

退款不会删除或改写原实际付款记录。系统分别展示审批金额、累计实付、退款金额和净支付金额。

### 9.3 超量到货

实际到货数量超过付款数量时，不得静默增加本付款申请金额：

- 如果属于商户无偿多送，单独记录无偿附赠数量和说明，不增加付款或发票金额。
- 如果超出部分需要付款，必须另行发起零星采购，不得在已经发生实际付款的原单上追加应付金额。
- 实际到货数量和无偿附赠数量合计超过采购批准数量时，必须醒目标记异常并由物资主管核对。

## 10. 发票附件与办结后补传

### 10.1 预计票据条件

预计票据方式在付款明细中审批，采购申请不含票据字段。每行可选择：

- 无发票。
- 增值税普通发票，并填写预计税率和含税单价。
- 增值税专用发票，并填写预计税率和含税单价。

预计票据条件属于付款审批快照，不因后续上传文件而改写。

### 10.2 实际发票文件

实际发票关联整张付款申请，不强制关联某一次实际付款。

- 日常界面按一张发票设计。
- 极少数拆票场景允许追加多份发票文件。
- 当前只上传图片或 PDF 文件。
- 当前不要求录入发票号码、开票日期、价税合计、销方、税额或验真结果。
- 当前不执行发票金额分摊、覆盖计算或 OCR。
- 当前不会自动判断实际发票是否与预计类型、税率或金额一致；如需结构化核验，留到未来发票系统统一建设。
- 经办人和当前项目财务人员均可补传。
- 上传不新增审批，只记录上传人、上传时间、文件哈希和审计。

### 10.3 发票状态

发票状态与采购业务状态独立：

- 无需发票：付款明细全部选择无发票。
- 待补发票：存在预计有票明细，但尚未上传实际发票文件。
- 已上传发票：至少有一份有效实际发票文件。

发票不是办结条件。业务办结后仍可从付款详情补传发票，补传不重新打开采购或付款审批，也不改变办结状态。

## 11. 状态、撤销和异常终止

### 11.1 主流程

```text
采购草稿
  -> 采购审批中
  -> 采购已批准/付款草稿
  -> 付款审批中
  -> 已批待付
  -> 部分付款或全部付款
  -> 收货待复核
  -> 差异处理中（如有）
  -> 已办结
```

第一次实际付款后即可收货。正常业务办结必须同时满足：

- 付款审批已经完成。
- 资金结算已经完成：无差异时累计有效付款等于审批金额；少货时未执行额度已关闭，且已多付部分已补货或退款。
- 收货确认已经由物资主管复核通过。
- 没有待处理收货差异。

发票未上传不阻断办结。

### 11.2 正常撤销

尚未发生任何实际付款时，允许按审批引擎和业务状态撤销：

- 采购申请撤销后，关联付款草稿或未付款付款申请失效。
- 审批和撤销历史永久保留。
- 不删除业务根单、版本、附件或审批记录。

### 11.3 异常终止

发生任何实际付款后，不允许普通撤销。经办人或财务人员可以发起异常终止并填写原因，由财务主管单独确认。

异常终止后：

- 状态显示“异常终止”，不显示“已办结”。
- 保留采购审批、付款审批、实际付款、凭证、收货、退款和附件。
- 项目经理可以查看结果，但不是确认节点。
- 本轮不设计退款之外的损失核销流程。

正式办结后不允许撤销或更正采购、付款、收货和差异事实；办结后补传发票属于追加归档，不属于更正。

## 12. PDF 与持续归档包

### 12.1 A4 采购申请审批单

沿用公司现行 A4 竖向《零星/小额材料采购申请表》。标题下增加项目名称和系统采购申请编号。

主表布局：

1. 申请部门、申请人、采购部门。
2. 采购人、全单统一的要求采购到位日期。
3. 材料表：序号、名称、型号、单位、数量、备注。
4. 物资用途及采购原因。
5. 物资部部长意见。
6. 项目经理意见。

不显示申请日期、供应商、单价、金额和票据条件。

### 12.2 A5 付款申请审批单

沿用公司现行 A5 横向《项目零星付款申请单》。系统付款编号和关联采购编号作为标题下的小号元数据，不破坏原表格结构。

主表布局：

1. 项目名称、自动申请日期。
2. 付款主体。
3. 付款事由。
4. 申请金额小写和大写。
5. 付款类型与拟付款方式。
6. 对方账户信息：户名、账号、开户行或对应渠道；存在多个批准渠道时，主表展示主要渠道，A4 付款明细列出全部渠道。
7. 经办人、部门经理、综合部、财务部、董事长/总经理固定签字格。

版面以已确认的 A5 横向视觉稿为基准：整体垂直空间均衡，主表不溢出纸张，董事长/总经理签字区不占用过多高度。

### 12.3 A4 付款明细附页

付款主表后生成 A4《零星材料付款明细》，至少展示：

- 付款主体。
- 付款类型。
- 实际采购商户。
- 收款对象和不一致说明。
- 材料名称/型号、单位、批准数量、付款数量、单价、金额、预计票据条件。
- 已批准收款渠道。
- 可选付款依据附件目录。
- 审批金额、累计已付、退款、净支付和剩余待付。
- 当前付款、采购和发票状态。

材料较多时自动续页，每页重复表头、付款编号、版本号和连续页码。

### 12.4 不可变审批 PDF

采购和付款审批最终完成时分别生成审批 PDF。审批 PDF 保存审批结束时的表单、审批人姓名快照、时间、结果、意见和公共签名引用，生成后永久冻结。

- 后续实际付款、退款或发票补传不得改写该审批 PDF。
- 审批节点固定格子的统一签名渲染继续接入公共审批单能力，本轮不建立第二套签名系统。
- 自动跳过、未处理、退回或驳回节点不得生成虚假通过签名。

### 12.5 持续归档包

付款审批后另维护“最新归档包”，按事实追加生成新版本，旧版本不覆盖、不删除。页面顺序固定为：

1. A5《项目零星付款申请单》审批原件。
2. A4《零星材料付款明细》。
3. 审批前可选付款依据：报价单、收据、当时已有的发票。
4. 分次实际付款记录及每笔付款凭证。
5. 办结后补传的发票文件。

图片和原 PDF 可以作为归档包页面；Word/Excel 只进入附件目录并保留私有原文件。所有归档页使用同一付款编号、版本标识和连续页码。

“已付款事实”显示在最新版付款明细和实际付款记录页，不覆盖审批时的 A5 原件。这样既满足归档包反映真实付款，又保持签批原件不可变。

### 12.6 归档版本触发

以下动作成功后生成新的归档包版本：

- 付款审批最终完成。
- 每一笔实际付款和凭证登记成功。
- 付款执行作废或退款登记成功。
- 采购正常办结或异常终止。
- 办结前或办结后补传发票。

归档生成失败不得回滚已经成功的审批、付款、退款或发票上传；应标记失败、记录原因并允许重试。

- 业务列表和详情按项目、岗位、本人关系和待办关系授权。
- 银行账号等敏感信息在列表脱敏。
- 完整账户、付款凭证、发票原件和归档包仅对业务必需人员开放。
- 敏感下载必须填写原因、写下载审计并使用短时效地址和下载水印。

## 14. 后端不变量与审计

### 14.1 后端不变量

- 一张采购只有一个当前有效版本和一张当前有效付款申请。
- 采购申请不保存商户、价格、金额或票据条件。
- 付款明细只能引用采购批准材料，付款数量不得超过批准数量。
- 付款申请金额由后端按付款数量和单价重算。
- 一张付款申请只有一个收款对象，可以有多个该对象的收款渠道。
- 经办人垫付报回的收款对象和账户持有人必须为经办人本人。
- 商户和收款对象不一致时说明必填。
- 所有实际付款使用同一批准付款主体和收款对象。
- 每笔实际付款方式必须属于批准方式，累计付款不得超过审批金额。
- 每笔付款和退款必须分别拥有自己的有效凭证。
- 未发生实际付款时才允许普通撤销或替代付款申请。
- 收货提交前必须至少存在一笔有效实际付款和一张成功生成水印的材料照片。
- 实际到货数量不能静默超过采购批准数量。
- 少货差异未解决时不得正常办结。
- 不建立或执行商户余额。
- 发票状态不参与办结条件。
- 正式办结后业务事实不可变，发票只可追加。

### 14.2 必须审计

- 采购、付款和收货的创建、修改、提交、退回、驳回、撤销、作废和版本切换。
- 申请人/申请部门文本建议的选择结果，但不需要记录未选中的建议。
- 审批实例冻结、节点跳过和每个审批动作。
- 付款主体、拟付款方式和关键付款事实的每次变化及重审原因。
- 实际付款、付款凭证、退款和退款凭证。
- 收货委托、照片上传、水印生成、提交、复核、退回和修订。
- 异常终止的发起和财务主管确认。
- 发票上传、追加和文件失效。
- 审批 PDF、归档包的生成、失败、重试、版本和下载。
- 权限拒绝和敏感文件下载。

审计不得保存密码、短时效令牌、完整银行账号或不必要的敏感原值。

## 15. 数据迁移和旧能力收口

### 15.1 前向迁移原则

生产新零星采购记录为 0，本轮仍只允许前向迁移：

- 新增申请部门、申请人、采购部门、要求到位日期等字段。
- 将价格、金额、商户和预计票据条件移动到付款及付款行事实。
- 增加我方付款主体快照、商户文本、收款渠道和付款方式集合。
- 增加发票附件状态、异常终止和持续归档包版本所需事实。
- 通过数据库唯一约束或事务锁保证一张采购只有一张当前有效付款申请。
- 原有零星采购表即使为空，也不通过手工 SQL 直接改生产；必须使用可复现迁移。

### 15.2 停写但暂不破坏性删除

新流程不再调用：

- 供应商余额形成、预留、转入和抵扣。
- 以发票金额分摊和无票确认驱动采购自动办结。
- 为同一采购创建多张并行付款申请。
- 收货前无实际付款的入口。

相关表、列、路由和历史代码的物理删除必须另写退役计划。重构完成前，测试必须证明新路由不会写入这些旧事实。

### 15.3 旧项目支出

既有 `ProjectExpenseRequest` 历史记录继续只读，不迁移、不删除、不伪造新表单缺失事实。新零星采购写入口不再写旧表。

## 16. 测试和验收

### 16.1 后端重点测试

- 采购申请没有商户、价格、金额和票据字段也可提交。
- 手填申请人/申请部门、同项目历史建议和版本快照。
- 全单统一要求到位日期。
- 材料范围和批准数量冻结，付款新增材料或超数量失败。
- 采购批准后只自动创建一张付款草稿，并发创建不能产生重复有效付款。
- 付款金额、含税单价、无票单价、税率和大写金额的后端计算。
- 商户自由文本、同项目历史建议和不复制账户。
- 商户与收款对象不同的说明校验。
- 经办人垫付报回只能付给经办人本人。
- 付款主体的角色、阶段锁定和财务主管调整后退回综合部重审。
- 一张付款多笔实际付款、不同批准方式、同一付款主体/收款对象和累计上限。
- 银行、微信、支付宝和现金凭证规则。
- 第一次实际付款前不能收货，付款后可以收货。
- 单张最终收货、同项目委托、相机/相册、不请求定位、水印和可选送货单。
- 收货退回、办结前修订、办结后不可更正。
- 少货未付款额度关闭、继续补货、退款凭证和禁止转商户余额。
- 正常办结、待补发票办结和异常终止。
- 办结后发票追加不重开审批。
- 审批 PDF 不可变，付款或发票追加只生成新归档包版本。
- 权限、项目范围、敏感字段脱敏和下载审计。

### 16.2 Web 重点测试

- 零星采购四个入口和“费用与报销”独立菜单。
- A4 采购申请字段责任、材料表和附件上传。
- A5 付款申请、付款主体阶段控制、商户/收款人和付款行编辑。
- 采购工作台付款金额“待确定”到实际金额的推进。
- 付款工作台审批金额、累计已付、退款、净支付、剩余和发票状态。
- 一张付款的多笔实际付款及凭证展示。
- 收货照片拍摄/相册上传、水印、委托和物资主管复核。
- 差异处理中、补货、退款、正常办结和异常终止的下一步动作。
- 办结后仍可补传发票，但不能修改审批和收货。
- A4/A5 打印尺寸、分页、长项目名、长商户名、九行以上材料和中文金额大写。
- PDF 原件与最新归档包的版本区分。

### 16.3 受控真实场景

重新开放试点前至少验证：

1. 采购申请无价格审批，付款申请后确定商户、价格和有票条件。
2. 公司直付，商户与收款对象一致，一次付款、一次收货。
3. 公司直付，商户与个人收款对象不同并填写说明。
4. 经办人垫付报回，收款对象锁定经办人本人。
5. 同一付款申请分两次付款，分别上传凭证，第一次付款后完成收货。
6. 现金付款，只上传收据，后续补传发票。
7. 采购全部无票并正常办结。
8. 预计有票但办结时未取得发票，状态保持待补发票，办结后补传。
9. 经办人委托同项目人员使用相册照片确认收货，物资主管复核。
10. 少货后商户继续补货。
11. 少货多付后商户退款，财务登记退款和凭证。
12. 已有实际付款后由财务主管确认异常终止。
13. 审批 PDF 永久不变，付款、退款和发票追加形成连续归档包版本。

每个场景必须同时核对 API 事实、数据库不变量、Web 状态、PDF/归档包、私有文件、权限和审计，不能只看页面按钮。

## 18. 完成定义

只有满足以下条件，才能宣称本次零星采购真实表单重构完成：

- 采购申请真实复刻 A4 纸质表，只审批申请、材料范围和数量。
- 付款申请真实复刻 A5 纸质表，并在付款明细中确定商户、金额、票据、收款和付款主体。
- 一张采购只有一张当前有效付款申请，一张付款可登记多次实际付款。
- 第一次实际付款后开放收货，资金结算和收货复核完成后正确办结。
- 少货只能补货或退款，不产生商户余额。
- 发票不阻断办结，办结后仍可补传。
- 审批 PDF 不可变，持续归档包准确反映付款、退款和发票追加事实。
- 工作台、权限、私有文件、审计、并发和失败补偿均通过验收。
- 生产入口只在全部闸门通过并获得新授权后恢复。

只完成页面、只调整 PDF、只修改数据库或只恢复白名单，均不能宣称重构完成。
