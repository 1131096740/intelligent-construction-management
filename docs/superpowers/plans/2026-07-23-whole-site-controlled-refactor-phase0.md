# 建工智管整站受控改造：阶段 0 总控方案

日期：2026-07-23
状态：阶段 0 已于 2026-07-23 获用户书面确认；阶段 1 可开始
执行分支：`codex/whole-site-phase0`（基于 `codex/whole-site-foundation@07b23f6d`）

## 1. 目标、边界与事实来源

目标是在不丢失现有业务能力和业务数据的前提下，将系统收口为一套响应式 Web 业务工作台，并补齐费用报销、借款、签名、正式编号、统一待办和正式文件能力。完成定义以总规格第 29 节为准；本文件只定义受控实施方法、迁移边界和验收门禁。

事实优先级如下：

1. `PROGRESS.md`：当前实施、测试、发布和生产状态。
2. `AGENTS.md`：架构、安全、目录、组件库和生产操作边界。
3. `docs/superpowers/specs/2026-07-23-whole-site-business-ui-and-expense-design.md`：目标业务与 UI 标准。
4. 当前代码、Schema、迁移、自动化测试、Git 拓扑和阶段 0 生产只读快照：实现与存量事实。

本改造是受控重构，不是一次性重写。以下行为在没有单独授权时禁止：生产发布、生产迁移、正式业务数据初始化/清理、批量改写草稿、删除旧能力、删除旧文件、强制覆盖分支。

## 3. 改造策略

采用“共享交互骨架，领域规则独立”的增量路线：

```text
现有领域服务、审批、文件、账本、PDF、审计
              │ 保留不变量、逐域补齐读取模型
              ▼
共享应用层：导航 / 工作项 / 读取模型 / 编号 / 签名 / 组件契约
              │
              ▼
Vue + TDesign 页面层：工作台 / 详情 / 移动端 / JgBusinessGrid
```

不得建设第二套权限、文件、审批、审计、付款账本或低代码运行时。共享组件只承担展示与交互契约；金额、权限、状态、版本、归档和并发仍由各领域后端事务决定。

实施顺序选择“兼容层优先 + 只读金丝雀 + 费用垂直闭环”。它比先全站换皮更容易隔离行为变化，也比先做费用模块更能避免重复组件和读取模型。

## 4. 目标架构

### 4.1 Web 应用

- `apps/web-admin/src/app/`：外壳、导航、全局刷新、设计 token、响应式规则。
- `apps/web-admin/src/components/`：跨域 `Jg*` 组件。现有 `Business*` 组件在迁移期作为兼容层演进，不平行复制视觉系统。
- `apps/web-admin/src/pages/<domain>/`：领域页面与领域组件；页面不直接调用 `fetch`。
- `apps/web-admin/src/api/`：每个领域的 API 类型和请求；只接收后端投影的 `availableActions`、工作项和只读快照。

目标共享组件按总规格固定为 `JgWorkbenchShell`、`JgPageHeader`、`JgTaskCard`、`JgFilterBar`、`JgBusinessGrid`、`JgStatusTag`、`JgDetailTabs`、`JgApprovalTimeline`、`JgAttachmentPanel`、`JgActionBar`、`JgDocumentPreview`、`JgSignaturePanel`、`JgResultState`。每个组件必须有 props/slots 边界、Vitest 行为测试和至少一个真实页面消费者。

### 4.2 业务应用服务

- 保留合同、结算、付款、零星采购、私有文件、审批、审计和现有 PDF 的事务不变量。
- 建立统一工作项投影，首页、侧栏、审批中心与领域工作台都从同一服务端事实计算；页面不按岗位字符串猜测动作。
- 建立共享正式编号服务与签名版本服务，但通过领域适配器接入，不能以一次大迁移替换所有现有编号/签名。
- 新费用报销/借款建立独立领域模块和不可变分录账本；旧 `ProjectExpenseRequest` 不改写为万能新表。

### 4.3 数据与文件

- 所有 Schema 变更均为前向兼容迁移：先新增表、列、索引和读路径，再双读/切流，最后经单独授权处理旧写入口或清理。
- 历史业务、历史 PDF、旧签名和高精度字段保持只读可见。不能从旧数据可靠推断的事实必须显示为“历史单据，未按新流程采集”。
- 私有文件仍只经后端鉴权与短时票据下载；新费用附件、签名版本和 PDF 版本进入现有文件绑定、审计和归档体系。

## 5. 数据迁移策略

### 5.1 通用模式

每个领域遵循以下顺序：

1. **发现**：阶段 0 只读统计行数、状态、附件、审批、精度和异常比例，不输出敏感字段。
2. **扩展**：新增可空列或独立表、读模型和索引；旧写路径继续可用。
3. **双读验证**：新旧读模型对同一记录输出等价业务状态、金额、文件和权限；不做自动回填推断。
4. **切流**：仅新建记录进入新流程，历史记录继续走兼容读路径。
5. **受控迁移（如需要）**：先 dry-run、备份、隔离恢复演练、逐批审计；每批生产写入均需用户单独授权。
6. **退役**：旧写入口先隐藏并拒绝新写，保留只读和回退开关；物理删除仅在数据保留期、回滚窗口和用户授权同时满足时进行。

### 5.2 重点领域

| 领域 | 数据策略 | 不允许的操作 |
| --- | --- | --- |
| 合同/结算/付款 | 保留主键、版本、付款条款、归档和审批引用；页面和读取模型增量迁移 | 改写生效版本、重算历史金额、重走历史审批 |
| 历史合同接管 | 仅补充受控的新事实；保留接管等级、确认人和原文件 | 批量重建、伪造过去审批、自动修复不确定金额 |
| 零星采购 | 仅迁移工作台外观和工作项投影；保留采购、付款、收货、退款、票据状态机 | 合并付款/收货记录、重算退款、覆盖冻结税率 |
| 旧项目支出 | 冻结为历史兼容域；新费用/借款不再向其写入 | 自动拆成报销行、借款或还款分录；删除旧附件 |
| 费用/借款新域 | 新表承载报销单、费用行、附件版本、借款分录、冲销预留、还款和付款接力 | 使用浮点金额、直接编辑余额、无审批/审计写入 |
| 正式编号 | 新服务按领域事务分配；保持已发编号不变 | 重新编号、回收断号、用前端生成正式号 |
| 签名 | 新增不可变签名版本；审批冻结引用签名版本和哈希 | 用用户当前签名覆盖历史审批、把上传图片伪装成手写签名 |

## 6. 阶段 0 工作包与验收

### 0A：事实冻结

- 记录分支、worktree、基线 SHA、工作树、远端引用和当前规格版本。
- 核对路由、页面、共享组件、API、服务、Schema、迁移、测试和 UI 检查规则。
- 产物：本文件、能力矩阵、Git 收据。

### 0B：生产只读兼容快照

- 通过受限凭据执行聚合只读检查：旧项目支出、合同编号规则、草稿状态、签名覆盖、高精度记录、迁移状态和关键文件绑定。
- 不打印姓名、电话、账户、文件名、对象键或密钥；不手动触发备份，不进行任何写入。
- 产物：脱敏只读收据和“可迁移/需人工确认/阻断”清单。

### 0C：规格冲突决议

用户已于 2026-07-23 书面确认以下业务/数据/发布风险决策：

1. **合同编号**：所有未来合同在首次成功保存时由统一日流水服务分配正式号；已发合同号永不改写、不得回收断号。
2. **精度**：所有未来新增或修改的业务写入均最多两位小数，包括零星付款税率、收货数量和结算导入。历史事实、冻结文件和已发布模板按原精度只读；旧草稿再次保存前必须人工调整至两位，禁止自动舍入或静默改写。
3. **签名**：Canvas 签名版本上线后，所有未来审批必须具有有效 Canvas 签名；历史上传签名只用于既有审批和 PDF 的只读展示，未设置新签名一律阻断审批动作。
4. **真实 UAT**：仅在最终候选完成后，以用户另行授权的生产测试项目执行；此前的本地/生产等价验证不宣称为真实 UAT。
5. **实施分支**：`codex/whole-site-phase0` 升级为唯一实施分支；不合并或覆盖正被占用的 `codex/whole-site-foundation`。

### 0D：计划基线验证

在不改业务代码的前提下，执行当前基线的 API/Web/shared typecheck、lint、test、Web `check:ui`、build、P0 E2E、Prisma validate/generate 和 `git diff --check`。任何失败都按“既有/环境/本阶段新增”分类，不以静态检查替代 UAT。

阶段 0 完成标准：两份文档完整、只读快照完成、上述五项决策签认、基线验证有可复现收据、`PROGRESS.md` 更新并形成单一文档提交。未满足前不得进入阶段 1。

## 9. 发布与回滚原则

- 任何生产候选须绑定精确 SHA，给出变更范围、迁移影响、备份、隔离恢复、健康检查和回滚命令。
- 新表/列与新读路径可以随候选发布；正式数据回填、旧写入口关闭、旧能力隐藏或清理均是独立授权动作。
- 回滚优先采用代码回退和开关回切；已经提交的前向迁移不在生产做破坏性回滚，使用兼容代码和修复迁移。
- 发布后只读核验部署 SHA、迁移、服务健康、核心读取和审计；不通过真实业务数据写入来证明发布成功。
