## 2. 结论摘要

最新主线已经形成四类有价值的基础：主体版本快照、若干追加/更正事实、合同历史接管事务、表格与 Excel 基础设施。但它尚不是正式规格所定义的“项目经营管理总账”。

最严重的差距不是页面缺少字段，而是经营口径冲突：

1. 当前项目经营成本由实际付款、代付、施工企业对下付款和施工企业扣款相加得到；规格要求成本在结算、费用、工资或最终扣费确认时形成，付款只清偿应付款。现有公式会把现金动作当成成本动作。
2. 旧一步式施工企业代付路由已经返回 410；但当前可写的 `ProjectAffiliatePaymentFact` 仍可在没有我方付款申请的情况下登记并确认施工企业付款结果，而正常付款申请又被强制限定为我方公司付款。规格要求两类付款共用内部付款申请与审批，审批后才按付款主体分流。
3. 当前上游事实没有具体我方公司字段，无法推导多公司项目资金余额；`availableFunds` 又混入融资额度、审批预占和已批待付，既不是施工企业账上剩余项目资金，也不是公司项目资金余额或当前可分配利润。
4. 当前项目施工企业映射允许结束旧映射并创建新映射；规格要求首笔正式事实后锁定，普通业务不允许中途更换。
5. 当前合同接管只能处理合同中心数据，并要求“接管截止日”；无合同历史支出、项目人员工资、施工企业扣费、公司调拨和外部对账尚无通用接管通道。
6. 当前中文检查器只扫描 Web 的 `.vue`/`.config.ts` 中少量已知英文模式，不能覆盖 API 错误、Excel、PDF、导出、审计详情以及所有技术字段；主线仍存在“挂靠企业”、技术标识列及金额“分”等用户可见表达。

因此，这次变更应当视为经营事实内核与统一录入层的正式重构，而不是在现有“项目经营概览”上继续叠加统计卡片。可复用的是底层事实、审批、附件、审计、Excel 和网格基础设施；必须替换的是旧经营公式、施工企业直付入口、主体切换规则和用户可见技术表达。

## 4. 详细源码证据

### 4.1 经营事实和三层口径（G01、G02、G06）

**现状证据**

- `services/api/prisma/schema.prisma:2336-2374` 的 `ProjectUpstreamFundFact` 已有 `entryKind`、`adjustsFactId`、方向、幂等键、确认状态和主体快照；`2376-2502` 的施工企业合同/结算/付款事实采用相似结构。这是可复用的追加、更正、冲销和证据模式。
- `services/api/prisma/schema.prisma:2562-2589` 的 `ProjectProxyPayment` 又提供另一套施工企业代付事实，但没有跨表来源键或幂等键；`ProjectAffiliatePaymentFact` 与其可以表达相同的施工企业对下付款。
- `ProjectService.getOperatingFundsOverview` 同时查询 `ProjectProxyPayment` 和 `ProjectAffiliatePaymentFact`（`services/api/src/project/project.service.ts:618-717`），再分别汇总（`790-804`）并相加到成本（`819-834`）。数据库和服务均没有证明二者互斥。
- 同一方法把付款执行、项目支出执行和零星采购执行相加为 `actualPaidCents`（`819-826`），再把实付、代付、施工企业对下付款和全部扣款相加为 `operatingCostCents`（`827-834`）。这与规格“结算/费用确认形成成本，付款只清偿债务”相反。
- 收入有上游结算时取结算额，没有时直接取业主付款额（`827-829`），与规格“只有到账不能单独证明收入”相反。
- 当前测试固定了旧公式：`services/api/src/project/project.service.spec.ts:964-997` 期待实付和两类施工企业付款直接进入经营成本；`1006-1016` 又明确断言同时读取两个付款来源。现有测试不是新规格验收证据，反而是必须改写的旧口径基线。

**差距判断**

不能在该方法上继续加字段。需要一个服务端唯一的经营事实投影入口：业务来源事实仍归各领域所有，但每个正式来源只能投影一次，并以“来源业务类型 + 来源业务编号 + 来源版本/分录号”全局去重。收入、成本、应收应付和现金必须由不同投影规则生成，不能由页面或概览服务相加猜测。

### 4.2 主体、施工企业锁定与多公司项目（G03、G04、G07）

**可复用能力**

- `CompanyEntity` 和 `CompanyEntityVersion` 已提供我方公司字典与版本记录：`services/api/prisma/schema.prisma:60-89`。
- `ProjectAffiliateAssignment` 保存施工企业业务相对方版本和名称/信用代码快照：`services/api/prisma/schema.prisma:149-168`。
- `ProjectAffiliateCompanyContract` 能明确一份施工企业—我方公司合同的两边主体快照：`services/api/prisma/schema.prisma:2521-2560`。
- 报销已经保存所属公司与实际付款公司：`ExpenseClaim.companyEntityId`、`paymentSubjectCompanyEntityId`，见 `services/api/prisma/schema.prisma:2116-2165`。

**冲突和缺口**

- `ProjectAffiliateAssignment` 本身有 `endedAt` 和变更原因；`ProjectService.assignAffiliate` 在发现当前映射时结束旧行并创建新行（`services/api/src/project/project.service.ts:356-480`），没有检查是否已经产生正式合同、结算或资金事实。这违反首笔事实后锁定。
- 所有 DTO、异常和页面仍把主体称为“挂靠企业”，例如 `project.service.ts:361-375` 和 `apps/web-admin/src/pages/projects/ProjectOperatingOverviewPage.vue:297-359`，与正式用户语言“施工企业”冲突。
- `ProjectUpstreamFundFact` 的施工企业向我方拨款只有 `projectId`、相对方和施工企业快照，没有 `companyEntityId`（`schema.prisma:2336-2374`）。因此同一个项目多家公司收款时无法形成公司分账。
- `ProjectAffiliateCompanyContract` 只有合同事实；主线没有对应的公司结算、公司开票、施工企业应付、实际到账匹配和差异模型。
- `Project` 只有编号、名称和启停（`schema.prisma:140-147`）；没有正式的项目参与公司名单、加入原因、停止新增业务状态或公司盈亏分配关系。

### 4.3 付款分流和跨主体代付（G08、G09）

**现状证据**

- 正常结算付款申请创建时写死 `paymentSubjectType: "our_company"`：`services/api/src/payment/payment-request.service.ts:573-589`；合同到期付款同样固定我方公司（`734-752`）。
- 付款审批完成路径要求付款主体和合同签约主体均为我方公司并要求完整公司快照：`payment-request.service.ts:2332-2358`。
- 实际付款执行再次拒绝非我方公司付款主体：`payment-request.service.ts:2900-2956`。
- 旧 `POST /projects/:projectId/proxy-payments` 已在控制器中固定返回 410，且不调用仍保留的旧服务实现：`services/api/src/project/project.controller.ts:500-512`。旧 `ProjectProxyPayment` 仅作为历史事实继续读取。
- 当前可写的施工企业付款事实入口是 `POST /projects/:projectId/affiliate-payment-facts`，它直接调用 `recordPaymentFact`：`project.controller.ts:419-457`。`recordPaymentFact` 要求已确认合同，正常付款要求已确认结算，并形成待确认外部付款事实，但模型和方法都不要求关联我方 `PaymentRequest`：`project-affiliate-business.service.ts:641-836`。因此现行缺口是“外部付款事实没有我方内部审批申请来源”，不是旧一步式路由仍然可写。
- `PaymentRequest` 只有一个 `paymentSubjectType`；`PaymentExecution` 只有实际公司快照；`PaymentExecutionAllocation` 是付款到合同/结算的分摊。三者都没有同时保存原债务主体、批准付款主体、实际付款主体及主体间往来：`services/api/prisma/schema.prisma:1217-1295`。
- 报销允许财务在已批待付时直接把 `paymentSubjectCompanyEntityId` 改为另一家公司并记录审计（`services/api/src/expense-claim/expense-claim.service.ts:552-608`），但不会生成公司间代付应收应付。因此它是可复用的有痕调整交互，不是跨主体会计语义。

**差距判断**

需要把统一付款申请作为深模块边界：申请冻结债务主体和批准付款主体；执行登记实际付款主体和明确核销分配；三者不一致时同一事务清偿原下游应付款并追加主体间往来。施工企业分支只生成一个项目财务提示，不增加模拟施工企业内部流程的状态。

### 4.4 成本分类、无合同费用和工资（G05、G18）

- `ExpenseClaimLine.expenseCategory` 是自由字符串：`services/api/prisma/schema.prisma:2167-2184`；创建 DTO 同样接收普通文字，没有受控一级/二级分类标识：`services/api/src/expense-claim/dto/create-expense-claim.dto.ts:18-44`。
- 旧 `ProjectExpenseRequest` 使用独立的 `expenseType`/`expenseSubtype`（`schema.prisma:2046-2082`）；施工企业付款使用 `paymentType`（`2562-2589`）；施工企业扣款另有 `deductionCategory`（`2336-2374`）。这些字段没有共同分类权威，合同类型、资金用途和成本分类仍会混用。
- 全部 Prisma 模型清单中没有项目人员月度工资、施工企业派驻人员月度承担额或工资确认模型；相关检索只有通用付款类型 `salary`，不能形成“姓名/岗位 + 月份 + 项目承担额 + 依据 + 确认状态”。

统一成本分类必须成为 shared-domain 和数据库共同权威。旧类型保留为“原业务类型/原始分类”，通过显式映射生成八类成本，不能覆盖原值，也不能在各服务里各写一份映射。

### 4.5 财务对账、资金位置和利润（G10、G11、G12、G13）

**现状证据**

- `FinanceRecord` 只有项目、可选付款/费用/结算引用、方向、金额、日期和创建人：`services/api/prisma/schema.prisma:2030-2044`。它没有公司主体、交易对方、账户、凭证、外部对账基准日、核对状态或差异解决链路。
- `ProjectUpstreamFundFact` 支持 `unreconciled_receipt_difference`，但这只是一条待核对差额事实；其模型没有外部对账单、基准日、外部余额、系统推导余额或逐笔勾兑：`schema.prisma:2336-2374`。
- 当前 `availableFundsCents` 为“实际到账 + 可用垫资额度 - project_cash 已分配 - 审批中预占 - 已批待付”：`services/api/src/project/project.service.ts:805-862`。这不是规格中的施工企业账上剩余项目资金，也不是按公司推导的项目资金余额。
- `ProjectReceipt` 没有收款公司字段（`schema.prisma:2313-2334`）；`ProjectFundingAllocation` 只记录同一项目资金来源到付款/费用/零星采购执行的占用和冲回（`schema.prisma:2741-2765`），不能表达公司间、项目间、公司临时使用和归还。
- 页面把旧公式直接展示为“可用资金”“经营成本”“毛利”：`apps/web-admin/src/pages/projects/ProjectOperatingOverviewPage.vue:1101-1133`，没有施工企业余额、各公司余额、四层盈亏或双重可分配利润。
- `Project` 无阶段字段（`schema.prisma:140-147`），模型清单也没有独立项目阶段确认或利润分配实体。

**差距判断**

至少需要三组独立投影：施工企业项目资金位置、各我方公司项目资金位置、项目经营结果。对账保存外部事实和差额，不允许用手工最终余额覆盖投影。项目阶段确认和利润分配是追加式决策事实，不能再用一个 `isActive` 或“项目完成”状态代替。

### 5.3 必须新建的深模块边界

以下是领域边界，不要求每项对应单独微服务：

1. **经营事实投影内核**：接受已确认业务来源，保证来源唯一，生成项目经营、主体往来、应收应付和现金分录；支持更正、冲销、截至日重放和勾稽。
2. **成本分类权威**：八类一级分类、受控二级分类、旧类型映射、原始分类保留、退款冲减原分类。
3. **主体与债务内核**：项目参与公司、施工企业锁定、债务主体、批准/实际付款主体、主体间代付和项目/公司间往来。
4. **施工企业经营内核**：业主结算/付款、向我方合同结算开票付款、对下直付、扣费生命周期、管理费约定、派驻人员承担额。
5. **资金与利润投影**：施工企业余额、公司余额、项目合计、四层盈亏、双重可分配约束、暂分/最终分配和亏损分配。
6. **对账内核**：对账基准日、外部余额/明细、系统余额、逐笔勾兑、差异、提醒、复核和关闭。
7. **通用历史接管内核**：单项目批次、场景适配器、A/B/C、受控期初汇总、生效日、附件批量绑定、重复判定和原子创建。
8. **统一录入定义内核**：同一中文业务字段定义驱动页面网格、Excel 模板、API 校验、逐行错误、权限、草稿、提交和导出。
9. **项目阶段确认**：分别追加收入、成本、扣费、债务、最终盈亏和利润分配确认，不用一个总状态代替。
10. **归零与上线工具**：白名单预检、演练、执行、附件/FK/序列处理、后置核验、审计回执和回滚绑定。

## 6. 迁移与数据风险

| 风险 | 影响 | 必须在实施方案中明确的控制 |
|---|---|---|
| 同一施工企业付款存在两个来源表 | 迁移时可能把同一付款投影两次 | 建立来源交叉匹配规则；不自动合并，疑似重复进入人工复核 |
| 旧成本以付款认列 | 直接迁移旧毛利会污染正式经营结果 | 从结算/收货/费用确认/最终扣费重建成本；旧报表仅留对照 |
| 上游拨款没有公司字段 | 无法自动形成多公司分账 | 迁移前由财务补具体收款公司；不允许默认“我方” |
| 施工企业映射历史可切换 | 同项目可能已有多个主体版本 | 区分真实资料版本变化和业务主体更换；异常项目进入受控修复 |
| 扣款没有生命周期 | 暂扣可能已被算作最终成本 | 逐笔或按期间判定暂扣/最终/补扣/退回/待核对；未知不得进最终利润 |
| 费用分类自由文本 | 同义项和用途项会污染八类成本 | 保留原值，人工/规则映射到统一分类，无法映射的作为缺口而非“其他”静默吞并 |
| C 级合同可确认有效 | C 级金额可能已经影响可付与经营结果 | 新投影默认隔离 C 级正式盈亏；复核既有 C 级激活记录 |
| `FinanceRecord` 粒度不足 | 无法自动恢复公司、账户和外部对账关系 | 把它作为来源证据之一，不把它提升为对账总账；缺失维度由受控接管补齐 |
| 技术 ID 进入 Excel | 用户可能把错误 ID 当业务值并长期传播 | 改为中文业务值 + 系统匹配/选择；导入后展示匹配结果，歧义阻断 |
| 清数保留对象与业务 FK 交织 | 误删模板/人员或留下悬空附件 | 先生成保留/删除清单、FK 闭包和私有文件绑定清单；演练后才能执行 |
| 旧测试锁定旧公式 | 新实现可能为兼容旧测试而保留错误行为 | 先增加新规格特征测试，再有计划替换旧口径测试；不得只改期望值 |

## 7. 验证缺口

本次没有运行测试；以下是代码层面尚不存在或不足的验收证据：

1. 一个源事实只能进入经营总账一次，重复投影被数据库/事务阻断。
2. 结算确认形成成本、付款只减应付；部分付款、退款、更正和冲销在截至日重放后仍勾稽。
3. 项目合并账抵销施工企业—我方公司内部结算，且多公司分账之和等于项目合计。
4. 施工企业首笔正式事实后不可由普通接口更换。
5. 三个付款主体不一致时，原下游债务、实际资金和主体间往来同时正确，项目成本不重复。
6. 施工企业账上资金、各公司项目资金、项目资金合计、当前可分配利润逐公式验证。
7. 暂扣税费/保证金不进最终成本，最终确认、补扣和退回只改变正确的成本与资金分录。
8. 外部对账余额不能覆盖系统余额；差额必须有来源、状态、责任人和解决分录。
9. C 级缺口不进入正式利润；A/B 经复核后进入，重复/疑似重复按规格阻断或说明。

## 10. 审计结语

截至 `origin/main@202a1e12b70d34d6e486ff1680220ff2b6a2a10c`，主线具备建设新经营总账所需的一部分可靠基础，但尚未满足正式规格，也不能据此宣称经营数据完整可信或可以完成该范围的直接真实上线。

最优路径不是推倒合同、审批、附件、审计、金额和现有表格基础，而是保留这些成熟能力，在其上建立一个来源唯一、主体清晰、经营与资金分层、可截至日重放的经营事实投影内核；随后再让历史接管、统一录入、页面、Excel 和中文硬门共同使用这一个权威定义。

本结论严格限定于上述 SHA 的只读审计。后续主线变化、规格变化或工作树合并后，必须重新绑定新 SHA 做增量复核。
