## 当前结论

本切片把实施文档中“项目垫资额度申请、审批、实际占用与终止”的连续能力，按依赖关系拆成
F0→F1→F2→F3；这些 F 编号是本任务为控制风险采用的实施切片，不是锁定需求文档中的原文
编号。本次只闭合 F0：服务端权威只读模型、服务端推导动作能力、不可变资金占用台账和只读
前端面板。申请、审批和终止写入口仍分别留在 F1、F2、F3，页面当前不渲染任何写按钮。

F0 已形成可独立提交的本地实现，但不代表 Task 11、实施包 5 或五包发布候选完成。尤其既有
项目垫资额度审批 POST 尚未完成 F2 所需的行锁、生命周期 CAS、动作幂等和并发单赢家改造，
因此不得把本切片单独部署为完整垫资额度办理能力。

本轮未连接生产，未推送、合并、部署、执行生产迁移或修改生产业务数据；未执行 retention、
业务草稿 purge、正式业务记录删除、AuditLog/checkpoint 清理、旧表旧字段删除或其他物理删除。

## RED 与最小实现

### RED

改造前的失败证据锁定：

- 后端没有 `GET /projects/:projectId/financing-quotas` 权威工作台；
- 前端没有项目垫资额度 API wrapper、只读面板或项目经营页消费者；
- 项目经营概览仍读取两张旧 usage 表，不能以不可变 `ProjectFundingAllocation` 借贷净额为准；
- 已确认“挂靠企业向我方拨款”没有进入实际付款的项目自有资金来源；
- 资金来源总额仍为正但已低于历史占用时，会被静默夹成 0，并允许下一笔继续占用其他额度；
- 旧已终止/过期额度已超占时，新实付仍可从另一条有效额度写入；
- 经营总览只查询当前有效额度，未先验证旧终止/过期额度超占或账本引用不存在额度；
- 经营概览把 `owner_direct_payment` 业主直付误算为我方可用现金；
- credit 只按来源汇总，未证明其锚定同项目、同实付、同业务和同来源的原始 debit；
- 冻结审批链只做宽松 JSON 解析，不能阻止链路截短、错误岗位或申请人漂移；
- A→B→A 切项目或同项目重复刷新时，旧请求可能覆盖新额度台账；
- HTTP 200 成功响应未做运行时结构校验，错误金额类型或非数组明细会直接进入渲染；
- 前端会把非 approved 的过期记录误标成“已过期”，且未完整展示终止历史。

新增失败测试先分别证明缺失 read model/module/component、资金赤字可继续支付、错误 credit 锚点
可释放额度、异常冻结链仍发布动作、拨款冲减没有资金锁复核，以及旧请求/状态渲染偏差。

### GREEN

后端新增项目作用域 GET，并在 Repeatable Read 快照中读取：

- 当前启用项目；
- 全部项目垫资额度生命周期；
- `ProjectFundingAllocation` 不可变借贷流水；
- 已确认项目自有资金到账和挂靠企业向我方拨款净额；
- 垫资额度审批实例与持久化项目/全局岗位；
- 申请人、批准人、终止人显示名。

金额和状态不变量现在统一失败关闭：

1. 自有资金固定优先，只有实际付款才占用额度，使用人不能手工重排资金来源；
2. 自有资金占用超过当前确认来源、任一历史额度占用超过批准金额、账本引用不存在或未批准额度时均 409；
3. 每条 credit 必须指向同项目、同 execution、同 business、同 source 的原始 debit，且同一
   debit 的累计 credit 不得超过原始金额；
4. 挂靠拨款 decrease 确认会与实际付款共用项目资金锁，更新后在同一事务复核完整资金来源；
   复核失败时确认更新、签名结果和 Audit 全部回滚；
5. 冻结链必须精确为“财务主管 → 董事长/总经理”，进行中、驳回和已批准终态的实例状态、当前索引、
   approvedRoleKeys 和申请人身份必须一致；审批实例缺失/重复或批准人/批准时间终态事实不完整时失败关闭；
6. 业主直付不进入我方现金池；实付分配在写入前复用全量历史额度和不可变账本覆盖校验；
7. 经营总览先查询全部历史额度并复用同一资金覆盖校验，通过后才筛选当前 approved/未过期额度计算可用额；
8. 输出裁掉附件文件 ID、用户内部 ID、审批实例 ID及 allocation/reversal 内部主键和键值，
   只保留页面确实消费的生命周期、金额、业务对象和服务端动作坐标。

资金使用记录按 execution 一次建索引，再按涉及额度投影，避免逐额度反复全表扫描。当前 GET
仍须读取项目完整不可变账本以验证总额不变量；F0 不引入分页截断或近似金额。

前端只通过 `apps/web-admin/src/api/project-financing-quota.api.ts` 调用 API，不直接 `fetch`，
也不从 `auth.user` 猜测角色。项目经营页“资金办理”展示：固定资金顺序、额度汇总、生命周期、
当前审批节点、终止人/时间/原因及实际付款资金拆分。403 静默隐藏无权模块，其他读取失败明确
显示；单调请求 owner 和组件卸载失效机制阻止旧响应覆盖新项目或新刷新，清空项目时不会遗留
loading 状态。状态文字完全采用后端 `statusLabel`。
包装层对项目、分配策略、金额字符串、状态、动作及用量数组做运行时校验，异常 200 响应统一转为受控 502，不把损坏数据交给页面渲染。

## 权限与独立复核

- Controller 使用 path `projectId` 和 `PROJECT_OVERVIEW_READ_POSITION_KEYS`；PermissionGuard
  继续按该项目坐标解析持久 `UserPosition`/`ProjectMember`，不信任客户端角色；
- 项目经理等只读岗位可查看当前项目，但申请、审批、终止动作均由服务端能力矩阵决定；
- 财务主管发起人只可在第一财务主管节点独立自审，最终节点仍必须由董事长或总经理 OR-sign；
- 当前只读面板不渲染申请、审批或终止写动作；
- 三路独立复核初轮发现的资金赤字、credit 锚点、冻结链漂移、经营总览历史额度遗漏、旧响应覆盖、状态改写和响应过度暴露均已修正；当前精确 diff 最终复核 P0/P1/P2 均为 0。
