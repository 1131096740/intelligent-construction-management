## D01：保留领域边界，统一公开行为

继续使用 Vue 3/TypeScript/TDesign、NestJS/PostgreSQL、pnpm workspace。页面通过领域 API 模块访问后端，后台对权限、金额、签署版本、归档和状态转移负责。复用既有草稿聚合、合同版本、文件授权、审计、付款执行和项目经营投影，不增加通用流程引擎或第二套 UI 库。

这是统一产品目标下分片验证、最后统一切换的计划。不是一次提交全部改动；旧协议在兼容期间可读，新建和迁移后的业务统一走新机制，不给用户选择新旧流程。每一业务片必须能从公开 HTTP 到真实数据库和 Web 演示；共享数值和流程协议采用扩展、分批迁移、退役旧接口。

先固定现有混合工作区的文件指纹和归属，再确定集成候选。不能直接清理未提交文件、重置工作区、根据旧验收包继续部署。当前 PROGRESS 中资金真实提交门禁仍未闭合，属于本计划的前置验收约束，不因需求确认而解除。

## D02：精度协议与存储

| 对象 | 新协议 | 计算/展示 |
| --- | --- | --- |
| 合同、结算、采购、报销、经营等非付款金额；单价、数量 | 十进制定点，最多4位；API使用十进制字符串；金额/单价建议 PostgreSQL `numeric(24,4)`，数量同精度并明确单位 | 输入超过4位返回字段错误且保留输入；负数仅限允许冲减的业务；禁止科学计数、非有限值和隐式截断 |
| 实际付款、付款申请及其未付占用 | 整数分继续存储，以字符串传输大整数，或经统一边界转换；不能混用“元”与“分”字段 | 支付额按半入四舍五入到2位；JS Number不得承载账务计算 |
| 已有 cents 字段 | 保留原字段直到调用者迁完；新增字段及精度版本 | 旧整数分精确除100，无反推丢失的小数；只在旧消费者边界产生按规则舍入的兼容值 |
| 未约定/待补充 | 允许值为空并有明确业务状态 | NULL不同于0；原币种以现有人民币口径为准，不引入多币种 |

`numeric(24,4)`为实现建议：数量和金额均须有服务端有限范围校验，超过范围明确拒绝；历史扫描先检查旧值能否无损承载，不能靠数据库异常或缩小历史值迁移。现有6位小数真实资料超过4位时保留原值及来源并形成待核对报告，不自动舍入既有确认记录。新输入遵循4位，历史显示注明原精度；“全平台统一”不等于篡改历史。

统一数值模块必须显式区分“十进制元”“整数分”“数量”，有精度版本；使用定点/十进制库和数据库 numeric 运算，不采用 parseFloat 后乘100。草稿、API、数据库约束、Excel、PDF、列表和聚合都遵守同一协议。负零规范为0，结算0拒绝；税率最多4位且不做推断，税率空不得当0。

清单已知数量×已知单价先将行金额半入到4位，再逐行合计；缺一项不按0乘。明示包干金额是独立已知值；框架部分行金额不当作确定总价。结算累计先完整相加再转换支付口径：0.005+0.005→累计0.0100→可付0.01。100.005→支付上限100.01，付100.01视为付清，原业务金额仍100.005。负数采用绝对值半入后恢复符号，避免正负不对称。收款、退款、期初等未被明确限制到分的事实保留源精度；不能擅自把所有资金事实强制两位。

扩展顺序：建立数值适配与测试算例→逐领域双写校验→只读影子比对→按领域切新读写→停止旧写→全部调用迁完后另批退役旧字段。新4位值不能在旧协议下丢精度后回写覆盖。迁移过程中每条记录标来源、转换版本和核对状态，不叠加两套数值。

用户补充确认：业务金额中文大写精确到厘、毫，1.5340元为“壹元伍角叁分肆厘”；仅新精度协议文书接入，旧协议与实际付款到分规则保留。日期使用公共北京时间适配器，明确区分日期、无时区本地时间与带偏移时刻；实际资金登记保留未来时刻拒绝，退款不得早于原付款业务日。

## D03：并联审批状态与签字

保留审批实例和日志领域，增加流程版本、轮次、业务提交快照、必需职责集合以及每职责的办理状态/版本。职责实例与岗位候选人分开：一个职责可多人办理，首个有效动作完成该职责；同人兼多职责仍分别确认。GM/董事长属于同一可替代职责。所有必需职责创建后同时待办；不能用单个 currentNodeIndex 表示当前状态。固定岗位表以完整规格为准。

建议状态：单据草稿→本轮办理中→全部同意→业务后继；任一拒绝→退回草稿；全部通过前撤回→草稿。事务中锁本轮和职责，验证最新版本、操作者职责与项目范围；动作幂等。所有人同意才能提交业务通过事件。并发拒绝与同意不能双终态；旧轮迟到动作拒绝且不产生签字/待办。未配置的职责明确待配置，已配置职责照常办理；补人后仅唤醒缺失职责。禁用账号或调岗不能让旧链接继续授权。

创建人或提交人办理自己的职责，必须填写自审原因并验证本人密码；技术管理员不因管理权限成为审批人。临时委托限定业务职责、范围与有效期，委托人与被委托人任一完成即关闭对应待办，记录实际办理人和委托关系，不扩大原数据读取范围。

多节点结算审批退出；合同主管的单职责复核复用动作、待办、驳回与审计基础，不为结算再生成内部多节点流程。财务更正、补充协议复核及依赖前步输入的历史接管按各自业务模型处理，不能强行并联输入依赖。

新机制每轮冻结提交内容、签字位置及已通过职责；驳回不签字。退回/撤回后当前审批单清空本轮签字，重提创建新轮。用户只保留最新轮审批单：旧轮文书失效、停止访问并从可清理的生成产物中退出；保留动作人/时间/原因审计，不保留旧轮可下载审批单或可重建的历史签字快照。现存真实历史审批资料保持只读，不追溯清除。通用个人签名原件不因某轮失效删除；引用计数、隔离策略和保留审计须独立检查。

当前轮PDF允许办理中下载，清楚标示未完成、仅嵌入已同意签字，空位留空，不伪装通过。沿用既有水印与下载审计。后台每次校验当前轮及读取权；新生成/下载结果不得取到旧轮缓存。有权查看流程者可按一分钟规则催办；查看权不等于审批或修改权，单纯日志查询权也不扩大业务查看范围。

在途真实串联流程切换：保留提交内容与真实有效同意/动作，将原必需职责映射到新轮职责；已经有效完成的职责保留，其余同时唤醒；不因技术迁移重新要求已完成者签字，也不跳过未完成职责。若原岗位无法唯一映射，标待配置，由有权管理人员补齐；原事实和迁移映射审计保存。已驳回/草稿重提采用新全体审批。已通过的业务不因切换重审。

## D04：合同正文与版本

正式实现前用现有五类、八份模板、用户确认的材料/机械多列清单和字体样张做可编辑文档验证。先证明正文编辑、关键字段同步、手工条款保留、PDF/Word一致和分页，再固定编辑/转换方案；不在本规格未经验证指定大型编辑器或引入第二套UI。若候选无法保留格式，应记录具体样张差异，不以可编辑纯文本替代完整合同。

建议使用受控结构化文档模型：模板版本+关键字段锚点+可编辑普通条款块+清单表格+签署块。正文来源和导出来源同一版本。关键结构字段只在填写页改，映射锚点精确更新；自定义条款块独立持久化，不在每次保存时从原模板覆盖。全量重新生成/换模板显式确认覆盖影响，提供保存点。普通条款支持插入、修改、删除和排序；段落样式与条款编号受文档样式规则管理。上传模板先解析并由主管确认映射，不靠自动猜测建立错误字段。

草稿自动/手动保存均有修订号与冲突提示，不静默后写覆盖先写。提交冻结填写事实、正文、模板版本及文件校验值；审批中只能撤回修改。普通条款自由编辑不等于可以在正文另改一套甲乙方/金额绕过台账。签后补充协议为增量版本，原合同、历史结算和资金事实不改。

合同内部审批通过→综合主管盖章待办→点已盖章→合同员双方盖章PDF上传归档。生成PDF/Word和双方签署原件分开引用，不覆盖原文件。表外/对上不审批登记直接引用双方已签PDF/照片。合同金额口径含税/不含税明确标识、默认含税；未定税率不虚算另一口径，结算和付款按登记的真实已签金额核对，不因税率补充自动重算已确认金额。税率待补充可在合同层追加；已填事实更正由合同部提交主管复核并保留修订，不更新既有结算税快照。付款中显示当前新约定和提交时约定供核对，条款变化不单独自动暂停付款。

## D05：简易结算与支付容量

建议新结算记录只保留业务主键、项目/合同、手填编号、4位本期金额、创建人、附件、状态、修订及复核事实。编号不是全库唯一：同合同重复提示不阻断，故不能沿用唯一索引。内部分配稳定ID及有序确认序号；确认顺序以事务中确定的序号定义，不能只依赖同秒时间戳。草稿→待主管复核→确认；驳回回同一草稿。确认后金额、合同、附件等原事实不可改或作废，错误另发新正负结算。

提交和主管确认均检查“已确认历史基线+已确认新单+当前单≥0”；待复核负单不提前改变台账。确认时锁合同累计版本，重新求和、检查、写结算及审计/通知事件为同一事务。两笔冲减并发，后确认者必须以最新累计检查。累计不由前端提交；不设合同总额/付款比例额外硬门槛，不重复税率，不生成结算文书。

普通合同付款容量建议定义为：`支付口径累计有效结算 - 有效净已付 - 其他有效未支付申请占用`。累计净已付包括已确认历史付款和本系统后续实付，扣合规已收到退款；历史基线不可再从新流水重复累加。付款占用包括已提交待审批、通过未付、部分付款的未付余额；草稿/驳回/撤回不占。新申请提交及审批通过、实际付款前均按合同锁和版本复核，付款本身再次检查申请余额、合同容量和可用资金。

结算调减后，合同全部未付占用合计超出新余额时，统一标记该合同受影响待付事项暂停，不擅自按先后挑一笔付款；金额仍够时不暂停。部分实付保留，仅未付部分可由综合部撤回调整重审。新正数结算使总余额足够则自动解除客观暂停，无需额外核销仪式。已发生超付如实展示并提示，不能倒改资金记录。预付款有独立申请用途，允许无结算，但计入净已付；合法未结算预付款与异常超付分开显示。其他合同无总额/结算时允许业务判断直接付款，显示无法计算结算上限而非0。

“最新一期”指最后确认的有效结算，包含负数；付款仅选该单取得当前累计快照，不是把最后一期金额当全部可付。审批页及付款办理前重新读当前容量，提交快照用于解释变化，不使用旧快照绕过余额校验。

## D06：统一资金事实、现金与公司往来

不要把现有项目+公司强绑定资金批次简单改成无约束NULL。建议拆开三个维度：资金容器（每公司一个登记余额账户、全系统一个公共现金）、资金来源批次（出资方/待核对、可关联项目）、业务使用归属（项目/公司日常、费用或往来）。一个事实可有多条守恒分录/分摊，使用稳定事实ID关联，不能为展示不同视图复制付款事实。金额账户不代表真实银行账户档案，收款方银行信息与本方资金容器分开。

实际付款由财务或综合主管线下付款后登记；事务写付款事实、申请剩余、资金扣减、来源分摊、往来及审计，全部成功才返回成功。HTTP重试携带同一幂等键，响应丢失后查事实再重试，不能再次扣款。付款成功但数据库无记录的现有事务问题必须以真实PostgreSQL故障注入闭合；升级ORM只是候选，不是验收结果。

公共现金无公司主体，保管人是综合主管，可以用于任意项目或公司日常。已知余额与来源待核对分开，未知余额不当0；来源未明不自动FIFO归给某出资方。现金转公司登记后预占现金，财务确认到账才增加公司可用额；待确认期间不双可用，拒绝仅保持待核对，不凭拒绝自动虚构现金退回。公司转现金由现金保管人确认收到。现金交接记录交出、接收及实点余额，差额先待核对，不自动做费用/收入；原保管人离职可由财务发起接力。

垫资到账如实登记，不设额度审批，不构成收入。来源已知时归还申请关联原批次；已付及有效待付合计不得超过可归还本金，不计利息。资金账户可与原出资收款账户不同，不能因此重复确认本金。公共现金转公司、直接现金支付都保留来源链。

公司替项目补足资金由业务明确确认项目垫资，不从余额差自动创建到账。A欠供应商、B代付，形成A欠B，原供应商支付事实只一次；项目垫资与公司间代付不是自动双计同一债务。C替A归还B后，A-B减少、A-C增加，归还不产生成本/收入。每条往来、归还和更正有源事实引用，冲回采用补偿分录，不硬删资金事实。

财务登记错误用统一更正入口发起，财务主管复核后补偿原事实并登记修正，重算付款、余额、债权和成本的适用投影；保留原值、原因、复核人及来源。主管本人发起可自审但须密码和原因。退款不改原实付，退款金额不得超过有效已付可退余额；退货退款减少采购成本，单纯多付退回只改净付款，已确认合同成本调减仍走负数结算。

## D07：成本、经营投影与采购批次

采购需求与实际采购批次分开；批次记录供应商、实际明细、确定金额，付款/个人垫付报销引用批次并防重占用。收货登记不是本次流程；不能只隐藏收货菜单却让 API 仍依赖 receipt 才能付款。首次关联付款/报销审批通过确认整批实际采购成本，后续分次支付只改现金；普通直接报销通过确认费用。现金费用待公司归属保持明确未归属，不虚配公司，补归属经财务主管确认只改分账。

使用唯一来源键（来源类型、源事实、确认版本）写成本贡献，退款/更正用反向贡献，禁止同批采购付款和员工报销重复计成本。其他合同直接付款不自动代表全部履约成本，已完成工作金额由合同主管、项目经理和财务三职责确认。公司日常费用与项目费用不同范围，一单不混多个项目。

项目总览由已确认收入/成本、实际收付、资金归属和有效债权投影。业主结算形成收入，施工企业转给我方只转资金，不再形成收入；业主预付款未结算部分单列。施工企业直接付下游与我方实际付下游合并对外支付，施工企业转我方不再加一次项目对外支付。施工企业已付金额是其直接付下游+转我方，另有明确名称展示项目对外支付；不能把两指标相加。施工企业扣费按名称金额确认，减少施工企业持有资金和对应成本；其剩余资金不自动变利润。资料不全显示已知金额和待补充，不输出伪完整经营盈亏。

## D08：表格、草稿与台账

复用既有 JgBusinessGrid/RevoGrid，先把R20/21的已确认交互做成统一可验收契约，再逐页接入；不把原型HTML/localStorage直接当生产服务。草稿行有稳定内部标识便于移动、撤销、复制和错误定位，但导出不暴露。选择状态独立于焦点，中文输入期间不处理Enter提交/跳转。剪贴板按十进制字符串保留；复制新增行需新标识。

手机优先同一表格局部滚动和关键列固定，页面本身不横溢；320～1920多宽、横竖屏、软键盘视口、长名称及大表量用仿真验证。必要时用同数据模型的紧凑展示，不创建两套独立状态。底部操作不遮字段，离开未保存提示，断线保留当前输入，重连检查版本，不宣称离线提交成功。

合同/结算/付款/零星材料/综合采购/报销六个独立台账页面，入口一致。后台处理筛选、排序、权限与分页；个人列配置只影响查看。Excel按当前筛选和可见列导出，同时保留项目/实际双方等必要列；读取整套筛选结果而不是只导当前页，预览明确范围。中文模板、样式、合计和打印布局；危险公式前缀转文本，数字保真。导入只落草稿，逐格预检、追加/替换确认和撤销，不自动提交业务。档案打包每次逐文件授权，不缓存越权链接。

## D09：通知与短信

业务提交事务内写待办/通知事件和发送意图（outbox），提交后异步发送；不在事务内等待短信供应商。事件唯一键由事实+轮次+职责+收件人构成，重试不重复创建待办。自动通知覆盖审批以及采购、付款、补填、盖章、归档等非审批环节；所有并联职责同时可办即同时通知。

手动催办按流程/有效职责共享60秒冷却，支持全体或选人；不同点击者不能绕过，已完成职责不发。自动新任务通知不受手动冷却限制。供应商失败与未知结果分开：确定失败允许有记录地重试，未知不自动重发；受理不代表送达。短信含经批准丰富摘要和登录鉴权后的链接，不能放对象存储直链或绕过权限令牌。

网页通知桌面右下、手机网页顶部；初次新任务提示一次，任务数等于当前有权未完成待办而非未读。查看不清待办，任何有权人办完后所有视图同步消失。旧链接显示最新处理结果；无权时拒绝且不泄露摘要。用现有适配器做确定性模拟，真实短信签名/模板和送达另行授权验证。

## D10：真实资料保留、迁移及上线切换

| 阶段 | 行为与产物 | 必须停止的情况 |
| --- | --- | --- |
| 0 只读基线 | 固定代码/候选指纹，核实真实部署版本、Schema和已应用迁移校验值、数据分布、文件引用与权限；分类真实/合成记录 | 无法区分环境、迁移分叉不明、源数据归属不明 |
| 1 可恢复备份 | 受控备份数据库、私有附件/模板/有效签字及配置；在隔离环境实际恢复并核字节/数量/关联和抽样读取 | 只有“备份成功”没有恢复证据；文件缺失；生产凭据进入文档/日志 |
| 2 扩展 | 批准后仅添加兼容字段/关系、迁移映射、版本和唯一约束，旧事实不改 | 现有真实精度/状态无无损映射；既有迁移被改写 |
| 3 演练 | 复制数据脱敏隔离；幂等分批回填，按项目/合同/主体/账户对账，重跑与中断恢复，生成差异报告 | 历史金额/文件校验值改变、重复成本/扣期初、差异未经解释 |
| 4 在途映射 | 草稿原输入保留，串联在途映射并联职责；已付和未付拆开，未付保留申请引用 | 兼岗/委托/缺岗位映射不明；已付款被重置；任务或签字丢失 |
| 5 冻结与切换 | 确定最终候选，暂停写入和通知发送，尾差同步+全量核对，启新接口/页面；先只读核对，再开放写入；outbox按唯一键恢复 | 资金真实提交/权限/恢复门禁未过；任何余额/债权/成本重复；无可执行回退 |
| 6 观察 | 核对真实新单、待办、短信、导出、累计和资金分录；记录差异及责任人 | 返回成功但事实缺失、越权、重复支付/短信等立即停写排查 |
| 7 收缩 | 全部消费者迁完才退出旧写API/Schema；旧真实资料仍只读，清除合成资源需单独清单 | 真实/测试无法确认；共用功能还有引用；企图用删除代替迁移 |

历史原整数分转4位字段不添加想象精度；已有合同/审批/文件/实付/退款/垫资/公司间债权全部保留。历史接管基线有明确截止点，截止前已付只计累计，不再次扣期初资金；切换后新实付才产生新资金分录。历史源单、快照与新聚合用源事实ID去重，不能同时累计期初+原明细+兼容影子记录。

结算用户确认从未实际使用，按新流程实施，不再采访；技术核查只验证“没有真实已确认结算”假设。若发现真实记录，保留并迁移/只读兼容，报告冲突，不删除、不伪造确认。工资和员工借款同理，退出新入口和写路径，不因“未使用”连删共用费用/资金表。无关旧任务的临时目录/容器不接管、不重启、不删除。

回退分界：新系统开放写前，可回旧代码并撤销未启用的扩展（原数据保持）；开放新4位/并联/共享现金写入后，旧代码可能不能正确理解，不能直接回滚到旧二位/串联消费者。此时先停写、保留新事实，优先向前修复；如确需恢复备份，须先导出切换后全部真实增量并有审阅过的重放/对账方案，不能恢复旧备份抹掉新付款。文件和数据库恢复必须使用相同业务时间点。

最终发布以固定源码/迁移/配置指纹和完整门禁为单位，任何后续变动使受影响证据过期。原方案编写时无生产只读核查、无真实短信送达、无迁移执行；当前核查进度见集成起步交接，仍不授予Conditional Go或可上线结论。
