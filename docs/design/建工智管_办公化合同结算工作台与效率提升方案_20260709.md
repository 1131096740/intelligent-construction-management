# 建工智管办公化合同结算工作台与效率提升方案

生成时间：2026-07-09

## 1. 核心结论

建工智管下一阶段的产品方向是：

```text
前台像办公工具，后台像业务账本。
```

合同部、预算部、项目部、财务和领导不是技术用户。系统不能要求他们理解接口、状态码、字段编号、流程引擎或数据库模型。系统要适应他们已经熟悉的工作方式：

- 合同部习惯用 Word 起草合同。
- 预算和结算人员习惯用 Excel 做清单和结算。
- 审批领导习惯看审批稿、金额摘要、附件和风险点。
- 财务习惯看付款依据、可付额度、已付记录、凭证和入账结果。

因此，合同和结算的草稿阶段要尽量贴近 Word 和 Excel；提交审批后要冻结成中文业务审批稿；归档确认后才进入不可随意修改的业务账本。

经过代码库和开源部件可行性调研后，本方案修正为：

```text
账本模型和办公体验双主线推进。
```

当前系统已经具备合同版本、付款条款版本、结算、付款、归档、审批、私有文件和审计的核心账本基础，可以承载这个方向。但不能直接把在线 Office、表格组件、低代码平台或流程引擎接进来当主系统。

在线 Word 和在线 Excel 体验不是锦上添花，而是合同部、预算部和结算人员最高频的工作入口之一，必须尽早做可用体验验证。只是它们只能作为草稿层的办公体验，不能成为审批、归档和付款的事实来源。

对于已经真实在执行的项目，系统上线不是简单补录历史流水，而是做一次受控的在执行项目接管。接管前已经签订、结算、付款的事实，要以接管截止日为边界，经合同部、预算、项目、财务和必要时相对方确认后，形成系统期初事实；接管后新发生的合同、结算、付款、实付、凭证和归档，必须全部在系统内产生和留痕。只有这样，建工智管才可能成为现实业务的唯一真相。

第一批必须同时推进两条线：

- 办公体验线：让合同部能像使用 Word 一样编辑合同正文，让预算和结算人员能像使用 Excel 一样处理清单。
- 业务账本线：补强付款条款结构化录入和结算明细行账本，保证提交审批后可冻结、可追溯、可计算。

第一批必须补强三个业务基础：

- 合同付款条款必须能用中文业务项结构化录入和冻结。
- 结算必须有行级账本，每一行能追溯到合同清单、手工调整、变更签证或扣款依据。
- 在执行项目必须有接管截止日、期初余额、历史结算、历史付款、证据资料和复核确认机制。

办公化体验只能接在草稿层，审批和归档后的事实仍以后台账本为准。

## 2. 全项目用户体验底线

所有用户可见内容都必须是中文、业务化、可理解、能指导下一步。

这条规则覆盖所有页面、按钮、表单、错误、空态、确认弹窗、审批记录、下载原因、导出文件名、Word 占位符、Excel 表头、PDF 标题和审计展示。

### 2.1 不允许出现的用户体验

用户界面不得出现这类内容：

```text
Forbidden
Invalid status transition
contractVersionId required
Missing required project role
Failed to fetch
snapshot
workflow
forceSave
billItem
```

也不能只是生硬翻译成：

```text
无权限
状态流转无效
合同版本 ID 必填
```

### 2.2 应该出现的业务表达

系统应说明发生了什么、为什么不能做、下一步怎么办：

```text
你不是当前项目的合同人员，不能提交这份合同。请联系合同部主管调整项目人员。
这张结算单已经提交审批，不能直接修改。如需调整，请先退回修改。
当前合同还没有形成有效版本，不能发起结算。
本次付款超过当前可申请金额，系统已按合同付款条款和已付款记录重新计算。
审批稿生成失败，请重新保存合同正文后再提交。
```

### 2.3 命名口径

用户可见名称统一使用中文业务名：

| 技术概念 | 用户看到 |
| --- | --- |
| draft | 草稿 |
| submit | 提交审批 |
| snapshot | 审批稿 |
| workflow | 审批进度 |
| contract version | 合同版本 |
| payment terms version | 付款条款版本 |
| bill item | 合同清单项 |
| hash | 防篡改校验 |
| force save | 保存当前正文 |
| risk finding | 风险提示 |

技术名只允许存在于代码、接口、数据库、内部日志和开发文档中。

## 3. 业务边界

合同和结算可以在草稿期自由编辑，但提交前必须变成可追溯、可重算、可审计的业务事实。

### 3.1 合同边界

合同正文可以像 Word 一样编辑，业务事实必须结构化：

- 项目
- 合同编号
- 合同名称
- 相对方
- 合同类型
- 合同金额
- 税率和含税口径
- 付款条款
- 合同清单
- 附件要求
- 提交人和当前责任人

合同正文里的补充条款、说明、格式、备注可以自由编辑。但付款条款、合同金额、合同清单不能只藏在正文里，必须在系统中形成结构化数据。

调研后明确：合同正文编辑器只负责让合同部像使用 Word 一样修改文字和版式，不能反向改写合同金额、付款条款和合同清单。付款条款必须在系统中以中文业务项维护，例如：

- 预付款：合同生效后多少天内支付多少比例或固定金额。
- 当期结算款：结算归档确认后多少天内按多少比例支付。
- 质保金或尾款：最终结算或质保期满后按约定支付。
- 发票、资料、分批支付、预付款扣回等限制条件。

这些条款随合同版本冻结。合同正文里可以保留完整法律表述，但付款计算必须读取结构化条款。

### 3.2 结算边界

结算工作台要像 Excel，但每一行都要能追溯。

结算行分为四类：

| 结算行类型 | 业务要求 |
| --- | --- |
| 合同清单项 | 必须引用有效合同版本中的清单项 |
| 变更或签证项 | 必须上传变更、签证、收方等依据 |
| 合同外暂估项 | 必须单独提示风险并要求说明 |
| 扣款、罚款或调整项 | 必须说明原因并进入审批摘要 |

一线人员可以导入 Excel、粘贴多行、修改本期工程量、补充备注、上传附件。系统提交时必须重新计算金额，不能信任前端合计，也不能信任 Excel 公式。

调研后明确：第一版不能只把结算页改成前端表格。当前结算模型主要保存总金额，还缺行级账本。必须先补最小结算明细模型：

| 模型 | 用途 |
| --- | --- |
| 结算明细行 | 记录每一行来源、工程量、单价、税率、金额快照、附件和备注 |
| 结算导入记录 | 记录导入文件、预览结果、应用人、应用时间和错误行 |

第一版结算明细只需要支持两类来源：

- 合同清单项：必须引用有效合同版本中的清单行。
- 手工调整项：用于扣款、罚款、临时调整和合同外说明，必须填写原因。

变更、签证、扣款正式模块可以后续接入，但第一版必须先把结算行账本建起来。

### 3.3 付款边界

付款必须同时受有效结算和合同付款条款约束。

付款申请页面不能只让用户填写一个金额。系统应先展示：

- 当前合同付款条款
- 有效结算累计金额
- 已申请未付款金额
- 已实付金额
- 历史接管已付或扣减金额
- 历史接管已结算未付金额
- 预付款、质保金、扣回、代付和其他已确认占用
- 本次最多可申请金额
- 超额原因或缺资料原因

后端计算口径：

```text
本次最多可申请金额
= 按合同付款条款计算的可付上限
- 已申请未付款金额
- 已实付金额
- 历史接管已付或扣减金额
- 历史接管已确认占用金额
```

如果接管前已经形成有效结算但尚未付款，不能只作为一段备注或附件。它必须进入系统的期初可付款来源，否则后续付款会缺少依据，系统也不能成为唯一真相。

## 4. 推荐架构

### 4.1 四阶段模型

```text
草稿编辑
  -> 提交审批并生成审批稿
  -> 审批只读查看审批稿
  -> 归档确认后形成有效业务版本
```

草稿可以改，审批稿不可改，有效版本不可覆盖。

调研后的落地方式调整为双主线汇合：

```text
办公体验线：在线 Word/Excel 草稿体验验证
账本模型线：付款条款结构化和结算明细行账本
  -> 两条线在提交审批前汇合
  -> 提交审批并冻结审批稿
  -> 审批只读查看
  -> 归档确认并形成有效版本
```

也就是说，在线编辑器和表格组件不是业务事实来源，但体验验证要尽早启动。第一批既要让合同部和预算结算人员看到接近 Word/Excel 的操作体验，也要让付款条款和结算明细变成可追溯、可计算、可冻结的后台事实。

### 4.2 合同流程

```text
选择项目和合同类型
  -> 填写关键信息
  -> 选择常用合同模板
  -> 生成合同初稿
  -> 像 Word 一样编辑合同正文
  -> 维护合同清单和付款条款
  -> 系统检查缺项和风险
  -> 生成合同审批稿
  -> 提交审批
  -> 审批通过
  -> 用章审批
  -> 上传签署归档件
  -> 合同主管确认归档
  -> 形成有效合同版本和付款条款版本
```

### 4.3 结算流程

```text
选择有效合同版本
  -> 从合同清单选择结算项
  -> 导入或粘贴 Excel 结算清单
  -> 填写本期工程量、扣款和备注
  -> 上传签证、变更、收方资料
  -> 系统重新计算本次结算金额
  -> 系统提示超合同、缺资料和异常项
  -> 生成结算审批稿
  -> 提交审批
  -> 审批通过
  -> 上传签署归档件
  -> 合同主管确认归档
  -> 形成有效结算
```

### 4.4 付款流程

```text
选择有效结算
  -> 系统读取合同付款条款
  -> 系统计算当前可申请金额
  -> 填写本次申请金额和付款说明
  -> 上传发票、结算依据或其他凭证
  -> 提交付款审批
  -> 审批通过后进入待实付
  -> 出纳登记实付
  -> 上传付款凭证
  -> 财务入账
  -> 形成付款归档记录
```

## 5. 开源项目筛选结论

本轮筛选原则：不搬整套平台，不换现有后端，不换 Web 管理端组件库，不让外部流程或低代码运行时接管合同、结算、付款事实。只融合能提高效率、贴近用户习惯、降低自研风险的成熟部件。

### 5.1 第一轮可复用或可验证

| 方向 | 候选 | 用法 | 当前判断 |
| --- | --- | --- | --- |
| 合同正文编辑 POC | [ONLYOFFICE Docs](https://github.com/ONLYOFFICE/DocumentServer) | 内网部署，只作为合同草稿正文编辑器 | 应尽早做窄边界验证，作为合同部高频体验验收；进入生产前必须确认 AGPL/商业授权、安全隔离和回调可靠性 |
| 合同初稿生成 | [docxtemplater](https://github.com/open-xml-templating/docxtemplater) | 根据结构化字段生成 Word 初稿 | 已在项目中使用，继续保留和强化中文占位符 |
| 审批预览 | [PDF.js](https://github.com/mozilla/pdf.js) | 浏览器内查看审批稿和归档文件 | 适合做只读预览。必须复用后端权限、短时效访问和下载审计 |
| 结算表格体验原型 | [Tabulator](https://tabulator.info/) | 验证粘贴、键盘操作、行级校验和错误定位 | 可以并行做体验原型；生产落地必须等结算明细行账本可用 |
| Excel 导入导出 | [ExcelJS](https://github.com/exceljs/exceljs) | 生成结算模板、导入预览、审批清单 | 已在项目中使用，第一版继续用它，不新增解析口径 |
| PDF 转换 | LibreOffice 命令行转换 | 生成审批稿和归档 PDF | 已在项目中使用，继续用队列和超时守住可靠性 |

第一轮不同时验证 ONLYOFFICE 和 Collabora，也不同时引入多个表格库。合同编辑优先验证 ONLYOFFICE，结算表格可并行验证一个轻量原型；生产事实仍先用现有 docxtemplater、ExcelJS、LibreOffice、私有文件、审批和审计能力兜住。

### 5.2 只做专项验证，不进入第一轮主线

| 候选 | 借鉴价值 | 暂缓原因 |
| --- | --- | --- |
| [Collabora Online](https://github.com/CollaboraOnline/online) | 基于 LibreOffice 的在线编辑，授权压力相对较小 | 需要 WOPI Host，接口面比 ONLYOFFICE 更大，先作为备选 |
| [SheetJS CE](https://github.com/SheetJS/sheetjs) | 浏览器或后端解析复杂表格能力强 | 当前已用 ExcelJS；本项目不能信前端解析和 Excel 公式，暂不新增第二套解析口径 |
| [Univer](https://github.com/dream-num/univer) | 更接近完整在线表格，适合未来工作簿体验 | 导入导出和服务端能力边界较重，不能压住 P0 |
| FortuneSheet | 比普通表格更像电子表格 | 生态和维护风险较高，只适合拿真实模板试验 |
| Handsontable | 单元格编辑体验成熟 | 生产商用授权风险较高 |
| AG Grid | 大表性能和企业表格强 | 关键类 Excel 能力偏商业版 |
| SpreadJS | 最像 Excel 的商业方案 | 采购和部署成本高，只作为高预算备选 |

### 5.3 只借鉴产品形态，不接运行时

| 候选 | 可借鉴 | 不接入原因 |
| --- | --- | --- |
| [OpenProject](https://github.com/opf/openproject) | 项目事项、会议纪要、看板、进度和成本视图 | 技术栈和业务模型不同，不替换建工智管 |
| [ERPNext](https://github.com/frappe/erpnext) | 单据生命周期、会计和库存类台账思路 | 通用 ERP 过重，不接管本项目合同付款闭环 |
| [Odoo](https://github.com/odoo/odoo) | 业务应用组合、项目、会计、文档管理思路 | 平台过重，社区版和企业版边界需谨慎 |
| [NocoBase](https://github.com/nocobase/nocobase) | 使用模式和配置模式分离、可视化配置体验 | 不让无代码平台拥有合同、结算、付款事实 |
| [JeecgBoot](https://github.com/jeecgboot/JeecgBoot) | 表单、字典、权限、报表和代码生成治理 | 不引入 Java 后端和低代码运行时 |
| RuoYi / Yudao / Flowable 类项目 | 待办、已办、流转记录、转审、委托、催办 | 不引入 BPMN 引擎，不让流程图绕过后端规则 |
| Documenso / OpenSign | 电子签署、签署证书、审计轨迹 | 当前是用印和归档确认，不先接外部签署系统 |

### 5.4 在线办公安全边界

在线办公服务只能是草稿编辑器，不能成为业务事实来源。

必须坚持以下边界：

- 文档服务单独部署，不持有数据库、对象存储和生产密钥。
- 文档服务读取文件只能走后端一次性地址，不能拿到 COS 原始地址。
- 回调必须校验签名、来源、合同草稿、修订号和当前处理人。
- 回调里的下载地址必须限制为文档服务可信域名，不能让后端随意请求外部 URL。
- 提交审批前必须先保存当前正文，计算 DOCX 校验值，再生成 PDF 审批稿。
- 审批稿冻结后，迟到的保存回调不能覆盖审批稿，只能记录为被拒绝的回调日志。
- 审批领导只看 PDF、摘要、附件和风险提示，不进入在线编辑器。
- 编辑器保存回来的 DOCX 只能作为草稿或修订稿，不能自动改写合同金额、付款条款和合同清单。

### 5.5 ONLYOFFICE 最小 POC 边界

ONLYOFFICE 第一轮只验证合同正文草稿编辑，不进入生产主线。

POC 范围：

- 使用假项目、假合同和 1 份已发布版式模板。
- 只选 1 个合同类型和 1 个合同草稿。
- 复用现有合同工作台生成 DOCX 初稿。
- 打开在线编辑器后能保存 DOCX。
- 保存后的 DOCX 入私有文件，并登记为合同草稿修订稿。
- 保存后的 DOCX 能转成 PDF 给审批预览。
- 文件打开、保存、下载、失败回调都能审计。

POC 不做：

- 不做多人协同锁。
- 不做结构化字段反写。
- 不做模板在线编辑。
- 不做移动端编辑。
- 不做自动归档或自动生效。
- 不覆盖全部合同类型。

POC 通过标准只有五项：

```text
能打开
能保存
能入库
能转 PDF
审计可查
```

## 6. 效率提升重点

效率提升不是让页面更炫，而是减少重复录入、减少来回问、减少错单返工、让用户知道下一步。

### 6.1 合同部效率

- 常用合同模板一键生成初稿。
- 合同正文像 Word 一样编辑。
- 合同清单支持 Excel 导入和粘贴。
- 付款条款用中文业务项填写，不让员工填内部字段。
- 自动提示缺少相对方、金额、清单、附件和付款条款。
- 提交前自动生成审批稿，避免人工导出、转 PDF、发文件。
- 退回后能清楚看到领导要求改哪里。

### 6.2 预算和结算效率

- 从合同清单选择结算项，不重复录入清单名称和单位。
- 支持导入项目部常用 Excel 结算清单。
- 支持批量粘贴工程量、单价、备注。
- 每行可绑定签证、变更、收方资料。
- 系统自动计算本次结算金额和累计结算金额。
- 超合同、缺资料、合同外项目自动进入风险提示。
- 审批领导看到的是摘要、异常行和 PDF，不需要打开可编辑表格。

### 6.3 财务和出纳效率

- 付款申请自动展示可申请额度。
- 付款条款、已结算、已申请、已实付、历史扣减一屏说明。
- 超额时直接说明原因，不让财务手工追公式。
- 实付、凭证、入账和归档形成同一条证据链。

### 6.4 领导审批效率

领导审批页只回答五个问题：

```text
这是什么单？
金额是多少？
依据齐不齐？
有没有超过合同约定？
现在是否同意，还是退回修改？
```

审批页不进入编辑器，不展示内部编号，不展示技术详情。

## 7. 分期落地路线

### 第一阶段：账本模型补强和办公体验原型并行

目标：一边把可计算、可追溯、可冻结的业务事实补齐，一边让合同部和预算结算人员尽早试到接近 Word/Excel 的草稿体验。

- 补合同付款条款结构化录入，用中文业务项维护付款阶段、比例、期限、发票和扣回条件。
- 付款条款随合同版本冻结，归档确认后成为有效付款条款版本。
- 补结算明细行账本，第一版支持合同清单项和手工调整项。
- 补结算导入记录，记录导入文件、预览错误、应用人和应用时间。
- 结算金额、可付金额、异常项必须由后端根据结算明细重算。
- 并行做合同正文在线 Word 体验原型，只使用假合同或测试合同。
- 并行做结算清单在线 Excel 体验原型，重点验证复制粘贴、键盘录入、错误定位和行级提示。
- 体验原型要让合同部、预算部或结算人员试用，不只由技术人员判断。

### 第二阶段：全局中文业务体验和审批稿冻结

目标：让用户看得懂、知道下一步，并保证提交后不可变。

- 建立全局中文业务词典和页面检查清单。
- 建立错误提示规范：发生了什么、为什么不能做、下一步怎么办。
- 建立确认弹窗规范：说明业务后果。
- 建立合同审批稿和结算审批稿冻结模型。
- 提交时冻结结构化字段、清单、附件、DOCX/PDF 校验信息和风险提示。
- 合同、结算、付款审批页面只读审批稿。

### 第三阶段：合同工作台办公化

目标：合同部按 Word 习惯起草合同，系统背后保持结构化。

- 保留当前 docxtemplater 初稿生成能力。
- 完善合同正文草稿文件和修订稿管理。
- 优先做 PDF 内嵌只读预览，领导审批不进入编辑器。
- 将第一阶段验证通过的 ONLYOFFICE 体验收口到合同文档区。
- 提交前保存当前正文，生成 DOCX 和 PDF 审批稿。
- 归档确认后形成有效合同版本和付款条款版本。

### 第四阶段：结算工作台办公化

目标：预算和结算人员按 Excel 习惯处理清单，但每行可追溯。

- 结算草稿从有效合同清单引出。
- 普通结算行必须引用合同清单项。
- 手工调整项必须填写原因，并进入审批摘要。
- 复用现有 ExcelJS 模式做模板下载、导入预览、应用导入。
- 将第一阶段验证通过的在线表格体验收口到结算草稿页。
- 暂不引入第二套 Excel 解析口径。
- 后端重新计算本次结算金额、累计结算金额和异常项。
- 审批稿展示摘要、异常行、附件和 PDF。

### 第五阶段：付款额度透明化

目标：付款申请不再靠人工判断额度。

- 付款申请前展示合同付款条款。
- 展示有效结算累计金额、已申请未付、已实付、历史扣减。
- 后端计算本次最多可申请金额。
- 超额时给中文原因和下一步建议。
- 补测试证明付款仍从有效结算、付款条款和后端结算总额出发。

### 第六阶段：效率增强

目标：减少重复操作和返工。

- 最近打开单据继续增强。
- 常用模板、常用相对方、常用条款快速选择。
- 支持从上一次相似合同复制草稿。
- 支持导入失败时定位到具体行。
- 支持审批退回后只看需修改项。
- 支持合同、结算、付款一条线查看资金链。
- 等大批量行编辑成为真实阻塞后，再评估 Tabulator、Univer 或商业表格方案。

## 8. 关键验收标准

### 8.0 可行性闸门

- 不新增低代码、无代码、BPMN 或 ERP 运行时。
- 不让在线编辑器、表格组件或外部服务拥有业务事实。
- 在线 Word/Excel 体验必须进入第一批用户验收，不作为后续可选增强。
- 合同金额、付款条款、合同清单、结算明细和付款额度都必须由后端保存和计算。
- 审批稿必须能证明来自哪一次草稿、哪一版结构化数据、哪一份 DOCX/PDF 和哪些附件。
- 生产前必须完成授权、内网部署、安全隔离、回调验签、文件哈希和审计验收。

### 8.1 用户体验验收

- 普通用户页面不出现英文错误、内部字段、接口名和状态码。
- 每个禁用按钮都有中文原因。
- 每个失败提示都说明下一步。
- 每个提交动作都说明提交后的业务后果。
- 审批领导不需要理解技术词即可完成审批。

### 8.2 合同验收

- 合同部能用真实模板生成 Word 初稿。
- 合同正文能按 Word 习惯在线编辑，合同部人员试用后认为比下载、修改、再上传更省事。
- 合同金额、清单和付款条款仍由系统结构化保存。
- 付款条款能按中文业务项录入，并能形成付款条款版本。
- 在线编辑回来的 DOCX 不会自动改写金额、清单和付款条款。
- 审批稿和归档件版式可接受。
- 归档后不能覆盖有效合同版本。

### 8.3 结算验收

- 系统存在结算明细行账本，结算总额由明细行重算。
- 结算清单能按 Excel 习惯录入、粘贴、批量修改和定位错误。
- 结算行能追溯到合同清单、变更签证或扣款依据。
- Excel 导入后能定位错误行。
- 前端合计和后端重算不一致时有中文说明。
- 有效结算才能发起付款。

### 8.4 付款验收

- 付款申请必须引用有效结算。
- 付款额度必须按合同付款条款和结算金额计算。
- 超额付款被后端拦截。
- 已申请、已批待付、已实付、历史扣减都进入额度计算。

### 8.5 在执行项目接管验收

- 每个试运行项目必须先确定接管截止日。
- 接管日前的已签合同、补充协议、已确认结算、已批待付、已付款、预付款、质保金、扣回、发票和缺资料事项必须形成期初清单。
- 历史资料不能伪造流程。已经发生但资料不完整的事项，只能标记为待补资料、受限确认或争议事项。
- 选择 1 个真实项目、约 20 个历史合同做接管试点，其中 3-5 个近期要结算或付款的合同必须达到可继续业务的接管质量。
- A 级合同至少具备合同扫描件、付款条款、历史结算依据、历史付款或银行回单、发票或缺失说明。
- 接管确认前，不允许发起后续付款；确认后，付款预览必须能看到历史已付、已批待付、审批中、代付、预付款、质保金和其他占用的扣减结果。
- 接管资料必须能在资料库按项目和合同查到，并通过当前密码、下载原因和短时效链接完成授权下载。
- 合同部、预算、项目、财务和技术运维完成验收签字后，才能宣布接管数据成为系统唯一真相。

## 9. 在执行项目接管与唯一真相

### 9.1 核心判断

真实项目上线时，系统不能把历史资料当成普通补录。正确口径是：

```text
接管日前，系统承认经业务复核确认的期初事实。
接管日后，系统只承认系统内生成、审批、归档、付款并留痕的事实。
```

这意味着接管的重点不是还原每一条旧流程，而是确认截至接管截止日仍会影响后续结算、付款和审计的事实。

当前系统已经能支撑“历史合同以汇总期初余额接管，确认后继续跑新结算和新付款”。但要达到“真实项目唯一真相”，还必须补齐历史结算、历史付款、结构化付款条款、证据链和多部门复核。

### 9.2 接管截止日

每个真实项目接管前必须确定一个接管截止日。建议选择自然月末，例如：

```text
2026 年 7 月 31 日 24:00
```

从下一日零点开始：

- 新合同、新补充协议、新结算、新付款申请必须在系统内发起。
- 线下收到的合同、结算、发票、凭证必须上传系统归档后，才能进入后续流程。
- 无系统付款申请编号，财务不得付款。
- 无银行回单，不得标记为已付款。
- 任何绕开系统的补签、补结算、付款和抵扣，都必须进入异常事项说明。

### 9.3 期初事实范围

期初事实要同时覆盖合同、结算、付款、发票、资料和争议，不能只导入一个应付余额。

| 范围 | 接管口径 |
| --- | --- |
| 合同 | 截至接管日已签署、仍在履行或尚未结清的合同和补充协议 |
| 合同金额 | 以盖章合同、补充协议和变更协议为准 |
| 已结算金额 | 截至接管日双方已确认、公司内部认可的有效结算金额 |
| 已批待付 | 已完成付款审批但银行尚未付款的金额 |
| 审批中付款 | 已发起但尚未审批完成的付款金额 |
| 已付款金额 | 银行实际付款成功金额，不以口头承诺或申请单为准 |
| 预付款 | 已支付、应扣回、已扣回、未扣回分别列示 |
| 质保金或保留金 | 已扣留、可释放、未到期、争议金额分别列示 |
| 扣回和抵扣 | 预付款扣回、罚款、水电费、材料款、代垫款等必须有依据 |
| 发票 | 已收票、未收票、票款不一致、抬头或税率异常分别列示 |
| 缺资料事项 | 可作为待补资料或受限确认，不能伪造为已归档 |
| 争议事项 | 单独列争议金额、争议原因、责任人和下一步处理 |

### 9.4 接管工作台步骤

接管工作台应按业务人员能理解的步骤组织，不让用户自己猜流程。

1. 接管准备：选择项目、确定接管截止日、指定合同部、预算、项目、财务责任人。
2. 导入预检：粘贴或上传合同台账、历史余额、资料清单，只做校验和错误定位，不直接写入正式业务事实。
3. 生成草稿：把通过预检的数据生成接管草稿，按 A/B/C 分级、资料缺口、金额风险和处理状态筛选。
4. 单合同补录：补合同基础信息、付款条款、历史结算、历史付款、预付款、质保金、扣回和证据资料。
5. 多部门复核：合同部复核合同版本和付款条款，预算复核结算口径，项目经理复核现场履约，财务复核付款、发票和余额。
6. 接管确认：合同主管在看到复核摘要、差异清单和历史余额影响后，输入当前密码确认接管。
7. 接管后核验：系统展示合同详情、资料库、后续可结算状态、可付款状态和付款容量预览。

预检层可以反复修正，草稿层可以退回补充。确认后不得静默覆盖关键金额、付款条款和证据资料。

### 9.5 期初余额口径

期初余额至少要保存以下项目：

```text
当前有效合同金额
历史累计结算金额
历史审批中付款金额
历史已批待付金额
历史累计已付款金额
历史总包代付金额
历史预付款已付金额
历史预付款已扣回金额
历史质保金扣留金额
历史质保金释放金额
其他已确认占用金额
剩余可申请付款金额
```

后续付款额度应按合同付款条款、有效结算、历史已付、历史待付、预付款扣回、质保金和其他占用共同计算。

如果接管前已经有“已结算但未付款”的金额，必须形成期初可付款来源。建议优先复用结算账本，生成一条历史期初有效结算记录，让后续付款仍然从有效结算发起，而不是绕开结算直接付款。

### 9.6 A/B/C 分级

分级的目的不是给资料贴标签，而是决定后续业务能不能继续走。

| 等级 | 口径 | 后续控制 |
| --- | --- | --- |
| A 级 | 合同、结算、付款、发票或缺失说明齐全，金额能互相对上 | 可作为首批活跃合同继续跑结算和付款 |
| B 级 | 关键签署资料齐全，但部分明细、凭证或发票存在缺口 | 可建台账，可受限确认；付款前必须补齐影响金额的资料 |
| C 级 | 关键资料缺失、争议大、金额无法可靠确认 | 只能列为待处理或争议，不得直接进入可付款状态 |

缺资料时不能默认填 0，也不能编造明细。系统要保留“缺什么、谁负责、什么时候补、是否影响付款”的说明。

### 9.7 不得编造的历史事实

| 不得编造 | 正确处理 |
| --- | --- |
| 未签署合同 | 不能录为正式有效合同，只能列待补合同或无合同历史事项 |
| 未盖章补充协议 | 不能调整有效合同金额 |
| 未双方确认的结算 | 不能作为有效结算，只能列送审或争议金额 |
| 未发生的审批记录 | 不能倒造历史审批流 |
| 未付款的银行回单 | 不能录为已付款 |
| 未实际开具的发票 | 不能录为已收票 |
| 未确认的扣罚和抵扣 | 不能直接冲减应付，只能列待确认事项 |
| 未归档的合同或结算文件 | 不能标记为已归档确认 |
| 不清楚归属的付款 | 不能随意挂到某份合同，应列待清分款项 |
| 口头承诺的付款安排 | 不能作为已批待付 |

系统可以接收历史事实摘要，但不能伪造历史流程。接管前的流程不完整，就按资料状态和确认意见留痕；接管后的新流程，必须在系统内完整走完。

### 9.8 复核确认机制

建议采用“多方复核、差异清单、保留事项、主管确认”的机制。

| 角色 | 复核责任 |
| --- | --- |
| 相对方 | 确认已签合同、已结算、已收款、未收款和争议金额 |
| 项目负责人 | 确认现场履约、工程量、实际完成情况和扣罚事项 |
| 合同部 | 确认合同版本、补充协议、付款条款和归档资料 |
| 预算部门 | 确认结算金额、变更签证、扣款和结算依据 |
| 财务部门 | 确认银行付款、发票、应付余额、预付款和扣回余额 |
| 技术运维 | 确认权限、私有文件、下载审计、备份和防篡改措施 |

每一方只确认自己能够证明的事实。财务不能替项目确认工程量，项目不能替财务确认付款成功，技术运维不能替业务部门确认金额。

主管确认时必须看到：

- 期初合同清单。
- 累计结算确认表。
- 累计付款和已批待付确认表。
- 预付款及扣回余额确认表。
- 发票与付款凭证差异表。
- 缺资料和争议事项清单。
- 后续付款容量预览。

### 9.9 代码库验证后的边界

多智能体只读验证后，当前代码库的强项是：

- 已有历史合同接管模型，能记录 A/B/C 分级、合同事实、付款条款原文、历史余额和接管资料。
- 接管确认需要当前密码，确认后合同版本和付款条款版本会生效。
- 未确认接管或历史余额未确认时，付款申请会被后端拦截并写审计。
- 历史已付、审批中、已批待付、代付、预付款和其他占用已经能进入付款容量扣减。
- 付款审批和实际付款是分开的，审批通过后只是已批待付，出纳实付和凭证上传另走流程。

但当前还不能直接宣称“历史结算和历史付款逐笔账本已经完整”。主要缺口是：

- 历史结算和历史付款仍以汇总金额和附件为主，缺少逐期次、逐付款、逐凭证的结构化明细。
- 历史已结算未付款金额还需要形成期初可付款来源，否则后续付款依据不足。
- 接管付款条款不能只保存原文摘要，必须补结构化付款阶段、比例、期限、发票和扣回条件。
- 最终结算计算必须扣除已确认历史结算，避免把接管前已结算金额重复算入本期。
- 历史质保金不能只展示，要进入付款容量或释放路径。
- 接管资料必须能在资料库按项目归属查询和授权下载。
- 已确认接管后的更正必须走更正记录，不能静默覆盖原数据。
- 付款驳回状态不一致等已发现代码风险，应在真实接管前修正并补测试。

### 9.10 最小落地顺序

1. 先修复已发现的付款状态风险和接管资料归属下载风险。
2. 建立项目级接管批次，明确接管截止日、责任人、状态和验收结论。
3. 扩展接管预检模板，至少覆盖合同主表、历史余额表、资料清单和问题清单。
4. 接管草稿支持结构化付款阶段，不允许在执行合同只靠付款条款原文确认。
5. 增加历史期初有效结算来源，让接管前已结算未付款金额可以继续从结算发起付款。
6. 增加历史付款、实付、已批待付、预付款、质保金和扣回的只读明细快照。
7. 做步骤化接管工作台：导入预检、生成草稿、资料核验、复核确认、接管后核验。
8. 先选 1 个真实项目、3-5 个 A 级活跃合同跑通接管后新结算、新付款、实付和凭证。
9. 对账无误后，再扩到约 20 个历史合同。
10. 完成合同部、预算、项目、财务和技术运维签字后，才宣布该项目系统数据成为唯一真相。

## 10. 新会话执行提示

新会话接手时，先读：

1. `PROGRESS.md`
2. `AGENTS.md`
3. 本文档
4. `docs/design/建工智管_企业流程系统前端改造方案_20260707.md` 第 23 节
5. `docs/superpowers/specs/2026-06-24-enterprise-contract-workbench-design.md`

执行原则：

- 不引入新的大平台。
- 不换后端技术栈。
- 不换 Web 管理端组件库。
- 不把低代码、无代码或流程引擎作为运行时事实来源。
- 优先复用现有 docxtemplater、ExcelJS、LibreOffice、私有文件、审批和审计能力。
- 面向用户的所有文字必须中文业务化。
- 做每一个页面时都要问：用户现在知道自己该做什么吗？

推荐第一批实施任务：

1. 建立全局中文业务语言规范和检查清单。
2. 梳理合同、结算、付款所有可见错误和禁用原因。
3. 做 ONLYOFFICE 合同正文编辑内网 POC，让合同部实际试用。
4. 做结算在线表格体验原型，让预算或结算人员实际试用粘贴、录入、错误定位。
5. 设计合同付款条款结构化录入模型和中文表单。
6. 设计结算明细行和结算导入记录模型，第一版只支持合同清单项和手工调整项。
7. 设计合同审批稿和结算审批稿冻结读模型。
8. 用现有 ExcelJS 复制合同清单导入模式，做结算导入预览和错误行定位方案。
9. 做 PDF 只读预览方案，审批领导不进入编辑器。
10. 做付款可申请额度计算说明的页面和后端测试。
11. 设计项目级在执行接管批次，包含接管截止日、责任人、状态、复核意见和验收结论。
12. 扩展历史接管导入预检模板，覆盖合同主表、历史余额、资料清单和问题清单。
13. 设计历史期初有效结算来源，让接管前已结算未付款金额能继续从有效结算发起付款。
14. 设计历史付款、已批待付、实付、预付款、质保金和扣回的只读明细快照。
15. 修正接管资料在资料库的项目归属和授权下载口径。
16. 做步骤化接管工作台，按导入预检、生成草稿、资料核验、复核确认、接管后核验组织。
17. 做 A/B/C 接管分级的资料清单、缺口说明和付款阻断提示。
18. 用 1 个真实项目和 3-5 个 A 级活跃合同验证接管后新结算、新付款、实付和凭证闭环。

## 11. 本轮调研来源

本轮方案还融合了五个只读智能体对当前代码库、前端工作台、导入对账、财务控制和安全审计的复核结论：现有系统可以承载历史合同汇总余额接管，但要成为真实项目唯一真相，必须补齐历史结算和历史付款明细、接管批次、结构化付款条款、多方复核、证据链和接管后核验。

- [ONLYOFFICE Docs](https://github.com/ONLYOFFICE/DocumentServer)：在线文档、表格、演示、PDF 编辑；支持 DOCX/XLSX/PPTX；社区版为 AGPL，另有企业和集成版本。
- [ONLYOFFICE 回调文档](https://api.onlyoffice.com/docs/docs-api/usage-api/callback-handler/)：文档保存回调、保存状态和回调接口约定。
- [Collabora Online](https://github.com/CollaboraOnline/online)：基于 LibreOffice 的在线办公套件。
- [docxtemplater](https://github.com/open-xml-templating/docxtemplater)：从 Word、Excel、PPT 模板生成文件，模板可由非技术人员编辑。
- [PDF.js](https://github.com/mozilla/pdf.js)：浏览器 PDF 查看。
- [Tabulator](https://tabulator.info/)：可编辑表格、粘贴、校验、导入导出和虚拟滚动。
- [SheetJS CE](https://github.com/SheetJS/sheetjs)：Excel、CSV 等表格文件读取和生成。
- [ExcelJS](https://github.com/exceljs/exceljs)：Excel 文件生成和样式处理。
- [OpenProject](https://github.com/opf/openproject)：项目事项、看板、工期、成本、会议和文档管理。
- [ERPNext](https://github.com/frappe/erpnext)：开源 ERP，提供会计、采购、项目、库存等单据生命周期参考。
- [Odoo](https://github.com/odoo/odoo)：模块化业务应用和 ERP 形态参考。
- [NocoBase](https://github.com/nocobase/nocobase)：使用模式和配置模式分离、可视化配置参考。
- [JeecgBoot](https://github.com/jeecgboot/JeecgBoot)：表单、字典、流程、报表和代码生成治理参考。
- [Flowable](https://github.com/flowable/flowable-engine)：流程待办、流转记录、转办、委托等形态参考，不作为运行时引入。
