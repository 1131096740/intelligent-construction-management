# 建工智管企业流程系统前端改造方案（2026-07-07）

## 1. 调研结论

本次综合产品、UX、流程架构、安全四类智能体意见，并参考企业流程与工程项目系统的公开资料。结论是：建工智管下一阶段不应继续堆页面，而要把 Web 管理端改造成“以项目为容器、以单据生命周期为主线、以角色待办为入口、以附件和审计为证据链”的企业流程系统。

参考依据：

- [Microsoft Power Automate 审批工作流](https://learn.microsoft.com/en-us/power-automate/modern-approvals) 强调：审批应进入审批中心和消息入口，审批结果、意见要回写原业务记录。
- [Microsoft Business Process Flows](https://learn.microsoft.com/en-us/power-automate/business-process-flows-overview) 强调：用户应聚焦业务流程，而不是感知自己在操作哪张数据库表；流程还应按角色过滤并能进入视图、图表、仪表盘。
- [Procore Project Management](https://www.procore.com/project-management) 强调：项目资料、任务、RFI、文档、成本、承诺、变更和预算信息要在项目级统一连接。
- [Oracle Primavera Unifier](https://www.oracle.com/construction-engineering/primavera-unifier/) 强调：合同、成本、变更、付款和审批应由表单驱动流程连接，所有动作和决策要形成统一项目记录。
- [ServiceNow Automation Engine](https://www.servicenow.com/products/automation-engine.html) 强调：首页应是个性化工作入口，优先展示工作流、待办和推荐动作。
- [IBM Carbon Data Table](https://carbondesignsystem.com/components/data-table/usage/) 和 [Empty States](https://carbondesignsystem.com/patterns/empty-states-pattern/) 强调：企业后台表格要支持搜索、筛选、排序、行内动作和明确空态，不要把用户丢给空表格。
- [GOV.UK Error Message](https://design-system.service.gov.uk/components/error-message/) 和 [Error Summary](https://design-system.service.gov.uk/components/error-summary/) 强调：错误要出现在字段旁和页面顶部，保留用户输入，并说明如何修正。
- [WCAG 2.2](https://www.w3.org/TR/WCAG22/) 要求：金融或数据修改类操作要可检查、确认、纠正；所有功能可键盘操作，状态和错误能被辅助技术感知。
- [OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html) 和 [Transaction Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Transaction_Authorization_Cheat_Sheet.html) 强调：敏感交易要有明确授权、确认和可追踪日志。

## 2. 总改造原则

1. 不让用户手填内部 ID。合同、合同版本、结算、付款、文件、项目、人员都必须用业务选择器或页面上下文自动带出。
2. 首页先回答“我今天该处理什么”，不要先给用户看全量台账。
3. 详情页先回答“四个问题”：当前状态是什么、下一步是什么、谁负责、我能不能操作。
4. 所有按钮都必须由“角色 + 项目权限 + 单据状态 + 后端授权”共同决定。
5. 审批通过、归档确认、付款执行、敏感下载、作废、权限变更都要二次确认，并复述业务后果。
6. 错误提示讲业务原因，不展示接口路径、内部 ID、SQL、bucket、对象 key、权限策略名。
7. 文件不是网盘附件，而是业务证据。每个文件必须绑定业务对象、阶段、上传人、确认人、下载审计。
8. Web 端承担复杂录入、批量筛选、财务核对和审计；移动端后续只承担待办审批、查看附件、拍照上传、快速确认。

硬业务规则必须前后端一致：

- 合同未归档确认生效，不能创建结算。
- 结算未归档确认生效，不能创建付款申请。
- 付款审批通过只进入“已批待付款”，不等于已付款。
- 实付必须由财务/出纳登记，且上传凭证、写财务记录、写审计。
- 合同/结算归档件由合同部上传，合同部主管确认；财务只读取，不上传业务归档件。
- 董事长/总经理是合同终审、付款终审或签节点；结算不经过董事长/总经理。
- 归档确认、实付登记、敏感文件下载必须二次确认当前密码。
- `super_admin` 只做技术管理，不能替代业务审批角色。

## 3. 目标导航结构

建议主导航调整为：

```text
我的工作台
项目
合同
结算
付款
项目经营
资料库
审批中心
审计日志
基础设置
```

关键变化：

- `项目` 是第一层业务容器。合同、结算、付款、资料、审批、审计都可从项目详情进入。
- `合同 / 结算 / 付款` 仍保留一级入口，但默认按“需要我处理、阻塞中、最近更新”排序。
- `资料库` 不是独立网盘，而是项目业务档案索引。
- `审批中心` 不另造业务页面，点击审批任务后进入对应单据详情，并定位到审批区。

## 4. 通用页面规格

### 4.1 我的工作台

第一屏展示阻塞事项队列：

| 字段 | 说明 |
| --- | --- |
| 类型 | 合同、结算、付款、归档、接管、凭证、改密、委托 |
| 项目 | 项目名称，不只显示编号 |
| 单据 | 业务编号 + 名称 + 相对方 |
| 金额 | 合同额、结算额、付款额或影响金额 |
| 当前节点 | 例如“合同部主管归档确认”“董事长/总经理或签” |
| 停留时间 | 例如“已停留 3 天” |
| 下一步 | 例如“确认归档后合同生效” |
| 主操作 | 审批、确认归档、执行付款、上传凭证、补资料 |

工作台分区：

- 待我审批
- 待我归档上传
- 待我确认归档
- 待我执行付款
- 待我上传凭证
- 阻塞事项：缺附件、超账期、付款容量不足、历史余额未确认
- 我发起的进行中

### 4.2 列表页

合同、结算、付款列表统一字段语言：

```text
项目 / 编号 / 名称或相对方 / 金额 / 状态 / 当前节点 / 责任部门 / 停留时间 / 下一步动作
```

默认视图：

- 待我处理
- 阻塞中
- 审批中
- 待归档
- 已生效或已付款
- 全部

### 4.3 详情页

所有核心详情页顶部固定“流程摘要条”：

```text
当前状态 | 当前版本/来源单据 | 金额摘要 | 当前处理人/角色 | 下一步动作 | 主按钮
```

详情页中部按生命周期分区，不按数据库字段分区。底部固定：

- 附件与归档文件
- 审批时间线
- 审计日志

### 4.4 操作反馈

错误文案统一改为业务解释：

- 不说：“Internal server error”
- 改说：“该归档文件暂不可下载，请确认当前合同已有已确认归档件，或联系合同部主管。”
- 不说：“Forbidden”
- 改说：“当前节点由财务负责人处理，你暂无处理权限。”
- 不说：“参数错误 fileId”
- 改说：“请选择要下载的归档文件。”

## 5. 合同流程改造

合同详情页分区：

```text
合同概览 / 付款条款 / 审批流程 / 用章与归档 / 关联结算 / 关联付款 / 附件 / 审计
```

| 阶段 | 用户视角 | 主操作 | 角色 | UI 改造 |
| --- | --- | --- | --- | --- |
| 草稿创建 | 选择项目、相对方、模板、合同类型 | 新建草稿、保存草稿 | 合同员、合同主管 | 从项目或合同列表发起；不展示 `projectId`、`contractVersionId` |
| 付款条款录入 | 录入付款节点、比例、触发条件、发票要求 | 保存条款、校验条款 | 合同员、合同主管 | 实时展示比例合计、付款触发条件、后续影响 |
| 提交审批 | 系统检查必填项、附件、条款完整性 | 提交审批 | 合同员、合同主管 | 提交前弹窗列出合同额、相对方、付款条款摘要 |
| 合同审批 | 看冻结版本、附件、条款和审批历史 | 同意、驳回、退回、转审、委托 | 项目经理、合同主管、董事长/总经理等 | 审批页不让审批人编辑业务字段，只能发表意见和动作 |
| 用章 | 合同审批通过后进入用章节点 | 用章通过、驳回 | 有用章权限角色 | 明确“用章不是合同生效，仍需盖章件归档确认” |
| 上传盖章合同 | 上传签字盖章后的合同原件 | 上传归档件 | 合同员 | 从当前合同上下文上传，不选业务 ID |
| 归档确认 | 复核盖章件、版本、金额、相对方 | 确认归档 | 合同主管 | 二次确认：确认后合同版本生效，付款条款锁定 |
| 合同生效 | 后续结算只能基于生效版本 | 发起结算、查看资金链 | 合同部、项目、财务可读角色 | 顶部显示“可发起结算”；未生效时显示阻断原因 |
| 合同变更 | 生效后不能直接改条款 | 发起变更/补充协议 | 合同员、合同主管 | 不提供直接编辑入口，引导新流程和新版本 |

合同详情页必须取消所有手填文件 ID、版本 ID、归档 ID 的输入框。下载合同文件时，从当前合同归档文件列表选择或默认选中最新已确认文件。

## 6. 历史合同接管流程改造

历史合同接管不是普通新建合同，应独立成流程：

```text
导入/录入历史合同 -> A/B/C 分级 -> 资料上传 -> 业务复核 -> 余额确认 -> 接管生效 -> 后续结算/付款
```

| 阶段 | 主操作 | 责任角色 | UI 要点 |
| --- | --- | --- | --- |
| 录入历史合同 | 新增历史合同、批量导入 | 合同员 | 展示“历史已签，不重走审批”标签 |
| A/B/C 分级 | 标记资料完整度和风险 | 合同员、合同主管 | 用标签解释 A/B/C 含义，不让用户猜 |
| 资料上传 | 上传合同扫描件、历史结算、历史付款凭证 | 合同员 | 附件按资料类型分组 |
| 业务复核 | 核对合同额、已结算、已付、余额 | 合同主管、财务 | 展示计算依据和差异项 |
| 余额确认 | 当前密码确认 | 合同主管或指定确认人 | 二次确认后，付款容量开始受历史余额约束 |
| 接管生效 | 可进入后续结算/付款 | 相关业务角色 | 在合同详情显示“接管事实起点” |

## 7. 结算流程改造

结算只能从已生效合同版本发起：

```text
选择有效合同 -> 录入本期结算 -> 上传结算依据 -> 提交审批 -> 审批通过 -> 上传签认结算件 -> 归档确认 -> 结算生效 -> 发起付款
```

| 阶段 | 用户视角 | 主操作 | 角色 | UI 改造 |
| --- | --- | --- | --- | --- |
| 选择合同 | 只展示可结算合同 | 发起结算 | 合同员、预算/项目相关角色 | 显示合同额、累计结算、剩余可结算、不可选原因 |
| 录入结算 | 填期间、金额、结算说明 | 保存、提交 | 合同员、预算/项目相关角色 | 实时校验金额，不超合同/历史容量 |
| 上传依据 | 上传收方单、签工单、台班、清单等 | 上传附件 | 发起人 | 按模板类型引导，不只给一个文件框 |
| 审批 | 审批冻结结算金额和附件 | 同意、驳回、退回、转审、委托 | 物资、工程、预算、项目经理、财务等 | 流程图显示当前节点、处理人、停留时长 |
| 上传签认件 | 上传线下签字盖章结算件 | 上传归档件 | 合同员 | 文件绑定当前结算，不填 ID |
| 归档确认 | 确认签认件与审批结果一致 | 确认归档 | 合同主管 | 二次确认：确认后结算生效，可申请付款 |
| 结算生效 | 进入付款申请池 | 发起付款 | 合同/财务/项目授权角色 | 显示已申请、已批待付、已实付、剩余额度 |

结算详情必须展示：

- 来源合同版本
- 付款条款版本
- 本期结算金额
- 累计结算金额
- 已申请付款
- 已批待付款
- 已实付
- 剩余可申请金额

## 8. 付款流程改造

付款流程必须拆清“申请审批”和“实际付款”：

```text
选择生效结算 -> 创建付款申请 -> 容量校验 -> 付款审批 -> 已批待付款 -> 出纳实付 -> 凭证上传 -> 财务入账 -> 付款完成
```

| 阶段 | 用户视角 | 主操作 | 角色 | UI 改造 |
| --- | --- | --- | --- | --- |
| 选择结算 | 只展示可付款结算 | 新建付款申请 | 授权业务角色 | 展示剩余可申请金额，不可选时给原因 |
| 创建申请 | 填申请金额、收款方、用途 | 保存、提交审批 | 发起人 | 实时展示“本次申请后剩余额度” |
| 容量校验 | 后端校验合同、结算、历史余额、已批待付、已实付 | 自动 | 系统 | 前端展示校验明细，不能只报错 |
| 付款审批 | 审批付款申请，不代表已付款 | 同意、驳回、退回、转审、委托 | 项目、财务、董事长/总经理等 | 状态文案必须是“已批待付款”，不能写“已付款” |
| 出纳实付 | 真正登记支付 | 登记实付 | 财务/出纳 | 二次确认：金额、收款方、账户、结算、合同 |
| 凭证上传 | 上传银行回单等凭证 | 上传凭证 | 财务/出纳 | 支持多笔实付、多张凭证 |
| 财务入账 | 形成财务记录 | 确认入账 | 财务 | 展示实付与入账覆盖关系 |
| 完成 | 付款状态更新 | 查看资金链 | 相关角色 | 合同/结算详情反向展示这笔付款 |

付款详情必须展示付款容量计算过程：

```text
合同金额
- 历史已付
- 已批待付
- 已实付
- 其他占用
= 当前可申请付款
```

## 9. 资料库与敏感文件改造

资料库按业务归属组织：

```text
项目资料
合同原件
合同审批单
结算依据
结算签认件
付款申请单
付款凭证
财务归档 PDF
```

每个文件卡片展示：

- 文件名
- 业务归属：项目 / 合同 / 结算 / 付款
- 阶段：草稿附件、审批附件、归档件、凭证、系统生成 PDF
- 上传人、上传时间
- 确认人、确认时间
- 文件状态：待确认、已确认、已作废
- 下载按钮和下载审计提示

敏感下载流程：

```text
选择业务文件 -> 输入当前登录密码 -> 填写下载原因（P1） -> 生成短时效票据 -> 下载 -> 写审计
```

严禁在 UI 中要求用户输入 `fileId`、对象 key、COS URL。

## 10. 审批中心改造

审批中心分五个视图：

- 待我审批
- 我发起的
- 我已处理
- 委托给我
- 超时催办

审批任务卡片字段：

```text
业务类型 / 项目 / 单据编号 / 金额 / 当前节点 / 审批方式 / 发起人 / 停留时间 / 主操作
```

审批动作：

- 同意
- 驳回
- 退回上一节点
- 打回申请人
- 撤回（申请人）
- 催办（申请人）
- 转审
- 委托

审批详情不单独重做页面，应跳转到合同、结算或付款详情，并定位到审批区。这样审批人看到的是完整业务事实，而不是孤立流程卡。

## 11. 项目经营改造

项目经营不做装饰性大屏，先做项目资金链运营页。

核心指标：

- 合同总额
- 已生效合同额
- 历史接管余额
- 累计结算
- 已申请付款
- 已批待付款
- 已实付
- 未付余额
- 业主收款
- 总包代付
- 垫资金额
- 阻塞事项数量

项目详情页标签：

```text
项目概览 / 合同 / 结算 / 付款 / 收支与垫资 / 资料 / 审批 / 审计
```

项目经营页的关键是能点穿：从一个风险指标直接进入造成它的合同、结算、付款或附件。

## 12. 角色工作面

| 角色 | 首页优先事项 | 能做什么 | 不该看到什么 |
| --- | --- | --- | --- |
| 董事长 / 总经理 | 高金额付款审批、合同终审、项目风险 | 审批、查看项目资金链、查看审计摘要 | 不处理上传附件、技术配置 |
| 项目经理 | 本项目审批、结算/付款风险、阻塞事项 | 审批、查看项目全链路、催办 | 不越权看其他项目 |
| 合同主管 | 合同/结算归档确认、合同版本事实 | 确认归档、查看合同资金链、复核接管 | 不登记实付 |
| 合同员 | 新建合同、上传归档件、发起接管和结算 | 草稿、上传、提交审批、补资料 | 不确认自己上传的归档件 |
| 预算主管 / 预算员 | 结算金额复核、清单依据 | 结算审核、金额核对 | 不执行付款 |
| 财务总监 | 付款审批、资金风险 | 审批付款、查看已批待付与实付 | 不上传合同归档件 |
| 财务 / 出纳 | 已批待付款、凭证、入账 | 登记实付、上传凭证、财务入账 | 不审批自己的实付 |
| 物资主管 / 物资员 | 材料类结算核验 | 审核材料类结算依据 | 不看无关合同详情 |
| 工程主管 / 工长 / 技术 | 劳务、专业、机械类现场量核验 | 审核工程量、签工、台班依据 | 不看财务敏感下载 |
| 综合主管 | 综合费用审批与归档 | 审批综合费用、查看本范围资料 | 不看合同外敏感文件 |
| super_admin | 技术配置、账号、权限、运行状态 | 账号重置、权限配置、审计排障 | 不作为业务审批人使用 |

## 13. P0 / P1 / P2 改造顺序

### P0：立刻改，解决“不符合使用者常理”

1. 所有详情页取消内部 ID 输入，改为从当前业务上下文选择。
2. 合同、结算、付款详情页增加统一流程摘要条。
3. 工作台改成“待办 + 阻塞事项”。
4. 审批中心按“待我审批 / 我发起 / 我已处理 / 委托给我 / 超时催办”重构。
5. 附件区统一文件卡片：文件名、业务归属、阶段、上传人、确认人、下载审计。
6. 强制改密页修复为真正可操作页面，临时密码用户不能进入业务页。
7. 错误提示改成业务文案，禁止直接展示 `Internal server error`。

### P1：增强项目资金链

1. 项目详情页打通合同、结算、付款、资料、审批、审计。
2. 合同详情增加资金链时间轴。
3. 结算详情增加可付金额计算明细。
4. 付款详情增加多笔实付、凭证、入账覆盖关系。
5. 资料库增加缺附件、待确认、敏感下载筛选。
6. 委托台账增加范围、期限、到期提醒和“代某人处理”标识。

### P2：试运行稳定后再做

1. 审批流配置 UI。
2. 小程序移动待办、审批、附件查看、拍照上传。
3. 跨项目老板视图。
4. OCR/AI 识别合同条款、结算附件和付款摘要。
5. 采购、考勤、人事、安全等外围模块。

## 14. 最低验收口径

- 员工不复制粘贴任何内部 ID，也能完成合同、结算、付款、归档、下载。
- 每个角色登录后，第一屏能看到自己该处理什么。
- 每个单据详情页顶部能回答：当前状态、下一步、谁处理、我能不能操作。
- 未生效合同不能创建结算，未生效结算不能创建付款。
- 付款审批通过后只进入“已批待付款”，不会被误认为已经付款。
- 所有敏感文件下载都能在审计中追到人、文件、业务单据、时间和原因。
- 所有失败提示不暴露内部 ID、存储路径、数据库错误、权限规则名。

## 15. 当前实现差异与落地风险

1. 合同审批链需要专项复核。业务矩阵要求合同审批覆盖项目、合同、预算、财务、董事长/总经理等冻结节点；当前实现需确认是否只冻结了董事长/总经理终审。如果代码链路比制度链短，UI 不应先画完整多节点假象，应先补后端审批冻结节点或在试运行制度中明确前置审核由合同工作台就绪校验承接。
2. 强制改密页是 P0 缺口。生产现场出现临时密码用户进入 `/change-password` 仍只看到 `password change required`，必须修成真实改密表单，并确保临时密码用户只能访问改密接口。
3. 详情页错误提示仍需全量收口。合同下载已改为按当前合同归档件选择，但结算、付款、归档、审批等页面仍需逐页排查是否还有内部 ID 输入、`Internal server error`、技术 JSON 直出。
4. 角色可见操作需要统一组件化。不能每个页面各写一套按钮条件，否则很容易出现“列表能进、详情不能做”或“按钮能点、后端拒绝”的割裂体验。
5. 文件区要统一。合同、结算、付款、资料库应共用同一套文件卡片和下载确认体验，避免一个页面安全、另一个页面泄露内部 fileId。

## 16. 第二轮调研补充决策

第二轮调研进一步确认：不要复刻 Procore、Autodesk Construction Cloud、Oracle Unifier 的全套工程协同平台。建工智管当前应只吸收三件事：

1. 项目首页是行动入口，不是展示大屏。
2. 详情页是业务对象账本，不是数据库字段页。
3. 资料库是受控归档，不是网盘。

### 16.1 P0 工作台定型

工作台首屏只保留 3 个队列：

- 待我处理
- 阻塞事项
- 我发起的进行中

默认排序：

```text
超时/阻塞优先 -> 金额高优先 -> 最近更新优先
```

P0 不做批量审批。合同、结算、付款都涉及金额和证据链，逐单确认比批量处理更符合内控。

### 16.2 审批中心定型

审批中心只做队列，不另造孤立审批详情页。点击任务后进入合同、结算或付款详情，并定位到审批区。

固定视图：

- 待我审批
- 我发起的
- 我已处理
- 委托给我
- 超时催办

任务卡必须显示：

```text
审批方式 / 当前节点 / 发起人 / 停留时间 / 是否转审或委托 / 主操作
```

### 16.3 通用动作区模型

合同、结算、付款详情页的按钮不应各自手写权限判断。P0 应收敛为统一动作区，由后端返回动作元数据：

```ts
type BusinessAction = {
  key: string;
  label: string;
  visible: boolean;
  enabled: boolean;
  reason?: string;
  confirmText?: string;
  requiresPassword?: boolean;
  requiresComment?: boolean;
  requiresFile?: boolean;
  tone?: "primary" | "default" | "danger";
};
```

前端只负责展示、收集输入和提交；能不能做仍由后端最终校验。

### 16.4 动作交互规则

| 动作 | P0 规则 |
| --- | --- |
| 提交 | 只在草稿或退回可重提状态显示；提交前复述项目、相对方、金额、付款条款、附件缺口。 |
| 同意 | 只给当前节点处理人、转审人、有效受托人；涉及金额例外或风险时意见必填。 |
| 驳回 | 必须填写原因；弹窗说明本轮审批终止，后续需重新发起或新建。 |
| 退回 | 必须选择退回上一节点或打回申请人；展示退回后谁处理。 |
| 撤回 | 只给申请人；合同撤回回草稿，付款撤回应明确为终态或需新建。 |
| 催办 | 只给申请人；仅超 SLA 且未在节流期内显示；不改变单据状态。 |
| 转审 | 只给当前节点审批人；目标人页面显示“由某某转审”。 |
| 委托 | 必须有期限、范围、受托人；受托人操作时显示“代某某处理”。 |
| 归档确认 | 必须列出归档文件并核对编号、金额、版本、相对方；当前密码二次确认。 |
| 实付 | 只在“已批待付款/部分实付”显示；录入金额、日期、收款方、账户、凭证；当前密码二次确认。 |
| 下载 | 从文件卡选择文件；敏感文件输入当前密码，P1 增加下载原因。 |

### 16.5 角色认知走查结论

施工企业用户不是在管理数据表，而是在防止三类事故：

```text
钱错付
章错盖
资料缺证据
```

因此首页、详情页和弹窗文案都要围绕这三件事设计。各角色第一屏重点：

| 角色 | 第一屏优先显示 |
| --- | --- |
| 董事长 / 总经理 | 待终审合同、待终审付款、高金额/超期风险、项目资金摘要。 |
| 项目经理 | 本项目待审批、阻塞事项、超时节点、即将影响付款的结算。 |
| 合同员 | 待补资料、待上传归档件、草稿合同、历史接管未完成。 |
| 合同主管 | 待归档确认、待接管确认、版本/金额差异提醒。 |
| 财务 | 已批待付款、付款容量异常、待入账、缺凭证。 |
| 出纳 | 可执行付款清单、待上传凭证、付款失败/待补凭证。 |
| 物资 / 工程 | 本专业结算核验、缺附件、退回补充事项。 |
| 普通员工 | 我发起的申请状态、被退回需补充、最近通知。 |

### 16.6 内控与审计字段

敏感动作遵循：

```text
操作前看清事实 -> 操作中确认身份和影响 -> 操作后留下证据
```

所有敏感动作至少记录：

```text
event_id
trace_id
服务器时间
操作者
真实岗位
项目岗位
是否代办
被代理人
来源 IP
User-Agent
会话/设备标识
二次认证方式和时间
动作
资源类型和业务编号
项目
前后状态
结果
失败原因码
审批/权限策略版本
```

文件类追加：

```text
file_id
文件名
大小
hash
版本
下载票据 ID
过期时间
```

金额类追加：

```text
合同
结算
付款单
收款方
金额
余额快照
```

禁止记录密码、验证码、短链完整 URL、SecretKey。

### 16.7 可访问性与可用性 P0

P0 不追求全量 AAA，也不重写组件库。先做到高风险流程可理解、可键盘操作、可纠错。

必须补：

1. 全局跳过导航、`main` landmark、路由切换后聚焦页面标题、页面 title 同步。
2. 合同、结算、付款、接管、改密、登录统一为“字段 label + helper + inline error + 顶部错误汇总”。
3. 归档确认、付款审批、实付、入账、敏感下载提交前展示“本次将改变什么状态/金额/单据/附件”。
4. 结算/付款详情继续清除内部 ID 输入：文件、审批人、委托对象、付款凭证都从上下文选择。
5. 状态不能只靠颜色；必须有文本说明“已完成、当前节点、待谁处理、为什么不可操作、下一步是什么”。
6. 台账表格金额列右对齐并统一单位；操作链接要带上下文，例如“查看付款 FK-2026-007”。
7. 每个任务区只保留一个主按钮，撤回、催办、转审、委托、下载降级为次级或更多操作。
8. 低对比文字和状态色统一修正，普通文字达到 WCAG AA 对比度，状态点和边框至少 3:1。
9. 登录和强制改密支持密码管理器：设置合理 `autocomplete`，允许粘贴。
10. 文件上传显示文件类型、大小限制、选中文件名、上传中/成功/失败状态。

验收门槛：

- 只用键盘可完成首页待办到合同/结算/付款详情的主流程。
- axe 自动扫描无 P0 阻断项。
- 200%/400% 缩放下关键流程可用。
- VoiceOver 至少走通合同归档、结算归档、付款实付三条路径。

## 17. 云上营家只读参考走查

### 17.1 走查边界

参考站点：`http://www.inja.com` 及登录后的云上营家工作台。

本轮只做界面和流程观察：登录、展开菜单、查看已有列表、打开已有详情、观察页面结构。未执行新建、保存、确认、转交、提交、删除、导出、附件下载等会改变业务数据或导出业务数据的动作。

公开主页可见前端为 Next.js 应用壳；后台业务入口用普通 `curl` 抓取时被 CloudWAF 拦截，返回 418。因此本节依据浏览器只读观察，不按源码反推内部实现。

### 17.2 可借鉴的产品结构

#### 工作台

登录后不是直接进某一张表，而是进入企业工作台：

- 顶部有全局搜索、企业主体切换、通知、用户菜单、帮助入口。
- 左侧只保留大模块入口，例如意见反馈平台、招采系统。
- 当前业务页以底部页签方式保留上下文，计划管理、我的任务可以并存切换。

对建工智管的启发：

- 首页不应只是合同/结算/付款数量面板，应升级为“我的工作池”。
- 合同员、合同主管、财务、出纳、项目经理进入系统后，第一屏看到的是自己要处理的单据、被退回事项、超时事项、待补资料。
- 底部或顶部页签可作为 P1 能力；P0 可先做“最近打开”或面包屑，避免用户在台账和详情间迷路。

#### 模块菜单

招采系统菜单按业务过程组织：

- 采购计划管理：计划管理。
- 任务管理：我的任务、分包申请。
- 招标过程：招标大厅、资格审查、专家评分、招标变更、审查小组、标书报表管理、招标事件查询、招标作业。
- 寻源过程：寻源大厅、寻源事件查询、寻源过程控制。
- 采购设置：采购类型关联定义、采购计划自分配用户权限定义。
- 招标管理：寻源费用管理。

对建工智管的启发：

- 左侧导航不应只按数据库对象命名。建议按“业务入口 + 工作池 + 查询台账 + 设置”拆分。
- 合同模块可拆为：合同工作台、合同台账、待归档确认、合同变更、合同审批记录、合同模板。
- 结算模块可拆为：结算工作台、结算台账、待归档确认、可发起付款结算。
- 付款模块可拆为：付款工作台、待审批付款、已批待付款、实付登记、凭证补录、付款查询。

### 17.3 列表页模式

计划管理列表的稳定模式：

- 顶部为批量动作区：新建、退回、删除、终止、复制、导出等。无选中行时危险动作禁用。
- 筛选区只展示高频筛选：状态、编号、采购类型；更多筛选折叠到“更多”。
- 列表首列是勾选框，业务编号是链接入口。
- 表格列非常宽，支持横向滚动，并保留右侧操作列。
- 分页显示每页行数、总条数、页码。
- 数据列不仅有状态，也有耗时、退回原因、分配人、负责人等过程字段。

对建工智管的 P0 改造：

- 合同/结算/付款台账保留三到五个高频筛选，其他字段放入“更多筛选”。
- 业务编号必须是详情入口，操作列只放当前状态下最常用的一个动作，其余进入更多。
- 批量动作先只给低风险动作，例如批量导出查询结果可暂缓；审批、归档、实付不做批量。
- 列表应新增过程字段：当前处理人、当前节点、停留时长、退回原因、下一步动作。
- 空状态要说明下一步，而不是只显示“暂无数据”。

### 17.4 详情页模式

采购计划详情是典型企业单据页：

- 顶部是返回和单据标题。
- 主体按段落折叠：基本信息、补充信息、物资明细。
- 基本信息使用三列密集表单，必填字段红星，已锁定字段灰底只读。
- 关联对象使用放大镜选择器，附件使用“查看附件”链接。
- 明细区内置筛选、总计、横向表格、分页。
- URL 中带状态、业务 ID、采购类型、打开方式，说明页面能力由状态机和上下文驱动。

对建工智管的 P0 改造：

- 合同详情保留“概要条 + 分段信息 + 业务动作”，但字段组织应更像单据，而不是测试工具面板。
- 归档文件、审批单、付款凭证都应通过上下文文件卡直接选择或下载，禁止让用户手填文件 ID。
- 合同详情建议分为：基本信息、付款条款、当前流程、归档资料、关联结算、关联付款、审计记录。
- 结算详情建议分为：基本信息、计量/结算明细、归档资料、可付款余额、关联付款、审计记录。
- 付款详情建议分为：申请信息、审批记录、实付记录、凭证资料、余额校验、审计记录。
- 危险动作不应常驻堆叠在页面上；只显示当前角色和当前状态真正能做的动作，并给出禁用原因。

### 17.5 任务池模式

我的任务页展示的是个人处理池：

- 默认状态筛选为待接收、待启动。
- 顶部有组合、取消组合、终止等批量动作，但无选中行时禁用。
- 列表列包含任务编号、组合、任务名称、计划编号、项目名称、分配人、经办部门、接收时间、退回原因、终止原因、转交自。
- 无数据时给出空状态和调整筛选的提示。

对建工智管的 P0 改造：

- 首页需要独立“我的待办”数据源，而不是每个模块各查一次列表。
- 待办卡片至少包含：业务编号、业务类型、当前节点、发起人、项目、金额、停留时长、是否转审/委托、退回原因。
- 角色首页默认筛选应不同：合同员看待补资料/待上传，合同主管看待确认，财务看已批待付款，领导看待终审。
- 转审、委托、退回必须在任务上可见，避免用户只看到一个陌生单据。

### 17.6 我们不应照搬的地方

- 页面视觉有较重的渐变和毛玻璃，信息密度高时会降低对比度；建工智管应更克制。
- 只读字段仍显示下拉箭头，容易让用户误以为可以编辑；我们应区分“可编辑表单”和“只读描述”。
- 顶部动作如确认、保存、转交在部分页面里过于接近；我们应按风险分组，危险操作二次确认。
- 大量图标缺可访问名称；我们必须补按钮 `aria-label`、表单 label、路由焦点。
- 部分列表列过多，初次用户难以扫描；我们应提供默认列集和“列设置”。

### 17.7 落地优先级

P0 立即做：

1. 首页改为“我的工作池”：按角色展示待办、退回、超时、待补资料。
2. 三个详情页清除手填 ID：文件、凭证、归档、下载均从当前单据上下文选择。
3. 台账列表增加当前节点、当前处理人、停留时长、退回原因、下一步动作。
4. 详情页统一分段：基本信息、业务明细、资料附件、流程动作、审计记录。
5. 动作按钮由后端返回可执行动作和禁用原因，前端只渲染。

P1 做：

1. 模块菜单升级为业务过程菜单。
2. 最近打开/页签式工作区。
3. 表格列设置、保存个人筛选。
4. 任务组合/批量低风险处理。
5. 全局搜索。

## 18. 静态前端资源走查补充

### 18.1 资源边界

本轮在用户已登录浏览器中，只抓取云上营家前端静态 JS/CSS 资源，用于理解页面组织和交互模型。未调用业务接口抓取列表 JSON，未下载附件，未执行新建、保存、确认、转交、提交、删除、导出等业务动作。

抓取范围保存在本机临时目录 `/tmp/inja-frontend-capture`，覆盖：

- 招标大厅列表。
- 采购计划列表。
- 采购计划详情。
- 我的任务。

这些资源是生产压缩 chunk，没有 sourcemap，不能等同于原始源码。可参考的是页面路由、状态命名、按钮组织、表单分区和任务流设计；不复制其代码实现。

### 18.2 从 chunk 看到的可借鉴模式

#### 路由按业务状态组织，而不是只按表名组织

采购计划相关 chunk 中能看到同一业务对象被拆成多个入口：列表、详情、转交详情、审批详情、分配详情、任务释放、导入等。详情页 URL 里有 `handleType`、`status`、`purchaseType`、业务 ID 等上下文，页面根据这些上下文进入新增、查看、客户新增、回价、待确认、分配等不同模式。

对建工智管的判断：

- 值得做：合同、结算、付款详情都应有统一的 `pageMode/actionContext` 概念，至少区分 `create/edit/review/confirm/download/readonly`。
- 先别做重：P0 不需要搭一个完整页面编排引擎。先让详情接口返回当前单据状态、当前角色可执行动作、禁用原因，前端按这个元数据渲染。
- 应避免：同一个页面里堆满所有按钮，再靠用户自己判断能不能点。

#### “我的任务”是独立工作池，不是每个模块列表的别名

我的任务 chunk 中能看到独立路由：任务详情、任务查看、组合任务、按 `handleType` 打开的新详情，以及分配详情的特殊入口。任务列表字段也不是普通单据字段，而是任务编号、组合状态、任务名称、计划编号、项目、分配人、接收时间、退回原因、终止原因、转交来源等过程字段。

对建工智管的判断：

- 值得做：建立“我的待办 / 阻塞事项 / 我发起的进行中”三队列，作为首页第一屏。
- 值得做：待办项本身要带业务动作，例如“补归档件”“确认归档”“终审付款”“上传付款凭证”，而不是只显示“合同 HT-2026-001”。
- 暂缓做：任务组合、取消组合、批量终止这类能力目前不适合 P0。建工智管当前最重要的是单据链路跑通和证据链可靠。

#### 动作由状态和身份共同决定

采购计划详情 chunk 中可见退回至回价、退回至编辑、终止采购计划、催办等动作，并且会按状态、当前用户、分组标记等条件显示。列表中也能看到待启动、执行中、退回、终止等任务状态。

对建工智管的判断：

- 值得做：后端详情 read model 返回 `availableActions` 和 `disabledReason`，前端不再复制权限判断。
- 值得做：每个按钮旁边或禁用态提示“为什么现在不能操作”，例如“合同尚未归档确认，不能发起结算”。
- 必须守住：前端只负责解释和引导，真实权限仍由后端守住。

#### 明细表是业务主体，不是附件备注

采购计划详情里物资明细是页面核心区域，带筛选、总计、横向表格、分页、导入、同步价格、行级只读/编辑控制。它不是一个可有可无的备注区。

对建工智管的判断：

- 值得做：结算明细、付款占用明细、实付凭证清单都应成为详情页中的一等区域。
- 值得做：金额类页面必须展示“本次金额、累计金额、剩余额度、可付款额、已付额”的表格化计算过程。
- 暂缓做：复杂 Excel 导入纠错、批量同步价格、列级公式配置可放 P1/P2，先把真实业务链路中的明细读模型补齐。

#### 业务专用选择器优于过度通用弹窗

采购计划转交人员选择有本模块专用弹窗的迹象，说明复杂企业系统并不总是追求所有选择器完全通用。业务上下文强的动作，用专用弹窗更容易让用户看懂。

对建工智管的判断：

- 值得做：归档确认、转审/委托、敏感文件下载、付款实付分别做小而清楚的专用弹窗。
- 不值得做：一个万能“选择对象 + 输入密码 + 上传文件 + 填备注”的大弹窗。它会让关键动作失去业务语义。

### 18.3 接下来值得优化的点

| 优先级 | 优化点 | 价值判断 | 实施判断 |
| --- | --- | --- | --- |
| P0 | 取消所有手填内部 ID | 使用者不应知道 fileId、archiveId、versionId。合同下载已开始修正，结算、付款、归档确认、凭证下载要继续清理。 | 价值高、风险低，优先做。 |
| P0 | 详情页返回可执行动作和禁用原因 | 能从根上解决“按钮很多但不知道能不能点”的问题，也避免前端重复写权限。 | 价值高、风险中，先覆盖合同/结算/付款三类详情。 |
| P0 | 首页改成角色工作池 | 员工每天不是来查表，而是来处理待办、退回、超时、补资料。 | 价值高、改动中，先用现有接口聚合，不够再补小接口。 |
| P0 | 合同/结算/付款详情统一信息架构 | 单据页应围绕概要、明细、资料、流程、审计，而不是测试面板式动作堆叠。 | 价值高、改动中，逐页替换。 |
| P0 | 附件卡片和敏感下载统一 | 所有下载都从当前单据上下文选择文件，展示文件名、类型、上传人、版本、是否可下载。 | 价值高、风险低，和取消 ID 输入合并推进。 |
| P0 | 列表增加过程字段 | 当前处理人、当前节点、停留时长、退回原因、下一步动作比内部状态枚举更重要。 | 价值高、依赖读模型，先补合同列表。 |
| P1 | 最近打开 / 页签式工作区 | 企业系统中列表和详情来回切换频繁，但不是上线阻断。 | 有价值，等 P0 单据页稳定后做。 |
| P1 | 个人筛选和列设置 | 重度使用后会明显提升效率。 | 有价值，但先不要消耗 P0 资源。 |
| P2 | 任务组合、批量终止、复杂批量动作 | 对采购系统重要，对当前合同结算付款闭环不是第一优先。 | 暂缓，避免过早引入复杂状态。 |

### 18.4 建议实施顺序

1. 先把合同详情中“按当前合同直接下载文件”的模式固化，再复制到结算和付款，彻底清除手填文件 ID。
2. 给合同、结算、付款详情 read model 增加 `availableActions`、`disabledReason`、`primaryAction`，前端只渲染后端允许展示的动作。
3. 重做首页为三队列工作池：待我处理、阻塞事项、我发起的进行中。每个任务显示业务编号、类型、项目、金额、当前节点、停留时长、下一步动作。
4. 合同详情先改为正式单据页：基本信息、付款条款、流程状态、归档资料、关联结算、关联付款、审计日志。
5. 结算详情和付款详情按同一结构迁移，补齐明细表和余额解释。
6. 列表页增加过程字段和“更多筛选”，业务编号成为主要入口，操作列只保留当前最自然的一个动作。
7. 等试运行员工连续使用一周后，再决定是否做最近打开、页签式工作区、个人列设置。

当前最值得投入的不是视觉美化，而是把系统从“开发者能操作的管理台”改成“业务人员知道下一步该做什么的流程系统”。

## 19. 开源企业系统功能参考策略

### 19.1 架构决策

继续保留当前架构：

```text
Vue 3 + TypeScript + TDesign Web + Pinia
NestJS + PostgreSQL + Prisma
腾讯云 Lighthouse + Nginx + COS 私有桶
```

不切换到 Element Plus、Ant Design、若依、JeecgBoot、O2OA、Yudao 或 Snowy 作为底座。原因很简单：系统已经进入生产试运行，现有合同、结算、付款、归档、COS 私有文件、审计、权限和部署链路已经跑通。此时换底座不是省事，而是重新做一遍。

这些开源项目的价值在于参考功能和交互，不在于复制代码或迁移架构。

### 19.2 参考项目吸收范围

| 参考对象 | 值得吸收 | 不吸收 |
| --- | --- | --- |
| Flowable / 若依 Flowable 类系统 | 待办中心、流程历史、转办、委托、撤回、退回、流程节点可视化、审批意见沉淀。 | 不引入 Java Flowable 引擎，不重做 BPMN 设计器。 |
| JeecgBoot | 密集表单分组、字段字典、选择器、附件控件、列表筛选、代码生成后的页面结构。 | 不引入低代码表单引擎，不让业务字段变成运行时动态配置。 |
| O2OA | 工作台、收件箱/发件箱/草稿箱、公文式流转、附件列表、签批意见、阅读痕迹。 | 不引入 OA 大套件，不扩展到考勤、公文、人事等 Phase 1 之外模块。 |
| Yudao / Snowy 类现代后台 | 菜单权限、角色权限、数据权限、操作日志、登录日志、字典参数、统一后台布局。 | 不迁移 Spring Boot / Vue Admin 底座，不照搬它们的大而全模块。 |

### 19.3 对建工智管前端的具体落点

#### 工作台

参考 OA 和 BPM 系统的工作池模式，首页改成三队列：

1. 待我处理：当前角色必须处理的合同、结算、付款、归档、凭证事项。
2. 阻塞事项：退回、超时、缺附件、缺归档确认、金额校验失败。
3. 我发起的进行中：自己发起但还没闭环的单据。

每个待办项显示：

```text
业务类型
业务编号
项目
金额
当前节点
当前处理人
停留时长
下一步动作
退回/阻塞原因
```

#### 表单

参考 JeecgBoot 的密集表单能力，但不做低代码。P0 只沉淀固定业务组件：

- 业务编号选择器。
- 项目选择器。
- 合同选择器。
- 结算选择器。
- 文件卡片列表。
- 金额拆解表。
- 审批意见输入。
- 当前密码确认。
- Canvas 签名板。

合同、结算、付款表单必须从上下文带出关联数据。例如选择合同后，前端展示合同金额、已结算、可结算、已付款、可付款；后端仍负责最终事务校验。

#### 审批流

参考 Flowable 类系统，但 P0 只做业务可读时间线：

```text
已完成节点
当前节点
待处理岗位/人员
审批意见
签批图片
节点停留时长
下一步可能去向
```

暂不做在线流程设计器。流程规则仍由后端配置和代码守住，等审批规则需要由业务人员频繁调整时再考虑 BPMN 设计器。

#### 附件和归档

参考 O2OA 的附件区做法，每个业务详情页都有统一资料区：

```text
文件名
文件类型
业务用途
上传人
上传时间
版本
是否归档件
是否可下载
下载按钮或禁用原因
```

用户不填写 `fileId`、`archiveId`、`contractVersionId`。所有动作从当前单据上下文选择。

#### Canvas 签名

Canvas 签名作为内部签批能力纳入产品，不在页面中提示法律效力问题。

使用位置：

- 审批通过。
- 审批驳回或退回。
- 合同归档确认。
- 结算归档确认。
- 付款实付确认。
- 付款凭证确认。

交互要求：

```text
打开动作弹窗
展示本次动作影响
输入审批/确认意见
手写签名
当前密码二次确认
提交
生成审计记录
签名图片进入后续 PDF/审批记录
```

签名图片走后端文件服务，存入 COS 私有桶；前端不把签名长期放在 localStorage。

### 19.4 近期开发顺序

1. 先做合同详情“无 ID 下载 + 文件卡片 + 当前合同上下文下载”闭环。
2. 复制到结算详情、付款详情、归档确认、凭证下载。
3. 给合同、结算、付款详情 read model 加 `availableActions`、`disabledReason`、`primaryAction`。
4. 首页改成三队列工作池。
5. 增加 Canvas 签名板组件，并先接入审批通过、归档确认、付款实付三个高价值动作。
6. 把审批历史改成时间线，展示意见、签名、节点、处理人、停留时长。

这条路线保留现有系统资产，同时把成熟 OA/BPM/低代码系统里真正有用的功能吸收进来。

## 20. 开源项目深度功能拆解与稳态落地

### 20.1 调研依据

本轮参考来源：

- Flowable 官方开源文档与 `flowable-engine` 仓库：流程实例、任务、历史、REST API、BPMN/CMMN/DMN 能力。
- JeecgBoot 仓库：低代码/零代码、在线表单、表单设计、流程设计、门户、报表、按钮权限、数据权限。
- O2OA 仓库：OA 协同、流程引擎、表单定制、页面定制、业务数据服务、移动办公、备份恢复。
- RuoYi-Vue-Pro / Yudao 仓库：系统功能、基础设施、按钮权限、数据权限、操作日志、登录日志、Flowable 工作流、会签、或签、转办、委派、加签、超时提醒。
- Snowy 仓库：插件化代码结构、安全体系、登录/操作日志完整性、前后端分离后台组织方式。

结论保持不变：不引入 Java 流程引擎，不迁移低代码平台，不换 UI 库。只吸收成熟系统中被反复验证的功能形态。

### 20.2 可以稳定吸收的六个能力

#### 1. 工作池

成熟 OA/BPM 系统都会把“待办”做成一等入口，而不是让用户去合同、结算、付款三个列表里找事情。

落到建工智管：

```text
GET /me/work-items
```

返回三类队列：

```text
pendingForMe
blocked
startedByMe
```

每个任务项只放业务人员需要的字段：

```text
id
type: contract | settlement | payment | archive | voucher
businessCode
title
projectName
amountCents
currentNodeName
currentHandlerName
ageMinutes
reason
primaryAction
detailPath
```

先做只读聚合，不做任务引擎。数据从现有合同、结算、付款、归档状态拼出来即可。

#### 2. 动作元数据

Flowable/Yudao 的流程能力很大，但对我们最有价值的是“当前任务能做什么、为什么不能做”。

落到建工智管：

详情 read model 增加：

```text
availableActions[]
primaryAction
disabledReasons[]
```

动作结构：

```text
key
label
kind: primary | normal | danger
requiresPassword
requiresSignature
requiresComment
requiresFile
disabledReason
```

前端只负责渲染。后端写接口继续做真实权限和状态校验。

#### 3. 附件证据区

O2OA、JeecgBoot 的附件能力都说明一件事：企业系统里文件不是“上传控件”，而是证据链。

落到建工智管：

合同、结算、付款详情统一返回 `evidenceFiles[]`：

```text
fileId
name
purpose
mimeType
sizeBytes
uploadedByName
uploadedAt
businessVersion
isArchiveFile
canDownload
disabledReason
```

前端展示文件卡片，用户点击下载。彻底取消手填 `fileId`。

#### 4. 审批时间线

成熟工作流系统会把流程历史和当前节点放在一起，用户不用猜“这单卡在哪里”。

落到建工智管：

合同、结算、付款详情统一返回 `approvalTimeline[]`：

```text
nodeName
actionLabel
actorName
positionName
comment
signatureFileId
actedAt
durationMinutes
result
```

P0 只做时间线，不做 BPMN 图。BPMN 设计器等业务人员真的需要在线改流程时再说。

#### 5. Canvas 签名

手写签名作为内部签批图像使用，接入高风险动作。

落到建工智管：

先接三处：

- 审批通过。
- 归档确认。
- 付款实付确认。

前端组件只做三件事：

```text
签名
清除重签
提交为图片文件
```

后端按普通私有文件处理签名图片，纳入审计和 PDF 渲染。

#### 6. 系统治理能力

Yudao/Snowy 这类后台的价值不只是页面，还包括后台治理：在线用户、登录日志、操作日志、按钮权限、数据权限、字典、错误码。

落到建工智管：

P0 不扩一堆系统菜单，只补业务安全需要的最小集：

- 登录日志查询。
- 操作日志查询。
- 文件下载审计查询。
- 用户岗位/项目权限查看。
- 生产健康检查状态查看。

### 20.3 不该照搬的能力

| 能力 | 为什么暂不做 |
| --- | --- |
| 在线 BPMN 设计器 | 当前流程是强业务规则，不适合让业务人员自由拖拽修改。 |
| 低代码动态表单引擎 | 合同、结算、付款有金额和状态强约束，动态字段会增加校验风险。 |
| 多租户 SaaS | 当前是单企业生产系统，多租户会扩大权限和数据隔离复杂度。 |
| 报表大屏设计器 | 现阶段更需要真实业务链路闭环，不需要拖拽大屏。 |
| 插件市场 / 模块市场 | 对当前上线没有价值。 |
| AI 生成流程/表单 | 可以做内部研发辅助，不进入生产功能。 |

### 20.4 分阶段落地路线

#### Phase A：先把单据详情变成“可用的流程页”

范围：

- 合同详情。
- 结算详情。
- 付款详情。

最小改动：

1. 每个详情接口返回 `availableActions`。
2. 每个详情接口返回 `evidenceFiles`。
3. 每个详情接口返回 `approvalTimeline`。
4. 前端把动作区、资料区、审批历史统一成三个组件。
5. 合同详情先落地，稳定后复制到结算和付款。

验收：

- 用户不再输入任何内部 ID。
- 用户能看到当前能做什么、不能做什么、为什么。
- 用户能从详情页直接下载当前业务文件。
- 用户能看到完整审批历史。

#### Phase B：工作台改成“我的工作池”

范围：

- 首页。
- 待办聚合接口。

最小改动：

1. 新增只读聚合接口 `GET /me/work-items`。
2. 首页展示三队列：待我处理、阻塞事项、我发起的进行中。
3. 每个任务点击进入对应详情页。
4. 暂不做批量处理。

验收：

- 合同员登录后能看到待补资料、待上传归档件。
- 合同主管登录后能看到待归档确认。
- 财务登录后能看到已批待付款、待凭证。
- 领导登录后能看到待终审合同和待终审付款。

#### Phase C：签名与动作弹窗统一

范围：

- 审批通过。
- 归档确认。
- 付款实付确认。

最小改动：

1. 新增 `SignaturePad` 前端组件。
2. 动作弹窗统一展示“本次动作影响”。
3. 支持意见、签名、当前密码确认。
4. 后端保存签名文件并写审计。

验收：

- PDF 审批记录能看到签名图片。
- 审计日志能追到签名文件、动作、操作者、时间。
- 签名失败不产生半完成业务状态。

#### Phase D：流程辅助能力补齐

范围：

- 撤回。
- 退回上一节点。
- 打回发起人。
- 转审。
- 委托。
- 催办。
- 超时提醒。

最小改动：

1. 先把已有动作统一进 `availableActions`。
2. 每个动作都有独立后端校验和审计事件。
3. 超时提醒先做只读标记，再做通知。

验收：

- 详情页不出现无效按钮。
- 禁用动作都有明确原因。
- 所有动作有审计。

### 20.5 数据模型最小补充

不新增“大流程引擎表”。只补当前功能缺口。

建议新增或复用：

```text
SignatureFile
  id
  fileObjectId
  userId
  createdAt
  purpose

WorkItemReadModel
  不落表也可以，先由 service 聚合生成

BusinessAction
  不落表，先由 read service 计算返回
```

已有 `ApprovalActionLog`、`AuditLog`、`FileObject` 能承接大部分证据链，不要另起一套历史表。

### 20.6 前端组件最小清单

先做六个组件，够用再说：

```text
BusinessActionPanel.vue
EvidenceFileList.vue
ApprovalTimeline.vue
SignaturePad.vue
PasswordConfirmField.vue
WorkItemQueue.vue
```

不做：

- FormEngine。
- WorkflowDesigner。
- DynamicPageRenderer。
- LowCodeRuntime。

这些名字听起来高级，实际会把 Phase 1 拖慢。

### 20.7 试运行上线顺序

1. 合同详情无 ID 文件下载。
2. 合同详情动作元数据。
3. 合同审批时间线。
4. 合同审批/归档 Canvas 签名。
5. 结算详情复制同样结构。
6. 付款详情复制同样结构。
7. 首页三队列工作池。
8. 催办、转审、委托等辅助动作统一收口。

这条路线的关键是“每一步都能单独上线、单独验证、单独回滚”。不引入大平台，不一次性改完全部流程。

## 21. UI 与治理专项调研结论

本轮新增五个子代理专项研究 RuoYi/Yudao、Snowy、JeecgBoot、O2OA、Flowable 类项目的 UI 与治理。共识很一致：不换底座、不换 UI 库，只学习稳定后台系统的信息架构和治理套路。

### 21.1 UI 骨架

P0 统一后台骨架：

```text
工作台
合同管理
结算管理
付款管理
资料库
基础档案
系统治理
```

规则：

- 业务入口和系统治理分开。
- 系统治理只给管理员看。
- P0 不做完整多页签缓存，最多做“最近打开 5 个单据”。
- 首页不做技术看板，不展示服务器图表；首页只做业务工作池。

### 21.2 列表页套路

合同、结算、付款列表统一为：

```text
查询区
表格
分页
行操作
```

查询区 P0 只放 4-6 个高频项：

- 项目。
- 状态。
- 当前处理人。
- 时间范围。
- 金额范围。
- 业务编号。

表格列 P0 统一：

```text
业务编号
项目
相对方 / 收款方
金额
状态
当前节点
当前处理人
更新时间
操作
```

操作列只保留：

```text
查看
处理
下载 / 更多
```

危险动作不放列表行里直接执行，必须进入详情页或弹窗确认。

### 21.3 详情页套路

合同详情先改，结算和付款复用：

```text
顶部摘要
业务信息
业务明细
附件证据区
流程时间线
审计日志
动作区
```

顶部摘要必须回答：

- 这是什么单据。
- 当前是什么状态。
- 当前卡在哪个节点。
- 等谁处理。
- 下一步是什么。
- 为什么某些动作不能做。

详情动作只来自后端 `availableActions`，前端不自己判断权限。

### 21.4 工作池与任务治理

参考 O2OA 的待办/已办/待阅/已阅，以及 Flowable 的 assignee/candidate/dueDate/priority，建工智管 P0 做：

```text
待我处理
我发起的进行中
阻塞 / 逾期
```

P1 再补：

```text
我已处理
抄送我
已读归档
```

工作项字段：

```text
业务类型
业务编号
标题
项目
金额
当前节点
当前处理人
候选岗位
是否已认领
停留时长
是否逾期
优先级
主动作
详情路径
```

OR 签和岗位池任务引入“我来处理”：

- 未认领时，同候选岗位的人都能看到。
- 某人认领后，只允许认领人继续处理。
- 后端事务防并发认领。

### 21.5 附件与签批 UI

附件区必须业务语义化：

```text
上传盖章合同
上传结算单
上传付款凭证
下载审批单
下载归档件
```

文件列表字段：

```text
文件名
用途
版本
上传人
上传时间
大小
状态
下载 / 预览 / 作废
```

手写签批 P0 只做：

```text
签名
清除
确认
```

不用做画笔颜色、橡皮、历史回放。签名保存为私有文件或审批快照，审批历史展示签名缩略图。

### 21.6 系统治理 P0

系统治理 P0 只做只读台账：

```text
登录日志
操作日志
文件下载审计
审批动作日志
用户岗位/项目权限查看
生产健康状态
```

日志字段：

```text
时间
用户
岗位
IP
User-Agent / 设备
动作
对象类型
对象编号
结果
失败原因
traceId
```

禁止记录：

```text
密码
token
密钥
完整请求体
COS 原始地址
完整下载短链
```

生产 UI 不提供日志清空按钮。P1 可考虑关键动作 `previousHash/hash` 链，先保护审批、付款、文件下载、权限变更。

### 21.7 权限治理

P0 不做通用 SQL 数据权限引擎。

现阶段采用：

```text
项目参与关系
全局岗位
项目岗位
业务状态
```

在服务层过滤：

- 我能看的项目。
- 我能看的单据。
- 我能处理的动作。
- 我能下载的文件。

前端只做表现：

- 可执行动作。
- 禁用动作原因。
- 无权限空态。

### 21.8 配置与字典

P0：

- 代码枚举 + 前端统一标签。
- 后端校验状态、动作、附件用途。

P1：

- 字典只读页。
- 安全登录配置。
- 文件下载配置。
- 上传限制配置。
- 通知开关。

暂不开放普通管理员编辑业务状态字典，避免改坏业务语义。

### 21.9 专项落地顺序

1. 合同详情：摘要、附件证据区、流程时间线、审计日志、动作区。
2. 合同列表：查询区、表格、分页、操作列统一。
3. `availableActions`：后端统一返回动作、禁用原因、主动作。
4. `GET /me/work-items`：工作台三队列。
5. 系统治理：登录日志、操作日志、文件下载审计。
6. OR 签/岗位池：加入“我来处理”认领动作。
7. 结算详情和付款详情复制合同详情结构。
8. Canvas 签批接审批、归档、实付。
9. P1 再做最近打开、导入预检、字典只读页、配置页。

这轮专项的底线：后台 UI 要克制，治理能力要可查，动作权限要后端说了算。

## 22. Gitee 参考仓库融合结论（2026-07-08）

本轮补充研究 Gitee 上的 RuoYi-Vue、RuoYi-Vue-Plus、RuoYi-Flowable-Plus、JeecgBoot 和 Soybean Admin，并复核 `apps/web-admin` 当前实现。结论不变但边界更清楚：继续保留现有架构和 TDesign，不换底座；只吸收成熟后台的交互模式、治理能力和工程纪律。

### 22.1 当前前端现状

| 问题 | 当前判断 | 证据与处理 |
| --- | --- | --- |
| 是否统一一套设计语言 | 部分统一，但还不是设计系统驱动。整体已有“企业后台、白底面板、浅灰边框、低饱和状态色、高信息密度”的倾向。 | 颜色、字号、间距仍大量散落在页面级 scoped CSS 中，例如 `#151922`、`#dce1e8`、`#f4f6f9`、`#165dff`、`#2f6fed` 等重复出现。下一步用薄 token 层收口。 |
| 前端组件库是否统一 | 依赖层面统一，Web 管理端只注册 `tdesign-vue-next`。 | `apps/web-admin/package.json` 仅依赖 TDesign，`src/main.ts` 全局 `app.use(TDesign)`；未发现 Element Plus、Ant Design Vue、Naive UI、Vant、Arco 等第二套 UI 库。 |
| 实现层是否混用 | 有混用。 | 部分页面仍使用原生 `button`、`input`、`select` 和手写 tab、卡片、状态块；这些不是第二组件库，但会造成视觉和交互不统一。 |
| 是否有设计 token | 还没有项目级设计 token。 | 仅少量使用 `var(--td-...)`，尚无 `tokens.css` 或统一主题文件。P1 应新增薄 token 层，先替换高频硬编码值。 |

### 22.2 仓库借鉴矩阵

| Gitee 仓库 | 可借鉴 | 不照搬 | 风险 |
| --- | --- | --- | --- |
| RuoYi-Vue | 用户、岗位、菜单、角色、字典、参数、通知、操作日志、登录日志、接口文档等后台治理清单；动态菜单和按钮权限思路。 | 不照搬通用 CRUD 菜单结构，不让系统管理入口压过项目、单据、待办和证据链。 | 借鉴低，照搬高。 |
| RuoYi-Vue-Plus | OSS、工作流、接口文档、数据权限、二级认证、多租户等企业后台能力边界。 | 不引入 Java/Sa-Token/MyBatis-Plus/WarmFlow 后端生态，不改 NestJS + PostgreSQL 主架构。 | 借鉴中，照搬高。 |
| RuoYi-Flowable-Plus | 流程分类、流程表单、流程定义、流程发起、待办任务、任务办理、流转记录、流程跟踪等 UX 元素。 | 不引入 Flowable 引擎和 BPMN 设计器；当前 MVP 不把审批核心迁移到通用工作流平台。 | 借鉴中，照搬高。 |
| JeecgBoot | 密集表单、字段字典、附件控件、按钮权限、数据权限、流程与表单分离、报表/打印的产品边界。 | 不引入低代码/零代码主路径，不让运行时表单绕过合同、结算、付款强规则。 | 借鉴中，照搬高。 |
| Soybean Admin | Vue 3、Vite、TypeScript、Pinia 工程纪律，权限路由、主题配置、目录边界和移动适配思路。 | 不迁移 Naive UI，不追求高颜值模板化后台。 | 借鉴低，照搬中。 |

最稳的融合方式是：

```text
Soybean 的前端工程纪律
  + RuoYi 的权限/日志/字典治理清单
  + Flowable 类系统的任务办理与流转记录 UX
  + JeecgBoot 的密集表单和附件控件边界
  -> 收敛到建工智管自己的项目容器、单据生命周期、角色待办、附件审计证据链
```

### 22.3 设计语言与 token 决策

Web 管理端只做“薄 token 层”，不新建独立组件库，不引入第二套 UI 库。token 目标是把当前已经形成的朴素企业后台风格固定下来。

建议新增 `apps/web-admin/src/app/design-tokens.css`，由 `main.ts` 在 TDesign 样式后引入：

```css
:root {
  --jg-bg-page: #f4f6f9;
  --jg-bg-panel: #ffffff;
  --jg-bg-muted: #f7f9fc;

  --jg-text-strong: #151922;
  --jg-text-main: #424955;
  --jg-text-subtle: #5f6673;
  --jg-text-muted: #767f8d;

  --jg-border: #dce1e8;
  --jg-brand: #0052cc;

  --jg-success: #2ba471;
  --jg-warning: #d9822b;
  --jg-danger: #c9353f;
  --jg-info: #0052cc;

  --jg-font-page-title: 24px;
  --jg-font-section-title: 16px;
  --jg-font-body: 13px;
  --jg-font-meta: 12px;
  --jg-font-mini: 11px;

  --jg-space-xs: 4px;
  --jg-space-sm: 8px;
  --jg-space-md: 12px;
  --jg-space-lg: 16px;
  --jg-space-xl: 24px;

  --jg-radius-sm: 3px;
  --jg-radius-md: 6px;
  --jg-radius-lg: 8px;
}
```

落地规则：

- TDesign 是唯一组件库；表单、按钮、表格、弹窗、标签、抽屉优先使用 `t-*` 组件。
- 原生控件只保留在文件选择、Canvas 签名等 TDesign 没有直接覆盖或原生更合适的场景。
- 业务组件不是新组件库，只承载业务语义，例如 `BusinessActionPanel`、`EvidenceFileCards`、`ApprovalTimeline`。
- 状态色按语义收口：`default` 草稿/暂无，`primary` 审批中/当前节点，`success` 已完成/已确认，`warning` 待补充/暂不可操作，`danger` 驳回/作废/高风险。
- 普通页面标题只用 24px；区块标题 16px；表格和卡片主文本 13px；说明、审计提示和空态 12px。
- 卡片圆角默认 3px，登录页和项目概览独立面板可用 8px；不做卡片套卡片。

### 22.4 可直接落地的前端优化

| 优先级 | 事项 | 来源 | 落地方式 |
| --- | --- | --- | --- |
| P1 | 薄 token 层 | Soybean 主题纪律 + 当前页面高频色值 | 新增 token CSS，先替换公共组件和新增页面，不做大规模机械改色。 |
| P1 | TDesign 使用规范 | RuoYi/JeecgBoot 后台组件纪律 | 表格、筛选、表单、弹窗、标签统一优先用 TDesign；逐步替换项目经营和合同模板页的原生 `select/button/tab`。 |
| P1 | 台账工具条统一 | RuoYi 列表套路 | 合同、结算、付款、资料库、审计页统一查询区、摘要条、列设置、空态和操作列。 |
| P1 | 详情页流程摘要条 | Flowable 任务办理 UX | 合同/结算/付款详情顶部统一显示当前节点、处理人、停留时长、下一步、金额摘要、证据摘要。 |
| P1 | `BusinessActionPanel` 成为唯一动作状态入口 | Flowable/Yudao 按钮权限 | 详情页按钮状态、禁用原因、密码/意见/文件要求都从后端 `availableActions` 展示。 |
| P1 | 证据文件卡收口 | JeecgBoot/O2OA 附件区 | `EvidenceFileCards` 增加统一状态 tag、下载审计提示、不可下载原因；不要做图片式网盘卡。 |
| P1 | 审批时间线收口 | Flowable 流转记录 | `ApprovalTimeline` 继续轻量化，不做复杂流程图；只展示节点、动作、处理人、意见、停留时间。 |
| P2 | 权限/字典/配置只读治理页深化 | RuoYi/JeecgBoot 治理清单 | 先只读展示，等真实权限矩阵稳定后再考虑配置编辑。 |

### 22.5 风险分层

低风险立即落地：

- 后台布局、菜单分组、面包屑、最近打开和列表模板。
- 表格筛选、分页、列显隐、空态、错误态。
- 字典标签、金额/日期展示、状态 tag。
- 文件卡片、审批时间线、动作面板这些业务 UI 组件。

中风险需后端配合：

- 动态菜单和按钮权限：前端只做表现，后端必须返回权限点并继续强校验敏感 API。
- 工作流看板和流程进度：可以展示，不可用前端状态机替代后端审批引擎。
- 导入导出：导入必须预检和事务校验；导出必须有权限、原因和审计。
- 文件中心：必须按项目、合同、结算、付款上下文鉴权，不可变成普通网盘。

高风险暂不做：

- 引入 Gitee 仓库自带后端或 Flowable/低代码运行时。
- 引入第二套 UI 组件库。
- 前端直连数据库、对象存储或使用永久下载 URL。
- 用通用角色模型替代真实业务岗位。
- 用前端状态流转决定合同、结算、付款和实付状态。

### 22.6 更新后的融合路线

1. 先新增薄 token 层，并让公共组件和新页面使用 token。
2. 合同、结算、付款、资料库、审计列表统一为查询区 + 摘要条 + 表格 + 分页 + 操作列。
3. 合同、结算、付款详情统一顶部流程摘要条。
4. `BusinessActionPanel` 从“可执行动作状态展示”升级为详情页动作入口的唯一视觉标准。
5. `EvidenceFileCards` 和 `ApprovalTimeline` 接入 token 与统一状态 tag。
6. 项目经营、合同模板编辑等手写控件较多的页面，逐步替换为 TDesign 组件。
7. 权限、字典、配置、审计继续只读优先，等真实试运行稳定后再开放有限编辑。

这轮融合后的底线：设计语言要统一，但不为了统一而重写；能用 token 收口的先收口，能用 TDesign 的不自造，能由后端说清楚的动作和权限不交给前端猜。
