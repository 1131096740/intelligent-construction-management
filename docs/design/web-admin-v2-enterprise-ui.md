# 建工智管 Web Admin V2 UI 设计方案

## 设计判断

Reading this as: 企业级工程管理后台 for 合同部、财务部、项目管理人员；信任优先、台账优先、内控优先；采用 TDesign/政企后台语言，而不是展示型 SaaS Dashboard。

设计参数：

- DESIGN_VARIANCE: 3
- MOTION_INTENSITY: 1
- VISUAL_DENSITY: 8

## 目标

第二版必须像真实企业系统，而不是像 AI 生成的演示后台。

核心目标：

- 让合同、结算、付款三类业务按严格顺序绑定。
- 让每个阻塞事项都能看到责任部门、停留时间、下一步动作。
- 让付款审批通过和实际付款完成在界面上始终分开。
- 让合同部上传/确认归档、财务读取归档件的责任边界清楚。

## 总体方向

采用“政企台账系统 + 单据详情页 + 阻塞事项工作台”的混合方案。

- 工作台：不做大屏，不做营销式卡片，主区是阻塞事项队列。
- 合同台账：高密度表格为主，顶部只保留紧凑统计条。
- 合同详情：按单据系统组织，包含主信息、版本、归档、审批、关联结算/付款。
- 移动端：由微信小程序单独设计，只承载待办、审批、归档确认，不放入 Web Admin 预览页。

## 页面 1：我的待办

用途：每天打开系统首先处理阻塞事项。

首屏结构：

- 顶部栏：系统名、当前模块、当前角色。
- 左侧导航：我的待办、合同管理、结算管理、付款管理、归档资料、审批配置、审计日志、基础数据。
- 顶部统计条：合同待归档、结算待确认、付款待审批、待实际付款、超账期。
- 主表：阻塞事项队列。
- 右侧：今日处理原则。

阻塞事项队列表字段：

- 类型
- 业务单据
- 当前节点
- 责任部门
- 停留时间
- 下一步动作
- 操作

示例节点：

- 合同 / 待归档确认 / 合同部 / 主管确认归档
- 结算 / 待归档确认 / 合同部 / 确认结算归档
- 付款 / 董事长或总经理 / 总经办 / 二选一审批
- 付款 / 待实际付款 / 财务部 / 登记付款凭证

## 页面 2：合同台账

用途：合同部和管理人员查询合同版本、生效状态、付款条款版本、归档状态。

设计规则：

- 不使用大 KPI 卡片。
- 统计信息压缩为横向数字条。
- 表格行高建议 44-48px。
- 状态标签小尺寸、低饱和。

表格字段：

- 合同编号
- 合同名称
- 项目
- 相对方
- 金额
- 当前版本
- 当前节点
- 责任部门
- 更新时间
- 操作

筛选条件：

- 项目
- 合同状态
- 归档状态
- 付款条款版本
- 关键词

筛选区设计要求：

- 必须是紧凑查询条，不做大表单。
- 桌面端优先一行展示，空间不足时两行换行。
- 查询、重置按钮保持小尺寸，不允许横向撑满。
- 字段高度控制在 28-32px，标签使用 12px 辅助文字。
- 只有手机窄屏才允许单列堆叠。

## 页面 3：合同详情

用途：查看合同当前版本、付款条款版本、用章归档状态和后续结算/付款阻断关系。

顶部主信息：

- 合同编号
- 当前状态
- 当前版本
- 付款条款版本
- 责任部门
- 当前处理人
- 下一步动作

内容分区：

- 基础信息
- 生效流程与阻断点
- 付款条款版本记录
- 关联结算 / 付款

生效流程：

1. 合同审批
2. 用章
3. 归档上传
4. 主管确认
5. 合同生效

明确规则：

- 合同未生效，不能发起结算。
- 结算未生效，不能创建付款申请。
- 合同条款变化必须通过合同变更或补充协议生成新版本。
- 待用章状态下的主动作是发起/办理用章，不应出现上传归档件。
- 用章完成后才进入归档件上传，再由合同部主管确认。

## 微信小程序边界

移动端页面不属于 Web Admin。微信小程序用于手机上处理待办，不承载完整后台。

内容：

- 我的待办列表。
- 每条待办显示业务类型、单据号、责任部门、停留时间、下一步动作。
- 底部导航：待办、合同、结算、付款。

微信小程序不做：

- 完整合同台账。
- 复杂筛选器。
- 大量统计卡片。

## 去 AI 感规则

- 不做展示型 Dashboard。
- 不使用大号彩色 KPI 卡片。
- 不使用过多圆角、阴影、渐变、装饰图形。
- 不使用泛滥的彩色 pill 标签。
- 不用“闭环风险提醒”这类演示口吻，改成系统语言：阻塞事项、待确认归档、待实际付款、超账期。
- 不用“批量确认”处理审批、归档、付款等内控动作；可保留批量催办、批量分派等非最终确认动作。
- 页面主视觉让位给表格、单据、审批记录和归档记录。

## 实现建议

Vue/TDesign 实现时优先使用：

- `t-layout`
- `t-menu`
- `t-table`
- `t-form`
- `t-tag`
- `t-descriptions`
- `t-tabs`
- `t-timeline`
- `t-drawer`
- `t-dialog`

CSS 方向：

- 背景：`#f4f6f9`
- 面板：`#ffffff`
- 边框：`#dce1e8`
- 主色：TDesign 蓝
- 状态色：低饱和蓝、绿、橙、红
- 圆角：3-4px
- 表格行高：44-48px
- 页面字号：12-14px 为主

## 当前 UI 审计结论

截至 2026-07-08，Web 管理端依赖层面已经统一为一套组件库：`tdesign-vue-next`。`apps/web-admin/src/main.ts` 全局注册 TDesign，未发现 Element Plus、Ant Design Vue、Naive UI、Vant、Arco 等第二套 UI 库。

但设计语言还没有完全收口：

- 页面已经有企业后台倾向：白底面板、浅灰边框、低饱和状态色、12px 辅助文字和高密度表格。
- 这些规则主要靠各页面 `<style scoped>` 手写，没有项目级设计 token。
- 项目经营页、合同模板编辑页等仍有原生 `button`、`select`、`input` 和手写 tab；这不是第二组件库，但会造成交互语言不一致。
- 状态色散落较多，例如蓝色系同时出现 `#0052cc`、`#0052d9`、`#165dff`、`#2f6fed`，危险色同时出现 `#b51d2a`、`#b42318`、`#c9352b`、`#d54941`。

结论：组件库已统一，设计语言需要用薄 token 层收口。

## 组件库规则

- TDesign 是唯一 UI 组件库。
- 表单、按钮、表格、弹窗、标签、抽屉、分页、空态优先用 TDesign。
- 原生控件只用于文件选择、Canvas 签名等平台原生能力更合适的场景。
- `BusinessActionPanel`、`EvidenceFileCards`、`ApprovalTimeline` 是业务组件，不是第二套视觉组件库。
- 新增页面不得引入其他 UI 库，也不得复制 Gitee 模板中的 Element Plus、Ant Design Vue 或 Naive UI 组件。

## 状态语言

状态 tag 只保留 5 类语义：

| 语义 | 使用场景 |
| --- | --- |
| `default` | 草稿、已撤回、暂无、普通资料。 |
| `primary` | 审批中、处理中、当前节点、可执行主动作。 |
| `success` | 已生效、已归档、已完成、已付款、已确认。 |
| `warning` | 待归档、待付款、待补充、暂不可操作、付款容量紧张。 |
| `danger` | 已驳回、付款阻断、作废、权限/校验失败、高风险动作。 |

优先使用：

```vue
<t-tag theme="primary" variant="light" size="small">审批中</t-tag>
```

不要为每个模块重新发明状态颜色。

## 核心组件融合

### BusinessActionPanel

作为合同、结算、付款详情页唯一动作状态入口：

- 可操作动作显示 `primary` 或 `success`。
- 暂不可操作统一显示 `warning`，必须展示原因。
- 高风险动作显示 `danger`，例如作废、撤回、敏感下载。
- “需当前密码 / 需填写意见 / 需选择文件”保留文字说明，不改成图形谜语。

### EvidenceFileCards

作为证据文件面板，不做网盘卡片：

- 保留 13px 文件名、12px 元信息。
- 增加统一状态 tag。
- 始终展示业务归属、文件用途、上传人、确认人、下载审计提示。
- 不可下载时展示禁用原因。

### ApprovalTimeline

作为轻量流转记录，不做复杂 BPMN 图：

- 展示节点、动作、处理人、意见、时间和停留时长。
- 驳回、退回、撤回类节点可用 `danger`。
- 当前节点可用 `primary`。

## Gitee 参考融合边界

本轮参考 RuoYi-Vue、RuoYi-Vue-Plus、RuoYi-Flowable-Plus、JeecgBoot 和 Soybean Admin。UI 方案只吸收三类东西：

- Soybean Admin 的 Vue 3 / Vite / TypeScript / Pinia 工程纪律。
- RuoYi 类后台的权限、日志、字典、菜单治理清单。
- Flowable 类系统的待办、办理、流转记录和流程跟踪 UX。

明确不吸收：

- 第二套 UI 组件库。
- Java 后端、Flowable 引擎、低代码运行时。
- 通用 CRUD 菜单优先的信息架构。
- 前端状态机决定合同、结算、付款和实付状态。

这套 UI 的核心不是好看，而是让施工企业用户少犯三类错：钱错付、章错盖、资料缺证据。
