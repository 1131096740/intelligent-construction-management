# 建工智管 - 认证与授权设计方案

> 状态：历史设计草案（Claude，2026-06-22），2026-07-03 已同步当前实现状态。手机号密码登录、JWT、refresh、改密、项目岗位权限 Guard、写端点取登录态、文件下载鉴权和多类敏感动作二次确认已基本落地；后续重点是真实账号/岗位初始化、seed 密码停用、历史合同接管权限和生产安全验收。
> 实现前请先读 AGENTS.md 的「Key Roles」「Approval Rules」「Security Baseline」。

## 1. 为什么这块最优先

本文成稿时，后端还没有登录和权限校验；当时所有写接口（如合同审批、付款审批、出纳付款）都直接信任请求体里传进来的 `reviewedByUserId` / `confirmedByUserId` / `executedByUserId`。这已经在后续开发中改为以登录态为准，并由后端 Guard 与 service 层共同校验。

本方案目标：给系统装上「门锁」（认证）和「按岗位放行」（授权），并把现有「前端传谁就信谁」改成「以登录身份为准」。

## 2. 登录方式（已与产品方确认）

- **Web 管理端**：手机号 + 密码。管理员创建员工并发初始密码，员工首次登录强制改密。
- **小程序端**：微信一键登录（`wx.login` 拿 code → 后端 code2session 换 openid → 绑定到 `User.wxOpenid`，首次绑定手机号/员工身份）。

两端登录成功后都拿到同一套后端签发的 JWT，调用同一套 API。

## 3. 认证设计（Authentication）

### 3.1 令牌策略

- **Access Token**：JWT，有效期约 15 分钟，放 `Authorization: Bearer`。无状态，载荷含 `sub`(userId)、`name`，**不放岗位**（岗位实时查库，避免授权后变更不生效）。
- **Refresh Token**：有效期约 7 天，用于换新 access。落库到 `RefreshToken` 表，支持「登出即失效」「踢下线」。
- 两个 secret 已在 `.env` 预留：`JWT_ACCESS_SECRET`、`JWT_REFRESH_SECRET`（上线必须换成长随机值，不入库不入前端）。

### 3.2 Web 端密码登录流程

1. `POST /auth/login`：手机号 + 密码 → 校验 `User.passwordHash`（bcrypt）→ 签发 access + refresh，写登录审计。
2. 若 `mustChangePassword=true`，返回标记，前端引导改密，未改密前限制访问。
3. `POST /auth/refresh`：refresh token → 新 access。
4. `POST /auth/logout`：作废该 refresh token。
5. `POST /auth/change-password`：旧密码校验 → 更新哈希 → 清 `mustChangePassword`。

### 3.3 小程序微信登录流程

1. 小程序 `wx.login()` 拿 `code` → `POST /auth/wx-login` 带 code。
2. 后端用 AppID/AppSecret 调微信 code2session 换 `openid`（+ unionid）。
3. 按 `openid` 找 `User`：找到则登录；未绑定则进入「绑定流程」（手机号 + 员工核验后写入 `wxOpenid`）。
4. 同样签发 JWT。

> 微信 AppID/AppSecret 属敏感配置，进环境变量，不入库、不下发前端。

## 4. 授权设计（Authorization）

### 4.1 模型：基于岗位的 RBAC（贴合现有结构）

系统**没有独立角色表，角色就是岗位（Position）**。授权完全围绕「用户担任哪些岗位」：

- 全局岗位 / 项目内岗位：`UserPosition(userId, positionId, projectId?)`，`projectId` 为空表示全局岗位。
- 项目成员岗位：`ProjectMember(projectId, userId, positionKey)`。
- 岗位 key 用 AGENTS.md 的 17 个真实岗位（chairman、general_manager、contract_director ……）。

「用户的有效岗位集合」= 全局岗位 ∪ 该项目下的项目岗位。授权判断都基于这个集合。

### 4.2 实现：两道 NestJS Guard + 声明式装饰器

- `JwtAuthGuard`（全局）：校验 access token，把当前用户挂到 `request.user`。用 `@Public()` 标记放行登录等公开端点。
- `PermissionGuard`：读端点上的装饰器要求，查当前用户岗位集合，决定放行。
- 装饰器：
  - `@RequirePositions('chairman','general_manager')`：持有任一岗位即可（OR）。
  - `@RequireProjectRole('contract_director')`：要求在「该单据所属项目」下持有此岗位。
  - 复杂规则（如 OR-sign 最终审批）在 service 层再校验一次，Guard 只做粗放行。

### 4.3 关键改造：不再信任请求体里的「操作人 ID」

现有写接口把 `reviewedByUserId` 等当入参。改造后：

- **操作人一律取自登录态 `request.user.id`**，请求体里的 `*ByUserId` 字段移除或忽略。
- 受影响端点（来自现有 controller）：
  - 合同：`approval-submission`、`approval`、`seal-approval`、`archive-files`、`archive-confirmation`
  - 结算：`approval`、`archive-files`、`archive-confirmation`
  - 付款：`approval`、`executions`、`finance-records`、`pdf-archive`
  - 文件：`POST /files`（`uploadedByUserId` 改取登录态）
- 端点 ↔ 岗位 映射（依据 AGENTS.md 审批规则）：

| 动作 | 要求岗位 |
| --- | --- |
| 合同最终审批 | chairman **或** general_manager（OR-sign）|
| 用章审批 | comprehensive_director |
| 合同/结算归档件上传 | contract_staff |
| 合同/结算归档确认 | contract_director |
| 结算审批 | 按合同类型的审核岗（**不经过**董事长/总经理）|
| 付款最终审批 | chairman **或** general_manager（OR-sign）|
| 实际付款登记 + 凭证上传 | finance_staff（出纳）|

> `verify-core-flow.cjs` 目前用同一个 userId 串全流程，改造后会失效——需要让验证脚本为不同步骤用不同登录身份。这一步要和认证一起改，列入验收。

## 5. 数据模型改动（需 migration）

- `User` 增加：`passwordHash String?`、`mustChangePassword Boolean @default(true)`、`lastLoginAt DateTime?`。
- 新增 `RefreshToken`：`id, userId, tokenHash, expiresAt, revokedAt?, createdAt`。
- seed 补齐 17 个 Position；给种子用户设密码哈希与岗位，便于本地登录与验证。
- 微信相关字段已有（`User.wxOpenid`），无需新增。

## 6. 安全基线（对齐 AGENTS.md）

- 密码用 bcrypt（cost ≥ 10），绝不明文、不可逆存储、不记日志。
- 登录失败限流 / 多次失败锁定，防撞库。
- 登录、改密、登出、权限变更写审计日志。
- JWT secret、微信 AppSecret、COS 密钥一律环境变量，禁止入库/入前端/入仓库。
- 生产强制 HTTPS。

## 8. 验收标准

- 未登录调用任何业务写接口 → 401。
- 登录用户调用其岗位无权的动作 → 403。
- 非董事长/总经理无法完成合同/付款最终审批；任一二者可通过（OR-sign）。
- 非 contract_director 无法确认归档；非 finance_staff 无法登记实际付款。
- 操作人以登录身份记录，伪造请求体 `*ByUserId` 无效。
- 登录、改密写审计。
- `verify:core-flow` 在带认证后仍能（用正确身份）跑绿。
