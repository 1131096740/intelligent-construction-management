## 1. 产品目标

本次改造不以“换一个更大的表格组件”为完成标准，而以以下目标为准：

> 用户像填写 Excel 一样完成合同清单和结算，后台始终以合同版本、清单行来源、历史结算、审批证据和资金余额作为唯一账本。

只有录入密集、需要粘贴、批量校验和跨行计算的明细场景使用
`JgBusinessGrid`。只读台账、审批时间线、附件上传、收款账户等场景不迁移为通用网格。

## 2. 当前缺口

### 2.1 合同清单版本关系不完整

- 创建合同变更草稿时，当前实现会复制上一有效版本的清单，并保留 `rowKey`。
- 当前合同工作台 Excel 上传固定使用整表替换；替换结果清空既有行标识，保存后形成全新行。
- `ContractBillRow.rowKey` 仅在一张清单内唯一，不是正式的跨版本身份。
- 当前没有一对多、多对一的清单拆分/合并关系，也没有历史结算分配事实。

### 2.2 结算占用只在同一合同版本内计算

当前结算来源行只查询当前合同版本的清单行，并只汇总同一
`contractVersionId` 下的有效结算。合同变更新版本后，旧版本已结算数量不会自动扣减。

### 2.3 最终结算仍使用旧口径

当前最终结算要求手工填写“审定累计结算金额”，并逐项确认五个布尔值。
新口径要求所有金额来自本期明细，累计金额由后台计算，最终结算只承担关闭后续结算的业务语义。

## 3. 统一业务流程

### 3.1 合同

```text
填写合同
  -> 乙方签章
  -> 内部审批与我方用章
  -> 归档生效
```

### 3.2 结算

```text
填写结算
  -> 乙方签章
  -> 内部审批
  -> 归档生效
```

已完成和当前阶段可以进入查看；未来阶段只显示进入条件。工作台顶部始终显示当前状态、阻断原因和下一步动作。

## 4. 合同是否需要结算

合同草稿新增明确业务事实：

- `settlement_required`：需要先形成有效结算，再申请付款。
- `direct_payment`：按已生效合同付款条款直接申请付款。

系统根据合同类别和是否存在清单给出默认建议，合同部主任确认。合同生效后只能通过正式合同变更修改该事实。

有金额上限的合同不能通过结算签证绕过合同变更。无上限框架合同可以超过预计总额，但仍保留累计、超量说明和审批记录。

## 5. 单一进行中结算与期间

### 5.1 单一进行中结算

同一合同同一时间只允许一份未结束的结算。占用范围包括：

- 草稿；
- 已生成冻结版或已上传乙方签章件；
- 已提交审批；
- 审批中、审批完成待最终件；
- 待归档确认。

退回、驳回、撤回继续修改同一份结算。只有显式“作废本期结算”、填写原因并二次确认后，才释放新建资格。作废记录和文件证据不得物理删除。

上一期结算只要审批、归档并生效，即可发起下一期，不要求已经付清。

### 5.2 结算期间

- 第一期开始日等于合同生效日。
- 后续开始日等于上一份有效结算结束日的次日。
- 经办人只选择本期结束日。
- 期间不得重叠，结束日不得早于开始日。

### 5.3 合同变更并发

- 合同新版本生效时，基于旧版本的普通结算草稿自动失效，保留原始输入和失效原因。
- 经办人必须从最新有效合同版本重新发起。
- 如果旧版本结算已经提交、签章、审批或待归档，合同新版本不得生效；必须先使结算归档生效，或者正式作废结算。

## 6. 跨版本清单账本

### 6.1 稳定身份

`rowKey` 不再承担完整的跨版本语义。P1 引入正式的清单行来源身份：

- 每个首次出现的业务清单行拥有稳定 `lineageId`。
- 未变化和普通修改行继续使用同一 `lineageId`。
- 新增行创建新 `lineageId`。
- 历史版本行及历史结算行保持不可变。

P2 增加版本间映射边：

- 一对一；
- 一对多；
- 多对一。

映射边记录来源行、目标行、承接历史数量、承接历史金额、确认人和确认时间。存在历史结算时，拆分/合并的分配合计必须守恒。

### 6.2 跨版本占用

下一期可结算数量和金额按合同全生命周期计算，而不是只按当前
`contractVersionId`：

```text
当前可结算数量
= 当前有效版本合同数量
- 沿清单来源关系累计的有效历史结算数量
```

历史结算只统计正式占用状态；草稿、退回未重提、已作废和已失效记录不占用。

### 6.3 调减、取消与超结

- 有历史结算的行不能直接删除。
- 取消未实施余量时，新版数量收敛到历史累计已结算数量，并标记“剩余范围取消”。
- 新版数量低于历史累计时，形成明确的超结数量或金额。
- 超结行禁止继续正向结算。
- 后续通过关联的负向调整、扣回或抵扣处理。
- 未纳入本期处理的超结事实阻断最终结算。

### 6.4 单价变更

- 默认只影响合同变更生效后的剩余数量。
- 历史结算继续保留原单价和原合同版本。
- 明确选择“追溯调整”时，系统计算历史价差，并在下一期形成独立补差或扣减项目。
- 不修改历史结算。

## 7. 合同清单 Excel

### 7.1 导入模式

工作台不再把用户暴露给“replace/update/append”技术模式。用户动作统一为“导入新版清单”。

导入后展示：

- 未变化；
- 已修改；
- 新增；
- 删除；
- 待人工确认。

明确项目自动匹配；编码重复、名称变化或其他模糊项目由合同员手工关联。存在未确认项目时不能保存为可提交的合同变更事实。

### 7.2 原子性

合同清单整表导入必须全部预检通过后才能替换。任何错误均不写入候选清单，不允许“正确行先替换、错误行以后补”。

预检至少校验：

- 模板版本和字段；
- 编码重复；
- 数量、单价和金额精度；
- 一对一匹配；
- 删除已有历史结算行；
- 拆分/合并历史分配；
- 合同金额差额；
- 历史超结。

### 7.3 变更金额

清单型合同发起变更时只填写变更原因。完成在线修改或 Excel 导入后，系统比较前后版本并自动计算增减方向和变更金额。

无清单合同才手工填写变更方向和金额。

## 8. 结算工作台

### 8.1 页面结构

工作台采用合同工作台同类外壳：

- 固定状态区；
- 项目、合同、结算期间和类型摘要；
- 全宽明细工作区；
- 准备情况和下一步动作；
- 底部固定汇总。

选定明细后，项目和合同锁定。显式执行“更换合同”时清空当前明细并二次确认。

默认展示未结清项目，可切换全部清单；支持按原合同清单分组、编码/名称搜索和“仅看已选”。

### 8.2 三类来源

#### 合同清单项

先选择，再填写本期数量。系统显示：

- 合同数量；
- 历史累计数量；
- 本期数量；
- 本期后累计数量；
- 剩余数量；
- 合同单价；
- 本期金额。

无上限框架合同的预计数量允许超量，但必须填写超量说明，并在合同部主任节点醒目标示。有上限合同的数量为硬限制。

#### 签证/变更项目

不要求双方签字盖章，也不建立独立签证审批模块。经办人在结算中填写：

- 项目类型；
- 发生日期；
- 项目名称；
- 情况说明；
- 数量与单价，或者直接金额；
- 计价依据；
- 可选附件。

合同部主任在现有结算审批节点一并审核。不同意时退回整份结算。

有金额上限的合同累计结算不得因这些项目超过当前有效合同金额；超额必须先办理合同变更。

#### 金额调整项

独立位于合同清单下方，用于扣款、奖罚、舍入、超结冲减等。支持正负金额，原因必填。

### 8.3 精度与计算

- 新合同和新结算数量最多两位小数。
- 新合同和新结算单价最多两位小数。
- 每行金额按数量乘单价四舍五入到分，再汇总。
- 历史高精度数据按原值只读保留，不批量回写。
- 前端只做即时预估；后台返回权威计算结果。
- 保存、生成冻结版、提交和归档前均重新计算。

### 8.4 粘贴和 Excel

- 支持从 Excel 原生复制多行数量。
- 支持批量备注。
- 结算 Excel 作为“更多”中的辅助入口。
- 结算导入允许正确行先载入、错误行保留定位。
- 错误未处理完不能提交，但已填写内容不清空。

### 8.5 保存与恢复

- 业务草稿只在用户点击“保存草稿”后写入后台。
- 使用修订号进行并发控制。
- 不完整但合法的数据可以保存。
- 非法值阻止保存，跳到首个错误，页面输入不清空。
- 离开未保存页面必须确认。
- 浏览器按账号、设备和草稿保存临时恢复副本；它不参与审批，也不对其他人员可见。
- 后台保存成功、草稿作废、退出账号或过期后清理临时副本。

## 9. 本期、累计与最终结算

所有结算只填写本期业务事实：

```text
合同清单本期金额
+ 签证/变更项目
+ 正负调整项
= 本期结算金额
```

累计金额由后台根据有效历史结算自动计算，不再接受用户手工填写。

最终结算不再保存五个人工确认布尔值。页面展示后台自动检查结果，提交时只做一次总体确认：

> 本次为最终结算，生效后不再发起新结算，未实施余量不再结算。

最终结算归档生效后：

- 合同关闭新的结算入口；
- 未实施余量不产生调整；
- 已生效各期未付余额继续保留；
- 付款和结算继续是两套独立事实。

## 10. 零金额、负金额与退款/抵扣

允许零金额或负金额结算，但必须由可追溯的冲减、扣回或超结处理产生，并填写原因。

负数结算生效后：

- 减少累计结算金额；
- 不生成负数付款申请；
- 形成待退款/待抵扣财务余额；
- 最终结算仍可归档生效并关闭结算阶段。

财务人员登记实际退款或后续抵扣，并上传银行回单或抵扣凭证。合同人员只读查看，不得登记资金完成。

## 11. PDF 核对、冻结与归档

### 11.1 核对体验

- 桌面端左右并排，移动端同页切换。
- 默认同步页码和缩放，可以解除同步并重新对齐。
- 不做 OCR 正文对比。
- 不要求逐页勾选。
- 浏览器只恢复页码、缩放、旋转和查看进度。
- 经办人整体点击一次“核对通过”。

页数、方向和页面尺寸差异可以人工核对通过。后续审批人默认只看到“经办人已核对”，并可通过不醒目的“查看文件事实”入口查看原始检测信息。

### 11.2 技术硬门槛

以下情况仍阻断提交：

- 文件损坏；
- PDF 加密且无法读取；
- 内容无法辨认；
- 页面无法安全规范化；
- 无法形成可靠的签名合成区域。

系统保留乙方上传原件，并对内部签名合成副本进行旋转、缩放和页面规范化，不修改原件。

### 11.3 证据生命周期

- 提交前文件是临时工作文件，可以替换。
- 提交时原子冻结文件 SHA、页数、检测事实、核对声明、草稿修订号和审批参与人。
- 提交后不得物理删除；替换只能生成新证据，并将旧证据标记失效。
- 内部审批结束后，系统将审批签名叠加到规范化副本，生成最终内部签署版。
- 合同部主任审核最终件并确认归档生效。

## 12. 合同工作台保持一致

已完成的合同工作台能力继续作为统一基线：

- 条款在草稿阶段支持选择、修改、新增、删除和排序；
- 条款作为结构化数据随显式保存持久化；
- 草稿期提供浏览器本地恢复；
- 合同清单使用全宽 `JgBusinessGrid`；
- 顶部“最近打开”已经移除。

后续合同文件状态只向普通用户展示：

- 正在编辑；
- 待审批签署稿；
- 已生效正式版。

技术修订号、失效文件和完整证据链进入版本历史，不占据主流程。

## 13. P1 实施范围

P1 必须形成一个后台账本和前台工作台同时闭环的可发布版本：

1. 清单稳定来源身份及一对一跨版本继承；
2. 结算跨版本累计占用；
3. 单一进行中结算的数据库和服务端约束；
4. 自动结算期间；
5. 全宽结算业务网格；
6. 合同清单、签证/变更、调整项三类来源；
7. 两位数量/单价和后台权威计算；
8. 结算 Excel 部分载入与错误定位；
9. 显式保存、修订控制和本地恢复；
10. 最终结算新口径；
11. PDF 核对、规范化、冻结和归档；
12. 权限、状态、金额、版本、文件和审计测试。

P1 未支持的一对多、多对一、追溯调价和负数资金处理必须明确阻断，不能静默按普通一对一场景计算。

## 14. P2 实施范围

1. 清单一对多、多对一映射；
2. 历史结算数量/金额守恒分配；
3. 追溯调价补差；
4. 超结冲减和负数结算完整体验；
5. 财务退款/抵扣台账和凭证；
6. 无上限框架合同超量说明；
7. 合同整表导入的高级变更对照；
8. 合同与结算统一文件事实查看；
9. 移动端 PDF 核对增强。

P2 是完整目标的一部分，不是长期可忽略的装饰项。P1 只能在明确阻断尚未支持的复杂场景后发布。

## 15. 数据迁移边界

应用代码发布与生产业务数据迁移分别授权。

### 15.1 Schema 前向迁移

- 只新增字段、表、索引、外键和检查约束；
- 不删除历史合同、清单、结算、付款或文件；
- 不在迁移 SQL 中模糊匹配业务行；
- 保持旧版本读模型兼容，直到回填完成。

### 15.2 历史来源身份回填

- 同合同相邻版本中，`rowKey` 一致且唯一的行可以生成自动建议；
- 没有歧义的原始单版本行可以直接建立来源身份；
- 编码、名称或 `rowKey` 冲突的行进入待人工复核清单；
- 未复核完成的合同不得使用跨版本剩余量发起新结算；
- 回填批次、操作者、匹配依据和确认结果全部审计。

历史回填不得随普通应用发布自动执行。执行前需要生产备份、隔离恢复验证、只读预检结果和单独的数据变更授权。

## 16. 验收场景

至少覆盖：

1. 100 行以上清单可填写、粘贴、筛选和保存；
2. 合同 Excel 存在错误时不应用任何行；
3. 结算 Excel 正确行先载入，错误行保持定位；
4. v1 数量 100、已结算 30、v2 数量 120，剩余量为 90；
5. v2 数量降为 20，形成超结 10并禁止继续正向结算；
6. 拆分/合并历史分配合计守恒；
7. 追溯调价生成独立价差，不修改历史结算；
8. 同合同不能存在两份进行中结算；
9. 新合同版本使旧普通结算草稿失效；
10. 已提交旧版结算阻断合同新版本生效；
11. 最终结算忽略未实施余量并关闭新结算入口；
12. 零金额和负金额结算不能生成付款申请；
13. 页数差异可核对通过，损坏或无法安全合成的 PDF 被阻断；
14. 保存失败、冲突、刷新和离开时不静默丢失用户输入；
15. 权限、文件下载、审批、归档、退款和敏感操作均有审计。

## 17. 明确不做

- 不做 OCR 正文对比；
