## 1. 规范用语

- “必须”表示实现、测试和验收都不可省略。
- “不得”表示任何前端、接口、导入或后台任务都不可绕过。
- “应”表示默认要求；偏离时必须有书面原因和等价控制。
- “可以”表示允许但不强制。
- 所有金额以人民币分为后台账本单位；数量、单价使用十进制定点数，不使用二进制浮点数作为业务事实。

## 2. 目标与范围

### 2.1 目标

用户应像操作办公表格一样选择、填写、粘贴和复核清单；后台必须始终保留以下可追溯事实：

1. 当前合同版本及其结算模式；
2. 清单行跨版本来源；
3. 历史有效结算占用；
4. 本期结算明细和后台权威计算；
5. 审批、签名、文件、归档与资金证据。

### 2.2 范围

- 合同版本的“需要结算/按合同直接付款”事实；
- 合同清单一对一继承、整表导入和跨版本占用；
- 结算期间、来源明细、最终结算和负向结算；
- 结算工作台、Excel 辅助导入和本地恢复；
- 乙方签章 PDF 核对、规范化、冻结和归档；
- P2 清单拆分/合并、追溯调价、退款/抵扣闭环。

### 2.3 明确不做

- 不做 OCR 正文比对；
- 不建设独立签证审批模块；
- 不把全站只读台账改为多维表格；
- 不引入第二套基础 UI 组件库或低代码运行时；
- 不覆盖历史正式结算、付款或文件；
- 不用 Excel 公式、浏览器合计或本地恢复副本作为后台账本；
- 不在普通应用发布中自动执行生产历史业务数据回填。

## 3. 角色与权限

| 业务动作 | 允许角色 | 控制 |
| --- | --- | --- |
| 创建、编辑、作废结算 | `contract_staff`、`contract_director` 中实际经办人 | 所属项目、本人草稿、修订号 |
| 确认合同结算模式 | `contract_director` | 合同版本事实、审计 |
| 审核结算及签证/变更项目 | 当前冻结审批路线中的合同部主任 | 随审批实例冻结 |
| 上传合同/结算业务归档文件 | `contract_staff` | 私有文件、用途绑定 |
| 确认结算归档生效 | `contract_director` | 密码二次确认、上传确认分离 |
| 登记退款/抵扣 | `finance_staff` | 资金证据、金额余额、二次确认 |
| 查看资金闭环 | 合同人员只读，财务人员按权限读写 | 项目可见性与敏感下载审计 |

现场复核人继续沿用现有按角色筛选、唯一候选自动选中、多候选人工选择、无候选阻断的规则，并在提交时冻结。结算审批继续使用现有类型化路线，不增加董事长/总经理节点。

## 5. 合同结算模式

### 5.1 规范要求

- `CSW-CON-001`：每个合同版本必须具有 `settlement_required` 或 `direct_payment` 之一。
- `CSW-CON-002`：系统根据合同类别、清单和付款条款给出建议，合同部主任确认后形成版本事实。
- `CSW-CON-003`：合同生效后不得原地修改结算模式，只能通过新合同版本变更。
- `CSW-CON-004`：合同变更草稿默认继承前一有效版本的结算模式。
- `CSW-CON-005`：历史版本模式未确认时，系统必须阻断新结算和普通合同到期款，并给出补确认入口。

### 5.2 对付款的约束

- `settlement_required`：除合同付款条款明确允许的预付款外，普通进度/到期付款必须引用有效结算。
- `direct_payment`：普通到期付款复用现有 `contract_due` 来源，引用当前有效合同版本和付款条款版本，不创建空结算。
- 两种模式都继续使用现有付款审批、待付款、实际付款、凭证和财务记录链路。

## 6. 结算过程与期间状态

### 6.1 过程状态

一个业务结算过程从草稿开始，跨越正式结算状态，最终只能进入以下结束状态之一：

```text
open
  -> effective
  -> voided
  -> invalidated
```

- `open`：草稿、已生成冻结稿、乙方签章件已上传、已提交、审批中、退回、驳回、撤回、审批完成待文件、待归档确认。
- `effective`：归档确认完成，形成有效结算。
- `voided`：经办人显式作废，填写原因并二次确认。
- `invalidated`：仅限未提交普通草稿因新合同版本生效而失效。

退回、驳回和撤回不得释放同合同新建资格；用户继续修改同一业务过程。

### 6.2 期间

- `CSW-PER-001`：用户只选择本期结束日，开始日由后台计算并只读展示。
- `CSW-PER-002`：结束日不得早于开始日，也不得晚于系统允许的业务截止日。
- `CSW-PER-003`：保存草稿时校验日期合法性，提交时在合同锁内再次校验期间连续且不重叠。
- `CSW-PER-004`：旧结算仅有自由文本 `periodLabel` 且无法无歧义解析时，不得猜测日期；该合同进入历史期间待确认清单。
- `CSW-PER-005`：期间确认结果必须进入审计，原 `periodLabel` 保留为兼容展示，不作为新计算依据。

### 6.3 合同版本并发

- `CSW-VER-001`：创建合同变更不会立即改写旧版结算资格。
- `CSW-VER-002`：新版本归档生效事务必须检查旧版结算过程。
- `CSW-VER-003`：旧版仅有未提交普通草稿时，事务将其标记 `invalidated` 并保留明细和原因。
- `CSW-VER-004`：旧版已有提交、签章、审批或归档中结算时，新版生效失败，不得先替代旧版。
- `CSW-VER-005`：版本失效或阻断都必须返回稳定业务错误码、合同/结算编号和下一步动作。

## 7. 合同清单跨版本账本

### 7.1 稳定来源身份

- `CSW-BIL-001`：业务清单行首次出现时创建稳定 `lineageId`。
- `CSW-BIL-002`：相邻版本中未变化或普通修改的一对一行继承同一 `lineageId`。
- `CSW-BIL-003`：新增行创建新 `lineageId`；被删除行保留在历史版本，不物理迁移到新版本。
- `CSW-BIL-004`：每次版本继承必须记录来源行、目标行、关系类型、匹配依据和确认事实。
- `CSW-BIL-005`：编码、名称相似度不得直接形成自动历史关系；只能用于待确认建议。
- `CSW-BIL-006`：单位发生变化时不得按普通一对一自动继承历史数量，必须进入人工映射或剩余范围取消流程。

### 7.2 历史占用与可用量

对当前有效版本目标行：

```text
历史承接数量
= 已确认来源关系分配到该行的有效历史结算数量

本期前可结算数量
= 当前版本合同数量 - 历史承接数量 - 当前版本已生效占用数量

本期后剩余数量
= 本期前可结算数量 - 本期数量
```

- 有效历史结算包括 `effective`、`partially_paid`、`paid` 等不会因付款状态释放结算事实的状态。
- 草稿、已作废、已失效记录不计入占用。
- 历史占用金额按正式结算行金额累计，不以当前单价重算。
- 新版本 100 改为 120、历史已结算 30 时，可结算数量必须为 90。

### 7.3 调减、取消和超结

- 有历史结算的来源行不得直接作为普通删除应用。
- “取消未实施余量”将新版合同数量收敛到历史累计数量，并保存取消标记、原因和确认人。
- 新版数量低于历史累计数量时形成超结事实，禁止继续正向结算。
- 超结通过关联负向调整、扣回或抵扣处理，不回写历史结算。
- 未处理超结必须阻断最终结算。

### 7.4 一对多、多对一

P2 支持一对多和多对一。每条映射边必须记录：

- 来源行和目标行；
- 来源已结算数量分配；
- 目标期初数量；
- 历史金额分配；
- 单位不同时的换算依据；
- 合同部主任确认人、时间和修订。

同一来源的历史数量和金额分配合计必须守恒；同一目标的期初值必须等于其全部有效入边合计。未确认或不守恒时，合同变更不得提交或生效。

### 7.5 单价变更

- 默认只对合同变更生效后的剩余数量使用新单价。
- 历史结算保持原合同版本、原单价和原金额。
- 选择追溯调价时，系统在下一结算生成独立价差行，引用原结算行和调价依据。
- 追溯调价不得更新原结算行。

## 8. 合同清单 Excel

- `CSW-XLS-001`：普通用户只看到“导入新版清单”，不暴露 `replace/update/append` 技术模式。
- `CSW-XLS-002`：预检必须输出未变化、已修改、新增、删除、待人工确认五类结果。
- `CSW-XLS-003`：整表应用必须原子化；任一模板、字段、精度、关系、金额或历史占用错误都不得应用任何行。
- `CSW-XLS-004`：预检和应用必须冻结文件 SHA、来源版本、清单修订号和幂等键。
- `CSW-XLS-005`：应用前清单修订、文件事实或映射确认发生变化时必须整体失败。
- `CSW-XLS-006`：清单型合同变更金额由前后清单后台计算；无清单合同才允许手工填写变更方向和金额。

## 9. 结算工作台

### 9.1 页面结构

工作台必须复用合同工作台视觉骨架和 `JgBusinessGrid`：

1. 固定状态、阻断原因和下一步；
2. 项目、合同、期间、结算类型摘要；
3. 全宽录入区；
4. 合同清单项；
5. 签证/变更项目；
6. 金额调整项；
7. 准备情况；
8. 固定汇总与主动作。

选择合同并产生明细后合同锁定；“更换合同”必须二次确认并清空当前结算明细。

### 9.2 合同清单项

- 默认只显示未结清行，可切换全部。
- 支持按原清单分组、编码/名称搜索、仅看已选。
- 用户先选行，再填本期数量。
- 必须显示合同数量、历史累计、本期、本期后累计、剩余、单价和金额。
- 已完全结清行只读；关键识别列冻结。
- 有上限合同不得通过清单或签证项目超过当前有效合同金额。
- 无上限框架合同可超预计数量，但必须填写说明，并在合同部主任节点醒目标示。

### 9.3 签证/变更项目

签证/变更项目属于结算明细，不建立独立审批模块，也不要求双方另行盖章。每行必须具有：

- 项目类型；
- 发生日期；
- 项目名称；
- 情况说明；
- 数量和单价，或直接金额；
- 计价依据；
- 可选附件。

合同部主任在现有结算审批节点审核；不同意时退回整份结算。

### 9.4 金额调整项

金额调整项用于扣款、奖罚、舍入、超结冲减等，必须填写原因。负向调整还必须引用原超结、原结算行或其他允许的可追溯来源。

### 9.5 计算规则

- 新数量最多两位小数。
- 新单价最多两位小数。
- 数量乘单价后，每行四舍五入到分，再汇总行金额。
- 直接金额以分保存。
- 历史高精度事实只读保留，不批量回写。
- 合同清单本期金额、签证/变更金额、调整金额之和等于本期结算金额。
- 后台响应必须返回逐行权威结果、汇总、阻断项和计算版本。

### 9.6 保存、粘贴和 Excel

- 保存是显式动作，不以静默后台写入代替。
- 不完整但字段值合法的草稿可以保存；非法值阻断保存并定位首错。
- 保存必须使用修订号和幂等键；冲突不覆盖远端或本地输入。
- 原生粘贴支持多行数量和批量备注。
- 结算 Excel 位于“更多”；正确行可载入，错误行保留定位。
- 任一未解决导入错误都阻断提交，但不得清空已载入正确行。
- 离开未保存页面必须确认。
- 浏览器本地恢复按账号、设备、草稿和修订隔离；后台保存成功、作废、退出或过期后清理。

## 10. 最终结算

- 页面不再要求手填“审定累计结算金额”。
- 页面不再要求五个人工确认框。
- 系统展示期间连续性、未处理超结、未结束结算、金额上限、文件和审批准备情况。
- 提交最终结算时只确认一次：

> 本次为最终结算，生效后不再发起新结算，未实施余量不再结算。

- 最终结算归档生效时，后台在同一事务中关闭合同新结算入口。
- 未实施余量不产生零金额明细或虚构冲减。
- 既有有效结算未付余额、付款申请和资金执行继续有效。

## 11. 零金额、负金额与资金回收

- 零金额和负金额结算必须具有可追溯来源和原因。
- 负金额结算生效后减少累计结算金额，不创建负数付款申请。
- 负金额形成待退款/待抵扣余额。
- 财务人员登记实际退款或后续抵扣，金额不得超过未处理余额。
- 每次登记必须记录方式、日期、金额、经办人、关联付款或抵扣对象、凭证文件和幂等键。
- 退款/抵扣更正采用反向记录，不物理删除原记录。
- 最终负金额结算可以归档生效并关闭新结算入口，未处理资金余额继续留在财务工作台。

## 12. PDF 文件事实与证据

### 12.1 用户体验

- 乙方上传一份完整办公扫描 PDF。
- 桌面端左右并排；移动端同页切换。
- 默认同步页码和缩放，允许解除同步、重新对齐。
- 不做 OCR、不要求逐页勾选，只记录已查看页数。
- 浏览器可恢复最后页码、缩放、旋转和查看进度。
- 经办人执行一次“核对通过”。

页数、方向或页面尺寸不同不构成自动拒绝条件。后续审批人默认看到核对结论，可按需查看页数、方向、尺寸和原件信息。

### 12.2 技术硬门槛

文件损坏、无法解密、内容无法辨认、无法安全规范化或无法可靠合成签名时必须阻断。系统保留上传原件，内部签名只叠加到派生规范化副本。

### 12.3 冻结

- 提交前临时文件可替换。
- 提交时原子冻结原件 SHA、页数、文件事实、核对声明、草稿修订、审批参与人和业务快照。
- 提交后不得物理删除；替换只能创建新证据并失效旧证据。
- 审批结束后生成内部签署派生版，合同部主任确认归档后结算生效。

### 12.4 普通用户可见状态

合同和结算文件只向普通用户展示三类主状态：

- 正在编辑；
- 待审批/签署；
- 已生效正式版。

技术修订、失效证据和完整历史进入“版本与证据”查看，不占据主流程。交给乙方直接签字盖章的待签文件必须是干净文件，不叠加系统水印；内部审批签名只在审批完成后写入派生副本。

## 13. 接口与错误契约

### 13.1 接口原则

- 页面不得直接调用 `fetch`，统一通过领域 API 模块。
- 创建、保存、导入应用、提交、作废、归档确认、退款/抵扣都必须支持幂等。
- 写接口必须在事务中锁定合同或业务过程，再重新读取版本、修订、占用、金额和文件事实。
- 读接口返回 `calculationVersion`、`sourceSnapshotToken` 和阻断项，前端不得自行拼装提交资格。

### 13.2 稳定业务错误码

| 错误码 | 含义 |
| --- | --- |
| `CONTRACT_SETTLEMENT_MODE_UNCONFIRMED` | 合同结算模式尚未确认 |
| `SETTLEMENT_ACTIVE_PROCESS_EXISTS` | 同合同已有未结束结算 |
| `SETTLEMENT_FINAL_CLOSED` | 最终结算已生效 |
| `SETTLEMENT_PERIOD_CONFLICT` | 期间不连续、重叠或非法 |
| `SETTLEMENT_SOURCE_LINEAGE_UNRESOLVED` | 清单来源未确认 |
| `CONTRACT_VERSION_BLOCKED_BY_ACTIVE_SETTLEMENT` | 旧版结算阻断新版合同生效 |
| `SETTLEMENT_SOURCE_OCCUPANCY_CHANGED` | 历史占用或来源快照已变化 |
| `SETTLEMENT_NEGATIVE_SOURCE_REQUIRED` | 负向明细缺少可追溯来源 |
| `SETTLEMENT_FILE_FACT_CHANGED` | 提交前文件事实已变化 |
| `SETTLEMENT_PDF_UNSAFE` | PDF 无法安全读取或合成 |

错误响应必须同时提供中文可执行说明，不向用户暴露 SQL、存储路径或内部异常。

## 14. 审计要求

至少审计：

- 合同结算模式建议、确认和版本变更；
- 清单导入预检、应用、映射确认、余量取消；
- 清单来源回填批次和人工复核；
- 结算创建、保存冲突、提交、退回、撤回、作废、失效；
- 最终结算声明；
- PDF 上传、替换、核对、冻结、派生和归档确认；
- 负向结算、退款、抵扣和反向更正；
- 敏感文件下载。

审计元数据保存业务 ID、修订、前后摘要、操作者、原因和幂等摘要，不保存密码或完整敏感正文。

## 15. 兼容与废弃

- `ContractBillRow.rowKey` 继续作为单清单内技术行键，不再代表跨版本业务身份。
- `SettlementDraft.lines` 在兼容期保留为旧客户端快照；新结构化草稿行成为权威事实后再另行评估删除。
- `periodLabel` 继续展示旧记录，新记录同时保存结构化开始日和结束日。
- 旧五项最终确认字段和 `finalCumulativeAmountCents` 只读保留，不再用于 V2 提交判定。
- 旧 PDF 原件和旧归档入口不回写、不物理删除。

## 16. 验收矩阵

| 场景 | 对应要求 | 最低验收 |
| --- | --- | --- |
| 同合同并发创建两份结算 | `CSW-INV-001` | 数据库并发测试只有一份成功 |
| v1=100、已结30、v2=120 | `CSW-INV-006` | 当前可结算=90 |
| v2 调减到20 | 7.3 | 显示超结10，正向结算被阻断 |
| 合同 Excel 第 100 行错误 | `CSW-XLS-003` | 一行也不应用 |
| 结算 Excel 100 行中 2 行错误 | 9.6 | 98 行保留、2 行定位、提交阻断 |
| 旧版已有已提交结算 | `CSW-VER-004` | 新合同版本不能生效 |
| 旧版只有普通草稿 | `CSW-VER-003` | 新版本生效后草稿失效且可查看 |
| 最终结算仍有未实施余量 | 第 10 节 | 可生效、余量忽略、后续入口关闭 |
| 最终结算仍有未处理超结 | 7.3 | 提交被阻断 |
| 负金额结算 | 第 11 节 | 不生成付款，生成待退款/抵扣余额 |
| PDF 页数不一致 | 12.1 | 允许人工核对通过 |
| PDF 损坏或加密不可读 | 12.2 | 提交被阻断 |
| 保存冲突或网络失败 | 9.6 | 用户输入不丢、不静默覆盖 |
| 100 行以上清单 | 第 9 节 | 可粘贴、筛选、编辑、保存，无 100 行硬限制 |

## 17. 发布门禁

P1 候选必须同时具备：

1. Schema、迁移、DTO、服务、页面和读模型一致；
2. 金额、数量、状态、权限、并发、文件和审计自动化测试；
3. 历史数据只读预检报告；
4. P1 未实现复杂场景的明确阻断；
5. `PROGRESS.md` 和任务证据更新；
6. 独立的应用发布授权。

生产历史来源回填、结算模式确认、期间补录或业务数据修正必须另行授权，不得由应用发布授权替代。
