依据：本会话的《合同分类与核算只读检查》（审阅提交 835ce1d7c6215626677bce19609aa38b111c3aa8）、2026-08-12 项目经营正式规格及 2026-09-17 轻量产品蓝图。本方案以既有审计为问题基线，本轮未重新连接生产，实施时必须刷新版本与实际状态。

## 1. 整改目标和范围

同一项目的合同、结算、收付款、财务往来及经营汇总使用同一套分类和金额来源。经办人能知道“这是谁与谁的合同、谁欠谁、目前确认多少、实际收付多少、下一步谁办”；负责人能分清承诺、已确认成本、欠款、资金和盈亏。

覆盖：合同办理与台账、结算办理与台账、付款申请与台账、收款登记与台账、资金执行、财务应收应付与主体往来、项目经营、公司经营、跨项目总览、对账、历史接管、审批待办、全局搜索、相关详情、Excel/PDF/导出和移动端。无合同费用、零采、工资、借款、调拨也须正确标识业务来源，但不强行归入三类合同。

复用现有响应式 Web、TDesign、领域服务及审批能力。具体接口和表结构在规则确认后设计；不在本阶段预设大规模重建或新增通用引擎。

## 2. 统一分类词典

“表内/表外”仅沿用用户的签约管理称呼，不表示法定财务报表内外，也不表示是否纳入项目经营账。

| 显示名称 | 真实合同关系 | 用途 | 项目整体经营口径 |
| --- | --- | --- | --- |
| 表内合同（我方签约） | 参与本项目的我方具体公司 → 下游供应商/班组等 | 管理我方下游履约及应付 | 下游承诺；结算确认成本 |
| 表外合同（施工企业签约） | 本项目施工企业 → 下游供应商/班组等 | 管理施工企业下游履约及应付 | 同样纳入下游承诺与确认成本 |
| 对上合同（施工企业—我方） | 本项目施工企业 ↔ 我方具体公司 | 管理双方合同、结算、应收和实际拨款 | 保留往来，合并时排除内部重复收入/成本 |
| 业主合同（业主—施工企业） | 业主 ↔ 施工企业 | 作为项目整体上游合同依据 | 业主确认结算形成项目收入 |

业主合同单独列示，不能与上述“对上合同”同名。业主合同不要求扩大本轮为完整业主合同审批系统；至少明确依据、金额及与业主结算的关系。现有产品中的“对上”标签必须按真实关系逐项改名，不能批量字符串替换。

另保留“待确认分类”“非合同业务”。若出现我方 A 公司与我方 B 公司签约、多方合同、同一企业同时具有两种项目身份，进入例外核对，不能自动套入表内或表外。

## 3. 分类如何确定和继承

1. 经办人先选项目，再选真实签约双方及各自履约角色；系统在页面即时说明推导类别，后台再次校验。入口按钮只是办理意图，不是会计口径权威。
2. 我方公司按真实法人身份和项目参与关系识别；施工企业取项目绑定主体；相对方用受控档案识别，不能仅按名称文字匹配。
3. 签约关系、合同类型、计价方式、成本分类、实际付款方、资料来源是不同维度。例如“表内＋材料采购＋固定总价＋材料成本＋施工企业代付”。
4. 结算、付款、核销及归档自动继承来源合同分类和主体快照，不让员工在后续单据重新选择。
5. 签约主体与实际付款人不同，记代付；不得因此改变合同分类或原债务主体。批准付款方和实际付款方分别保存。
6. 草稿允许按权限修正；首次正式提交/接管确认后冻结分类和签约主体。退回修订保留旧快照；正式事实更正走追加式处理，不直接覆盖历史。
7. 主体档案改名、公司停止参与或角色调整不得重算旧单分类。新增业务使用当前有效身份，历史显示当时身份。
8. 允许保存未完成资料的草稿或缺口记录；分类/债务主体无法确定时，阻断该笔正式确认和依赖它的金额业务，不能默认为我方公司或下游成本。
9. 不允许通过另一入口、导入、接口、批处理绕开相同规则。

## 4. 办理入口与工作链

统一从“合同与结算”进入，合同台账提供“全部、表内、表外、对上、待确认”分类页签；业主合同依据单独呈现。项目内的合同入口带入项目，跨项目岗位入口保留授权项目选择。现有历史链接跳转到同一条详情，不复制出第二份单据。

### 4.1 表内合同

新建/接管 → 确认我方具体签约公司与下游 → 原合同审批、用章、归档、生效链 → 原结算确认链 → 付款申请与审批 → 财务登记实付及核销。

历史已签合同走接管确认，不补造过去审批。新签与历史接管用同一分类规则，保留各自真实来源和状态。

### 4.2 表外合同

“登记施工企业签约合同”入口 → 录入/接管真实合同及签约依据 → 必要合同专业复核 → 登记并确认施工企业下游结算 → 我方内部提出付款需求并按既有项目流程审批 → 项目财务跟进并登记施工企业实际付款结果。

系统不替施工企业盖章，不把我方内部审批显示成施工企业的审批。未签资料可先保留为待签资料；只有已签/生效事实经必要复核后计入相应正式口径。已经发生的历史付款仍走例外/接管规则，不补造事前申请。

新业务按既有规格办理内部付款审批；纯外部事实接管与新业务申请清晰区分。表外并不等于我方永远不能代付：真实代付按受控代付规则办理，不能沿用“只能由施工企业付款”的绝对文案。

### 4.3 对上合同

“登记施工企业与我方合同”入口 → 指定具体我方公司 → 合同编号、原件、金额性质、结构化金额、签约日期、履约范围及必要条款 → 合同专业确认 → 独立“对上结算”入口 → 应收及拨款核对 → 财务记录我方实际到账。

不再借“外部下游结算”加一个选填字段决定是否抵销。对上结算必须关联明确的对上合同，债务方为施工企业、债权方为我方公司，后台强制排除项目重复成本。资料未齐可保存待核对，不能按下游结算入账。

拨款可以先到账、后核对：真实银行到账可先登记为待匹配拨款，不因合同资料未齐丢掉事实，也不能把到账直接当收入或虚构结算。公司实收与施工企业拨出是同一资金事件的两个视角；双方各自提供证据时先匹配，不生成两次资金增加。

### 4.4 页面上的状态和下一步

分别显示资料/审批状态、合同效力、结算状态、收付款状态，避免用一个“已完成”掩盖余额。例如：“表外｜施工企业甲签约｜结算已确认｜待登记外部实付｜责任人：项目财务”。原始资料、确认人、确认时间和更正记录可追溯。

## 5. 金额与汇总契约

### 5.1 四个层次独立

| 层次 | 主要数字 | 不得混淆 |
| --- | --- | --- |
| 合同承诺 | 原签金额、已确认变更、现行有效金额、预计金额、未定价事项 | 合同金额不是成本或收入 |
| 已确认经营 | 已确认收入、表内成本、表外成本、无合同等成本 | 付款/开票不再次确认成本 |
| 应收应付 | 原应收应付、净调整、已核销、未清余额 | 预付款不直接算已完成成本 |
| 实际资金 | 实际收付、退款、拨款、代付、调拨、资金位置 | 现金余额不等于利润 |

合同默认展示合同约定含税金额并明确税务口径；成本与盈亏沿用批准的现有核算规则，不在此次页面整改中暗改税务政策。对比或汇总必须同币种、同金额口径、同基准日；不能混加含税额与不含税额。多税率按原逐行精确计算契约执行。

### 5.2 合同金额

- 每份独立合同在同一基准日只贡献一次有效金额。当前合同额取当时有效的权威合同状态；如采用差额式变更则原额加已确认增减，如版本保存完整总额则取有效总额。二者不能同时累加。
- 草稿、审批中变更、已作废资料不进入有效合同额，单独显示“待生效”。已结束合同的真实累计签约、结算和付款历史仍可查，不能随状态结束全部从历史统计消失。
- 同一事项的关联/补充/替代文件不自动当成新的独立合同额度。保存原文书金额，同时给出计入管理汇总的依据和排除说明。
- 框架合同区分“有上限、无固定总额、预计金额”；无确定总额显示“未约定总额”，不伪装为 0。汇总显示“已确定金额＋若干份未定总额合同”。
- 对上合同与业主合同分别具备结构化金额或明确未定价状态。不得通过附件有金额而让结构化指标默认为零。
- 项目展示“表内下游合同额”“表外下游合同额”“下游合同额合计”“对上合同额”“业主合同额”。不提供把五项再次相加的总计。
- 下游合同额合计＝经确认不重复的表内合同额＋表外合同额。对上与业主金额属于不同层级，不参与下游合计。
- 汇总需要完整来源链、状态过滤和调整规则；不能只把现有零金额提示字段换成原值，导致内部引用/变更版本同时被累加。

### 5.3 结算与欠款

- 表内/表外分别展示当期结算、累计确认结算、已确认应付、有效核销、未付余额；对上展示累计确认结算、我方应收、已匹配实收及未收余额。
- 未清应付＝已确认应付净额－有效核销额；有效核销包含经确认允许抵扣的预付款等，不能简单以“合同额－实付”替代。
- 保留结算额、应付额、到期可付额及付款审批额度之间的区别；质保、扣款、预付抵扣按原规则独立表达。
- “付款申请中、已批准、已实付”互不替代。未实付审批单可以占用可申请额度，不能减少账面应付或现金。
- 累计对账单若是此前逐期结算的汇总佐证，仅关联原事实，不再次入账；确需累计式接管时只形成有依据的未覆盖差额，并保留覆盖清单。

### 5.4 成本与抵销

项目已确认成本＝表内真实下游确认成本＋表外真实下游确认成本＋无合同费用/零采/工资等真实成本＋施工企业最终确认扣费－对应成本冲减，各事实只能进入一个来源分项。

对上合同及结算保留在主体往来视角；在项目整体视角不新增一层收入或成本。公司分账保留我方应收、施工企业应付和真实收款，不因项目抵销把这些往来抹掉。公司视角旁列项目整体指标时显著注明，不能把同一个项目总利润重复归给数家公司。

“抵销”由经过确认的主体关系和事实类型自动推导，普通用户不能用任意勾选“是否计入成本”调账。界面提供“本条计入表内成本/表外成本/仅影响主体往来/仅改变资金”的原因，能下钻原单据。

合同额度、发票、收款、付款都不独立复制已确认的成本。负向结算、退货等冲减原成本分类；超付退款只恢复资金/更正核销，不把退款当收入或额外再冲减成本。真实代付先核销原下游债务并形成主体间往来，归还代付款只清偿往来。

### 5.5 统一数字样例（均为万元、同一金额口径）

| 事项 | 金额 | 影响 |
| --- | ---: | --- |
| 业主确认结算 | 900 | 项目收入 900 |
| 施工企业与我方对上合同 | 800 | 对上合同额 800，不加入下游承诺 |
| 对上已确认结算 | 600 | 我方应收 600；项目收入/成本均不因此增加 |
| 表内合同 / 已确认下游成本 | 500 / 400 | 表内承诺 500、成本 400 |
| 表外合同 / 已确认下游成本 | 200 / 150 | 表外承诺 200、成本 150 |
| 项目管理及最终扣费等其他成本 | 30 | 其他成本 30 |

结果：下游合同额 700；已确认项目成本 580；当前经营盈亏 320，未扣除尚待清算费用，也不表示可分配现金为 320。

若我方先收到施工企业拨款 300，再向表内下游付 250，施工企业向表外下游付 100，且本例没有预付、保留款等调整，则我方对上应收余额 300；下游未付为 150＋50＝200。内部拨款 300 不作为项目对外支出；对外下游实付 350，项目成本仍为 580。

若施工企业另代付表内欠款 50，则表内欠款从 150 降为 100，形成施工企业与我方之间代付往来 50；表内合同仍为表内，项目成本不变。

## 6. 全页面统一呈现

所有相关页面共用中文名称、金额计算服务、筛选语义与权限结果。分类用文字标识并可辅以颜色，不能只靠颜色区分。

共同摘要：所属项目、合同分类、签约双方、所属我方公司（适用时）、原债务主体、当前状态、责任人、下一步、统计基准日、资料完整性。付款页再突出批准付款方和实际付款方。

| 页面/入口 | 分区与筛选 | 核心金额/信息 | 办理动作 |
| --- | --- | --- | --- |
| 合同工作台/合同台账 | 全部、表内、表外、对上、待确认；业主依据独立展示 | 原额、净变更、有效金额、结算累计、未清款；签约双方常驻 | 按类别办理/接管、查看关联文件、发起相应结算 |
| 结算台账 | 表内结算、表外结算、对上结算；业主结算单列 | 当期/累计、成本影响、应收或应付、核销与余额 | 自动继承合同，预算/合同专业确认；对上进入收款核对 |
| 付款申请与付款台账 | 表内、表外、非合同；另按自付/代付及付款主体筛选 | 申请、批准、实付、未执行、核销；原欠款人与实际付款方 | 我方实付、施工企业结果登记、代付、更正/退款 |
| 收款/拨款台账 | 业主→施工企业、施工企业→我方、其他真实收款 | 到账、已匹配结算、待匹配、未收；不能仅显示付款 | 登记真实到账、匹配对上应收、差异核对 |
| 资金执行案件 | 继承来源类别；按实际资金持有人和动作分组 | 本次执行金额、原债务、已核销和待核销 | 复用原执行与核销规则，不由标签生成第二笔事实 |
| 财务工作台 | 应收、应付、收付款、代付往来、待匹配、差异 | 表内/表外应付与对上应收分开；不做应收应付混加 | 财务确认、对账、核销及受控更正 |
| 项目经营管控 | 合同承诺、经营结果、应收应付、资金位置、缺口 | 三类合同额分列；表内/表外成本；对上往来单列 | 任一指标下钻同条件明细，查看超额/逾期/待办 |
| 公司经营/公司分账 | 选具体公司与授权项目 | 该公司对上应收、表内应付、代付款、资金、已确认分配 | 查看公司真实事实，项目整体参考数单独标注 |
| 跨项目经营总览 | 授权项目范围及统一日期 | 分类型汇总承诺、成本、欠款及资金；覆盖范围提示 | 从指标进入对应项目和业务明细 |
| 施工企业对账 | 对上往来、表外应付/实付、代付、扣费 | 双方原值、系统值、匹配及差异；内部关系注明 | 保存对账快照，差异不自动覆盖业务事实 |
| 审批中心/我的工作 | 类别、项目、责任人、待办性质 | 申请金额与成本/资金影响说明 | 显示原审批链，表外付款审批不伪装为外部审批 |
| 历史接管/Excel导入 | 分类、签约身份、资料等级、确定/疑似重复 | 预览进入何种统计、金额变化、未确认项 | 先预检及专业复核，再正式接管 |
| 全局搜索/资料库 | 分类、项目、合同号、真实主体 | 文件关联哪份合同及哪次结算，是否仅作依据 | 回到同一正式详情，不新增记录 |
| PDF/导出/移动端 | 继承页面同条件和权限 | 中文类别、双方主体、口径、日期、单位元、缺口 | 无技术编号泄漏；手机核心主体和状态不被截断 |

付款页不把“对上到账”混作我方对外付款。若提供总收付款视图，可显示对上类别，但必须同时标注方向及观察主体；单纯付款工作台通过“对上收款”链接进入收款台账。

“全部”视图允许混合列出各类单据，但按类别分组小计，不给出把收入方向和支出方向相加的无意义总额。非合同来源显示“无合同费用/零采/工资/借款/调拨”等真实类别，待确认资料不能冒充非合同来源。

所有筛选由后台作用于完整授权数据，汇总与分页明细同范围。详情、导出和手机使用相同后台口径。展示授权数据不扩大岗位权限；全站标签可见不等于敏感金额或个人信息可见。

## 7. 防重复与关联文件

### 7.1 三层控制

| 层次 | 识别内容 | 处理 |
| --- | --- | --- |
| 技术重复 | 双击、重试、并发、同一来源再次投影 | 后台幂等、唯一约束、事务校验；返回原结果 |
| 确定业务重复 | 同一来源单据/原始合同身份再次正式登记；同笔实际付款或到账被重复确认；累计材料重复覆盖原结算 | 阻断再次正式入账；指向已有单据；允许把新证据关联原事实 |
| 疑似经济重复 | 不同合同号但同相对方、同工程范围/批次/期间、相近金额；表内表外交叉覆盖 | 允许保存草稿，要求说明关系与专业复核；未澄清前阻断重叠部分正式确认 |

相同金额、同一供应商、相同文件哈希都不能单独证明经济重复。一次真实付款可核销多笔符合规则的债务，一份对账资料也可支持多项事实；应复用证据和明确分配，不复制交易或禁止合理的证据关联。

### 7.2 同一事项的多份文件

在存在重叠时建立“关联履约事项”：标明工程分项/供货批次/服务期间、文件关系（独立、补充、替代、共同依据）、覆盖金额/数量、唯一结算归属和未覆盖部分。普通独立合同不增加无意义的必填负担，可由系统建立关联基础。

该关联用于经营去重，不自动认定合同法律效力。两份真实文件全部保留，不能凭系统判断删除其中一份。替代合同需确认替代范围和日期，历史履约仍保留；部分重叠按明细划分，不能对整份合同简单清零。

确认由原合同/预算岗位核对范围；涉及应收应付或已入账金额变更时由项目财务核对影响。重大差异沿既有权限处理，不新加所有记录强制三方会签。经办人与必要复核的职责分离沿用现行制度。

### 7.3 错记的纠正

正式入账后发现重复，通过受控更正或冲销，保留原分类、原金额、调整原因、依据、办理人和影响清单；恢复或重分配核销关系必须核对真实款项。对受影响对账快照和盈亏确认标记需要重新核对，不覆盖旧结果，也不直接重写已付款合同的主体。

## 8. 历史数据处理

1. 先生成只读盘点与归类建议：来源、真实双方、现有金额、结算/付款依赖、疑似重复、可自动识别程度。不能用默认 our_company 当作真实签约证明。
2. 有充分依据的记录形成待确认映射；不明确的列入待核对，不强制猜类别、不自动删单。
3. 合同岗位核对签约关系和合同额度；预算/结算岗位核对履约与结算覆盖；财务核对应收应付及资金。仅相关差异要求相关岗位参与。
4. 在隔离环境按同一基准日对比旧/新合同额、确认成本、各方债务和实际资金，差异必须逐项解释。修复原错账可能合理改变成本/利润，不能把“新旧数字必须相同”当唯一验收标准。
5. 已有真实金额不能因分类未完成而静默消失。过渡期保留原记录/旧口径查询；新视图单列待核对余额和影响，不能宣称完整或显示虚假零。
6. 未核清范围只限制受影响业务；不冻结无关项目。历史已发生收付可如实补记为待匹配事实，不能靠补造合同和结算来通过校验。
7. 分类或金额修复进入生产前，先备份并验证可恢复，保存映射/更正清单和前后校验。任何实际数据转换、迁移、部署均待单独明确授权，本方案不包含执行。

## 10. 验收矩阵

| 场景 | 必须得到的结果 |
| --- | --- |
| 表内/表外/对上三种正常链 | 自动带入同一分类和真实主体，收入/成本/往来按规定分离 |
| 同一项目多家我方公司 | 各公司分账正确，项目金额不按参与公司数重复 |
| 业主合同与对上合同同时存在 | 项目收入取业主确认结算，对上不再新增一遍收入 |
| 对上结算漏合同/主体冲突 | 不能正式确认，不能落入下游成本分支 |
| 对上先到账后结算 | 真实资金保留为待匹配，收入成本不凭到账虚增 |
| 普通和外部非零合同 | 承诺汇总正确，不再非零合同显示为零；按三类分别核对 |
| 全额版本与差额变更 | 只按权威口径累计一次；历史基准日回读正确 |
| 无上限、预计、未定金额 | 分开显示，缺金额不作零，不能形成误导性完整总额 |
| 部分结算/部分付款/预付抵扣/保留款 | 成本、应付、到期可付、已付、未付分别正确 |
| 自付/其他我方公司代付/施工企业与我方互相代付 | 原合同分类和债务人不变；核销一次、往来一次、成本不再增加 |
| 双击、网络重试、两人并发、导入重复 | 无重复合同、经营事实、收付或核销，失败零正式写 |
| 不同合同号、同一事项或部分范围重叠 | 要求确认独立/补充/替代/共同依据关系；不能双计相同履约 |
| 累计结算资料覆盖既有逐期结算 | 只关联证据或确认未覆盖差额，不重复累计 |
| 退款/负向结算/冲销重做 | 各自影响正确，历史保留；多次重放不能重复冲减 |
| 每个业务入口及直接 API | 相同分类、金额、权限、幂等规则，不能绕过前台 |
| 合同、结算、付款、收款、财务、项目/公司总览、导出 | 同筛选/基准日明细与汇总可勾稽；不把内部拨款当对外支出 |
| 空数据、未接管、部分缺失、无权限、接口失败 | 状态清楚；不得将未知显示成完整零余额或完整经营结果 |
| 桌面和手机真实岗位任务 | 合同、预算/结算、财务、项目负责人能找到入口和说明数字；未参加记未验收 |

技术验证沿仓库规定：最窄测试、受影响包类型/lint、Web check:ui、涉及金额权限状态的后端测试、真实 PostgreSQL 事务/并发与浏览器验证。最终候选冻结到精确 SHA 后跑全部要求门禁；读模型可重建且不生成第二份正式事实。

验收不只看测试数量：由岗位代表用隔离合成数据完成“登记三类合同→确认结算→收付款/代付→说明项目和公司余额”。生产真实首批业务另行验收，不以合成数据代替。

## 11. 用户已确认的四项业务口径

用户已确认以下四点，并要求财务、项目经营和各类台账一并贯通：

1. 采用“表内（我方签约）/表外（施工企业签约）/对上（施工企业—我方）”作为跨页面统一名称；“业主合同”独立，不混称对上。
2. 统一办理与查询入口，同时保留各类真实流程：表内原审批链、表外外部事实管理及我方付款需求审批、对上合同/结算及收款核对。
3. 财务同时看主体分账与项目合并口径；对上往来在分账保留，在项目整体收入/成本中排除；实际付款方不改变原合同分类。
4. 历史不明分类和疑似经济重复先核对，只限制受影响部分；不按默认值自动归类、不静默改金额、不删除真实文件。

我方公司之间互签、多方合同及无法识别的主体关系，暂作为例外核对事项，不默认纳入此次三分类自动办理；若确有常态业务，需在实施前补充场景和口径。
