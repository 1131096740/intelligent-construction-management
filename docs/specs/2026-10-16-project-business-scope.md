# 多项目业务范围统一

状态：所有者于 2026-10-16 确认规则，授权实现、测试并上线。

## 业务规则

- 项目人员选择本人当前所属的启用项目；兼任多个项目时取并集。所属关系包括项目岗位和项目花名册。
- 公司级业务岗位选择全部启用项目，后续新增项目自动纳入。岗位必须是系统支持的公司级岗位；不能把错误存成公司级的项目经理等岗位解释为全公司权限。
- 项目选择范围和业务操作权限分别判断。合同经办办理合同，材料岗位办理零星材料采购，综合部办理综合采购归档和后续请款，财务依原规则办理付款。技术管理员不成为业务审批人。
- 合同、历史合同接管、结算、付款、零星材料采购及付款、综合采购及付款、费用报销和借款、项目经营入口使用一致的项目范围。
- 新业务选项目；结算、付款等后续业务继承来源项目，后端拒绝串项目关联。已提交单据不能通过改项目绕过原审批。
- 项目经理、项目总工等项目岗位仅从单据项目解析；综合部、合同部、财务主管、董事长等公司岗位沿用既有审批链。候选人必须有效，缺人时提示配置，不借用其他项目人员。已冻结审批的身份、授权、委托和自审规则继续有效。
- 每笔金额进入单据所属项目的账目。结算确认成本，付款清偿应付；禁止在付款时重复计成本。原公司主体分账保留。
- 停用项目不承接新业务；已有业务的历史查询、结项和尾款规则保持原有约束。

## 范围及实现约束

统一后端项目范围和各页面下拉，修复遗漏的公司合同岗位、花名册与项目岗位入口差异。零星采购结束单项目试点，以全部项目模式运行，仍保留岗位、启用状态、审批和金额校验。不得通过给真实人员补全局岗位解决页面问题。

不代录真实业务、不调整真实人员职责、不替员工签名；本次不变更业务金额、历史事实、公司关联或经营账日期。无需新增工作流引擎或另一套权限系统。

## 验收

1. 使用一次性 PostgreSQL 16、真实登录和 HTTP 接口，覆盖项目人员、多项目人员、公司岗位、纯技术管理员及停用/新建项目。
2. 各入口列出正确项目；合法创建成功，越界创建和读写被拒绝，不能只靠前端筛选。
3. 两个项目配置不同经理/经办/财务。甲项目人员不能收到或办理乙项目审批；单据、来源和付款始终属于同一项目。
4. 既有合同、结算、付款、零采和综合采购完整流程及独立核算回归通过，普通员工不能因项目可选范围扩大而读取他人私有材料。
5. 电脑与手机的项目筛选和新建入口均验证；相关测试、类型、lint、UI 检查、双轴审查、CI 和正式发布门禁通过。
6. 上线后核验准确版本、服务健康及只读项目选项，不创建测试业务污染生产。

所有公开测试仅用合成项目与人员。执行日志及生产核验保存在私有目录。
