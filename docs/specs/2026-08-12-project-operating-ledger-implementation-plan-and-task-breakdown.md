## 2. 最新主线差距结论

### 2.1 可复用的现有能力

最新主线已经具备以下实现基础：

1. 合同、结算、付款申请、实际付款、凭证、归档和审批主链；
2. 历史合同接管的批量预检、原始文件留存、逐笔历史实付、双专业修订确认、幂等激活及更正流水；
3. 新版报销、借款、零星费用和零星采购的正式单据及实际付款事实；
4. 项目与施工企业版本绑定、施工企业上游资金事实、对下合同、结算和付款事实；
5. 上游资金事实的原始、更正、冲销、重分类、确认和幂等机制；
6. 我方公司版本、付款主体快照、金额整数分、私有文件绑定和审计基础；
7. JgBusinessGrid、多行粘贴、合同清单和结算导入等局部表格能力；
8. 统一错误转换、页面规则检查、发布检查和本地 PostgreSQL 动态验证的现有骨架。

这些能力应通过适配器、公共校验和兼容读模型复用，不复制业务表，不导出后重新导入。

### 2.2 必须新建或重构的能力

当前缺少：

1. 一次事实、多视角投影的项目经营事实账和统一来源坐标；
2. 项目合并账、施工企业账、我方公司分账、应收应付、实际资金和主体间往来；
3. 无合同历史费用、工资、扣费、资金调度和其他经营事实的通用接管；
4. 费用发生与实际付款、原债务主体与批准付款主体及实际付款主体的分离；
5. 管理费、暂扣税费、最终税费、保证金、保险、手续费和派驻工资的清算生命周期；
6. 我方项目管理人员工资承担；
7. 非固定日期对账、外部余额、差异和确认快照；
8. 七阶段项目结束、最终盈亏、暂分利润和公司分配；
9. 页面、粘贴、Excel、手机卡片和只读详情共享的业务字段定义；
10. 全站用户可见技术语言清零及自动化制品门。

### 2.3 必须替换的旧口径

- ProjectService.getOperatingFundsOverview 当前在查询时拼接多个业务表，且遗漏新版费用实付和部分历史接管事实。它只能作为切换期兼容接口，不能继续成为新总账的计算核心。
- FundsWorkbenchService 可以保留为待办和导航聚合，但不得成为经营事实来源。
- ContractTakeover 继续负责历史合同，不扩展为所有历史经营事实的万能实体。
- 旧 ProjectExpenseRequest 只保留历史读取、必要的存量完成和兼容，不再承担新无合同支出入口。
- JgBusinessGrid 作为 Web 表格适配器复用，不提升为可以自由搭业务和审批的低代码平台。
- 现有页面级枚举映射、原始 error.message 和导出 fallback 必须被统一业务语言机制替换。

### 3.3 依赖方向

允许的依赖方向为：

1. 业务源模块依赖 OperatingLedgerModule 的写入端口；
2. OperatingLedgerModule 依赖 shared-domain 的经营类型和数据库事务端口；
3. OperatingProjectionModule 只读取经营事实及分录，不反向调用业务流程；
4. 页面只调用业务场景 API，不直接写经营事实；
5. 对账、关账和利润模块只读取统一投影，并通过自己的正式业务单据产生新事实；
6. 导出和页面共用同一个读模型，不各自重新计算金额。

禁止：

- OperatingLedgerModule 反向修改合同、结算或付款源单；
- 页面直接调用通用“新增经营分录”接口；
- 每个领域各写一套项目利润公式；
- 为迁移方便长期保留新旧两套可写经营口径；
- 把所有字段和规则塞入无类型 JSON。

## 4. 经营事实与影响分录

### 4.1 经营事实信封

每个进入正式账的业务事实至少具有以下强类型字段：

| 字段组 | 必要内容 |
| --- | --- |
| 来源 | 来源类型、来源业务主键、来源影响键、来源版本、来源业务编号 |
| 时间 | 业务发生时间、系统登记时间、正式确认时间 |
| 范围 | 项目、经营账生效前后属性、历史接管批次 |
| 主体 | 债务主体、批准付款主体、实际付款主体、收款主体、成本承担公司 |
| 业务 | 事实种类、经营层级、成本分类、资金用途、证据等级 |
| 金额 | 原币种、精确金额、方向；所有参与计算金额使用整数分 |
| 治理 | 状态、确认人、幂等键、原事实、更正或冲销关系 |
| 依据 | 原业务单据、附件组、对账和说明引用 |

来源唯一键至少覆盖“来源类型 + 来源业务主键 + 来源影响键”。同一付款可以合法产生“资金流出”和“清偿应付款”等不同影响，但它们属于同一经营事实下的不同影响分录，不是用户重复登记的两笔业务。

### 4.2 经营影响分录

分录只表达经营影响，不模拟会计科目。首批强类型影响包括：

- 已确认收入；
- 已确认成本；
- 预计待清算费用；
- 应收增加或减少；
- 应付增加或减少；
- 施工企业项目资金增加、减少、冻结或解除；
- 我方公司项目资金增加或减少；
- 公司为项目垫资、公司应归还项目；
- 公司间、项目间或施工企业与我方公司之间的主体间往来；
- 暂分利润、最终利润分配及后续应补分或应退回；
- C 级缺口和不参与正式金额的提示。

核心金额、主体和分类必须使用数据库字段及约束。附加来源快照可以使用 JSON，但不得让 JSON 成为金额平衡、来源唯一或权限判断的唯一依据。

### 4.3 事务与历史

- 正式业务源确认与经营事实写入必须在同一个数据库事务中完成。
- 暂时无法同事务接入的旧源，在切换前只能用可重复执行的补投影工具，并以来源唯一键保证不重复。
- 更正和冲销追加新事实并引用原事实；原行不得静默覆盖或物理删除。
- 发生日用于按业务基准日查询，登记日用于判断迟录，两者都必须保留。
- 读模型可以重建；正式源事实、经营事实信封和确认记录不得依赖读模型才能恢复。
- 必须提供“按项目重建并比较但不写回”的一致性检查，再提供受控的幂等重建操作。

## 5. 现有业务源接入策略

| 正式来源 | 首批经营影响 | 复用点 | 必须修正的缺口 |
| --- | --- | --- | --- |
| 生效业主结算或上游结算事实 | 收入、业主应付款或预收待结算 | Settlement、ProjectUpstreamSettlement | 统一收入权威来源及优先级，禁止查询时 fallback 造成口径漂移 |
| 业主向施工企业付款 | 施工企业资金增加、上游应收减少或预付款 | ProjectUpstreamFundFact | 区分结算收款和预付款，不能进入我方现金 |
| 下游结算 | 成本、具体主体应付下游 | Settlement、施工企业下游 SettlementFact | 统一成本分类和债务主体 |
| 有合同付款执行 | 资金减少、清偿应付、必要时主体间代付 | PaymentExecution、Allocation | 同时保留原债务、批准付款、实际付款主体 |
| 零星采购收货、付款、退款 | 材料成本、应付、资金及冲减 | SpotProcurement 全链、InvoiceRecord | 明确成本确认时点，付款不得重复计成本 |
| 报销和零星费用 | 费用成本、员工垫资或公司应付、资金 | ExpenseClaim、PaymentExecution、Loan | 把新版费用实付纳入经营账；旧 ProjectExpense 停止新增 |
| 员工借款与还款 | 员工往来、资金 | EmployeeLoanAccount、entries | 借款不直接形成成本；冲账才确认费用 |
| 历史合同接管 | 历史合同、累计结算、逐笔历史实付、余额 | ContractTakeover 逐笔付款及激活 | 历史实付必须进入经营账；不得只影响合同和合成结算 |
| 施工企业事实 | 上游资金、对下成本或付款、扣费 | 现有 ProjectAffiliate 系列事实 | 用户语言改为施工企业；扣费扩展生命周期和类别 |
| 通用历史经营接管 | A/B 正式事实、C 缺口 | 复用批次、预检、指纹、双专业确认模式 | 新建 OperatingTakeover，不伪造合同或审批 |
| 项目工资 | 工资成本、工资应付或施工企业扣费 | 人员、岗位、公司主体 | 新建月度承担单和敏感权限 |
| 资金调度与利润分配 | 资金位置、主体间往来、暂分或最终分配 | 我方公司主体、现有资金展示 | 新建真实资金移动和经营含义，不滥用 funding allocation |

每个来源适配器必须有一组契约测试：给定冻结源快照，断言产生的事实种类、主体、金额、时间、分类和来源唯一键；重复执行结果不变；更正或冲销产生预期反向影响。

## 6. 统一经营投影

### 6.1 一个读取接口

项目页面、公司页面、对账、关账、导出和权限后的 API 必须调用同一投影服务。读取接口至少支持：

- 项目、公司、施工企业、相对方、成本分类和事实来源筛选；
- 业务发生日期基准；
- 明细、汇总和来源下钻；
- 正式、预计、暂扣、冻结、待核对和 C 级缺口分层；
- 当前值与指定日期快照；
- 中文业务导出。

### 6.2 关键公式

公式实现必须集中在 OperatingProjectionModule，并以强类型分录为输入。

施工企业账上项目资金：

    已确认业主实际付款
    + 施工企业收到的项目退款及其他确认项目流入
    - 施工企业实际支付我方公司
    - 施工企业实际支付下游
    - 已实际退回业主
    - 其他已确认施工企业资金流出
    - 已最终确认归施工企业所有的扣费

当前经营盈亏：

    已确认收入 - 已确认成本

当前预计盈亏：

    当前经营盈亏 - 预计待清算费用

当前可分配利润：

    min(
      非负可使用项目现金
      - 未付下游款
      - 待清算费用及必要准备
      - 冻结、争议、未解决差异
      - 尚未收回的公司垫资
      - 已暂分利润,
      当前预计盈亏 - 已暂分利润
    )

实现时必须通过去重键确保：

- 同一下游应付款只保留一次；
- 公司负数项目资金余额和公司垫资不重复扣除；
- 暂扣费用与预计费用不因不同页面重复扣除；
- 施工企业与我方公司之间的项目内部载体关系在项目合并账中抵销；
- 付款只清偿债务或改变资金，不重复产生已经确认的成本。

### 6.3 兼容与替换

切换期保留现有项目经营总览 API 路径时，内部必须改为调用统一投影。旧查询拼接实现完成等价测试后删除，不允许长期双算后由页面选择一个数字。

FundsWorkbench 保留待办和跳转能力，行金额与状态可以从源单据读取；任何“项目余额、经营成本、利润”都必须从统一投影读取。

## 7. 通用历史经营接管

### 7.1 模块边界

OperatingTakeover 负责合同接管之外的历史经营事实，包括无合同费用、工资、扣费、资金、对账和 C 级缺口。ContractTakeover 继续负责历史合同、累计结算和合同项下逐笔付款。

两者通过同一经营来源接口进入总账，并共享：

- 项目、业务日期、相对方和金额基础校验；
- 来源文件、批次指纹、行指纹和幂等键；
- 确定重复阻断、疑似重复说明和人工复核；
- 原始工作簿及附件组留存；
- 修订、专业确认、激活、更正和冲销的通用模式。

不得把两者合并为一张同时承载所有字段的数据库表。

### 7.2 接管实体

首批实体：

- OperatingTakeoverBatch：项目、来源文件、场景集合、状态、指纹；
- OperatingTakeoverRow：场景、业务字段、金额、主体、期间、证据等级、复核结论；
- OperatingTakeoverIssue：错误、疑似重复、C 级缺口和中文处理建议；
- OperatingTakeoverAttachmentGroup：批次或行级附件；
- OperatingTakeoverConfirmation：专业、修订、确认人和冻结快照；
- OperatingTakeoverActivation：批次激活及生成事实清单。

Excel 中只出现中文业务字段，不得包含隐藏工作表、隐藏列、受保护单元格中的内部行键、主体主键或选项键。离线往返使用中文业务编号或批次内业务整理编号，数据库对象关联由服务器在导入后完成。

### 7.3 原子性

- 预检不创建批次和正式事实；
- 创建草稿批次整批成功或整批失败；
- 草稿行可以在页面逐行修正；
- 批次确认时只有 A/B 级生成正式事实，C 级生成缺口；
- 一个批次激活必须在 Serializable 事务中完成；
- 激活重复调用由幂等键返回同一结果；
- 激活后只能补充、更正、冲销，不能修改原行。

## 8. 统一业务录入

### 8.1 不是低代码平台

BusinessEntryDefinitionModule 只服务由产品和代码注册的封闭业务场景。业务人员可以调整列宽、顺序、筛选和个人视图，不能自行增加影响金额、主体、审批或总账的字段和公式。

### 8.2 单一字段定义

每个场景的字段定义至少包含：

- 中文名称、中文说明和业务示例；
- 数据类型、单位、精度和格式；
- 必填、只读、条件显示和跨字段校验；
- 受控选项及中文展示；
- 查看、编辑、导入、导出和敏感字段权限；
- 表单、表格、手机和只读详情的展示提示；
- Excel 列、粘贴解析和错误定位规则；
- 定义版本和提交冻结方式。

后台根据场景版本执行最终校验。前端和 Excel 只复用定义，不得各自成为业务规则权威。

### 8.3 适配器

- 单条表单适配器：少量字段、复杂说明和附件；
- JgBusinessGrid 适配器：多行录入、键盘操作、复制粘贴和逐格错误；
- Excel 适配器：中文模板、下拉、样例、导入预检和原文件留存；
- 手机卡片适配器：窄屏分组、关键字段优先和分段编辑；
- 只读详情适配器：提交快照、来源和审计友好展示。

所有适配器提交同一 DraftPayload，并由同一场景服务生成同一正式业务源。

### 8.4 一次性全站切换

实现可以拆为多票、多分支和多轮审查，但正式发布必须满足：

1. 用户可填写入口清单已经冻结；
2. 清单中每个入口已经绑定场景定义；
3. 单条、表格、粘贴、Excel 和手机端适用入口通过一致性测试；
4. 旧入口不再能够新增正式事实；
5. 所有现有业务数据保存和历史只读页面仍能正确展示；
6. 上述条件不全部满足时，整个统一录入候选不得上线。

## 9. 数据库迁移和切换

### 9.1 迁移原则

- 只使用向前迁移，不修改旧迁移文件，不重置迁移历史；
- 先新增表和可空关联，再接入来源，再切换读模型，最后关闭旧写入口；
- 金额使用 BigInt 整数分，日期和时区延续现有 PostgreSQL 口径；
- 关键唯一性、非负或平衡、项目隔离、只追加和状态前置规则由数据库约束或事务锁保护；
- 每个迁移必须能在与生产同版本 PostgreSQL 上从空库和现有快照两条路径验证；
- 新表不能假定“未来一定先清空数据”，开发和迁移必须面对当前主线已有数据安全运行。

### 9.2 建议迁移批次

1. 经营档案、参与公司、成本分类和场景定义版本；
2. 经营事实、经营影响分录、来源唯一与更正关系；
3. 债务、核销、主体间往来和资金移动；
4. 施工企业清算、发票关联、工资、对账和阶段；
5. 通用历史接管；
6. 盈亏确认、分配和投影快照；
7. 兼容字段回填、旧入口关闭及最终约束收紧。

每一批迁移都必须配套 Prisma Schema、SQL 约束、PostgreSQL 动态测试和回滚兼容说明。

### 9.3 投影回填

在测试环境或经授权的目标环境中：

1. 只读扫描正式源，生成来源计数和预期影响摘要；
2. 用来源唯一键幂等投影；
3. 比较源金额、经营事实金额和页面旧口径；
4. 差异输出中文清单，不自动调平；
5. 通过后切换统一读模型；
6. 旧查询保留短期兼容路径但不能继续独立计算；
7. 稳定后删除旧计算实现。

## 10. 测试业务归零方案

### 10.1 只读预检产物

归零工具必须先只读生成：

- 精确环境、数据库标识、Schema 版本和候选 SHA；
- 中文保留白名单及每类记录数量；
- 测试业务删除候选清单及每类数量；
- 文件业务绑定、对象存储键和孤儿风险清单；
- 外键依赖图、删除顺序和预计释放编号；
- 备份位置、校验值、可恢复验证和执行前后断言；
- 无法分类或同时关联保留资料与测试业务的阻断项。

任何“等等”“相关记录”或仅按创建时间猜测的范围都不得进入执行脚本。

### 10.2 执行边界

归零执行必须另行授权，并满足：

1. 精确目标环境和维护窗口已确认；
2. 数据库及私有文件可恢复备份已经验证；
3. 删除目标使用显式业务类型与主键清单；
4. 单一事务或可证明一致的分阶段方案；
5. 文件先解除并记录绑定，数据库删除成功后再按明确清单处理对象；
6. 删除失败立即停止，不扩大范围重试；
7. 后置核验业务事实为零、保留数量正确、无孤儿文件和悬空外键；
8. 归零审计永久保留。

本文不执行也不授权归零。

## 11. 自动化上线硬门

一个候选 SHA 必须完整通过：

| 门 | 最低证据 |
| --- | --- |
| 领域单元测试 | 每个来源适配器、公式、状态和更正路径 |
| PostgreSQL 动态测试 | 来源唯一、并发、金额、分配、跨项目权限、事务回滚和迁移 |
| 总账重建测试 | 从正式源重建后，事实及分录计数和金额完全一致 |
| 业务主线测试 | 正式规格第 28 节全部 15 条主线 |
| 统一录入一致性 | 同一场景通过表单、表格、粘贴和 Excel 得到同一冻结快照 |
| 页面和手机端 | 桌面、窄屏、键盘、逐格错误、附件和敏感字段 |
| 中文业务语言 | 页面、错误、审计、Excel、PDF 和导出制品无技术泄漏 |
| 用户入口清单 | 全部可填写入口已迁移，旧入口不可新增正式事实 |
| 数据归零预检 | 白名单、数量、附件、备份和后置断言均可验证 |
| 发布与恢复 | release:local 精确 SHA 收据、迁移、备份、回退兼容及受影响功能暂停方案 |

验证应复用并扩展现有 test、typecheck、lint、check:ui、check:business-errors、数据库动态验证和 release:local。不能用部分测试、旧 SHA 收据或静态扫描代替完整候选证明。

不设置生产试点，也不设置隔离环境人工业务验收；这不降低上述自动化门。

## 13. 候选任务卡

### POL-PARENT：项目经营总账统一交付

- 目标：引用正式规格、差距审计和本方案，维护范围、阻塞关系、候选 SHA 与最终验收收据。
- 负责：只维护交付控制面，不直接承载大段实现。
- 完成条件：所有子任务关闭；同一候选通过第 11 节硬门；归零、部署和开放分别取得授权。
- 不包含：把全部实现塞入一个 PR；预先授权生产动作。

### POL-01：共享领域契约与统一成本分类

- 负责路径：packages/shared-domain/src/，services/api/src/validation/，新增经营领域契约文件。
- 交付：施工企业业务用语；事实、影响、主体角色、证据等级、扣费生命周期、项目阶段、对账状态；八个一级成本分类和受控二级分类规则。
- 依赖：POL-PARENT。
- 验收：穷尽类型测试、未知值中文失败关闭、金额单位测试、一级分类不可改名。
- 不包含：数据库总账或页面重写。

### POL-02：项目经营档案、参与公司与双日期

- 负责路径：services/api/prisma/，services/api/src/project/，packages/shared-domain/src/，项目设置页面。
- 交付：经营账生效日、接管完成日、接管状态、唯一施工企业锁定、动态参与公司及停用规则。
- 依赖：POL-PARENT、POL-01 的主体词汇。
- 验收：首笔正式事实锁定施工企业；有事实公司不可删除；项目财务只能管理本项目公司；双日期不互相推导。
- 不包含：资金余额和利润。

### POL-03：经营事实账与影响分录

- 负责路径：services/api/prisma/，新增 services/api/src/operating-ledger/。
- 交付：事实信封、强类型影响分录、来源唯一键、快照、更正和冲销关系、只追加数据库保护、事务写入接口。
- 依赖：POL-01、POL-02。
- 验收：重复来源阻断；同一来源不同影响键合法；更正不覆盖原行；跨项目引用失败；PostgreSQL 并发测试通过。
- 不包含：具体业务源映射和页面。

### POL-04：来源适配器注册表、重放与一致性校验

- 负责路径：services/api/src/operating-ledger/，services/api/prisma/ 验证脚本。
- 交付：封闭适配器注册表、源快照契约、按项目只读重建比较、受控幂等重放、差异报告。
- 依赖：POL-03。
- 验收：重复重放不新增事实；缺少适配器失败关闭；只读比较不写库；差异输出来源和中文业务编号。

### POL-05：合同、结算、付款和财务事实接入

- 负责路径：services/api/src/contract/、settlement/、payment/、project/，相关 Prisma 模型。
- 交付：生效结算确认收入或成本；付款执行清偿应付并改变资金；明确债务主体、批准付款主体、实际付款主体；现有 FinanceRecord 仅作为财务依据或兼容来源。
- 依赖：POL-04。
- 验收：结算与付款不重复计成本；部分付款、多结算核销、超批复例外、公司或施工企业代付均有契约和并发测试。

### POL-06：报销、借款、零星费用和旧项目费用接入

- 依赖：POL-04。

### POL-08：施工企业既有事实接入与业务语言迁移

- 依赖：POL-01、POL-02、POL-03、POL-17 的字段定义接口；可在 POL-18 之前先完成 API。

- 不包含：历史合同本身，仍由 ContractTakeover 负责。

### POL-11：施工企业扣费、税费、保证金、派驻工资与发票清算

- 负责路径：新增 services/api/src/construction-enterprise-clearing/，扩展 invoice-ledger 复用接口，Prisma 和相关页面。
- 交付：管理费约定版本；暂扣、预计、最终、补扣、退回、待核对；税费清算；可选保证金；保险、手续费、派驻工资及其他扣费。
- 依赖：POL-01、POL-03、POL-08。
- 验收：暂扣不进最终成本；最终确认才影响最终盈亏；税费退回冲减原税费；保证金可无；派驻工资不与我方工资混账；发票只作为清算事实。
- 不包含：发票开具、认证和税务申报。

### POL-12：我方项目管理人员工资承担

- 负责路径：新增 services/api/src/project-wage/，Prisma、项目工资页面和敏感权限。
- 交付：公司、人员、月份、工资构成、跨项目人工分配、确认、应付和实际发放关联；历史 B 级岗位汇总。
- 依赖：POL-01、POL-02、POL-03。
- 验收：月度确认形成一次成本；实际发放只清偿；普通项目用户只能看岗位或汇总；不含考勤、个税、社保申报和工资条。

### POL-13：应付核销、跨主体代付和项目资金调度

- 负责路径：新增 services/api/src/project-funds/ 与 payable-clearing/，扩展 payment allocation，Prisma 和资金页面。
- 交付：原债务、批准付款、实际付款；公司或施工企业代付往来；公司间、项目间、公司临时使用、归还、垫资收回和利润用途的真实资金移动。
- 依赖：POL-05、POL-08、POL-03。
- 验收：银行付款只登记一次；跨主体付款只计一次成本；归还代付只清往来；公司间调拨不改变项目合计；公司其他用途不进项目成本。
- 不包含：公司完整银行账和强制资金专户。

### POL-14：施工企业及我方公司对账

- 负责路径：新增 services/api/src/financial-reconciliation/，Prisma 和对账页面。
- 交付：对账基准日、事件提醒、外部对账值、系统值、匹配建议、人工确认、差异、快照和后续更正影响。
- 依赖：POL-11、POL-13、POL-15 的稳定读取接口；可先实现数据结构。
- 验收：不使用固定月结；外部值不覆盖事实；基准日后数据不改变旧快照；施工企业余额与我方公司财务账严格分开。
- 不包含：银行直连和自动会计记账。

### POL-15：统一经营投影、按日回看和旧总览替换

- 负责路径：新增 services/api/src/operating-projection/，services/api/src/project/，funds-workbench/，项目和公司读 API。
- 交付：项目合并、施工企业、公司、应收应付、资金、盈亏和证据质量投影；按日期查询；旧总览兼容适配及旧算法删除。
- 依赖：POL-05 至 POL-13 的已接入来源。
- 验收：所有汇总能从分录重算；页面与导出一致；新版费用及历史接管不遗漏；内部载体抵销；旧查询不再独立拼金额。

### POL-16：七阶段、最终盈亏、暂分利润和公司分配

- 负责路径：新增 services/api/src/project-close-profit/，Prisma、审批或确认接缝和页面。
- 交付：七阶段前置、快照、受后续事实影响、最终盈亏、暂分利润、公司分配和应补分或应退回。
- 依赖：POL-15、POL-11、POL-14。
- 验收：盈亏确认与债务支付分离；可分配利润双重约束；公司合计等于项目最终盈亏；新金额事实触发重新确认；个人不能成为分配对象。

### POL-17：受控业务字段定义引擎

- 负责路径：packages/shared-domain/src/，新增 services/api/src/business-entry-definition/，场景注册和版本测试。
- 交付：封闭场景注册、字段定义、业务选项、跨字段规则、权限、冻结版本和后台权威校验。
- 依赖：POL-01。
- 验收：同一草稿载荷在各入口结果一致；未知场景和未知字段失败关闭；提交冻结定义版本；不提供用户自由搭业务规则。

### POL-18：表单、JgBusinessGrid、复制粘贴、Excel、手机和只读适配器

- 负责路径：apps/web-admin/src/components/、lib/、api/，services/api 中 Excel 生成解析公共层。
- 交付：统一 DraftPayload；逐格错误；追加或新建选择；中文 Excel；手机卡片和只读快照。
- 依赖：POL-17。
- 验收：同样数据经表单、表格、粘贴和 Excel 得到同一标准草稿；追加不静默覆盖；Excel 无任何技术字段或隐藏技术层，离线关联只使用中文业务编号或业务整理编号；页面金额为元。
- 不包含：具体业务页面迁移。

### POL-19：全站用户填写入口迁移

- 负责路径：apps/web-admin/src/pages/ 全部可填写业务入口及对应 API 场景注册。
- 交付：冻结入口清单；按合同结算付款、费用零采、施工企业、接管、工资对账资金和项目设置分批实现；最终一次切断旧写入口。
- 依赖：POL-18；各领域页面还依赖对应业务 API。
- 验收：入口清单零遗漏；旧入口不能新增正式事实；桌面和手机可用；不改变已提交历史含义；只有全部入口完成才允许发布。
- 不包含：允许部分页面先生产切换。

### POL-20：中文业务语言硬门与已知泄漏清零

- 负责路径：apps/web-admin/scripts/、services/api 的错误、Excel、PDF、审计和导出层，相关测试。
- 交付：用户可见表面登记表、字段来源分类、静态 AST 规则、制品扫描、错误契约测试和结构化例外清单；清零审计原始枚举、ID、JSON，接管技术键，结算 DRAFT、revision、分及 raw error.message。

- 验收：未知枚举中文失败关闭；业务原值允许但技术字段阻断；实际生成 Excel/PDF 扫描；新增页面和制品自动过门。

### POL-22：测试业务归零预检与受控执行工具

- 负责路径：services/api/scripts/、prisma 验证、docs/runbooks/，不直接改业务模块。

- 依赖：POL-PARENT；最终清单依赖所有新增表稳定。

### POL-23：统一切换发布候选

- 负责路径：全仓发布清单、运行手册、PROGRESS.md 和精确 SHA 收据。
- 交付：旧写入口关闭、统一读模型启用、完整自动化门、迁移与回退兼容设计、归零工具只读预检收据，形成唯一待部署候选。
- 依赖：POL-21、POL-22 以及所有业务任务。
- 验收：一个候选 SHA 的 release:local 完整收据；旧入口不能写；候选不依赖尚未执行的数据清理才能通过空库和现有快照迁移；数据归零、部署和开放均未被本票擅自执行。

### POL-24：测试业务归零执行与核验

- 负责路径：已冻结的 POL-22 工具、归零运行手册、PROGRESS.md 和归零审计收据；不得临时扩大脚本范围。
- 交付：在单独授权的精确环境中完成备份恢复验证、中文保留/删除清单复核、测试业务归零、文件绑定处理和后置核验。
- 依赖：POL-23；另需用户对环境、清单、备份和执行窗口的明确授权。
- 验收：保留资料数量正确；测试业务事实为零；无悬空外键和孤儿文件；编号状态符合规格；有可恢复备份和完整审计。

### POL-25：候选部署、数据库迁移与健康核验

- 交付：在单独授权下部署 POL-23 的同一精确候选，执行向前迁移，完成健康、权限、私有文件、关键读写和回退兼容核验。
- 依赖：POL-24；另需部署与迁移的明确授权。
- 验收：运行 SHA 与候选一致；迁移状态正确；自动化硬门收据仍绑定同一 SHA；没有真实业务写入；不安全回退时已验证受影响功能可暂停。

### POL-26：正式开放与持续观察

- 负责路径：正式开放清单、功能暂停开关、观察与反馈收据、PROGRESS.md。
- 交付：在单独授权下向全部真实项目开放；记录正式启用时间；从第一笔真实业务起启用不可清空保护；按规格处理反馈和局部暂停。
- 依赖：POL-25；另需正式开放的明确授权。
- 验收：不做生产试点；不恢复隔离人工验收；真实权限、金额、文件和审计基础检查通过；状态表述为“正式启用、持续观察”；金额、主体、重复或越权故障能暂停受影响功能。
- 不包含：把持续观察声称为已经充分真实业务验证。

## 14. 建议执行顺序

### 第一并行带：基础

- POL-01、POL-02；
- POL-20 先建立基线式硬门，阻止新增泄漏；
- POL-22 先形成只读归零预检设计，不运行执行模式。

### 第二并行带：总账与字段引擎

- POL-03、POL-04；
- POL-17、POL-18。

### 第三并行带：正式来源和新业务

- POL-05 至 POL-09；
- POL-10 至 POL-13。

每个来源先完成契约测试和总账投影，再进入页面迁移，不允许为了赶页面在前端复制金额公式。

### 第四并行带：读取、对账、结束和页面

- POL-14、POL-15、POL-16；
- POL-19 全站入口迁移；
- POL-20 清零全部既有泄漏。

### 第五带：一个候选与分离的生产动作

- POL-21 组装完整自动化硬门；
- POL-22 完成默认只读的归零工具和预检；
- POL-23 形成一个精确 SHA 的统一切换候选；
- POL-24、POL-25、POL-26 分别在独立授权下执行归零、部署迁移和正式开放。

实现可以并行，但数据库 Schema、shared-domain 契约和同一页面必须明确单票所有权，协作者不得相互回退修改。

## 15. 任务发布规则

取得创建 GitHub Issues 的单独授权后：

1. 先创建 POL-PARENT，正文只链接正式规格、差距审计和本方案；
2. 再按第 13 节创建子任务，记录 Part of 和 Blocked by；
3. 已被正式规格确认的任务无需重新分诊；
4. 阻塞未关闭时不标记 ready-for-agent；
5. 每票只引用权威规则，不复制整份规格；
6. 每票列出负责路径、完成条件、非目标和最小验证；
7. 每票实现前重新核验当时 origin/main SHA；
8. 每票完成后更新 PROGRESS.md，并与代码同一提交；
9. push、PR、合并、数据动作和部署继续分别授权。

## 16. 方案完成判定

本实施设计只有在以下条件同时满足时才算可以进入任务发布：

- 最新主线差距审计已经完成并有精确 SHA；
- 所有正式业务源都有唯一接入任务，不存在未归属事实；
- 总账、投影、接管、清算、工资、对账、利润和统一录入之间没有循环依赖；
- 旧口径的替换点、旧入口关闭点和数据迁移边界已经写明；
- 每个候选任务都有路径所有权、阻塞关系、验收和非目标；
- 数据归零和生产发布被明确保留为后续单独授权；
- 全站一次切换与“不做生产试点、不做隔离人工验收”的业务决定没有被实施分票改变。
