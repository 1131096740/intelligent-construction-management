# 统一审批进度与短信催办

## 本地实现边界

2026-10-27 用户授权本地实现、验证、提交、推送与创建 PR；暂不合并和部署。此文不构成生产启用或真实短信发送授权。

十二类审批实例统一接入：合同、结算、付款、费用与报销（含借款）、项目支出、零采申请、零采付款、项目垫资额度、结算例外额度、综合采购、公司间划转、资金执行事项。审批中心的“我参与的流程”提供统一入口；七类单据详情复用同一进度组件，两类额度流程可在审批中心查看。

另纳入 31 类独立审核：用章、合同/结算归档、收货复核、税务事实两阶段复核、历史接管复核/批次验收/合同侧及财务侧确认/更正、异常终止、员工还款、无票及票据异常确认、七类项目经营事实确认、四类模板发布，以及员工入职、履约范围复核、银行流水核验、代付及往来确认、对上合同金额修订、对上到账核销。独立审核在审批中心统一查看和催办；读取原业务状态，不创建第二套审批执行流程。具体来源和权限映射见本地验收记录。

- 发起人、该流程全部审批节点人员、明确转审/委托人员及已实际处理人员可以查看整条流程，包括尚未轮到和已经结束的流程。无关人员不可访问，技术管理员身份本身不提供业务审批权限；结算模板发布保留其原有技术管理权限，不扩展到业务审核。
- 已冻结人员名单的流程使用冻结名单；旧流程只有岗位而没有人员名单时，明确标注当前岗位人员，实际历史处理人以处理记录为准，不伪造历史名单。
- 入职申请在批准前没有系统用户身份，不能伪造申请人 ID；只有原有公司级审核人员及实际处理人员可从本入口查看。已生成的独立审核正式凭证映射回其原业务，避免生成重复待办。
- 查看权限不等于执行审批权限。审批执行仍使用原领域校验；催办接收人由服务端重新计算，仅限当前有效待审批人，会签已完成角色不再催办。委托沿用原业务允许的范围，资金执行事项的限定委托必须匹配同一事项；不支持转审的流程不因进度展示新增转审资格。受活跃项目限制的审核在项目停用后关闭催办，保留明确参与人员的历史回看。
- 费用与报销列表及详情补充流程参与人可见性，草稿不因参与历史流程而开放。仅凭历史审批资格查看借款单时，不返回员工整个借款账户或其他还款，只显示该单据自身的放款记录。头部显示真实当前环节，不再显示“按冻结审批节点办理”。

## 短信行为

点击“短信催办”后确认接收人。请求携带当前进度确认令牌；节点、状态或接收人变化时拒绝旧确认，要求刷新重确认，不能静默换人发送。服务端先持久化请求，再发送短信，逐人留存结果。相同请求标识重复提交不会再次发送；同一流程十分钟内只接受一次催办，各参与人共享冷却时间。实际发送前再次检查当前节点和待审批人，变化时取消该接收人的发送。

短信结果分别显示“已提交发送”“失败”“结果待确认”，已提交不等于手机已送达。网络超时或进程中断后不自动重发；保留请求及已有接收人结果。十分钟后的新催办是用户主动发起的新请求，可能再次通知同一待审批人。手机号无效时记录失败，不展示完整手机号或供应商原始错误。未启用零采业务的项目保留进度查看，但不能催办零采审核。

## 供应商与配置

实现使用腾讯云 [SendSms 2021-01-11](https://cloud.tencent.com/document/product/382/55981)，固定供应商地址、TC3 签名、五秒超时，不跟随重定向、不自动重试。默认关闭；未启用时页面显示“短信服务尚未启用”，不会虚报已发送。

后续实际启用时，通过既有安全配置渠道注入以下环境变量，不把密钥写进仓库、日志或聊天：

| 变量 | 用途 |
| --- | --- |
| `APPROVAL_SMS_ENABLED` | 必须显式为 `true` |
| `APPROVAL_SMS_SECRET_ID` / `APPROVAL_SMS_SECRET_KEY` | 供应商调用身份 |
| `APPROVAL_SMS_APP_ID` | 短信应用 ID |
| `APPROVAL_SMS_SIGN_NAME` | 已审核的短信签名 |
| `APPROVAL_SMS_TEMPLATE_ID` | 已审核的通知模板 |
| `APPROVAL_SMS_REGION` | 供应商支持的地域 |
| `APPROVAL_SMS_SESSION_TOKEN` | 使用临时凭证时的可选令牌 |

模板参数固定为三个，依次为审批业务名称、业务单号（额度为项目额度申请标识）、当前审批环节。示例模板：“您有一笔{1}（单号{2}）等待您在{3}环节处理，请登录建工智管查看。”实际模板需要供应商审核，本地实现不表示模板已经获批。

真实供应商账号、签名模板、手机送达仍需后续经授权的部署与真实发送验收。本轮未启用生产配置，未发送真实短信。

## 本地复验

- API 定向测试：审批目录、费用服务、合同/结算/付款控制器、写冻结守卫。
- `pnpm verify:approval-progress:local`：先构建 API，再创建只绑定本机回环地址的一次性 PostgreSQL 16，应用当前迁移并运行真实 Nest HTTP/Prisma 验证。短信供应商替换为测试适配器。结束后删除本次创建的容器及匿名卷，不连接生产。
- `pnpm --filter @jiangkong/web-admin test`：Web 全量单测。
- Web 构建后运行 `pnpm --filter @jiangkong/web-admin exec playwright test --config playwright.approval-progress.config.ts`：桌面 Chromium 与手机 WebKit，所有业务接口由虚构测试数据模拟；覆盖成功、失败、结果待确认、确认接收人、刷新留痕和防重复点击。
- API/Web 类型检查和 lint，Web `typecheck:e2e`、`check:ui`。

新增接口为 `GET /approval-progress`、`GET /approval-progress/:instanceId`、`POST /approval-progress/:instanceId/remind`。审批实例沿用 ApprovalInstance/ApprovalActionLog；独立审核读取原业务表，以 AuditLog 留存催办预留及逐人结果。锁定业务记录并在发送前复核；不新增 Schema 或迁移。Web 统一使用新入口；合同、结算、付款三条旧催办 HTTP 入口按主线退役机制返回 410，避免遗留入口绕过统一流程。
