# 多项目业务范围发布

所有者已授权 Issue #333 统一项目选择、按项目审批及核算，并在测试通过后直接上线。规格见 [多项目业务范围](../specs/2026-10-16-project-business-scope.md)。不代建业务、调动人员、签名或填经营账日期。

本次无 Schema 和迁移新增。原 174 项迁移、数据库权限、备份、已有流程状态和金额规则保持。新增 PostgreSQL 16 / HTTP 与电脑手机验收纳入原 `general_procurement` 必跑组；保持原完整 17 门和全部 CI 检查。

## 发布顺序

1. 固定候选完成两轴审查、相关与全量回归、UI 和发布清单核验；PR 固定头 CI 通过后合并。准确 main 的完整 17 门及主线 CI 通过，原发布收据验证和 dry-run 通过。
2. 生产只读确认当前版本、服务健康、运行权限、迁移、备份及零采配置。只读判断配置模式，不输出完整环境文件或密钥。当前只有限定项目时，发布执行将其切换为全部项目模式。
3. 私下保存 `/etc/jiangkong/api.env` 的原字节和权限，只修改 `SPOT_PROCUREMENT_PILOT_PROJECT_IDS=*` 一项，核对差异和属主/权限。原 API 进程在正式部署重启前沿用内存配置；不得为此提前重启旧版本。保留原值用于失败恢复。
4. 使用现有 `full/manual` 发布入口：服务器自行构建、完整备份、检查迁移、切换运行时及健康检查。准确版本进入确认窗口后，核查进程确实读取全部项目模式、API/Web 文件一致、公开和本地健康及匿名权限边界；通过现有用户真实会话只读核验项目选项。
5. 全部核验通过才写准确 SHA 的确认，检查原部署自然终态、systemd/定时备份告警和运行目录。生产不得写测试单或代员工登录审批。发布备份与自然计划备份分别记录。

## 失败恢复

保留失败证据。若在重启前失败，立即还原该配置项的原字节；若原部署恢复旧代码，必须同时还原配置并按既有恢复步骤重启，避免旧代码无法识别 `*`。仅在旧版本、配置及健康均验证后恢复使用。配置恢复前核对文件仍为本次安装版本，防止覆盖并行人工修改；发生差异时停下诊断。

如果已产生新业务，不能删除或改写业务来回退。项目数据和审计始终保留；修复后再发布兼容版本。生产证据和配置备份仅保存在私有位置，公开 PR 仅记录测试及通用发布结论。
