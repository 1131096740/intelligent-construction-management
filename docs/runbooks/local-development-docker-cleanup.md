# 本地测试 Docker 资源清理

适用范围：本地一次性 PostgreSQL 测试容器；不适用于生产、恢复证据容器或日常开发的持久数据库。

## 2026-10-23 排查结论

在本地 `main` 基线 `a6a9b08a94c0ac9747b9741bb5563e8522ce435c` 的测试脚本中，18 个容器所有者均以 `docker run --rm` 创建 PostgreSQL 容器，却在清理时执行 `docker rm --force <本次容器>`。真实 Docker 最小复现确认：强制删除后容器消失，但 PostgreSQL 镜像自动创建的匿名数据卷仍存在。反复运行迁移和数据库测试会不断累积这些卷。

这证明仓库测试入口存在泄漏路径；此前遗留卷只有匿名标签，无法将历史每个卷逐一归因到具体入口。

修复后的删除命令为 `docker rm --force --volumes <本次容器>`。该命令只清理该容器的匿名卷；命名卷和挂载的宿主机目录不在此删除范围。日常开发的 `api_jiangkong_pgdata` 持久卷保持原用途。

两个旧入口 `run-contract-settlement-v2-local.cjs`、`run-database-dynamic-remaining-local.cjs` 同时接入已有的进程跟踪和幂等清理运行时：在启动容器前记录尝试状态，正常结束、启动失败、测试失败及 SIGINT/SIGTERM 都执行清理；除容器已不存在外，清理错误必须使脚本失败。成功结果在清理完成后才输出。

## 主线交付适配

交付分支以远端主线 `6bf7820c0d925e5804ad7d03ae8b983a9220b5e3` 为基线，保留新增迁移基线、分组、银行运行时夹具和 pnpm 入口配置。同形修复覆盖主线上全部 33 个一次性 PostgreSQL 容器所有者（含新增 POL、入职、通采及 fund-execution-v7 验证入口）。除前述两个旧入口的生命周期补齐外，其余入口只补匿名卷删除参数。

上述范围是当时基线的交付记录，不能证明后来新增或复制的入口已有相同清理能力。

## 任务收尾

新增或修改一次性测试入口时，资源归属和清理必须随入口一起实现：

1. 启动前固定本机 Docker endpoint 与 daemon 身份，为本轮生成唯一 runId；记录源码 SHA、实际 runner 文件摘要及本轮 artifacts 目录。调用已修复的工作目录，历史 checkout、临时副本和现有工作树不会自动获得新提交。
2. 创建资源后立即记录实际 container ID 及其独占匿名卷 ID。只清理本任务新建且已确认不再使用的临时资源；持久数据库、恢复证据、其他任务资源、当前回滚备份和用途未知的历史卷保留。
3. 正常成功、测试失败、启动失败以及可捕获的 SIGINT/SIGTERM 都进入幂等收尾：先结束本轮子进程，保留脱敏失败摘要及必要测试、恢复或回滚证据，再按本轮确切 container ID 清理容器及其匿名卷。必要证据应保存到 artifacts 后才移除承载它的临时资源；清单不替代证据保留。
4. 核验本轮目标容器和匿名卷已清理，记录完成状态与 cleanup outcome 后才输出成功。清理失败必须返回失败并留下可核对的清单，不得把测试通过当作任务收尾成功。

`docker rm --force --volumes <本次容器 ID>` 只处理本次容器及其匿名卷；`--rm` 不替代主动强制删除时的卷清理。按固定 ID 核对和清理，禁止用全局 prune、cron 或后台清理任务代替，也不自动接管历史未知卷。

## Classification 入口的持久清单

本次补齐 `services/api/prisma/run-contract-classification-local.cjs` 的匿名卷清理、可捕获中断收尾及清理失败处理，并在每轮 artifacts 目录保存 `resource-manifest.json`。该清单记录 runId、sourceSha、runner 文件摘要、Docker endpoint/daemon ID、实际 container ID 与匿名卷 ID、运行完成状态及 cleanup outcome；不保存密码、连接串、认证信息或完整环境变量。

在包含本修复的工作目录运行 `pnpm --filter @jiangkong/api verify:contract-classification:local`，入口会自动执行上述收尾并输出本轮清单路径，无需另跑全局清理。清单采用同目录临时文件加原子替换；银行运行时夹具作为有界、可跟踪子进程执行。业务通过后若在清理期间收到中断，也不得输出成功。

若启动过程中中断且尚未确认容器身份，清单保守记录 `cleanup_failed`，按本轮名称、runId 标签及固定 endpoint 人工复核；不能据一次“未找到”就保证 daemon 后续不会完成创建。SIGKILL、断电或 daemon 不可用仍可能遗留资源，清单不是万能自动清理保证。

这次持久清单接入仅限 classification 入口；其他入口仍须核对各自源码和收据，不能据此声称全部 runner 已有持久清单。新增入口、入口复制或 runner 变更需要同步检查清理守卫及真实资源验证的覆盖，包含成功、失败、启动失败、可捕获中断、重复收尾和清理失败路径；测试结果以当前准确源码的实际收据为准。

## 真实 Docker 回归

在已缓存 `postgres:16` 的本地环境运行：

```sh
pnpm verify:docker-cleanup:local
```

命令先验证并固定本机 Docker socket，然后逐一执行实际 runner 源码中的删除参数。每例创建一个禁止联网、不发布端口的睡眠容器，让 PostgreSQL 镜像创建匿名卷，额外挂载一个本次自建的命名卷，验证匿名卷被删除、命名卷保留。完成后删除自建测试资源，并核验运行前所有既有卷仍在。不启动 PostgreSQL、不迁移、不拉镜像、不读取既有卷内容。

2026-10-23 首次旧基线本地验证为 18/18；基于上述最新主线的交付适配验证为 33/33，泄漏 0、运行前 1,744 个卷全部保留。该结果是清理机制验证，不是完整业务数据库门、GitHub CI 或生产发布证据。

## 无法由进程自行处理的退出

SIGKILL、机器断电、Docker daemon 不可用时，进程无法保证执行清理。处理遗留前，先保留失败摘要、必要证据及当前回滚备份，再核对原 artifacts 中的资源清单、runId、源码 SHA、runner 摘要和实际资源身份；缺少清单或无法证明归属的资源继续保留。

执行精确清理前重新核对 Docker endpoint/daemon ID、当前发布活动及全部现有容器（含停止容器）的挂载引用。当前发布或其他活动任务仍使用的资源保留；单独处理遗留匿名卷时，只能选取清单内确属本任务且已无任何容器引用的固定 ID，并沿用该次清理的具体授权范围。核对不一致、身份复用、引用变化或保留用途不明时停止该项清理并记录原因，不依据名称、年龄或匿名标签推断可删。

本规则不安装全局定时清理，不删除历史未知资源，也不把用户的日常收尾偏好扩展为生产、其他任务或持久数据清理授权。
