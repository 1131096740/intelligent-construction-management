# 余额核对以明确冻结的实付集合承接资金

用户已确认：缺少冻结历史来源证明时，由当前有权登记人明确确认实付已含或未含期初，冻结核对版本、原因和依据；无法确认则保留填写、不正式提交，不能按日期猜测。已含不再扣资金，未含正常扣；资金已含不代表合同历史累计已含，各轴仍按明确源身份去重，不改历史基线或制造成员。

余额更正发起时明确冻结本次核对金额已经包含的正式实付事实集合，待复核期间的新实付不自动并入；财务主管确认后，未覆盖分录继续扣减。选择冻结集合而非每次新付款都重提，是为了让核对与正常付款可同时推进且不吞掉期间支出：核对100元待审时新增未覆盖实付30元，确认后仍为70元。原实付与旧核对记录保持原值，正式付款仍只有一份，容器/来源分录只引用其稳定身份。

用户补充确认（`call_61d5916d058e4b94932678b2ed58f164`）：核对金额已知且不足覆盖未包含的实际支出时，拒绝确认、该更正保持待复核，原有效核对及实际支出不变，不造资金来源。例：更正核对20元、冻结已包含清单为空，待审新增未覆盖实付30元，不能确认成负10元。原有效核对100元及真实支出30元继续推导70元，直到有依据的新核对获确认。

未知余额与已知不足分别处理：余额明确未知时可确认并继续显示未知，保留真实30元支出及来源待核对，不填0、不自动纳入冻结清单；之后未含期初的新付款不得从未知余额扣款。此选择同时保留如实核对未知和已知资金容量约束，不能用一种状态代替另一种。已接受的补充规则已落实到本地确认前的容量检查与prepared SQL；公开HTTP合成反例已先证明错误确认成负10元，再验证明确拒绝且旧有效70元/更正待审不变。未知确认、原100减30为70、拆分来源保持未知三个相关正向案例也已通过。上述仅本地合成证据，prepared SQL未执行，尚未取得对应真实PG证据。

这是已接受的业务决定；当前仅在本地实施源码与合成公开验证，草案Schema不代表迁移已执行。真实PostgreSQL、故障和竞争、资源、SQL迁移、真实交易及部署均未验、未执行，需另行授权。
